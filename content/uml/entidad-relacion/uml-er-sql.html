5.1. Mapeo de entidades a tablas

Un diagrama ER bien hecho se traduce casi mecánicamente a DDL. Reglas del mapeo:

Diseño lógicoModelo físico
EntidadTabla
Atributo simpleColumna
Atributo identificadorPRIMARY KEY (idealmente surrogate key: id)
Atributo multivaluadoTabla aparte con FK a la entidad
Atributo compuesto (dirección)Columnas atómicas (calle, ciudad, cp)
Atributo derivado (edad)No se almacena; se calcula con consulta o vista

Partimos del ejemplo de la lección anterior: Cliente, Pedido, Producto.

5.2. Traducción de relaciones y cardinalidades

  • 1:N — la clave foránea vive en el lado N. Un Pedido pertenece a un Cliente: pedidos.cliente_id → clientes.id.
  • 1:1 — FK en cualquiera de los dos lados + constraint UNIQUE para garantizar exclusividad.
  • Opcionalidad: si la entidad del lado N puede existir sin padre, la columna es NULL; si no, NOT NULL.
CREATE TABLE clientes (
  id     BIGSERIAL PRIMARY KEY,
  nombre VARCHAR(120) NOT NULL,
  email  VARCHAR(160) NOT NULL UNIQUE
);

CREATE TABLE pedidos (
  id         BIGSERIAL PRIMARY KEY,
  cliente_id BIGINT NOT NULL REFERENCES clientes(id),
  fecha      TIMESTAMP NOT NULL DEFAULT now(),
  total      NUMERIC(10,2) NOT NULL DEFAULT 0
);

5.3. Relaciones N:M y tablas intermedias

La relación "Pedido incluye muchos Productos / Producto aparece en muchos Pedidos" no existe como tal en relacional: se materializa una tabla intermedia cuyos atributos propios pasan a ser columnas (cantidad, precio histórico):

CREATE TABLE productos (
  id       BIGSERIAL PRIMARY KEY,
  nombre   VARCHAR(150) NOT NULL,
  precio   NUMERIC(10,2) NOT NULL CHECK (precio >= 0)
);

CREATE TABLE pedido_producto (
  pedido_id   BIGINT NOT NULL REFERENCES pedidos(id) ON DELETE CASCADE,
  producto_id BIGINT NOT NULL REFERENCES productos(id),
  cantidad    INT NOT NULL CHECK (cantidad > 0),
  precio_unit NUMERIC(10,2) NOT NULL,
  PRIMARY KEY (pedido_id, producto_id)
);

Notas: la PK compuesta evita duplicar el mismo producto dos veces en un pedido; precio_unit congela el precio al momento de la venta aunque el catálogo cambie después.

5.4. Normalización aplicada al diseño

Verificación rápida contra las formas normales antes de ejecutar el script:

  • 1FN: todas las columnas atómicas (no guardamos "calle y ciudad" juntas ni listas separadas por comas).
  • 2FN: en pedido_producto, cantidad depende de la clave completa (pedido+producto), no solo de parte.
  • 3FN: ningún atributo no-clave depende de otro no-clave: el nombre del cliente no se copia en pedidos, se obtiene por JOIN.

Desnormalizar (guardar total en pedidos) es aceptable cuando es un valor calculado costoso que además tiene semántica de "foto histórica". Documenta siempre esa decisión.

5.5. Script SQL final completo

Orden de creación respetando dependencias de FK e índices útiles:

-- 1. Catalogos base
CREATE TABLE productos (...);

-- 2. Maestros
CREATE TABLE clientes (...);

-- 3. Transacciones dependen de maestros
CREATE TABLE pedidos (...);

-- 4. Tabla puente
CREATE TABLE pedido_producto (...);

-- Indices para rutas de consulta frecuentes
CREATE INDEX idx_pedidos_cliente ON pedidos(cliente_id);
CREATE INDEX idx_pp_producto ON pedido_producto(producto_id);

Ciclo completo dominado: diagrama ER → mapeo → DDL → índices según consultas esperadas. Cuando el modelo cambie, actualiza primero el diagrama: es más barato mover rectángulos que migraciones en producción.
