5.1. Planteamiento del sistema

Vamos a modelar "TiendaCloud", una aplicación web de e-commerce con esta descripción funcional:

  • SPA React: catálogo, carrito y checkout en el navegador.
  • API Gateway: punto único de entrada HTTPS, autentica tokens.
  • Servicio de Catálogo: productos y búsquedas (lectura intensiva, cacheable).
  • Servicio de Pedidos: crea órdenes y coordina el pago.
  • Pasarela de Pagos externa (Stripe): cobro con tarjeta.
  • Base de datos PostgreSQL para pedidos; Redis como caché de catálogo.

Pregunta guía del diagrama: ¿qué piezas existen, qué interfaces ofrecen y qué requieren?

5.2. Identificación de componentes e interfaces

Pasos aplicados:

  1. Listar componentes: cada desplegable independiente es candidato (SPA, Gateway, Catálogo, Pedidos).
  2. Definir interfaces provistas: lo que cada uno ofrece. Ej.: «provide» ICatalogoAPI, IPedidosAPI.
  3. Definir interfaces requeridas: lo que cada uno consume. Ej.: Pedidos requiere IPagos (externa) y usa la API de Catálogo.
  4. Distinguir protocolos: REST/JSON entre SPA-Gateway-Servicios; SQL hacia PostgreSQL; Redis protocolo RESP.
  5. Marcar lo externo: Stripe vive fuera de nuestra frontera → estereotipo «external» o contorno distinto.

Regla usada: una interfaz por responsabilidad cohesiva. No creamos IServicioPedidosCompletoGigante; separamos IConsultaPedidos de ICreacionPedidos.

5.3. El diagrama completo

@startuml
skinparam componentStyle rectangle

component "SPA Tienda" as spa <>
component "API Gateway" as gw <>
component "Servicio Catalogo" as cat <>
component "Servicio Pedidos" as ped <>
database "PostgreSQL" as db
database "Redis Cache" as redis
component "Stripe API" as stripe <>

interface "ICatalogoAPI" as icat
interface "IPedidosAPI" as iped
interface "IPagos" as ipag

spa --> gw : HTTPS + JWT
gw --> icat
gw --> iped
cat -(0- icat
ped -(0- iped
ped --(0- ipag : requiere
ipag -0- stripe

cat --> redis : lectura cache
ped --> db : persistencia
@enduml

Lectura del diagrama en voz alta: "La SPA habla solo con el Gateway. El Gateway expone dos contratos que implementan Catálogo y Pedidos. Pedidos además requiere la interfaz IPagos, satisfecha por Stripe. Catálogo acelera lecturas con Redis; Pedidos persiste en PostgreSQL."

Esa narrativa es la prueba de que el diagrama funciona: cualquier miembro del equipo puede reconstruir la arquitectura sin leer código.

5.4. Lecciones aprendidas del diseño

  • El Gateway absorbe complejidad transversal: auth, rate limiting y CORS viven ahí, no repetidos en cada servicio.
  • Las interfaces revelan acoplamiento: al ver que Pedidos requiere IPagos apuntando afuera, queda claro dónde aislar fallos (circuit breaker) y mockear en tests.
  • Caché es un detalle arquitectónico: Redis aparece como decisión explícita, no como optimización invisible.
  • Fronteras externas claras evitan sorpresas contractuales: todo lo que cruza a Stripe merece timeouts y reintentos documentados.
  • El diagrama evolucionó con el sistema: cuando agreguemos notificaciones, será un componente nuevo con sus interfaces — no un parche oculto.

Ejercicio propuesto: agrega un componente "Servicio Notificaciones" que recibe eventos de Pedidos mediante cola de mensajes. ¿Qué interfaz provee? ¿Quién la requiere?
