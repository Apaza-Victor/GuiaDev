Antes de dibujar: define el objetivo

Un diagrama UML no se dibuja "porque sí". Antes de tocar ninguna forma, responde tres preguntas: qué quieres comunicar, a quién se lo muestras y cuál es el nivel de detalle.

Las tres preguntas previas

PreguntaQué defineEjemplo de respuesta
¿Qué quiero comunicar?El tipo de diagrama y los elementos"Cómo interactúa el cliente con el sistema" → caso de uso
¿A quién va dirigido?El nivel de detalle (resumen vs. técnico)Stakeholder → diagrama simple; developer → diagrama detallado
¿Qué decisión debe facilitar?Qué información es imprescindible"Mostrar el flujo alternativo de un pago fallido"

Antes de comenzar

Haz la pregunta clave del método de modelado: "si este diagrama no existiera, ¿qué decisión sería más difícil de tomar?". Si no hay una respuesta clara, probablemente no necesitas el diagrama todavía.

Regla de oro: un buen diagrama se entiende sin que nadie lo explique. Si necesitas hablar durante cinco minutos para explicarlo, está mal hecho.

Secuencia de creación de un diagrama

El orden correcto para construir cualquier diagrama UML, sin importar el tipo (clases, secuencia, actividades, casos de uso...). Sigue este flujo:

Ver código PlantUML 
@startuml
title Proceso para crear un diagrama UML
start
:Definir el objetivo;
:Identificar los elementos;
:Elegir el tipo de diagrama;
if (¿Evita errores?) then (sí)
  :Dibujar la estructura;
else (no)
  :Revisar la notación;
endif
:Validar el resultado;
stop
@enduml

Paso a paso

#PasoQué haces
1Define el objetivoFija qué proceso, estructura o interacción vas a mostrar.
2Identifica los elementosLista actores, clases, nodos o acciones que participan.
3Elige el tipo de diagramaSelecciona el diagrama UML que mejor represente el objetivo.
4Dibuja la estructuraColoca primero los elementos principales y luego las relaciones.
5Revisa la notaciónVerifica que cada símbolo se usa con el significado UML correcto.
6Valida el resultadoComprueba que otra persona lo entienda y que no falten casos.
Consejo de flujo de trabajo: para dibujos rápidos usa draw.io; para diagramas que viven en el repositorio (versionables y con diffs) usa PlantUML o Mermaid como código.

Reglas de estilo y limpieza

Buenas prácticas visuales

  • Una idea por línea: evita cruces de flechas; reordena los elementos para que las líneas no se solapen.
  • Nombres claros: usa verbos en infinitivo en acciones y sustantivos en clases o entidades.
  • Consistencia: el mismo tipo de elemento siempre con la misma forma y color.
  • Menos es más: si un diagrama tiene más de ~15 elementos, divídelo en varios.
  • Alineación: ordénalo de izquierda a derecha o de arriba abajo según el flujo.

Señales de un diagrama a mejorar

SíntomaPor qué ocurreSolución
Muchas flechas cruzadasFaltan agrupaciones o está mal ordenadoReagrupa por paquetes o agrega el detalle en otro diagrama
Nombres genéricosFalta claridad ("Entidad", "Proceso")Usa nombres precisos ("Factura", "Validar pago")
Demasiado grandeIntentas meter todo en unoDivide por subprocesos o módulos
Elementos sin relación visibleSobran datos que no aportanElimina lo que no ayude a tomar la decisión

Errores comunes al hacer diagramas

Fallos frecuentes y cómo evitarlos

ErrorImpactoCómo evitarlo
Confundir clases con objetos o tablasModelo incorrecto que lleva a mal diseñoTenga presente la diferencia entre diagrama conceptual y físico
Usar el mismo símbolo para cosas distintasEl lector interpreta malRespeta la notación UML estándar de cada forma
Poner demasiado detalle en un diagrama de alto nivelDifícil de leerSepara vistas: conceptual, lógica y física
Olvidar los casos alternativos o de errorEl modelo está incompletoAñade siempre el flujo "else" o "excepción"
No validar con el equipoSuposiciones no confirmadasRevisa el diagrama con quien conoce el negocio
Truco de revisión: explica el diagrama en voz alta a un compañero. Donde te quedes atascado, ahí está el error o el vacío de información.

Elección del diagrama correcto

No todos los diagramas UML sirven para lo mismo. Esta referencia te ayuda a elegir el adecuado según lo que quieras comunicar.

Guía rápida de selección

Quieres mostrar...DiagramaPregunta que responde
Quién interactúa con el sistema y para quéCasos de Uso¿Qué funciones ofrece el sistema?
La estructura de datos y sus relacionesClases¿Qué entidades existen y cómo se relacionan?
El orden temporal de los mensajesSecuencia¿Quién llama a quién y en qué orden?
El flujo de trabajo o de un procesoActividades¿Qué pasos se ejecutan y en qué orden?
Los componentes y sus interfacesComponentes¿De qué módulos se compone el sistema?
La infraestructura física del sistemaDespliegue¿Dónde se ejecuta cada parte?
Los estados por los que pasa un objetoEstados¿Qué estados puede tener un objeto?
Entidades, atributos y relaciones (BD)Entidad-Relación¿Cómo se modela la base de datos?
Recuerda: la mayoría de proyectos reales usan un número reducido de diagramas: casos de uso, clases, secuencia, actividades y, a veces, despliegue. No es obligatorio usarlos todos.
