Estados, transiciones y eventos

La notación completa de una transición combina hasta cuatro piezas opcionales:

        evento [guarda] / acción
Origen ────────────────────────────► Destino
  • Evento: estímulo externo o llamada que dispara el cambio (clicPagar(), timeout).
  • Guarda [condición]: expresión booleana; la transición solo ocurre si es verdadera ([saldo >= monto]).
  • / Acción: efecto ejecutado al cruzar (/ enviarRecibo()). Debe ser rápida; para trabajo largo, usa acciones internas del estado.

Un estado también puede tener acciones internas, listadas dentro del rectángulo redondeado con palabras clave estándar:

╭─────────────────────╮
│ Procesando          │
├─────────────────────┤
│ entry / abrirLote() │  ← al entrar
│ do / validarDocs()  │  ← mientras dura (actividad)
│ exit / cerrarLote() │  ← al salir
│ cancelar / limpiar()│  ← reacción interna sin cambiar de estado
╰─────────────────────╯

Guardas y acciones

Ejemplo con decisiones condicionales en las transiciones — retiro bancario:

@startuml
state "Esperando Monto" as espera
state "Validando" as valida
state "Dispensando" as dispensa

[*] --> espera
espera --> valida : montoIngresado(m)
valida --> dispensa : continuar [saldo >= m] / debitar(m)
valida --> espera : rechazar [saldo < m] / mostrarError()
dispensa --> [*] : completar() / expulsarTarjeta()
@enduml

Reglas de oro:

  • Dos transiciones saliendo del mismo estado no deben poder activarse simultáneamente: sus guardas deben ser mutuamente excluyentes.
  • Si un estado tiene muchas salidas idénticas, considera una pseudoelección (rombo) como en actividades.
  • Los eventos sin transición correspondiente se ignoran silenciosamente según la especificación — decide si eso es aceptable en tu dominio.

Estados compuestos e iniciales anidados

Cuando un grupo de estados comparte lógica, se agrupan en un estado compuesto. El ejemplo clásico: "Activo" contiene subestados, y un evento exterior (suspender) aplica desde cualquiera de ellos:

@startuml
state Activo {
  state "Navegando" as nav
  state "Comprando" as comp
  [*] --> nav
  nav --> comp : iniciarCompra()
  comp --> nav : abandonarCarrito()
}

state Suspendido
state Cerrado

[*] --> Activo
Activo --> Suspendido : inactividad90dias
Suspendido --> Activo : reactivar()
Suspendido --> Cerrado : borrarSolicitud
Cerrado --> [*]
@enduml

Ventajas: elimina decenas de flechas repetidas hacia Suspendido y documenta jerarquía real del dominio. También existen historial superficial (H) y profundo (H*) para volver al último subestado tras una interrupción.

Ejemplo completo: ciclo de vida de un pedido

@startuml
state "Nuevo" as nuevo
state "Pagado" as pagado
state "En Preparacion" as prep {
  state "Empacando" as empaca
  state "Etiquetado" as etiqueta
  [*] --> empaca
  empaca --> etiqueta : imprimirGuia()
}
state "Enviado" as enviado
state "Entregado" as entregado
state "Cancelado" as cancelado
state "Devuelto" as devuelto

[*] --> nuevo
nuevo --> pagado : pagar() [stock reservado] / notificarCliente()
nuevo --> cancelado : cancelar() / liberarStock()
pagado --> prep
prep --> enviado : entregarTransportista()
enviado --> entregado : confirmacionCourier() / solicitarResena()
entregado --> devuelto : iniciarDevolucion() [dentroDe30Dias]
devuelto --> [*] : reembolsar()
cancelado --> [*]
entregado --> [*]
@enduml

Este diagrama responde preguntas de negocio directamente: ¿se puede cancelar tras pagar? No hay flecha Pagado→Cancelado: la política dice que no. ¿Cuándo se puede devolver? Solo desde Entregado y con guarda temporal. Esa precisión es lo que convierte al diagrama en especificación ejecutable.

Buenas prácticas

  • Nombres adjetivos o sustantivos: los estados son condiciones ("Pagado", "Enviado"), no acciones ("Pagando" ambiguo).
  • Todo estado alcanzable y con salida: estados huérfanos o trampas (sin salida) son errores de diseño.
  • Un solo diagrama por clase protagonista: mezclar Pedido y Pago en una máquina confunde; cada objeto su máquina.
  • Sincroniza con el código: si implementas con librerías tipo XState o Spring Statemachine, mantén nombres idénticos entre diagrama y enum.
  • Documenta eventos imposibles: anotar qué NO puede pasar ("no existe cancelar tras Enviado") previene features mal especificadas.
