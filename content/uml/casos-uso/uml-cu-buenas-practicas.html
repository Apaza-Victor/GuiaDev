5.1. Errores frecuentes al modelar casos de uso

Estos son los fallos clásicos que arruinan un diagrama de casos de uso:

  • Convertir pasos en casos de uso: "Ingresar usuario", "Validar contraseña" y "Mostrar menú" no son casos de uso; son pasos internos de "Iniciar Sesión". Un caso de uso entrega un resultado completo y valioso para el actor.
  • Actores que son sistemas sin rol: modelar "Base de Datos" como actor. La BD es interna; los actores son externos (personas u otros sistemas).
  • Casos CRUD mecánicos: cuatro burbujas "Crear Usuario", "Editar Usuario"... cuando una sola "Gestionar Usuarios" comunica mejor.
  • Abusar de include/extend: si cada caso tiene cinco flechas punteadas, el diagrama se vuelve ilegible. Úsalos solo para comportamiento realmente compartido u opcional.
  • Flujo dentro del diagrama: el diagrama muestra qué, no cómo. Los pasos van en la especificación textual.
  • Sin frontera del sistema: rectángulo ausente → imposible distinguir actores de procesos internos.

5.2. La granularidad correcta

La pregunta filtro: "¿El actor obtiene aquí un objetivo de negocio completo?"

Muy pequeño ❌Correcto ✔Muy grande ❌
"Guardar venta""Registrar Venta""Administrar Tienda"
"Abrir formulario""Reservar Habitación""Operar Sistema Hotelero"
"Enviar email""Notificar Pedido Listo""Gestionar Logística Completa"

Regla empírica: un sistema mediano suele tener entre 10 y 30 casos de uso. Si superas 50, estás fragmentando; si tienes menos de 8, probablemente agrupaste demasiado.

5.3. Documentar el flujo de cada caso de uso

El diagrama por sí solo no basta: cada burbuja merece una especificación textual mínima. Plantilla recomendada:

# CU-07: Retirar Efectivo

- **Actor principal:** Cliente del banco
- **Precondición:** Tarjeta válida insertada y PIN verificado
- **Flujo principal:**
  1. El cliente selecciona "Retiro"
  2. Ingresa el monto deseado
  3. El sistema verifica fondos disponibles
  4. El cajero dispensa el efectivo e imprime comprobante
- **Flujos alternativos:**
  - 3a. Fondos insuficientes → se informa y se solicita otro monto
- **Postcondición:** Saldo actualizado y transacción registrada

Esa especificación vive en la wiki o en el propio repositorio; el diagrama enlaza a ella mediante el ID (CU-07).

5.4. Casos de uso vs historias de usuario

En equipos ágiles surge la duda natural. No compiten: cubren necesidades distintas.

AspectoCaso de Uso (UML)Historia de Usuario
FormatoDiagrama + especificación formalFrase corta: "Como X quiero Y para Z"
DetalleFlujos principales y alternativos completosCriterios de aceptación puntuales
DuraciónVive durante toda la vida del sistemaSe cierra al terminar el sprint
Audiencia idealDiseño, contratos, sistemas críticosBacklog ágil, conversación diaria

Patrón híbrido habitual: las historias del backlog cortan horizontalmente un caso de uso grande ("Implementar flujo principal de CU-07").

5.5. Checklist de calidad

Antes de presentar el modelo, verifica:

  • [ ] ¿Cada caso de uso entrega valor observable a un actor?
  • [ ] ¿Los nombres empiezan con verbo fuerte en infinitivo?
  • [ ] ¿Todos los actores están fuera de la frontera?
  • [ ] ¿Cada actor participa en al menos un caso de uso?
  • [ ] ¿«include» se usa solo para lógica compartida obligatoria?
  • [ ] ¿«extend» se usa solo para comportamiento opcional/condicional?
  • [ ] ¿Los casos críticos tienen especificación textual documentada?
  • [ ] ¿Un lector ajeno al proyecto entiende el sistema en 2 minutos?

Si respondiste "no" a dos o más, dedica otra iteración al modelo antes de avanzar a diseño detallado.
