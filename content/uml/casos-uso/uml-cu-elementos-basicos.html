2.1. Actores (usuarios y sistemas externos)

Los actores representan entidades externas que interactúan con el sistema. Pueden ser personas, organizaciones o incluso otros sistemas informáticos.

Definición de actor

Un actor es cualquier entidad externa que intercambia información con el sistema. Los actores no forman parte del sistema en sí, sino que representan roles que interactúan con él.

Tipos de actores

Ver código PlantUML 
@startuml
' Definición de actores principales
actor "Actor" as ActorGenerico
actor "Usuario Registrado" as UsuarioRegistrado
actor "Administrador" as Administrador
actor "Cliente" as Cliente

' Definición de actores secundarios
actor "Actor Secundario" as ActorSecundario
actor "Sistema de Pago" as SistemaPago
actor "Servicio de Correo Electrónico" as ServicioCorreo
actor "Base de Datos Externa" as BaseDatos

' Relaciones de herencia
ActorGenerico <|-- UsuarioRegistrado
ActorGenerico <|-- Administrador
ActorGenerico <|-- Cliente

ActorSecundario <|-- SistemaPago
ActorSecundario <|-- ServicioCorreo
ActorSecundario <|-- BaseDatos
@enduml
Este diagrama muestra la jerarquía de los diferentes tipos de actores en UML. Se presentan los actores primarios (Usuario Registrado, Administrador, Cliente) que heredan de un Actor genérico, y los actores secundarios (Sistema de Pago, Servicio de Correo Electrónico, Base de Datos Externa) que heredan de un Actor Secundario. Los actores se representan con figuras hexagonales siguiendo la notación estándar de UML.

Actores primarios

Inician la interacción con el sistema para lograr un objetivo específico.

  • Usuario registrado
  • Administrador
  • Cliente

Actores secundarios

Proporcionan un servicio al sistema (reactivos).

  • Sistema de pago
  • Servicio de correo electrónico
  • Base de datos externa

Actores físicos vs lógicos

  • Actores físicos: Personas reales que interactúan con el sistema (Cliente, Empleado)
  • Actores lógicos: Roles que pueden ser desempeñados por diferentes personas (Administrador, Usuario)

Características de los actores

  • Externos al sistema: Los actores siempre están fuera del límite del sistema.
  • Representan roles: Un actor es un rol, no una persona o entidad específica.
  • Pueden ser humanos o no humanos: Sistemas externos, dispositivos, sensores, etc.
  • Pueden tener relaciones entre sí: Principalmente relaciones de generalización/especialización.
Al identificar actores, pregúntese: ¿Quién o qué inicia acciones en el sistema? ¿Quién o qué proporciona o recibe información del sistema?

2.2. Casos de uso (funcionalidades del sistema)

Los casos de uso representan funcionalidades o servicios que el sistema proporciona a sus actores. Cada caso de uso describe una secuencia de acciones que el sistema realiza para producir un resultado observable y valioso para un actor.

Definición de caso de uso

Un caso de uso es una descripción de una secuencia de interacciones entre el sistema y uno o más actores, que produce un resultado valioso y observable para los actores involucrados.

Ver código PlantUML 
@startuml
' Definición de casos de uso
usecase "Consultar Saldo" as ConsultarSaldo
usecase "Transferir Fondos" as TransferirFondos
usecase "Retirar Dinero" as RetirarDinero

' Relaciones entre casos de uso
RetirarDinero ..> ConsultarSaldo : <<include>>
RetirarDinero ..> TransferirFondos : <<extend>>

' Actor que interactúa con los casos de uso
actor Cliente
Cliente --> ConsultarSaldo
Cliente --> TransferirFondos
Cliente --> RetirarDinero
@enduml
Este diagrama muestra cómo se representan los casos de uso en UML. Se muestran tres casos de uso (Consultar Saldo, Transferir Fondos y Retirar Dinero) con sus relaciones de inclusión y extensión, y un actor (Cliente) que interactúa con ellos.

Características de los casos de uso

  • Orientados a objetivos: Cada caso de uso representa un objetivo específico de un actor.
  • Iniciados por actores: Generalmente son desencadenados por una acción de un actor.
  • Proporcionan valor: Deben producir un resultado observable y valioso.
  • Completos: Describen una funcionalidad completa, desde el inicio hasta el final.

Niveles de detalle en casos de uso

Casos de uso de alto nivel

Descripciones breves que capturan la esencia de un caso de uso sin entrar en detalles.

Caso de Uso: Retirar Dinero
Actor Principal: Cliente
Descripción: El cliente retira dinero de su cuenta bancaria a través del cajero automático.

Casos de uso expandidos

Descripciones detalladas que incluyen flujos principales, alternativos y excepcionales.

Caso de Uso: Retirar Dinero
Actor Principal: Cliente
Precondiciones: Cliente tiene tarjeta válida y cuenta activa
Flujo Principal:
1. Cliente inserta tarjeta
2. Sistema solicita PIN
3. Cliente introduce PIN
4. Sistema valida PIN
5. Sistema muestra opciones
6. Cliente selecciona "Retirar dinero"
7. Sistema solicita cantidad
8. Cliente introduce cantidad
9. Sistema verifica fondos
10. Sistema dispensa dinero
11. Sistema actualiza saldo
12. Sistema devuelve tarjeta

Flujos Alternativos:
4a. PIN incorrecto:
  1. Sistema muestra mensaje de error
  2. Vuelve al paso 2 (máximo 3 intentos)

9a. Fondos insuficientes:
  1. Sistema muestra mensaje de error
  2. Vuelve al paso 7
En los diagramas de casos de uso UML, solo se representa el nombre del caso de uso. Los detalles se documentan por separado en especificaciones de casos de uso.

Límite del sistema

El límite del sistema es un rectángulo que engloba todos los casos de uso, representando la frontera entre el sistema y los actores externos.

Ver código PlantUML 
@startuml
rectangle "Sistema" {
  usecase "Caso de Uso 1" as CU1
  usecase "Caso de Uso 2" as CU2
  usecase "Caso de Uso 3" as CU3
}

actor Actor

Actor --> CU1
Actor --> CU2
Actor --> CU3
@enduml
Este diagrama muestra el límite del sistema en UML. El rectángulo representa el sistema que contiene los casos de uso, mientras que los actores se encuentran fuera del sistema.
  • Define claramente qué está dentro y fuera del sistema.
  • Ayuda a establecer el alcance del sistema.
  • Todos los casos de uso deben estar dentro del límite.
  • Todos los actores deben estar fuera del límite.

2.3. Relaciones entre actores y casos de uso

Las relaciones en los diagramas de casos de uso conectan actores con casos de uso, o casos de uso entre sí, mostrando cómo interactúan.

Asociación (actor-caso de uso)

La asociación es la relación más básica y común, que conecta un actor con un caso de uso indicando que el actor participa en ese caso de uso.

Ver código PlantUML 
@startuml
actor Usuario
usecase "Iniciar Sesión" as IniciarSesion

Usuario --> IniciarSesion
@enduml
Este diagrama muestra la asociación entre un actor (Usuario) y un caso de uso (Iniciar Sesión). La flecha indica que el actor inicia la interacción con el caso de uso.
  • Se representa con una línea sólida entre el actor y el caso de uso.
  • Indica que el actor se comunica con el sistema mediante este caso de uso.
  • No tiene dirección específica (aunque a veces se usa una flecha para indicar quién inicia la interacción).
  • Un actor puede asociarse con múltiples casos de uso.
  • Un caso de uso puede asociarse con múltiples actores.
La asociación responde a la pregunta: ¿Qué actor interactúa con qué funcionalidad del sistema?

Ejemplo completo de elementos básicos

Ver código PlantUML 
@startuml
rectangle "Sistema Bancario" {
  usecase "Consultar Saldo" as ConsultarSaldo
  usecase "Transferir Fondos" as TransferirFondos
  usecase "Retirar Dinero" as RetirarDinero
  
  RetirarDinero ..> ConsultarSaldo : <<include>>
  RetirarDinero ..> TransferirFondos : <<extend>>
}

actor Cliente

Cliente --> ConsultarSaldo
Cliente --> TransferirFondos
Cliente --> RetirarDinero
@enduml
Este diagrama completo muestra un sistema bancario con tres casos de uso (Consultar Saldo, Transferir Fondos y Retirar Dinero) y un actor (Cliente). También muestra relaciones entre casos de uso: "Retirar Dinero" incluye "Consultar Saldo" y puede extenderse a "Transferir Fondos". El rectángulo representa el límite del sistema.

Buenas prácticas al definir elementos básicos

  • Nombrar correctamente:
    • Actores: sustantivos que describan roles (Cliente, Administrador)
    • Casos de uso: verbos en infinitivo + objeto (Registrar Usuario, Procesar Pago)
  • Nivel adecuado de detalle: Evitar casos de uso demasiado generales o demasiado específicos
  • Enfoque en valor: Cada caso de uso debe proporcionar un resultado valioso para al menos un actor
  • Claridad en los límites: Definir claramente qué está dentro y fuera del sistema
  • Evitar diagramas sobrecargados: Si hay muchos casos de uso, considerar dividirlos en varios diagramas
Un error común es confundir pasos de un caso de uso con casos de uso independientes. Por ejemplo, "Introducir PIN" no debería ser un caso de uso separado, sino un paso dentro del caso de uso "Retirar Dinero".
