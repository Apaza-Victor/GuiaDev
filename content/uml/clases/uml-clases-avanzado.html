5.1. Clases abstractas e interfaces

Una clase abstracta no puede instanciarse: define comportamiento común para sus hijas. En UML se escribe su nombre en cursiva o con el estereotipo {abstract}. Una interfaz es un contrato de métodos sin implementación; se representa como un círculo (lollipop) o como clase estereotipada «interface».

@startuml
abstract class Figura {
  {abstract} +calcularArea() : double
  +describir() : String
}

interface Movable {
  +mover(x: int, y: int)
}

class Circulo {
  -radio : double
}
class Cuadrado {
  -lado : double
}

Figura <|-- Circulo
Figura <|-- Cuadrado
Figura ..|> Movable
@enduml

Cómo distinguirlos en el diagrama:

ConceptoNotaciónRelación típica
Clase abstractaNombre en cursivaHerencia: flecha con triángulo vacío
Interfaz provistaCírculo unido a la claseRealización: ..|> línea discontinua
Interfaz requeridaSemicírculo (socket)Dependencia de uso

Regla práctica: herencia (es-un) solo entre clases fuertemente relacionadas; si la relación es puede-hacer, modela interfaz.

5.2. Clases parametrizadas (genéricos)

Las colecciones tipadas se modelan con un rectángulo punteado anclado que indica el parámetro de tipo:

┌╌╌╌╌╌╌╌╌╌╌╌╌╌╌┐
╎ <T>          ╎   ← parámetro formal
╎ List<T>      ╎
╎ +add(t: T)   ╎
└╌╌╌╌╌╌╌╌╌╌╌╌╌╌┘
        ┊ «bind»
   List<Cliente>   ← enlace de vinculación

En PlantUML basta escribir el genérico directamente:

@startuml
class "List" as List
class Cliente
List "clientes *" --o "1..*" Cliente : contiene
note right of List : «bind» List<Cliente>
@enduml

5.3. Miembros estáticos y de clase

Los miembros estáticos (de clase, no de instancia) se subrayan en la notación UML clásica. En PlantUML se marcan con el modificador {static}:

@startuml
class MathUtils {
  {static} +PI : double = 3.14159
  {static} +max(a: double, b: double) : double
  +normalizar(valor: double) : double
}
@enduml

Convenciones habituales del equipo: constantes en MAYÚSCULAS, fábricas estáticas (+crear()) junto a constructores privados cuando aplicas el patrón Singleton o Factory Method.

5.4. Estereotipos estándar útiles

Los estereotipos refinan el significado de un elemento. Los más usados en diagramas de clases:

  • «entity» — clase persistente mapeada a base de datos.
  • «control» — lógica de coordinación/orquestación.
  • «border» / «boundary» — interfaz con el usuario.
  • «utility» — colección de funciones estáticas.
  • «exception» — clase de error lanzable.
  • «DTO» / «ValueObject» — objetos de transferencia sin lógica.
@startuml
class Usuario <> {
  -id : UUID
  -email : String
}
class RegistroController <>
class VistaRegistro <>

VistaRegistro --> RegistroController
RegistroController --> Usuario
@enduml

Esta correspondencia es lo que convierte al diagrama de clases en el plano maestro del diseño OO: quien lee el código debería poder dibujar el diagrama mentalmente.

5.6. Errores comunes en diagramas de clases

  • Todo privado vs todo público: exponer todo rompe el encapsulamiento; ocultarlo todo obliga a getters absurdos. Decide por responsabilidad.
  • Herencia para reutilizar código: si la relación no es "es-un", usa composición ("tiene-un").
  • Dibujar getters/setters: ruido innecesario; omítelos salvo que aporten semántica.
  • Confundir agregación con composición: pregunta: ¿si muere el contenedor, muere la parte? Sí → composición.
  • Diagramas enciclopédicos: un diagrama con 40 clases no comunica nada; parte por dominio o capa.
  • Multiplicidades olvidadas: una asociación sin multiplicidad está incompleta.
