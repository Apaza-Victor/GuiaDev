Notación de un objeto

Un objeto se dibuja como un rectángulo con dos o tres compartimentos, siempre subrayado. El título admite tres variantes:

1) Con nombre y clase:        2) Anónimo (solo clase):    3) Solo nombre:
┌─────────────────┐           ┌──────────────────┐         ┌───────────────┐
│  pedido47 :     │           │   :Pedido        │         │  pedido47     │
│  Pedido         │           ├──────────────────┤         └───────────────┘
├─────────────────┤           │ total = 250.00   │          (clase deducible
│ total = 250.00  │           │ estado = "nuevo" │           del contexto)
│ estado = "nuevo"│           └──────────────────┘
└─────────────────┘

Detalles de notación:

  • Formato del título: nombreObjeto : NombreClase, subrayado, con espacios alrededor de los dos puntos.
  • Cada atributo muestra su valor actual: atributo = valor.
  • No se dibujan métodos: todos los objetos de una clase comparten la misma operación.
  • Los valores pueden llevar estado: items = [A, B, C] para colecciones.

Enlaces entre objetos

Un enlace (link) es la instancia de una asociación. Se dibuja como línea sólida entre rectángulos; puede tener nombre y navegabilidad igual que las asociaciones:

┌──────────────┐   jefe_de    ┌──────────────┐
│ maria :      │─────────────►│ pedro :      │
│ Empleado     │              │ Empleado     │
└──────────────┘              └──────────────┘

Diferencias respecto a las asociaciones de clases:

  • Sin multiplicidades: el enlace conecta exactamente un objeto con otro; ya no hay "0..*" porque la cantidad está fijada por la foto.
  • Sí puede haber rol y navegabilidad: jefe_de con flecha indica dirección de acceso.
  • Agregación/composición sí aparecen: un carrito contiene ítems concretos con rombo relleno.

Ejemplo completo con PlantUML

Foto instantánea de un carrito de compras en memoria:

@startuml
object "maria : Cliente" as c {
  email = "maria@mail.com"
}

object "pedido47 : Pedido" as p {
  fecha = "2026-08-21"
  total = 318.00
  estado = "confirmado"
}

object "item1 : LineaPedido" as l1 {
  producto = "Teclado"
  cantidad = 2
  precio = 89.90
}

object "item2 : LineaPedido" as l2 {
  producto = "Monitor"
  cantidad = 1
  precio = 129.20
}

c --> p : realizo
p *--> l1
p *--> l2
@enduml

Análisis de la foto: el pedido 47 pertenece a María, está confirmado, y se compone de dos líneas (composición — si muere el pedido, mueren sus líneas). El total coincide con 2×89.90 + 129.20 = 318.00: los diagramas de objetos permiten verificar aritmética del dominio.

Buenas prácticas

  • Nombres significativos: pedido47 mejor que p1; el identificador debe contar historia.
  • Pocos objetos por diagrama: 5–10 instancias comunican bien; 30 convierten la foto en ruido. Filtra al subdominio relevante.
  • Consistente con las clases: ningún atributo ni enlace que no exista en el diagrama de clases correspondiente.
  • Momento explícito: titula el diagrama ("tras confirmar el pedido", "estado inicial del test") — una foto sin contexto temporal confunde.
  • Útil en documentación de API: ejemplos JSON de request/response son, en esencia, diagramas de objetos serializados.
