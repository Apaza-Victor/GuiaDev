4.1. Flujos de objetos y pines

Además del flujo de control (flechas sólidas), un diagrama de actividades puede mostrar el flujo de datos: qué objeto produce y consume cada acción. Los pines son los pequeños cuadrados en el borde de una acción que reciben o emiten esos objetos.

┌─────────────┐        ╔═══════════╗        ┌──────────────┐
│ Tomar Pedido│ ─────► ║  Pedido   ║ ─────► │ Procesar     │
└─────────────┘  out   ╚═══════════╝  in    │ Pago         │
                    flujo de objeto         └──────────────┘

En PlantUML se expresan con nodos de objeto conectados a las acciones:

@startuml
start
:Tomar pedido;
:Pedido] as pedido
:Procesar pago;
pedido --> :Preparar envio;
:Envio] as envio
stop
@enduml

Regla práctica: usa flujos de control para el orden lógico y flujos de objetos cuando el dato que se transforma es lo importante (procesos ETL, pipelines).

4.2. Nodos de datos (almacenes)

Los nodos de almacenamiento de datos (cilindro) representan información persistente entre actividades: bases de datos, colas, archivos:

  • Nodo de datos central: todos leen/escriben del mismo almacén (patrón compartido).
  • Almacén pasivo vs activo: un archivo es pasivo; una cola de mensajes («centralBuffer») procesa y entrega, siendo activo.
@startuml
start
:Generar reporte CSV;
database "Cola de exportacion" as cola
cola -> :Worker procesa export;
:Notificar usuario;
stop
@enduml

Cuando modelas arquitecturas con mensajería (RabbitMQ, Kafka), este elemento comunica mejor la desacoplamiento que una simple flecha.

4.3. Señales de envío y recepción

A veces el flujo no continúa "porque sí", sino porque llegó un evento externo. Para eso existen las señales:

  • Send signal (convexo): la actividad dispara un evento hacia fuera — notificación, webhook, mensaje.
  • Accept signal (cóncavo): la actividad queda esperando un evento externo para continuar — respuesta de pasarela de pago, confirmación humana.
  • Accept time (reloj de arena): espera temporal — timeout de 24 horas antes de cancelar el pedido.
@startuml
start
:Solicitar verificacion por email;
:Enviar email (senal);
repeat
  :Esperar click del usuario;
repeat while (recibio confirmacion?) is (no) 
->si;
:Cuenta verificada;
stop
@enduml

Sin señales, los procesos asíncronos se dibujan mal; con ellas, el diagrama refleja fielmente sistemas dirigidos por eventos.

4.4. Actividades anidadas (subactividades)

Una acción puede expandirse como un diagrama completo mediante el estereotipo «subactivity» o la referencia con horquilla (rake symbol). Esto permite:

  • Mantener el nivel alto legible ("Onboard Cliente" como caja negra) y detallar internamente en otro diagrama.
  • Reutilizar subprocesos idénticos en varios flujos (ej.: "Validar Identidad").
┌──────────────────────────────┐
│ Onboarding de Cliente        │
│ ⌐ «subactivity»              │ → se detalla en otro diagrama
│ Validar Identidad            │
└──────────────────────────────┘

Equivalente conceptual al ref de secuencia y a las funciones en código: abstracción por niveles.

4.5. Regiones de interrupción

Una región de interrupción (área punteada con rayo) define eventos que, si ocurren dentro de ella, abortan inmediatamente el resto del flujo:

@startuml
start
:Procesar pedido;
if (region interrumpible) then
  partition ZonaInterrumpida {
    :Verificar inventario;
    :Reservar stock;
  }
  if (timeout de reserva) then (si)
    :Liberar recursos;
    :Avisar cliente;
    stop
  endif
endif
:Confirmar venta;
stop
@enduml

Escenarios típicos: timeouts, cancelaciones del usuario, fallos de red. La región documenta explícitamente dónde el proceso puede morir y qué limpieza se ejecuta.

4.6. Buenas prácticas en procesos complejos

  • Un solo inicio visible: si necesitas muchos nodos iniciales, probablemente son procesos distintos; sepáralos.
  • Verbo + objeto en cada acción: "Validar tarjeta", no "Tarjeta".
  • Máximo 15–20 acciones por diagrama: más allá, extrae subactividades.
  • Nombrar todas las guardas: una decisión sin etiquetas en ambas salidas obliga a adivinar.
  • Distingue decisión de fusión (merge): el rombo con una entrada y dos salidas decide; con dos entradas y una salida fusiona. No mezcles roles en el mismo rombo si buscas precisión.
  • Swimlanes cuando hay actores múltiples: sin particiones, un proceso de 3 departamentos parece mágica interna.
