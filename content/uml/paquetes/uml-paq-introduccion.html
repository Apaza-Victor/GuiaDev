¿Qué es un paquete en UML?

Un paquete es el mecanismo de UML para agrupar elementos relacionados y tratarlos como una sola unidad. No describe comportamiento ni lógica: describe organización. Es al diseño de software lo que las carpetas son a los archivos.

Mientras que el diagrama de clases muestra "cómo es" cada pieza, el diagrama de paquetes muestra "dónde vive" cada pieza y cómo dependen los grupos entre sí. Es, en la práctica, una vista de la arquitectura del sistema:

Sistema completo
├── paquete Presentacion  → pantallas, controladores UI
├── paquete Aplicacion    → casos de uso, servicios
├── paquete Dominio       → entidades y reglas de negocio
└── paquete Infraestructura → BD, APIs externas, framework

Cada paquete puede contener clases, interfaces, otros paquetes (anidamiento) e incluso diagramas completos. En el código se refleja como namespaces (C#, PHP), packages (Java, Go) o módulos/carpetas (Python, TypeScript).

Organización por capas

El uso más común del diagrama de paquetes es documentar una arquitectura en capas, donde cada capa tiene una responsabilidad única:

CapaResponsabilidadEjemplos de contenido
PresentaciónInteracción con el usuarioVistas, componentes, controladores HTTP
AplicaciónOrquestar casos de usoServicios, manejadores, DTOs
DominioReglas de negocio purasEntidades, objetos de valor, interfaces de repositorio
InfraestructuraDetalles técnicosORM, clientes REST, envío de email, configuración

La regla de oro: las dependencias apuntan hacia adentro. La presentación depende de aplicación, aplicación de dominio... pero el dominio no sabe nada de nadie. Esto permite cambiar la base de datos o el framework sin tocar las reglas de negocio.

Dependencias entre paquetes

Una dependencia entre paquetes significa que si el paquete destino cambia su interfaz pública, el origen debe revisarse. Se dibuja con flecha punteada:

@startuml
package Presentacion
package Aplicacion
package Dominio

Presentacion ..> Aplicacion : usa
Aplicacion ..> Dominio : usa
@enduml

Tres señales de alerta que este diagrama hace visibles al instante:

  • Dependencias circulares: A depende de B y B de A; ningún paquete puede compilarse ni entenderse sin el otro.
  • Dependencias cruzadas entre capas: presentación accediendo directo a infraestructura salta la capa de aplicación.
  • Paquete "comodín": todos dependen de él y él de todos; suele ser un cajón desastre mal nombrado como Common o Utils.

Cuándo usarlo

  • Al iniciar un proyecto grande: define los módulos antes de escribir clases; es más barato mover paquetes en papel que refactorizar carpetas con código.
  • Para documentar la arquitectura: un diagrama de paquetes actualizado comunica la estructura a nuevos integrantes mejor que mil párrafos.
  • Al dividir trabajo entre equipos: cada equipo es dueño de paquetes; las dependencias definidas son contratos de integración.
  • Antes de extraer microservicios o librerías: los límites de paquetes limpios son candidatos naturales a módulos independientes.

No lo uses en proyectos pequeños: si todo cabe en tres carpetas y cabe en pantalla, el diagrama de paquetes añade ruido, no claridad. Su valor aparece cuando la cantidad de clases supera lo que una persona puede mantener en la cabeza.
