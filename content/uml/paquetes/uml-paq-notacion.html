Notación de paquetes y dependencias

Un paquete se dibuja como un rectángulo con pestaña (una lengüeta arriba a la izquierda). El nombre va dentro del cuerpo, o en la pestaña si el cuerpo muestra contenido:

@startuml
package "Ventas" {
  class Factura
  class Cliente
}

package VentasSimple
note right of VentasSimple : nombre solo en la pestana
@enduml

Las dependencias se dibujan con flecha discontinua abierta (..>) desde el paquete que necesita hacia el que provee. La flecha nunca es decorativa: marca la dirección del riesgo — quien recibe la punta es quien puede romper al otro al cambiar.

  • Línea sólida con círculo (+) = realización: el paquete implementa una interfaz.
  • Anidamiento visual = composición de paquetes (el interno existe solo dentro del externo).
  • Calificación: Padre::Hijo referencia un elemento anidado sin dibujarlo.

Elementos importados y visibilidad

UML distingue dos formas de acceder a elementos de otro paquete, con estereotipos sobre la dependencia:

RelaciónSintaxis PlantUMLSignificado
Import (privado)A ..> B : <<import>>Los elementos de B se usan dentro de A con su nombre simple
Import públicoA ..> B : <<access>>A usa B pero no re-exporta: C no ve B a través de A
MergeA ..> B : <<merge>>B se fusiona conceptualmente en A (usado con perfiles)

La visibilidad dentro del paquete funciona como en las clases: un elemento +publico es visible fuera del paquete; uno -privado solo es accesible desde su propio paquete. Así se ocultan clases internas de implementación y se expone únicamente la interfaz del módulo.

Estereotipos estándar útiles

Los estereotipos documentan la intención arquitectónica de cada paquete:

  • <<facade>>: paquete que actúa como puerta de entrada; simplifica el acceso a un subsistema complejo.
  • <<framework>>: paquete reutilizable que extiende el sistema (Spring, React).
  • <<subsystem>>: grupo cohesivo con comportamiento propio, candidato a servicio independiente.
  • <<system>>: el sistema completo visto como una unidad.
  • <<layer>>: rebanada vertical de la arquitectura (presentación, dominio...).

No hay que abusar: dos o tres estereotipos bien elegidos comunican más que una taxonomía completa que nadie recuerda.

Ejemplo completo con PlantUML

Arquitectura en capas de una tienda en línea, con reglas de dependencia explícitas:

@startuml
skinparam packageStyle rectangle

package "Presentacion <>" as UI {
  package Web
  package API_REST
}

package "Aplicacion <>" as App {
  package Servicios
}

package "Dominio <>" as Dom {
  package Entidades
  package ReglasNegocio
}

package "Infraestructura <>" as Infra {
  package Persistencia
  package Notificaciones
}

Web ..> Servicios : <>
API_REST ..> Servicios : <>
Servicios ..> ReglasNegocio : <>
Persistencia .up.> Entidades : <>
Notificaciones .up.> Entidades : <>
@enduml

Lectura del diagrama: toda petición entra por Web/API, pasa por servicios, aplica reglas del dominio y se materializa mediante infraestructura. Ningún elemento de UI conoce Persistencia directamente — cambiar Oracle por PostgreSQL no toca ni una línea de la capa de presentación.

Reglas de dependencias limpias

  • Cero ciclos: si A→B→A, extrae lo compartido a un tercer paquete C del que ambos dependan.
  • Depende de abstracciones: la capa alta debería depender de interfaces (definidas en capas internas), no de implementaciones concretas.
  • Estable abajo, volátil arriba: los paquetes de los que muchos dependen deben cambiar poco; el detalle cambiante vive en los bordes.
  • Un motivo por paquete: si para describir un paquete necesitas la palabra "y", probablemente sean dos.
  • Revísalo en cada release: las dependencias ilegales empiezan con un import "rápido"; automatiza la detección (Dependency Cruiser, ArchUnit, phparkitect).

Ejercicio propuesto: dibuja los paquetes de tu proyecto actual tal como están hoy, no como deberían estar. Marca con rojo cada dependencia que viole las reglas anteriores — ese es tu mapa de deuda arquitectónica.
