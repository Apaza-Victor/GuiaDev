Clases, constructores y la regla de cinco

Una clase agrupa datos + comportamiento y controla quién accede a qué mediante visibilidad. En C++ existe también struct, y la única diferencia técnica es mínima pero reveladora:

Aspectostructclass
Visibilidad por defectopublicprivate
Herencia por defectopublicprivate
Convención comunitariaAgregados de datos pasivosTipos con invariantes y encapsulación

Anatomía de una clase completa

class CuentaBancaria {
public:
    // Constructor con lista de inicialización (preferible a asignar en el cuerpo)
    explicit CuentaBancaria(std::string titular, double saldoInicial = 0)
        : titular_{std::move(titular)}, saldo_{saldoInicial} {
        if (saldo_ < 0) throw std::invalid_argument{"saldo negativo"};
    }

    // Métodos consultores: const = prometen NO modificar
    [[nodiscard]] double saldo() const { return saldo_; }
    [[nodiscard]] const std::string& titular() const { return titular_; }

    bool depositar(double monto) {
        if (monto <= 0) return false;
        saldo_ += monto;             // invariante protegida aquí
        return true;
    }

private:
    std::string titular_;   // datos privados: nadie los corrompe desde fuera
    double saldo_;
};

CuentaBancaria c{"Ada", 1000};
c.depositar(500);
std::cout << c.saldo();      // 1500
// c.saldo_ = -9999;         ❌ no compila: privado

: titular_{...}, saldo_{...} es la lista de inicialización: inicializa directamente (una construcción), mientras que asignar en el cuerpo construye Y luego copia. Además el orden de ejecución sigue el orden DECLARACIÓN de miembros, no el del constructor — mezclar ambos estilos genera bugs sutiles.

La regla de cinco

Cinco operaciones especiales define el compilador automáticamente… hasta que tú declaras cualquiera. Entonces debes decidir las cinco conscientemente:

OperaciónSintaxisCuándo importa
Destructor~T()Recursos RAII que liberar
Constructor de copiaT(const T&)Duplicar objetos
Asignación por copiaT& operator=(const T&)a = b;
Constructor de movimientoT(T&&) noexceptRobar recursos de temporales
Asignación por movimientoT& operator=(T&&) noexcepta = std::move(b);
 
class Buffer {
public:
    explicit Buffer(size_t n) : tam_{n}, datos_{new int[n]{}} {}
    ~Buffer() { delete[] datos_; }                    // 1

    // Copia PROFUNDA: cada objeto dueño de SU memoria
    Buffer(const Buffer& o) : tam_{o.tam_}, datos_{new int[o.tam_]} {  // 2
        std::copy(o.datos_, o.datos_ + tam_, datos_);
    }
    Buffer& operator=(const Buffer& o) {              // 3 (copy-and-swap idiom)
        Buffer tmp{o};                                // copia segura
        std::swap(tam_, tmp.tam_);
        std::swap(datos_, tmp.datos_);
        return *this;                                 // tmp muere liberando lo viejo
    }

    // Movimiento: ROBAR en O(1) y dejar al origen vacío
    Buffer(Buffer&& o) noexcept                       // 4
        : tam_{std::exchange(o.tam_, 0)}, datos_{std::exchange(o.datos_, nullptr)} {}
    Buffer& operator=(Buffer&& o) noexcept {          // 5
        std::swap(tam_, o.tam_);
        std::swap(datos_, o.datos_);
        return *this;
    }
private:
    size_t tam_;
    int* datos_;
};

Si tu clase solo agrega otros objetos RAII (strings, vectors, smart pointers): declara NADA y deja los defaults — serán correctos. La regla de cinco aplica cuando gestionas recursos crudos directamente. Regla de CERO > regla de cinco.

Herencia, virtual y polimorfismo

La palabra clave virtual: despacho dinámico

Sin virtual, las llamadas se resuelven por el TIPO ESTÁTICO en compilación. Con virtual, se resuelve por el tipo REAL en ejecución — eso es polimorfismo real:

class Animal {
public:
    explicit Animal(std::string nombre) : nombre_{std::move(nombre)} {}
    virtual ~Animal() = default;              // ¡DESTRUCTOR VIRTUAL OBLIGATORIO!

    [[nodiscard]] virtual std::string sonido() const { return "..."; }
    void presentarse() const {                 // método NO virtual: compartido
        std::cout << nombre_ << " dice: " << sonido() << '\n';
    }                                          // ...pero LLAMA a la virtual ✨

protected:
    std::string nombre_;    // visible para derivadas, oculto para el mundo
};

class Perro : public Animal {
public:
    using Animal::Animal;                     // hereda constructores
    [[nodiscard]] std::string sonido() const override { return "¡guau!"; }
};

class Gato : public Animal {
public:
    using Animal::Animal;
    [[nodiscard]] std::string sonido() const override { return "miau"; }
};

void hacerHablar(Animal& a) {     // acepta Animal Y cualquier derivada
    a.presentarse();               // llama al sonido() REAL del objeto
}

Perro p{"Rex"};
Gato g{"Michi"};
hacerHablar(p);   // Rex dice: ¡guau!
hacerHablar(g);   // Michi dice: miau   ← decidido EN EJECUCIÓN

override, final y clases abstractas

HerramientaEfecto
overrideEl compilador VERIFICA que realmente sobrescribes algo (firma exacta). Sin él, un typo crea método nuevo silenciosamente
finalProhibe seguir sobrescribiendo (método) o heredar (clase)
= 0 (virtual pura)Método SIN implementación → clase ABSTRACTA: no instanciable, contrato puro
 
class Forma {                              // ABSTRACTA
public:
    virtual ~Forma() = default;
    [[nodiscard]] virtual double area() const = 0;          // sin cuerpo
    [[nodiscard]] virtual double perimetro() const = 0;
    virtual std::string nombre() const final { return "forma"; } // congela este
};

class Circulo final : public Forma {
public:
    explicit Circulo(double r) : r_{r} {}
    [[nodiscard]] double area() const override { return M_PI * r_ * r_; }
    [[nodiscard]] double perimetro() const override { return 2 * M_PI * r_; }
private:
    double r_;
};

// Forma f;                     ❌ abstracta: no instanciable
auto formas = std::vector<std::unique_ptr<Forma>>{};
formas.push_back(std::make_unique<Circulo>(5));
for (const auto& f : formas) std::cout << f->area();  // polimorfismo vía puntero

El destructor virtual en clases base polimórficas NO ES OPCIONAL: delete basePtr sobre derivada sin destructor virtual es comportamiento indefinido (solo corre el destructor de la base — fugas garantizadas). Regla: ¿algún virtual? → destructor virtual.

Composición sobre herencia

Como en Go y casi todo lenguaje moderno, la sabiduría acumulada dice: jerarquías profundas = fragilidad. Prefiere componer comportamientos:

// ❌ Jerarquía frágil: PatoVoladorNadadorConSonidoCuac...
// ✅ Composición de capacidades:
class Volador { public: virtual ~Volador() = default; virtual void volar() = 0; };
class Nadador { public: virtual ~Nadador() = default; virtual void nadar() = 0; };

class Pato : public Volador, public Nadador {
public:
    void volar() override { std::cout << "batir alas\n"; }
    void nadar() override { std::cout << "remar\n"; }
};
// Un RobotVolador reutiliza Volador SIN tocar Pato ni jerarquía alguna.

Ejercicios prácticos

  1. Banco encapsulado: implementa CuentaBancaria completa (constructor validador, depositar/retirar, getters const [[nodiscard]]); intenta corromper el saldo desde main y verifica que no compila.
  2. Zoológico polimórfico: clase abstracta Animal con sonido()/patas() puras; deriva Perro, Gato, Serpiente; recorre vector<unique_ptr<Animal>> imprimiendo fichas; añade un override con typo SIN override y observa el error del compilador al agregarlo.
  3. Buffer con regla de cinco: completa la clase Buffer de la lección; demuestra copia profunda (modificar copia no afecta original) y movimiento (el origen queda vacío).
  4. Composición de habilidades: modela Personaje de RPG componiendo interfaces Atacante, Defensor, Curandero; crea tres combinaciones distintas sin duplicar lógica.
  5. Ciclo de vida instrumentado: clase con prints en constructor/destructor/copia/movimiento; crea, copia y mueve en distintos escenarios y predice el orden de mensajes ANTES de ejecutar.
