Índices: cuándo y cómo

Un índice es una estructura auxiliar (típicamente B-tree) que permite encontrar filas sin recorrer la tabla completa. Es la optimización con mejor relación esfuerzo/beneficio en SQL:

-- MySQL
CREATE INDEX idx_pedidos_cliente ON pedidos(cliente_id);
CREATE INDEX idx_productos_busqueda ON productos(nombre(20));

-- Oracle
CREATE INDEX idx_empleados_dept ON empleados(departamento_id);

Reglas prácticas para decidir dónde indexar:

  • Todas las FOREIGN KEY deben tener índice (MySQL InnoDB no las crea automáticamente).
  • Columnas frecuentes en WHERE, JOIN ... ON y ORDER BY.
  • Columnas con alta selectividad (muchos valores distintos) rinden más; indexar un campo "activo S/N" casi no ayuda.
  • Más no es mejor: cada índice penaliza INSERT/UPDATE/DELETE porque debe mantenerse.

Escribir consultas eficientes

  • Nunca SELECT * en producción: trae columnas innecesarias, impide usar índices cubrientes y rompe contratos si el esquema cambia.
  • Filtra lo antes posible: condiciones en WHERE reducen datos antes de joins y agrupaciones.
  • Cuidado con funciones sobre columnas: WHERE YEAR(fecha) = 2026 invalida el índice; usa rangos: fecha >= '2026-01-01' AND fecha < '2027-01-01'.
  • LIMIT/TOP siempre en listados: paginar 1 millón de filas "por si acaso" mata la aplicación.
  • Evita SELECT DISTINCT como parche de joins mal planteados: suele esconder duplicación real de datos.
-- Lento: función sobre columna
SELECT * FROM ventas WHERE UPPER(pais) = 'MEXICO';

-- Rápido: usa el índice
SELECT id, total FROM ventas WHERE pais = 'MEXICO';

Analizar planes de ejecución

Antes de optimizar a ciegas, pregunta al motor cómo ejecutará tu consulta:

EXPLAIN SELECT p.id, c.nombre
FROM pedidos p JOIN clientes c ON c.id = p.cliente_id
WHERE p.total > 1000;

-- Oracle: EXPLAIN PLAN FOR ... ; luego SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

Lo que debes buscar:

  • Full table scan sobre tablas grandes → falta índice o condición no indexable.
  • Tipo de join: nested loops para pocos registros, hash/merge para volúmenes grandes.
  • Filas estimadas vs reales: estimaciones absurdas indican estadísticas desactualizadas (ANALYZE TABLE).

Optimiza midiendo, nunca por intuición: una consulta "feosa" con buen plan supera a una elegante con full scan.

Buenas prácticas de esquema

  • Tipos justos: VARCHAR(50) para un código postal, no TEXT; tipos pequeños = más filas por página = menos I/O.
  • NOT NULL por defecto: los NULL complican consultas e índices; nullabilidad debe ser una decisión explícita.
  • Normaliza hasta 3FN, luego desnormaliza con evidencia de rendimiento, no por comodidad.
  • Claves subrogadas simples (AUTO_INCREMENT/IDENTITY/SEQUENCE) para joins limpios; deja las naturales como UNIQUE.
  • Constraints siempre: integridad en la base, no solo en la aplicación; la app puede tener bugs, la constraint no.

Mantenimiento y monitoreo

  • Estadísticas al día: el optimizador decide con ellas; actualízalas tras cargas masivas.
  • Índices muertos: audita uso (sys.dm_db_index_usage_stats en SQL Server, sys.schema_index_statistics en MySQL) y elimina los nunca leídos.
  • Slow query log: actívalo en desarrollo; cualquier consulta > 100 ms merece revisión.
  • Transacciones cortas: mantén locks mínimos; nada de esperar input de usuario dentro de una transacción abierta.
  • Bulk operations: inserciones masivas por lotes (500–5000 filas) en lugar de fila por fila.

Ejercicio propuesto: toma las tres consultas más frecuentes de tu proyecto actual, ejecútalas con EXPLAIN y aplica una mejora concreta (índice, rango en lugar de función, columnas específicas). Mide tiempos antes y después.
