Procesos ligeros

La unidad de concurrencia en Elixir es el proceso (no del OS): millones de procesos ligeros en la BEAM, aislados entre sí y comunicados por mensajes asíncronos. No hay memoria compartida ni locks.

# Lanzar un proceso que ejecute una función
pid = spawn(fn -> IO.puts("Proceso corriendo") end)
IO.inspect(pid)

# Sincronizar con el término del proceso
padre = self()
spawn(fn -> send(padre, :terminado) end)
receive do
  :terminado -> IO.puts("Terminó OK")
end

# Ejecutar muchas a la vez
for i <- 1..5 do
  spawn(fn -> IO.puts("Tarea #{i}") end)
end

# PID = Process ID: puedes inspeccionarlo
IO.inspect(Process.alive?(spawn(fn -> :ok end)))   # true (puede morir rápido)

Cada proceso es aislado: si uno lanza una excepción, no tumba a los demás, solo se muere él (supervisado). self() devuelve el PID del proceso actual.

Mensajes y receive

La comunicación es con send/2 (asíncrono) y receive (bloqueante con selección por pattern matching). Un "actor" típico: bucle que procesa mensajes.

px = fn nombre ->
  receive do
    {:hola, quien} -> IO.puts("#{nombre} saluda a #{quien}")
    {:suma, a, b} -> IO.puts("#{nombre} ve que #{a}+#{b}=#{a+b}")
    :salir -> :ok
  end
end

proceso = spawn(fn -> px.(proc) end)

# Le enviamos mensajes
send(proceso, {:hola, "Ana"})
send(proceso, {:suma, 2, 3})

# Recibir de cualquier proceso (demo)
send(self(), :mensaje_para_mi)
receive do
  :mensaje_para_mi -> IO.puts("Recibido")
after
  1000 -> IO.puts("timeout")
end
# Demo corta: proceso que cuenta para siempre y capta :alto contador = spawn(fn -> loop(0) end) loop = fn n -> receive do :alto -> IO.puts("detenido en #{n}") {:mas, k} -> dame_loop(n + k) end end # Este patrón (proceso + receive + loop) es literalmente el GenServer manual

El bloque after evita bloqueos eternos. La disciplina: no uses variables de módulo compartidas; pasa mensajes. Esa pureza evita carreras.

GenServer: estado encapsulado

GenServer es el "servidor con estado" de OTP: recibe llamadas (call, síncronas) y cast (cast, asíncronas), manejando el estado dentro de un proceso. Es el bloque fundamental de aplicaciones Elixir.

defmodule Contador do
  use GenServer

  def start_link(inicial) do
    GenServer.start_link(__MODULE__, inicial, name: __MODULE__)
  end

  # Callbacks OTP
  def init(inicial), do: {:ok, inicial}
  def handle_call(:leer, _from, estado), do: {:reply, estado, estado}
  def handle_cast({:incrementar, n}, estado), do: {:noreply, estado + n}

  def leer, do: GenServer.call(__MODULE__, :leer)
  def incrementar(n \\ 1), do: GenServer.cast(__MODULE__, {:incrementar, n})
end

# Iniciar (en una sup servida o a mano en IEx):
# iex(1)> {:ok, pid} = Contador.start_link(0)
# iex(2)> Contador.incrementar(5)
# iex(3)> Contador.incrementar(3)
# iex(4)> Contador.leer()   # 8

GenServer encapsula el estado en un proceso aislado. Operaciones call esperan respuesta; cast no. Tu aplicación guarda estado en GenServers supervisados, nunca en variables globales.

Supervisión y tolerancia a fallos

La joya de OTP: los supervisores con árbol de supervisión (supervisor + workers) deciden la estrategia de reinicio cuando un proceso cae. Así se construye el sistema "let it crash" que nunca se apaga.

defmodule MiApp.Application do
  use Application

  def start(_tipo, _args) do
    children = [
      # un worker GenServer
      {Contador, 0},
      # un Supervisor dentro del árbol
      {Task.Supervisor, name: MiApp.TaskSupervisor},
    ]

    opts = [strategy: :one_for_one, name: MiApp.Supervisor]
    Supervisor.start_link(children, opts)
  end
end

Detalles de la estrategia:

EstrategiaComportamiento
:one_for_oneSolo reinicia el hijo caído
:one_for_allReinicia todo el árbol
:rest_for_oneReinicia el hijo caído y los siguientes
# Combinado con mensajes, un supervisor "repara" el sistema solo
# en producción: crashes = características de trabajo normal y programado
# (ej: falla de red, timeouts) se manejan como mensajes, no como abort de app

# También existen Task (un disparo), Agent (estado simple)
{:ok, pid} = Task.start(fn -> IO.puts("tarea") end)
IO.inspect(Task.async(fn -> 1 + 1 end) |> Task.await())   # 2

La doc oficial de Elixir ("Supervisor and Application") es la hoja de ruta. El consejo práctico: todo lo que inicie estado debe estar bajo un supervisor.

Phoenix: el framework web

Phoenix es el framework web Elixir: rápido, con canales en tiempo real (WebSocket) y arquitectura "LiveView" para réconcil de UI en el servidor. Se sirve sobre Plug/Erlang/OTP.

# Instalar el generador
mix archive.install hex phx_new

# Crear una app (usa el adaptador de base de datos deseado)
mix phx.new mi_web --database sqlite3
cd mi_web

# Crear la base y lanzar el servidor
mix ecto.create
mix phx.server
# Visita http://localhost:4000

# Generar un recurso (modelo + vistas + rutas)
mix phx.gen.html Blog Post titulo:string cuerpo:text
mix ecto.migrate
# Router: lib/mi_web_web/router.ex (extracto)
defmodule MiWebWeb.Router do
  use MiWebWeb, :router

  pipeline :browser do
    plug :accepts, ["html"]
    plug :fetch_session
  end

  scope "/" do
    pipe_through :browser
    get "/", PaginaController, :index
    resources "/entradas", EntradaController
  end
end

Ejercicios prácticos

Practica en orden: cada ejercicio asume lo aprendido en el anterior.

  1. spawn: lanza tres procesos que impriman sus números; verifica con Process.alive?.
  2. Mensajes: crea un proceso que reciba {:suma, a, b} y devuelva el resultado mediante un mensaje de vuelta a self().
  3. GenServer: implementa una ColaSimple con call :agregar y cast :agregar, manteniendo una lista en el estado.
  4. Supervisor: arma una Application que supervise tu Contador y prueba que se reinicia (mata el pid y vuelve a preguntar).
  5. Phoenix: crea mix phx.new, genera el recurso Entrada y publica en mix phx.server.
