Clases y propiedades

C# eleva el encapsulamiento a nivel de lenguaje con las propiedades: campos que parecen variables pero ejecutan código al leerse/escribirse. Son la forma idiomática de exponer estado — nunca campos públicos crudos.

Propiedades: getters/setters civilizados

public class CuentaBancaria
{
    // Auto-propiedad: el compilador genera campo oculto + acceso
    public string Titular { get; set; }

    // Solo lectura desde fuera (set privado):
    public decimal Saldo { get; private set; }

    // init: solo asignable EN CONSTRUCCIÓN, luego inmutable (C# 9)
    public string NumeroCuenta { get; init; }

    // Propiedad calculada: no almacena, computa
    public bool EstaVacia => Saldo == 0;

    // Validación en setter: lógica de negocio protegida
    private int _edad;
    public int Edad
    {
        get => _edad;
        set => _edad = value >= 0 && value <= 150
            ? value
            : throw new ArgumentOutOfRangeException(nameof(value));
    }

    public CuentaBancaria(string titular, string numero)
    {
        Titular = titular;
        NumeroCuenta = numero;
    }
}

Constructores y primary constructors

public class Producto
{
    public string Nombre { get; }
    public decimal Precio { get; }

    // Constructor clásico:
    public Producto(string nombre, decimal precio)
    {
        if (precio < 0) throw new ArgumentException("Precio negativo");
        Nombre = nombre;
        Precio = precio;
    }

    // Delegación entre constructores con : this(...)
    public Producto(string nombre) : this(nombre, 0m) { }
}

// Primary constructor (C# 12): parámetros viven en toda la clase
public class Cliente(string nombre, string email)
{
    public string Nombre => nombre;
    public string Email => email;
    public void Saludar() => Console.WriteLine($"Hola {nombre} ({email})");
}

Los primary constructors son azúcar de captura, no propiedades: los parámetros son campos invisibles compartibles. Para APIs públicas donde el contrato importa (serialización, validación), mantén propiedades explícitas.

static: miembros de clase

public static class Matematicas   // clase estática: solo miembros static
{
    public const double Pi = 3.14159;
    public static double AreaCirculo(double r) => Pi * r * r;
}

Matematicas.AreaCirculo(5);   // sin instanciar nada

// Contador de instancias:
public class Sesion
{
    private static int _total;
    public static int Total => _total;
    public Sesion() => _total++;
}

Herencia e interfaces

public abstract class Animal          // ABSTRACTA: no instanciable
{
    public string Nombre { get; }

    protected Animal(string nombre) => Nombre = nombre;

    public virtual string Sonido() => "...";      // virtual: sobrescribible
    public void Presentarse() =>                  // concreto: heredado tal cual
        Console.WriteLine($"{Nombre} dice {Sonido()}");
}

public sealed class Perro : Animal     // sealed: nadie hereda más de aquí
{
    public Perro(string nombre) : base(nombre) { }   // llamar constructor base

    public override string Sonido() => "¡guau!";
}

public interface IVolador              // CONTRATO puro sin implementación
{
    double AlturaMaxima { get; }
    void Vol();
}

public class Pato : Animal, IVolador   // una clase base + N interfaces
{
    public Pato(string n) : base(n) { }
    public override string Sonido() => "cuac";
    public double AlturaMaxima => 1000.0;
    public void Vol() => Console.WriteLine("Aleteando");
}
HerramientaQué garantizaCuándo elegirla
abstract classBase común CON estado y código compartidoJerarquías con lógica heredada real (Plantilla Método)
interfaceCapacidad/contrato sin acoplar implementaciónPolimorfismo desacoplado, testeo con mocks, DI
virtual/overridePunto de extensión opcionalFramework que permite especializar pasos
sealedCierre definitivoClases de seguridad/performance; JIT optimiza mejor

Ecosistema .NET moderno: interfaces por todas partes (ILogger, IEnumerable<T>, IDisposable). Inyecta dependencias como interfaces — tu código queda testeable sustituyendo implementación real por mocks sin tocar producción.

Polimorfismo, records y structs vs classes

Polimorfismo en acción

List<Animal> zoologico = [new Perro("Rex"), new Pato("Donald")];

foreach (Animal a in zoologico)
    a.Presentarse();       // cada uno usa SU Sonido() real:
                           // Rex dice ¡guau!
                           // Donald dice cuac

// is-pattern para especializar cuando toca:
if (a is Pato patoVolador)
    patoVolador.Vol();

Records: datos inmutables con semántica de valor (C# 9)

// Una línea genera: constructor, props init, Equals/GetHashCode por VALOR,
// ToString() legible, y with-expressions:
public record Persona(string Nombre, int Edad);

var ana  = new Persona("Ana", 30);
var ana2 = new Persona("Ana", 30);
Console.WriteLine(ana == ana2);        // TRUE: compara CONTENIDO (class daría false)
Console.WriteLine(ana);                // Persona { Nombre = Ana, Edad = 30 }

// Non-destructive mutation con with:
var cumpleanos = ana with { Edad = 31 };
Console.WriteLine(cumpleanos);         // Persona { Nombre = Ana, Edad = 31 }

// Posicional patterns encajan perfecto con records:
string etapa = ana switch
{
    { Edad: < 13 }  => "niñez",
    { Edad: < 18 }  => "adolescencia",
    { Edad: < 65 }  => "adultez",
    _               => "vejez"
};

¿record, struct o class?

TipoIdeal paraEjemplo
record classDatos inmutables pasados por referencia, comparables por valorDTOs, mensajes, eventos de dominio
structValores pequeños (<16 bytes aprox.) tipo númeroPunto, Color, Money simple
record structValores pequeños inmutables comparablesRango, Coordenada
classEntidades CON identidad e identidad mutableServicios, repositorios, entidades con ciclo de vida

Regla moderna del ecosistema: modela DATOS con records (inmutables, thread-friendly, predecibles); reserva classes para comportamiento con identidad. La inmutabilidad elimina categorías enteras de bugs concurrentes.

Ejercicios prácticos

  1. Banco encapsulado: CuentaBancaria con Saldo get/private set, métodos Depositar/Retirar validando fondos; demuestra intento de saldo negativo lanzando excepción.
  2. Zoológico polimórfico: Animal abstracta + Perro/Gato/Pato con overrides; lista polimórfica + pattern is para capacidades extra (IVolador).
  3. Records de dominio: modela Pedido con items; usa with para "modificar" cantidad sin tocar original; verifica igualdad por valor entre dos pedidos idénticos.
  4. DI manual: interfaz INotificador con EmailNotifier y SmsNotifier; servicio que las recibe por constructor; cambia implementación sin tocar servicio.
  5. Struct vs class medido: benchmark básico (Stopwatch) creando 1M de puntos como struct vs class; documenta diferencia de memoria/tiempo observada.
