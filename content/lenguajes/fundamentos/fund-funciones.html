¿Por qué dividir el problema?

Un programa complejo, escrito todo seguido como un único bloque enorme, es difícil de leer, de probar y de corregir. Cuando el código crece, cualquier cambio puede romper algo en un lugar imprevisible. La solución que usan los programadores profesionales es dividir el problema: partir una tarea grande en tareas pequeñas, resolver cada una por separado y luego combinarlas.

Este enfoque tiene varios nombres —descomposición, divide y vencerás— y es una de las ideas más importantes de la programación. Cada pieza pequeña se convierte en una función con una responsabilidad concreta.

Beneficios de dividir

  • Código reutilizable: escribimos una vez y llamamos muchas veces, sin copiar y pegar.
  • Legibilidad: el programa principal se lee como un guion de pasos claros, cada uno delegado en una función.
  • Facilidad de prueba: una función pequeña se verifica de forma aislada; un bloque gigante es casi imposible de probar pieza a pieza.
  • Mantenimiento: corregir un fallo suele significar tocar un solo lugar.

Analogía del mundo real

Piensa en una receta de cocina: no hay una sola instrucción gigante, sino pasos organizados (mezclar, hornear, decorar), cada uno con sus subpasos. O en una empresa, dividida en departamentos (ventas, contabilidad, soporte), cada uno con su función. Un programa modular funciona igual: módulos que colaboran.

La alternativa —un único bloque gigante— a veces parece más rápido al empezar, pero se convierte en una "bola de barro" a medida que crece. Dividir desde el principio es una inversión que se paga en mantenimiento.

Definición de una función

Una función es un bloque de código con nombre que realiza una tarea concreta y que podemos invocar (llamar) cuando la necesitemos. En PSeInt se define con Funcion (o SubProceso) y se cierra con FinFuncion.

Sintaxis básica en PSeInt

Funcion <nombre> ( <parámetros> )
    // cuerpo de la función
FinFuncion

Cuando la función no devuelve ningún valor se le llama Procedimiento o SubProceso en PSeInt (en otros lenguajes, funciones void). Su propósito es ejecutar acciones (mostrar algo, leer datos, modificar el estado), pero no producir un resultado nuevo.

Función que calcula el cuadrado de un número

Funcion cuadrado( num )
    Definir resultado Como Entero
    resultado <- num * num
    Retornar resultado
FinFuncion

Algoritmo principal
    Definir x, y Como Entero
    Escribir "Ingrese un número:"
    Leer x
    y <- cuadrado(x)
    Escribir "El cuadrado es: ", y
FinAlgoritmo

Partes de una función

Distingue definir (escribir la función una vez) de llamar (usarla). Definir cuadrado no la ejecuta; solo al escribir y <- cuadrado(x) dentro del algoritmo principal se ejecuta.

Parámetros y retorno

Los parámetros son las entradas de una función: los valores que le pasamos para que trabaje con ellos. El retorno es el resultado que devuelve. Dominar esta comunicación entre la función y su llamador es clave para diseñar funciones bien hechas.

Parámetros como entradas

Cuando llamas maximoDos(3, 8), los valores 3 y 8 son los argumentos; dentro de la función se reciben en los parámetros. El orden y el tipo deben coincidir con la definición: pasar el nombre donde se espera un número es un error clásico.

Función que devuelve el mayor de dos

Funcion mayor <- maximoDos( a, b )
    Si a > b Entonces
        mayor <- a
    SiNo
        mayor <- b
    FinSi
FinFuncion

Algoritmo principal
    Definir x, y, m Como Entero
    Escribir "Ingrese dos números:"
    Leer x
    Leer y
    m <- maximoDos( x, y )
    Escribir "El mayor es: ", m
FinAlgoritmo

Pasar por valor vs por referencia

Por valor: la función recibe una copia; modificarla dentro no afecta a la variable original. Por referencia: la función recibe la variable original, de modo que puede modificarla. Por defecto, en la mayoría de los lenguajes los datos simples se pasan por valor. Es un concepto que verás con más detalle al trabajar con arreglos.

Llamar a una función desde otra

No hay límite: una función puede llamar a otra. Podemos reutilizar maximoDos para hallar el máximo de tres:

Funcion m <- maximoTres( a, b, c )
    m <- maximoDos( maximoDos( a, b ), c )
FinFuncion
ConceptoSignificadoUso
ParámetroEntrada que recibe la funciónPasa datos del llamador a la función

LlamadaEjecución de la funciónInvoca con argumentos reales

Una función bien diseñada hace "una sola cosa" y se comunica solo por parámetros y retorno. Evita que lea o escriba variables globales para hacer su trabajo: eso acopla y complica.

Ámbito de las variables

El ámbito (alcance) de una variable define dónde es visible y se puede usar. En PSeInt, las variables definidas dentro de un Algoritmo general o de los subprocesos tienen reglas claras: las variables creadas dentro de una función son locales y solo existen mientras la función se ejecuta.

Variables locales vs globales

  • Locales: se declaran dentro de la función; solo se usan ahí, y su valor no "se filtra" al exterior.
  • Globales: se declaran al nivel del programa principal y son visibles desde todas las funciones. PSeInt, como verás, favorece el paso de parámetros antes que las globales.

Variable local duplicada en dos funciones

Funcion primero( )
    Definir valor Como Entero   // local de primero
    valor <- 10
    Escribir "En primero: ", valor
FinFuncion

Funcion segundo( )
    Definir valor Como Entero   // local de segundo, independiente
    valor <- 99
    Escribir "En segundo: ", valor
FinFuncion

Algoritmo main
    primero()   // muestra 10
    segundo()   // muestra 99 (no comparte la variable)
FinAlgoritmo

Aunque las dos funciones usan la misma variable valor, son variables distintas: cada una tiene su propia copia local. Modificar una no afecta a la otra.

¿Por qué evitar las globales?

Las variables globales crean dependencias ocultas: cualquiera puede modificarlas y los errores se vuelven difíciles de localizar. Imagina que una función cambia una global y otra función esperaba su valor anterior. La recomendación es usar el menor alcance posible: declara la variable lo más cerca de donde se usa y comunícate con funciones mediante parámetros y retorno.

Las globales funcionan en programas pequeños, pero conforme crece el proyecto se convierten en una fuente de bugs difíciles de rastrear. Preferir parámetros y retorno es la práctica profesional.

Modularidad

La modularidad es la práctica de construir un programa a partir de muchas funciones pequeñas, cada una con una única responsabilidad clara. El programa principal se convierte en una sucesión de llamadas de alto nivel: leer datos, calcular, mostrar resultado.

Ejemplo completo: calculadora modular

Dividimos el problema en funciones de entrada, operación y salida:

Funcion a <- leerNumero( mensaje )
    Escribir mensaje
    Leer a
FinFuncion

Funcion op <- leerOpcion( )
    Escribir "1. Sumar"
    Escribir "2. Restar"
    Escribir "3. Multiplicar"
    Escribir "Elija:"
    Leer op
FinFuncion

Funcion r <- calcular( a, b, op )
    Segun op Hacer
        1: r <- a + b
        2: r <- a - b
        3: r <- a * b
    FinSegun
FinFuncion

Funcion mostrarResultado( r )
    Escribir "El resultado es: ", r
FinFuncion

Algoritmo principal
    Definir n1, n2, opcion, res Como Entero
    n1 <- leerNumero( "Ingrese el primer número:" )
    n2 <- leerNumero( "Ingrese el segundo número:" )
    opcion <- leerOpcion( )
    res <- calcular( n1, n2, opcion )
    mostrarResultado( res )
FinAlgoritmo

El algoritmo principal es ahora casi declarativo: solo llama funciones con nombres que explican qué hace cada paso. Cada función es corta, hace una cosa y puede probarse de forma aislada.

Ventaja de probar cada función

Si el programa falla, sabemos que el problema está en una de las funciones. Podemos probar calcular(2,3,1) y verificar que da 5, sin ejecutar todo. Eso es impensable en un bloque único gigante.

Regla de oro: si una función hace más de una cosa, divídela. Si un algoritmo principal supera unas pocas llamadas, mejor extrae una función. Un buen programa se lee como un índice de funciones bien nombradas.

---

Errores comunes

1. Olvidar el FinFuncion

Cada función debe cerrarse con su FinFuncion. Si falta, el intérprete "absorbe" el código siguiente dentro de la función y provoca errores confusos.

2. Llamar a una función antes de definirla

En PSeInt las funciones deben estar definidas antes de poder llamarse desde el algoritmo principal (o al menos antes del punto de uso). Asegúrate de colocar las definiciones primero y el Algoritmo principal después.

3. No usar Retornar

4. Sobrecargar la función con demasiadas tareas

Si una función "hace de todo" (lee, calcula, muestra, valida), cuesta leerla y reutilizarla. Divídela en funciones de una sola responsabilidad.

5. Variables globales duplicadas

Depender de globales que varias funciones cambian produce valores inesperados. Prefiere parámetros y retorno.

6. Parámetros en orden equivocado

Funcion m <- areaRectangulo( base, altura )
    m <- base * altura
FinFuncion

// ❌ m <- areaRectangulo( altura, base )  → si los tipos son iguales, error silencioso
// ✅ m <- areaRectangulo( base, altura )

El error nº 1 en funciones es olvidar el Retornar: sin él, la función no entrega un resultado, y la variable que espera el resultado puede quedar sin inicializar (valor basura). Verifica siempre que toda ruta del código devuelva algo.

Ejercicios

Resuelve estos ejercicios en PSeInt o en tu lenguaje favorito. De menor a mayor dificultad:

  1. Máximo de dos: escribe una función que reciba dos números y devuelva el mayor; pruébala desde el algoritmo principal.
  2. Es par: escribe una función que reciba un número y devuelva V/F (lógico) según sea par o impar; úsala para clasificar varios valores.
  3. Factorial: escribe una función que calcule el factorial de un número. Hazlo con un bucle y comenta qué ocurriría si usaras recursión.
  4. Promedio modular: divide el cálculo del promedio de N notas en funciones: una para leer las notas, otra para sumarlas y otra para mostrar el promedio.
  5. Detectar el error: revisa el siguiente pseudocódigo e indica qué falla y cómo corregirlo: una función Funcion saludar() que no devuelve valor pero se llama como s <- saludar().
