Clases: constructor primario, init y secundarios

Kotlin condensa en una sola línea lo que Java reparte entre campos, constructor, getters y setters: el constructor primario se declara en la cabecera de la clase, y anteponer val o var a un parámetro lo convierte automáticamente en propiedad con sus accesores generados. Esta decisión elimina de raíz la ceremonia del boilerplate, pero también cambia la mentalidad: declaras qué es un objeto, no cómo ensamblarlo.

// Constructor primario: propiedades declaradas EN la firma
class Persona(
    val nombre: String,          // val → solo getter (inmutable tras crear)
    var edad: Int                // var → getter + setter
) {
    fun cumplirAnios() { edad += 1 }
}

val p = Persona("Ana", 30)       // no existe "new" en Kotlin
p.cumplirAnios()
println("${p.nombre} tiene ${p.edad} años")   // Ana tiene 31 años

// Parámetros con valores por defecto: adiós a constructores telescópicos
class Servidor(val host: String, val puerto: Int = 8080, val ssl: Boolean = false)
val local = Servidor("localhost")               // usa los defaults

Bloques init: lógica al nacer el objeto

El constructor primario no admite código ejecutable, así que Kotlin ofrece bloques init: se ejecutan en orden de aparición, justo después de asignar las propiedades del constructor. Son el lugar natural para validaciones y derivaciones.

class Cuenta(val titular: String, saldoInicial: Double) {
    // saldoInicial NO es propiedad (sin val/var): solo vive durante la construcción
    val saldo = if (saldoInicial >= 0) saldoInicial else 0.0
    val historial = mutableListOf<String>()

    init {
        require(titular.isNotBlank()) { "El titular es obligatorio" }
        println("Cuenta creada para $titular")
    }

    init {   // puede haber VARIOS; corren en orden de declaración
        historial.add("Apertura con €$saldo")
    }
}

Constructores secundarios

Cuando necesitas rutas de construcción alternativas (por ejemplo, desde un String), los declaras con constructor. La regla de oro: deben delegar directa o indirectamente en el primario usando this(...).

class Articulo(val codigo: String, val precio: Double) {
    val etiqueta: String

    init {
        etiqueta = "$codigo — €$precio"
    }

    // Secundario: parsea un texto y delega en el primario
    constructor(descripcion: String) : this(
        codigo = descripcion.substringBefore("-"),
        precio = descripcion.substringAfter("-").toDouble()
    )
}

val porCampos = Articulo("A-101", 29.99)
val porTexto  = Articulo("A-102-45.50")     // misma clase, otra puerta de entrada

Antes de escribir un constructor secundario, pregúntate si una función factoría en el companion object (Articulo.desdeTexto(...)) no sería más idiomática: mantiene un único camino de construcción visible.

Propiedades con getters/setters personalizados

Toda propiedad Kotlin ya genera accesores por ti, pero puedes intervenirlos. Un getter personalizado calcula el valor en cada lectura (propiedad computada); un setter personalizado intercepta las escrituras para validar o normalizar. Dentro de un accesor personalizado, la palabra clave field referencia el campo de respaldo (backing field): usar el nombre de la propiedad provocaría recursión infinita llamándose a sí misma.

class Temperatura(var celsius: Double) {
    // Propiedad COMPUTADA: sin backing field, se recalcula en cada acceso
    val fahrenheit: Double
        get() = celsius * 9 / 5 + 32

    // Setter con validación sobre el campo de respaldo
    var escalaMaxima: Double = 100.0
        set(value) {
            field = if (value < 0) 0.0 else value   // field ≠ this.escalaMaxima
        }

    // Getter que deriva estado: nunca almacenamos dos veces la verdad
    val esCongelacion: Boolean
        get() = celsius <= 0
}

val t = Temperatura(25.0)
println(t.fahrenheit)          // 77.0 — calculado al vuelo
t.celsius = -5.0
println(t.fahrenheit)          // 23.0 — siempre sincronizado con celsius

// Con backing field explícito: caché perezosa manual
class Informe(pesado: () -> String) {
    val contenido: String by lazy(pesado)   // alternativa moderna al patrón manual
}

Error clásico: escribir get() = escalaMaxima dentro del propio getter de escalaMaxima. Eso llama al getter otra vez… que llama al getter… StackOverflowError inmediato. Dentro del accesor, usa SIEMPRE field, nunca el nombre de la propiedad.

Los setters personalizados son el lugar idóneo para invariantes ("el stock nunca negativo"): quien use la clase no puede olvidar la validación, porque vive dentro del propio tipo y no en cada punto de uso.

Visibilidad: public, private, internal y protected

Kotlin hereda de Java los modificadores de acceso pero con dos giros importantes: todo es public por defecto (no hace falta escribirlo), y aparece un modificador nuevo pensado para arquitectura de módulos: internal. Además, desaparece el package-private de Java: si algo debe verse solo dentro de tu módulo, esa es exactamente la palabra que buscas.

ModificadorVisible desde…Uso típico
publicCualquier código que vea la clase (por defecto)APIs públicas deliberadas
privateDentro de la clase; en top-level, solo el archivoEstado interno, helpers de implementación
protectedLa clase y sus subclases (no existe en top-level)Ganchos para jerarquías de herencia
internalSolo dentro del mismo módulo compiladoAPIs compartidas en el proyecto, ocultas a consumidores externos
class Billetera {
    private var saldo: Double = 0.0            // nadie externo toca el dinero directamente

    fun depositar(monto: Double) {
        require(monto > 0) { "El depósito debe ser positivo" }
        saldo += monto
    }

    fun consultar(): Double = saldo            // lectura controlada por método propio
}

internal class MotorReportes {                 // utilería interna del módulo
    fun generar(): String = "...reporte..."
}

abstract class Animal(protected val nombre: String) {   // visible SOLO para subclases
    abstract fun hablar(): String
}

class Perro(nombre: String) : Animal(nombre) {
    override fun hablar() = "$nombre dice guau"   // puede usar 'nombre' protegido
}

Que sea public por defecto no significa que deba serlo: cada miembro público es un compromiso de mantenimiento eterno. Antes de publicar una librería, recorre tus clases convirtiendo en internal/private todo lo que no sea contrato.

Bajo el capó, internal compila como público Java con el nombre "mutilado" (MotorReportes$modulo), impidiendo su uso accidental desde otros módulos aunque el bytecode técnicamente lo permitiera.

Data classes: datos con superpoderes automáticos

Marcando una clase con data, el compilador genera por ti el paquete completo de métodos que toda "clase de datos" merece: equals() y hashCode() comparando por VALOR, un toString() legible, la función copy() para clonar con cambios, y las funciones componentN() que habilitan la destructuración. Es la respuesta de Kotlin al interminable POJO de Java.

Miembro generadoQué aporta
equals() / hashCode()Dos instancias con los mismos valores son "iguales": ideal para comparar y usar como clave en Map/Set
toString()Punto(x=1, y=2): depuración instantánea sin concatenaciones
copy()Nueva instancia con algunos atributos cambiados: actualización inmutable funcional
component1(), component2()…Destructuring: val (x, y) = punto
data class Punto(val x: Int, val y: Int)

val a = Punto(1, 2)
val b = Punto(1, 2)

// EQUALS estructural: compara CONTENIDO, no identidad de objeto
println(a == b)              // true  (usa equals generado)
println(a === b)             // false (=== compara referencias de memoria)

// COPY: clona cambiando solo lo necesario — la base del estilo inmutable
val movido = a.copy(x = 10)
println(a)                   // Punto(x=1, y=2) — original intacto
println(movido)              // Punto(x=10, y=2)

// DESTRUCTURING: extrae componentes por posición
fun distanciaAlOrigen(punto: Punto): Double {
    val (x, y) = punto                       // component1() y component2()
    return Math.sqrt((x * x + y * y).toDouble())
}

// Útil también al iterar mapas (Pair ES una data class de la librería)
val edades = mapOf("Ana" to 30, "Luis" to 25)
for ((nombre, edad) in edades) println("$nombre → $edad")

Patrón estrella en apps reales: estados inmutables + copy(). Cada cambio produce una NUEVA data class en lugar de mutar la anterior, lo que hace trivial comparar "¿algo cambió?" antes de repintar una pantalla.

Evita propiedades var en data classes usadas como claves de HashMap/HashSet: si mutas el objeto después de insertarlo, su hashCode cambia y queda "perdido" dentro de la tabla. Regla práctica: data class ⇒ propiedades val.

Sealed classes, object singleton y companion

Sealed: jerarquías cerradas y when exhaustivos

Una clase sealed define una jerarquía cerrada: todas sus subclases deben vivir en el mismo paquete y módulo. El compilador conoce el árbol completo, así que un when que cubra todas las ramas es exhaustivo sin necesidad de else — y si mañana añades un caso nuevo, cada when olvidado deja de compilar. Es EL patrón para modelar estados de UI y resultados de operaciones.

sealed interface Resultado<out T> {
    data class Exito<T>(val datos: T) : Resultado<T>
    data class Error(val mensaje: String, val codigo: Int) : Resultado<Nothing>
    object Cargando : Resultado<Nothing>
}

fun renderizar(resultado: Resultado<String>): String = when (resultado) {
    is Resultado.Exito  -> "Datos: ${resultado.datos}"      // smart cast incluido
    is Resultado.Error  -> "Fallo ${resultado.codigo}: ${resultado.mensaje}"
    Resultado.Cargando  -> "Espera un momento…"
}   // ✅ SIN else: el compilador verifica que ningún caso falte

object: el singleton integrado en el lenguaje

La declaración object crea una única instancia, inicializada de forma perezosa y thread-safe en su primer uso. Adiós a los singletons manuales con constructores privados y dobles chequeos.

object ConfiguracionGlobal {
    var tema: String = "claro"
    val cargadaEn: Long = System.currentTimeMillis()
}

ConfiguracionGlobal.tema = "oscuro"      // siempre LA misma instancia

// También existen objetos ANÓNIMOS (expresiones object), equivalentes
// a las clases internas anónimas de Java:
val saludo = object {
    val texto = "Hola"
    fun gritar() = texto.uppercase()
}
println(saludo.gritar())

companion object: miembros "estáticos" con nombre

Kotlin no tiene static. Su equivalente idiomático es el companion object: un único objeto vinculado a la clase, perfecto para constantes y funciones factoría. Desde Java se accede vía MiClase.Companion.miembro() (la anotación @JvmStatic, que verás en la lección de interoperabilidad, lo convierte en estático real).

class Usuario private constructor(val email: String) {   // constructor PRIVADO
    companion object {
        const val MAX_INTENTOS = 3                        // constante de clase

        // Funciones factoría con nombres expresivos
        fun desdeEmail(email: String): Usuario {
            require(email.contains("@")) { "Email inválido" }
            return Usuario(email)
        }
        fun invitado(): Usuario = Usuario("invitado@guiadev.dev")
    }
}

val u1 = Usuario.desdeEmail("ana@correo.com")   // sin "new", con intención legible
val u2 = Usuario.invitado()

¿Enum o sealed? Si todas las variantes son fijas y sin datos propios (días de la semana), enum. Si las variantes llevan DATOS distintos (Exito trae datos, Error trae mensaje y código), sealed class/interface gana por goleada.

Buenas prácticas

Estas decisiones de diseño separan el Kotlin maduro del código "Java traducido". Todas nacen de características vistas en esta lección.

PrácticaRazón
Inmutabilidad primero: val en propiedadesObjetos que no cambian son fáciles de compartir, testear y cachear
Data class para portadores de datos, nada másSu valor está en equals/copy; meterles lógica compleja diluye su propósito
Sealed para estados finitos con datos distintosWhen exhaustivo = el compilador te avisa cuando agregas casos
Ojo: las clases son FINAL por defectoHeredar exige open consciente; favorece composición antes que herencia
Valida en init y setters, nunca confíes en el llamanteEl objeto protege SUS invariantes; nadie recuerda validar fuera
Factorías nombradas en companion (desdeEmail, invitado)Comunican intención mejor que sobrecargar constructores
private por defecto; sube visibilidad solo si hay consumidor realSuperficie pública mínima = menos acoplamiento y refactors baratos
// ❌ Clase "Java disfrazada": mutable, expuesta, sin garantías
class CarritoCompra {
    var items = mutableListOf<String>()   // público Y mutable: cualquiera lo rompe
    var total: Double = 0.0                // puede desincronizarse de items
}

// ✅ Encapsulada e inmutable donde importa
class CarritoCompraSeguro(private val items: List<String> = emptyList()) {
    val total: Double get() = items.sumOf { it.length * 0.5 }   // derivado, jamás desincroniza

    fun agregar(item: String) = CarritoCompraSeguro(items + item)  // devuelve NUEVO carrito
}

Señal de diseño sano: puedes cambiar la implementación interna completa de tu clase (cambiar la lista por un Set, renombrar campos privados) sin romper ni una línea de código cliente. Esa libertad solo existe cuando la superficie pública es mínima.

Ejercicios prácticos

Resuélvelos en orden: cada uno apila un concepto nuevo sobre el anterior. Todos caben en un archivo del playground oficial.

  1. Ficha de producto: crea la clase Producto(codigo, precioBase) con constructor primario, un bloque init que valide precio positivo mediante require, y una propiedad computada precioConIva (IVA 21%). Instancia tres productos y prueba que un precio inválido lanza el error esperado.
  2. Setter guardián: añade a Producto una propiedad var stock cuyo setter rechace valores negativos normalizándolos a cero, y un contador interno privado de "intentos inválidos" que se incremente en el setter. Demuestra su comportamiento desde un main.
  3. Catálogo con visibilidad: modela Catalogo con lista interna private, métodos públicos agregar/buscar, y marca la clase auxiliar CriterioOrden como internal. Explica en comentario qué pasaría si otro módulo intentara usarla.
  4. Estado de pedido: implementa el sealed interface EstadoPedido con variantes Pendiente, EnTransito(repartidor, etaMinutos) y Entregado(firma); escribe la función mensaje(estado) con when exhaustivo SIN else. Añade una variante nueva y comprueba cómo el compilador señala todos los when incompletos.
  5. Registro global tipado: combina todo: un object RegistroAuditoria con historial privado y método registrar(evento: String), un data class Evento(tipo, detalle, timestamp) usado como entrada, funciones factoría Evento.login(usuario) / Evento.error(mensaje) en su companion, y destructuring al imprimir el último evento registrado. El flujo completo debe demostrar encapsulación, inmutabilidad, singleton y factory pattern juntos.
