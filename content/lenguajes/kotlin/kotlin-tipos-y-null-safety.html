Tipos básicos: todo es un objeto

Kotlin ofrece los tipos numéricos y lógicos habituales de cualquier lenguaje serio, pero con una decisión de diseño importante: no existen primitivos crudos como en Java (int, double). Todo en Kotlin es un objeto con métodos y propiedades, lo que permite escribir cosas como 5.coerceAtLeast(3) o 1_000_000.countOneBits(). ¿Y el rendimiento? El compilador genera primitivos JVM automáticamente cuando detecta que no hay nulos involucrados, así que obtienes la elegancia sin pagar peaje.

Conversiones explícitas: nada de ensanchamiento silencioso

A diferencia de Java, Kotlin no convierte números implícitamente. Un Int nunca se vuelve Long por arte de magia; debes convertirlo con funciones como toInt(), toDouble() o toString(). Esto elimina bugs clásicos donde un valor pierde precisión sin que nadie lo note.

val entero = 42
val largo: Long = entero.toLong()   // conversión explícita obligatoria
// val largoMal: Long = entero      // ERROR: type mismatch

val texto = "123"
val numero = texto.toInt()          // parsea cadenas: 123
val decimal = "3.14".toDouble()     // 3.14
val letra = 'A'
val codigoAscii = letra.code        // 65 (antes era .toInt())

// Conversión segura de String a número: devuelve null si falla
val edadUsuario = "abc".toIntOrNull()       // null, ¡no excepción!
val edadValida = "25".toIntOrNull() ?: 0    // 25

Prefiere toIntOrNull() / toDoubleOrNull() sobre toInt() cuando el dato proviene del usuario o de archivos: convierte un posible crash inesperado en un caso manejable.

Tipos especiales: Any, Unit y Nothing

Tres tipos ocupan posiciones extremas en la jerarquía de Kotlin y aparecen constantemente en firmas de funciones y documentación. Entenderlos evita confusiones al leer código ajeno.

TipoRol en la jerarquíaAnálogo en JavaCuándo aparece
AnySupertipo de todos los tipos no nulosObjectContenedores genéricos heterogéneos, APIs reflexivas
UnitTipo de toda función que no devuelve nada útilvoidRetorno por defecto; a diferencia de void, es un tipo real con único valor Unit
NothingSubtipo de todos los tipos; no tiene instanciasNo existeFunciones que siempre lanzan excepción o no terminan (error(), TODO())
fun describir(objeto: Any): String =     // Any acepta cualquier valor no nulo
    when (objeto) {
        is Int -> "Es un entero"
        is String -> "Es texto de ${objeto.length} caracteres"  // smart cast a String
        else -> "Algo más"
    }

fun registrar(mensaje: String): Unit {   // Unit es opcional de declarar
    println("[LOG] $mensaje")
}

fun obtenerConfiguracion(clave: String): String =
    error("La clave '$clave' no existe") // error() devuelve Nothing: compila sin else

// Nothing hace útiles expresiones como esta:
val puerto = System.getenv("PORT")?.toIntOrNull() ?: error("Define PORT")

Any excluye null: si necesitas aceptar cualquier cosa incluyendo nulos, usa Any?. Esta distinción solo tiene sentido gracias al sistema de nulabilidad de Kotlin.

String templates: interpolación elegante

Olvídate de concatenar con + o de String.format(): Kotlin interpola variables y expresiones directamente dentro de las cadenas con el símbolo $. Para valores simples usas $variable; para expresiones completas las encierras entre llaves ${expresion}.

val usuario = "Ana"
var puntos = 120

println("Bienvenida, $usuario")                 // simple: $variable
println("Puntos totales: ${puntos + 50}")       // expresión: ${...}
println("Estado: ${if (puntos >= 100) "VIP" else "estándar"}")

// Con propiedades anidadas
data class Pedido(val id: Int, val total: Double)
val pedido = Pedido(101, 249.99)
println("Pedido #${pedido.id} por €${pedido.total}")

// Cuidado: sin llaves NO se evalúan propiedades complejas
println("id: $pedido.id")        // imprime Pedido(id=101...) seguido de ".id" ❌
println("id: ${'$'}{pedido.id}") // cómo escapar un $ literal si lo necesitas

// Cadenas multilínea con trimIndent()
val informe = """
    |REPORTE DE VENTAS
    |Cliente: $usuario
    |Total: €${pedido.total}
""".trimMargin()
println(informe)

Formateo de números dentro de plantillas

Las plantillas no formatean solas; combínalas con funciones de la librería estándar:

val ratio = 0.84723
println("Éxito: ${"%.1f".format(ratio * 100)}%")   // Éxito: 84.7%

val precio = 1234.5678
println("€${precio.toBigDecimal().setScale(2, java.math.RoundingMode.HALF_UP)}")
// €1234.57

Error frecuente en Android: escribir "$usuario.nombre" esperando la propiedad. Sin llaves, Kotlin interpola solo $usuario e imprime .nombre como texto plano. Usa siempre ${objeto.propiedad}.

Tipos anulables y null-safety

El error más famoso de la historia de la programación —según su propio creador, Tony Hoare— fue inventar null en 1965. Java heredó esa trampa: cualquier referencia puede ser null y el NullPointerException aparece en ejecución, muchas veces en producción. Kotlin ataca el problema desde el sistema de tipos: por defecto ningún tipo acepta null, y solo puedes asignarlo a tipos marcados con ?. El compilador te obliga a tratar los posibles nulos antes de que lleguen a producción.

var nombre: String = "Ana"
// nombre = null              // ERROR de compilación: String no admite null ✅

var apodo: String? = null     // el ? declara que PUEDE ser null
apodo = "anita"

// val longitud = apodo.length      // ERROR: debes verificar antes
val longitudSegura = apodo?.length  // safe call: Int? — null si apodo es null

// El operador !! fuerza el acceso: NPE garantizada si es null
val longitudForzada = apodo!!.length   // funciona aquí… pero es apuesta arriesgada

Los tres operadores frente al null

OperadorNombreQué haceResultado
?.Safe callLlama al método/miembro solo si el receptor no es nullEl tipo se vuelve anulable (Int?)
?:ElvisDevuelve un valor alternativo si la izquierda es nullElimina la nulabilidad del resultado
!!Non-null assertionAfirma "confía en mí, no es null"Valor directo… o KotlinNullPointerException
val entrada: String? = null

// Encadenar safe calls: se detiene en el primer null
val ciudad = pedido?.cliente?.direccion?.ciudad   // String?

// Safe call combinada con Elvis: patrón estrella
val longitudCiudad = pedido?.cliente?.direccion?.ciudad?.length ?: 0

// let ejecuta el bloque SOLO si el valor no es null
entrada?.let { valorNoNulo ->
    println("Procesando '$valorNoNulo' (${valorNoNulo.length} caracteres)")
} // con entrada == null este bloque simplemente no corre

Evita !! en código de producción. Cada aparición es una promesa que puede romperse: si tu razonamiento falla, el crash ocurre en tiempo de ejecución exactamente como en Java. Si estás seguro del valor, demuéstralo con requireNotNull(valor) o maneja el caso nulo con Elvis.

Elvis a fondo: patrones útiles

El operador Elvis recibe su nombre por su parecido con el peinado del rey del rock visto de perfil (?:). Su poder real va más allá de poner un cero por defecto: el lado derecho acepta cualquier expresión, incluidos return, throw o llamadas a funciones, lo que lo convierte en la herramienta ideal para validaciones tempranas.

// 1) Valor por defecto simple
val volumen = config?.getInt("volumen") ?: 50

// 2) Retorno anticipado (early return) en funciones
fun procesarPago(idTransaccion: String?): Boolean {
    val id = idTransaccion ?: return false   // sale limpiamente si es null
    println("Cobrando transacción $id")
    return true
}

// 3) Lanzar excepción cuando el null representa un estado inválido
fun conectar(url: String?) {
    val destino = url ?: throw IllegalArgumentException("URL requerida")
    println("Conectando a $destino...")
}

// 4) Con requireNotNull/checkNotNull: mensajes descriptivos integrados
fun abrirCuenta(titular: String?) {
    val nombre = requireNotNull(titular) { "El titular es obligatorio" }
    println("Abriendo cuenta para $nombre")
}

// 5) Elvis en cadena para fuentes alternativas
val tema = preferenciasUsuario?.tema
    ?: configuracionGlobal?.tema
    ?: "claro"   // último recurso

Regla mental: cada vez que escribas ?: estás convirtiendo un quizá en un siempre — el compilador deja de preocuparse por ese valor porque tú ya cubriste todos los casos.

Smart casts y platform types

Verificar un tipo o la nulidad con is / != null basta para que el compilador recuerde el resultado y trate el valor como su tipo concreto dentro del bloque: son los smart casts. No necesitas castear manualmente después de comprobar; Kotlin lo hizo por ti.

fun longitud(valor: Any): Int {
    if (valor is String) {
        return valor.length   // smart cast: aquí valor YA es String
    }
    return 0                  // fuera del if, valor sigue siendo Any
}

// También funciona tras verificar no-nulidad con var local
fun saludar(nombre: String?) {
    if (nombre != null) {
        println("Hola, $nombre")   // smart cast a String no nulo
    }
}

// Cast seguro con "as?" en lugar de "as" (que lanza ClassCastException)
val numero = (valor as? Int) ?: -1   // -1 si valor no era Int

// when con is combina verificación + smart cast
fun area(forma: Any): Double = when (forma) {
    is Circulo -> Math.PI * forma.radio.pow(2)   // forma es Circulo aquí
    is Rectangulo -> forma.base * forma.altura   // forma es Rectangulo aquí
    else -> 0.0
}

Platform types: la zona gris al venir de Java

Cuando consumes código Java, el compilador no sabe qué métodos pueden devolver null (Java no lo declara). Esos valores reciben el tipo platform type, notado String!: Kotlin confía en ti y no exige verificación… hasta que explota. La solución es tratarlos como anulables desde el primer contacto.

// Método Java: public String buscarUsuario(String id) — puede retornar null
val usuario = apiJava.buscarUsuario("42")   // tipo plataforma String!

// val inicial = usuario.substring(0, 1)    // ⚠ compila, pero NPE si venía null
val inicial = usuario?.substring(0, 1) ?: "?"  // defensa explícita ✅

// Mejor aún: normalizar el valor apenas entra al mundo Kotlin
val usuarioSeguro: String? = apiJava.buscarUsuario("42")
val nombreFinal: String = usuarioSeguro ?: "invitado"

Si controlas el código Java que consumen tus equipos Kotlin, anota sus APIs con @Nullable / @NonNull (JSR-305 o Jetbrains Annotations): Kotlin respetará esas anotaciones y los platform types desaparecerán.

Estos tropiezos aparecen en casi todo principiante de Kotlin (y algún veterano despistado). Reconocerlos acelera tu depuración.

// Caso clásico: smart cast imposible sobre propiedad mutable
class Sesion(var usuario: String?)

fun mostrarNombre() {
    // if (this.usuario != null) {
    //     println(this.usuario.length)   // ERROR: propiedad mutable de clase
    // }
    val actual = this.usuario           // copia local: el compilador la controla
    if (actual != null) {
        println(actual.length)          // smart cast OK ✅
    }
}

El mensaje "Smart cast is impossible" casi siempre indica que el valor podría cambiar entre la comprobación y el uso: guardar una copia local val lo resuelve en el 99% de los casos.

Ejercicios prácticos

Resuélvelos en el playground oficial (play.kotlinlang.org). Todos pueden resolverse con lo visto en esta lección.

  1. Conversor seguro: dado el val bruto = listOf("10", "abc", "42", "3.7"), imprime cada elemento convertido a Int usando toIntOrNull(), mostrando "inválido" cuando no se pueda convertir.
  2. Ficha con plantillas: crea variables para producto, precio unitario y cantidad, e imprime una ficha multilínea (con cadena triple) cuyo total use una expresión interpolada redondeada a 2 decimales.
  3. Clasificador con smart cast: escribe fun clasificar(x: Any): String que devuelva distinto texto según sea Int par/impar, String vacío/no vacío o Boolean true/false, aprovechando smart casts dentro de un when.
  4. Cadena de safe calls: modela con data classes Pedido(val cliente: Cliente?, ...) → Cliente(val direccion: Direccion?, ...) → Direccion(val ciudad: String?) y obtén la ciudad con encadenado ?. + Elvis, probando los cuatro escenarios de nulidad posibles.
  5. Validador sin !!: implementa fun registrar(correo: String?, edadTexto: String?): String que valide ambos parámetros usando exclusivamente Elvis con return anticipado y toIntOrNull(), devolviendo "Registro OK: correo, edad" o el motivo del rechazo. Prohibido usar !!.
