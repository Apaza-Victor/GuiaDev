Llamadas mutuas: Kotlin habla con Java y viceversa

La interoperabilidad fue la decisión de diseño fundacional de Kotlin: compila al mismo bytecode que Java, usa las mismas colecciones (java.util) y las mismas excepciones. No existen adaptadores ni capas puente: una lista creada en Kotlin ES una java.util.List, y una clase Java se instancia en Kotlin como si fuera nativa. Esta simbiosis bidireccional explica por qué adoptar Kotlin nunca exige "gran rewrit": convives archivo a archivo.

// KOTLIN consumiendo clases 100% JAVA, sin fricción alguna
import java.time.LocalDate
import java.util.ArrayList

fun main() {
    val hoy: LocalDate = LocalDate.now()            // API de fechas de Java
    val nombres = ArrayList<String>()               // colección clásica de Java
    nombres.add("Kotlin")
    nombres.add("habla")
    nombres.add("con Java")

    val texto = StringBuilder().apply {             // StringBuilder también es Java
        append("Hoy es ").append(hoy.dayOfWeek)
    }
    println("${texto} — ${nombres.joinToString(" ")}")
}

En dirección contraria, el código Java consume clases Kotlin casi sin enterarse. Los detalles finos (dónde aparece Companion, qué pasa con los valores por defecto) se controlan con anotaciones que verás en esta lección:

// utilidades.kt contiene: fun saludar(nombre: String) = "Hola, $nombre"
//                          class Contador { companion object { const val LIMITE = 100 } }

import UtilidadesKt;              // las funciones TOP-LEVEL viven en la clase "NombreArchivoKt"

public class App {
    public static void main(String[] args) {
        System.out.println(UtilidadesKt.saludar("Ana"));   // Hola, Ana

        int limite = Contador.LIMITE;                      // const val → constante real de Java
        System.out.println("Límite: " + limite);
    }
}

En un proyecto Gradle/Maven los archivos .kt y .java compilan juntos en el mismo módulo: puedes referenciarlos entre sí libremente incluso dentro del mismo paquete. IntelliJ además incluye el convertidor automático J2K (Ctrl+Alt+Shift+J) para migrar archivos completos.

Propiedades mapeadas y platform types

Getters/setters de Java son propiedades para Kotlin

Cuando Kotlin encuentra un par getX()/setX() en código Java, los presenta sintácticamente como una sola propiedad. Es puro azúcar de compilador: por debajo sigue llamando a los métodos. En sentido inverso, tus propiedades Kotlin generan getters/setters estándar que Java consume con total naturalidad.

// Clase Java: class Persona { private String nombre; getNombre(); setNombre(); boolean isActivo(); }
val persona = Persona()

persona.nombre = "Ana"           // invoca setNombre("Ana")
println(persona.nombre)          // invoca getNombre()
if (persona.activo) { }          // isActivo() se lee como propiedad booleana

// Propiedad Kotlin vista desde Java:
class Producto(val sku: String, var stock: Int)
//   → Java ve: getSku() (solo getter), getStock()/setStock(int)

Platform types: String!, la zona gris

Java no distingue tipos anulables en su sistema de tipos. Cuando Kotlin consume un método Java cuyo retorno podría ser null, recibe un platform type (notado String!): el compilador confía y no te obliga a verificar… pero si el valor era nulo, obtienes el mismo NPE de siempre. La defensa es tratar todo lo que viene de Java como sospechoso hasta anotarlo o normalizarlo.

// Método Java: public String buscarUsuario(String id)  ← puede devolver null
val usuario = apiLegada.buscarUsuario("42")      // tipo plataforma: String!

// val inicial = usuario.substring(0, 1)         // ⚠ compila… NPE si venía null
val inicial = usuario?.substring(0, 1) ?: "?"    // ✅ defensa explícita

// Mejor aún: normalizar EN LA FRONTERA, apenas entra al mundo Kotlin
val seguro: String? = apiLegada.buscarUsuario("42")
val nombreFinal: String = seguro ?: "invitado"

Si el equipo dueño del código Java puede colaborar, la solución definitiva es anotar sus APIs con @Nullable/@NonNull (JSR-305, JetBrains Annotations o las de Android). Kotlin respeta esas anotaciones y los platform types desaparecen del mapa.

Anotaciones JVM: afinando el puente

Las características puramente Kotlin (defaults, companion, propiedades privadas) necesitan traducción al hablar con Java. Las anotaciones @Jvm* son esa capa de control fino: le dicen al compilador qué firmas generar en el bytecode para que el lado Java quede tan cómodo como el lado Kotlin.

AnotaciónQué resuelveResultado visible en Java
@JvmStaticMiembros de companion object/object como estáticos realesUtil.formato(x) en vez de Util.Companion.formato(x)
@JvmOverloadsGenera sobrecargas para cada combinación de defaultsPuede omitir argumentos: new Usuario("Ana")
@JvmFieldExpone la propiedad como campo público directoconfig.timeout sin getter/setter
@JvmNameRenamea funciones/clases compiladas (o evita colisiones)Utilidades.saludar(...) en vez de UtilidadesKt.…
@ThrowsDeclara excepciones chequeadas en la firmaJava puede hacer catch (IOException e) sin advertencias
const valConstantes de tiempo de compilaciónConfig.MAX_REINTENTOS inline en el bytecode
class Formateador {
    companion object {
        const val SEPARADOR: String = ";"              // constante Java real

        @JvmStatic                                     // ← sin esto: Formateador.Companion.aplicar(...)
        fun aplicar(texto: String): String =
            texto.trim().replace(" ", "_").uppercase()
    }
}

data class Usuario @JvmOverloads constructor(          // genera 3 constructores Java
    val nombre: String,
    val rol: String = "editor",
    val activo: Boolean = true
)

class Config {
    @JvmField                                          // acceso directo sin getters
    var timeoutSegundos: Int = 30
}

@JvmName("validarCorreo")                              // renombra la función compilada
fun validar(email: String): Boolean = "@" in email

// A nivel de ARCHIVO: todas las top-level van a una clase con nombre amable
// @file:JvmName("Validaciones")   ← primera línea del archivo
// Cómo queda todo desde Java tras las anotaciones:
String limpio = Formateador.aplicar("  ana lopez ");  // ANA_LOPEZ — sin Companion ✨
Usuario u = new Usuario("Luis");                       // gracias a @JvmOverloads
int t = new Config().timeoutSegundos;                  // gracias a @JvmField
boolean ok = Validaciones.validarCorreo("a@b.com");    // gracias a @JvmName

Duda frecuente: ¿cuándo @JvmStatic? Regla práctica: si el consumidor Java esperaría un método static tradicional (factorías, utilidades matemáticas), anótalo. Si es lógica interna de estado compartido, déjalo en Companion.

SAM conversion, colecciones compartidas y @Throws

SAM conversion: lambdas donde Java espera interfaces

Toda la API antigua de Java (listeners, comparators, runnables) se basa en interfaces funcionales: interfaces con UN único método abstracto (Single Abstract Method). Kotlin convierte automáticamente una lambda en ese tipo, eliminando las clases anónimas verbosas de Java.

import javax.swing.JButton
import java.awt.event.ActionListener

val boton = JButton("Guardar")

// ❌ Estilo Java: clase anónima de 4 líneas
// boton.addActionListener(object : ActionListener {
//     override fun actionPerformed(e: ActionEvent) { guardar() }
// })

// ✅ Kotlin: SAM conversion — la lambda SE CONVIERTE en ActionListener
boton.addActionListener { guardar() }

// También funciona con interfaces funcionales DEFINIDAS en Kotlin,
// marcándolas explícitamente con "fun interface"
fun interface Filtro { fun cumple(valor: Int): Boolean }

val filtroPositivos = Filtro { it > 0 }        // lambda → implementación
println(filtroPositivos.cumple(7))             // true

Colecciones: mismas clases, distinta promesa

Kotlin no tiene colecciones propias: List<T> en Kotlin ES java.util.List. La diferencia vive en el compilador Kotlin (que bloquea add() sobre tipos solo lectura), pero el runtime de Java no sabe nada de esa promesa: si tu API Kotlin devuelve una List inmutable y Java llama .add(), recibirá UnsupportedOperationException en ejecución.

fun obtenerNombres(): List<String> = listOf("Ana", "Luis")   // promesa: solo lectura

// Desde Java alguien podría intentar: obtenerNombres().add("intruso");
// → UnsupportedOperationException. Devuelve defensivamente cuando importe:
fun obtenerNombresDefensivo(): List<String> = listOf("Ana", "Luis").toList()

Excepciones chequeadas: el puente @Throws

Kotlin elimina las checked exceptions: ninguna función declara throws. Pero Java SÍ las exige: sin ayuda, un método Kotlin que lanza IOException aparecería ante Java como si nunca pudiera fallar, impidiendo capturarla específicamente. La anotación @Throws restaura esa información en la firma compilada.

import java.io.File
import java.io.IOException

class Repositorio {
    @Throws(IOException::class)                        // ← Java verá "throws IOException"
    fun cargar(ruta: String): List<String> = File(ruta).readLines()
}
// El consumidor Java ahora PUEDE y DEBE manejar la excepción chequeada:
try {
    List<String> lineas = new Repositorio().cargar("datos.csv");
} catch (IOException e) {
    log.error("Fallo leyendo el archivo", e);
}

Sin @Throws, javac rechazará el catch (IOException e) con "exception is never thrown", obligando a capturar Exception genérico: pierdes precisión y claridad justo en la frontera donde más se necesita.

Data classes vistas desde Java

Una data class Kotlin genera automáticamente todo el ceremonial que en Java se escribe a mano (o se autogeneraba en el IDE): constructores sobrecargados, getters/setters, equals/hashCode, toString y las funciones de desestructuración. Esta tabla resume qué recibe exactamente el lado Java:

Miembro en KotlinLo que ve JavaObservaciones
data class Punto(val x: Int, val y: Int)Constructor Punto(int x, int y)Con @JvmOverloads: versiones con menos argumentos
val xgetX()Solo lectura: no hay setter
var ygetY() + setY(int)Par completo getter/setter
equals()/hashCode()/toString()Iguales a los de JavaComparación estructural automática
copy(x = 10)copy(int x, int y)⚠ Sin defaults en Java: hay que pasar TODOS los parámetros
Destructuring val (a, b)component1(), component2()Útiles para Kotlin; en Java casi nunca se usan
Propiedades en el cuerpo de claseGetters/setters normalesNo participan del constructor ni de copy
data class Articulo(
    val codigo: String,
    var precio: Double,
    val etiquetas: List<String> = emptyList()
)

fun demo() {
    val original = Articulo("A-101", 29.99, listOf("oferta"))
    val actualizado = original.copy(precio = 24.99)      // inmutabilidad funcional
    println(original)                                    // Articulo(codigo=A-101, ...)
    println(actualizado == Articulo("A-101", 24.99))     // true: equals estructural
}
// El MISMO data class consumido desde Java:
Articulo a = new Articulo("A-101", 29.99, List.of("oferta"));

System.out.println(a.getCodigo());                     // getter del val
a.setPrecio(27.50);                                    // setter del var

// copy() sin defaults: obligatorio pasar TODO, en orden
Articulo barato = a.copy(a.getCodigo(), 19.99, a.getEtiquetas());

// equals/hashCode/toString funcionan igual que en cualquier POJO Java
System.out.println(a.equals(new Articulo("A-101", 27.50, List.of("oferta"))));

Por eso muchas guías recomiendan que los data classes compartidos entre ambos lenguajes usen @JvmOverloads y propiedades var solo cuando el dominio lo justifique: minimiza la fricción de quien trabaja en el otro idioma.

Errores comunes y buenas prácticas

Los problemas de interop casi nunca son técnicos sino de expectativas cruzadas: cada lenguaje asume cosas que el otro desconoce. Esta tabla condensa los choques más frecuentes y su remedio.

@file:JvmName("PagosApi")

package com.guiadev.pagos

import java.io.IOException

data class Cobro @JvmOverloads constructor(
    val id: String,
    val monto: Double,
    val moneda: String = "EUR"
)

object Procesador {
    const val VERSION = "2.1"

    @JvmStatic
    @Throws(IOException::class)
    fun procesar(cobro: Cobro): Boolean {
        require(cobro.monto > 0) { "Monto inválido" }
        return true   // aquí iría la llamada real al gateway
    }
}

Prueba del nueve para APIs mixtas: escríbela en Kotlin y luego intenta usarla desde un pequeño Main.java. Si las llamadas quedan naturales sin anotaciones extrañas, tu diseño de interop ya está maduro.

Ejercicios prácticos

Los ejercicios 1–3 pueden resolverse íntegramente en el playground de Kotlin (que permite mezclar Java y Kotlin en el mismo proyecto). El 4 y el 5 se plantean como diseño reflexivo.

  1. Consumidor prudente: declara una función Java simulada (comenta su firma: public String getConfig(String key) que devuelve null si no existe) y consúmela desde Kotlin tratándola como platform type: primero demuestra la versión ingenua que rompería, luego la segura con ?. + Elvis y normalización en variable local anotada String?.
  2. Puente de propiedades: crea en Kotlin una clase Inventario(var capacidad: Int, private var ocupado: Int) y documenta (en comentarios con formato Java) exactamente qué getters/setters generará para Java. Luego añade un @JvmField donde tenga sentido y justifica la elección.
  3. Traductor de listeners: define una interfaz funcional propia fun interface Validador { fun validar(texto: String): Boolean }, implementa tres validadores distintos mediante lambdas (email no vacío, longitud ≥ 8, solo dígitos) y úsalos filtrando una lista de textos fijos.
  4. Contrato bidireccional: diseña un data class Pedido(id, total, urgente=false, notas="" ) destinado a ser usado por equipos Java. Escribe en comentario la clase Main.java COMPLETA que lo consuma usando constructor reducido (@JvmOverloads), setters de las propiedades var, copy() completo y una llamada estática a un companion con @JvmStatic. Verifica mentalmente cada anotación necesaria.
  5. Auditoría de frontera: toma este escenario: una librería Kotlin expone fun leerClientes(ruta: String): List<Cliente> que lanza IOException, devuelve lista solo lectura y usa defaults en Cliente(nombre, pais="ES"). Enumera TODAS las fricciones que encontrará un cliente Java y corrige el código aplicando @Throws, @JvmOverloads, @file:JvmName y estrategia de copia defensiva, explicando en un comentario por qué cada cambio importa.
