El problema: hilos pesados e infierno de callbacks

Casi toda aplicación moderna necesita hacer varias cosas "a la vez": una app móvil pinta la interfaz mientras descarga datos, un servidor atiende miles de peticiones simultáneas. Durante décadas hubo dos respuestas, ambas dolorosas. Los hilos (Thread) son caros: cada uno reserva ~1 MB de pila, el sistema operativo tarda en crearlos y cambiar entre ellos, y bloquear el hilo de la UI mientras llega una respuesta congela la aplicación. Las callbacks evitan el bloqueo, pero anidan funciones dentro de funciones hasta formar la temida pirámide de la perdición, donde los errores se manejan dispersos y el flujo se vuelve ilegible.

// ❌ Callback hell clásico: cada paso anida el siguiente
// api.obtenerUsuario(id) { usuario ->
//     api.obtenerPedidos(usuario) { pedidos ->
//         api.obtenerDetalle(pedidos[0]) { detalle ->
//             api.calcularEnvio(detalle) { costo ->
//                 ui.mostrar(costo)          // ¿y si falla el paso 3? 😱
//             }
//         }
//     }
// }

Las corrutinas atacan ambos problemas: son computaciones que pueden suspenderse sin bloquear el hilo que las ejecuta, cuestan unos pocos bytes (puedes lanzar decenas de miles donde antes cabían cientos de hilos) y permiten escribir código asíncrono con la apariencia lineal y legible del código síncrono.

AspectoHilosCorrutinas
Coste por unidad~1 MB de pila + gestión del SOUnos pocos bytes en heap
Escala prácticaCientos por procesoDecenas de miles por proceso
Bloqueosleep()/read() detienen el hilo enterodelay()/suspend liberan el hilo al instante
ComposiciónCallbacks o futures verbososCódigo secuencial normal con suspend

Las corrutinas NO son multihilo mágico: por defecto una corrutina corre sobre el hilo que la lanzó. Lo que aportan es concurrencia ligera; el paralelismo real se controla después con los dispatchers.

---

Funciones suspend y el modelo mental correcto

La palabra clave suspend marca funciones que pueden pausarse sin bloquear el hilo: entregan el hilo a otros trabajos y retoman su ejecución más tarde, exactamente donde la dejaron. La función delay() es el equivalente amable de Thread.sleep(): espera ese tiempo pero libera el hilo para que otros lo aprovechen. Regla de oro del lenguaje: solo se puede llamar a una función suspend desde otra función suspend o desde dentro de una corrutina.

import kotlinx.coroutines.*

suspend fun descargarPerfil(): String {
    delay(1000)                        // pausa SIN bloquear el hilo
    return "perfil@kotlin.dev"
}

suspend fun descargarAmigos(): List<String> {
    delay(1500)
    return listOf("Ana", "Luis")
}

fun main() = runBlocking {
    // Llamadas secuenciales: total = 1000 + 1500 ms
    val perfil = descargarPerfil()
    val amigos = descargarAmigos()
    println("$perfil con ${amigos.size} amigos")

    // Concurrencia ligera: dos latidos conviven en el mismo hilo
    launch {
        repeat(3) {
            delay(400)
            println("latido ${it + 1}")
        }
    }
    println("main sigue vivo")         // se imprime ANTES de los latidos
}

runBlocking: el puente, solo para demos

runBlocking crea una corrutina y bloquea el hilo actual hasta terminar. Es el puente perfecto entre el mundo síncrono (la función main de tus experimentos, tests unitarios) y las corrutinas… y también la peor elección en producción: bloquear el hilo principal de una app o servidor anula todo el beneficio. En aplicaciones reales existen scopes integrados (lifecycleScope en Android, el scope del framework en servidores).

// ✅ Aceptable en ejemplos/tests: main ya es "tierra firme" que puede esperar
fun main() = runBlocking {
    val datos = descargarPerfil()
    println(datos)
}

// ❌ En una app real jamás: bloquearía el hilo de la interfaz
// fun onClickGuardar() {
//     runBlocking { api.guardar(...) }   // UI congelada 💀
// }

Diferencia clave para entrevistas: Thread.sleep(1000) retiene el hilo secuestrado 1 segundo; delay(1000) devuelve el hilo al pool y programa la reanudación. Con miles de tareas concurrentes, esa diferencia es abismal.

Builders: launch vs async/await

Los builders son las funciones que crean corrutinas. Elegir bien entre ellos depende de una sola pregunta: ¿necesito el resultado?. Si solo quieres efectos secundarios (escribir logs, actualizar pantalla), launch; si esperas un valor futuro, async + await.

BuilderDevuelveIdeal para…Excepciones
launchJob (sin resultado)"Fire and forget": efectos, animaciones, logsFalla inmediatamente hacia el padre
asyncDeferred<T>Cálculos/descargas cuyo valor necesitarásSe lanza en await()
runBlockingT del bloquePuente síncrono: main y tests únicamenteSe propagan como normales
fun main() = runBlocking {
    // LAUNCH: enciende y sigue; el resultado (si hay) se ignora
    val job: Job = launch {
        delay(500)
        println("Tarea lateral terminada")
    }

    // ASYNC: arranca YA, en paralelo, y entrega promesas Deferred
    val perfil: Deferred<String> = async { descargarPerfil() }      // 1 s
    val amigos: Deferred<List<String>> = async { descargarAmigos() } // 1.5 s

    println("Descargando...")        // corre MIENTRAS ambas avanzan

    // AWAIT: espera el resultado (ya casi listo porque corrieron en paralelo)
    println("${perfil.await()} + ${amigos.await().size} amigos")
    // Total ≈ 1.5 s (el máximo), NO 2.5 s (la suma)

    job.join()                       // espera a que la tarea lateral acabe
}

// AWAITALL: muchas promesas a la vez
suspend fun cargarTodo(): List<Int> =
    listOf(async { servicioA() }, async { servicioB() }, async { servicioC() })
        .awaitAll()                  // lista con los tres resultados

Lanza varios async ANTES de llamar a sus await: así trabajan en paralelo. Si escribes a().await() y luego b().await(), cada async nace después del await anterior y recuperas la ejecución secuencial sin darte cuenta.

Jobs, scopes y concurrencia estructurada

Cada corrutina devuelve un Job: su identificador manipulable, capaz de join() (esperar), cancel() (abortar) o consultar estado (isActive). Sobre esa pieza se levanta la idea más elegante de la librería: la concurrencia estructurada. Toda corrutina vive dentro de un scope; si el scope termina, esperan a sus hijas; si se cancela, se cancela todo el árbol; si una hija falla, el padre se entera. Resultado: no existen corrutinas huérfanas que sobrevivan a quien las creó.

fun main() = runBlocking {
    // El scope PADRE no finaliza hasta que TODAS sus hijas terminen
    launch {
        delay(800)
        println("Hija lenta terminó")
    }
    val rapida = launch {
        delay(200)
        println("Hija rápida terminó")
    }
    rapida.join()                    // espera explícita a UNA hija concreta
    println("main termina")          // ...pero aún aguarda a la lenta
}

// COROUTINESCOPE: crea sub-scopes dentro de funciones suspend,
// heredando contexto y garantizando la misma estructura padre→hijas
suspend fun cargarPantalla(): String = coroutineScope {
    val encabezado = async { descargarPerfil() }
    val contenido  = async { descargarAmigos() }
    "${encabezado.await()} (${contenido.await().size} amigos)"
}   // si algo falla aquí, AMBAS hijas mueren con él: sin fugas

Cancelación cooperativa

Una corrutina no puede ser asesinada a la fuerza: se le solicita la cancelación y ella decide cuándo obedecer, comprobando puntos de suspensión como delay() o verificando isActive. Por eso un bucle intensivo de CPU debe cooperar expresamente.

val trabajo = launch {
    repeat(1000) { i ->
        ensureActive()               // lanza CancellationException si pidieron cancelar
        Thread.sleep(10)             // simulamos cálculo pesado SIN puntos de suspensión
        if (i % 100 == 0) println("progreso $i")
    }
}
delay(250)
trabajo.cancel("Ya no hace falta")
println("¿Activo? ${!trabajo.isCancelled}")

Huye de GlobalScope.launch en aplicaciones reales: sus corrutinas viven tanto como el proceso, ignoran ciclos de vida (pantallas cerradas, requests terminados) y producen fugas silenciosas. Todo trabajo debe nacer dentro de un scope con dueño.

Dispatchers y un ejemplo completo: UI + red

Los dispatchers deciden QUÉ hilos ejecutan cada corrutina. La función withContext(dispatcher) cambia de contexto para un bloque concreto y vuelve después: es la herramienta estándar para mover trabajo pesado fuera del hilo de interfaz.

DispatcherQué usaDiseñado para
Dispatchers.DefaultPool compartido (≈ núcleos de CPU)Cálculo intensivo: parsing, ordenamientos, criptografía
Dispatchers.IOPool elástico amplio (64+)Operaciones bloqueantes: archivos, red legacy, BD
Dispatchers.MainEl hilo de la UITocar vistas/pantalla (Android, Swing, JavaFX)
Dispatchers.UnconfinedEl que toque en cada momentoCasos raros; evitar salvo frameworks internos
import kotlinx.coroutines.*
import kotlin.system.measureTimeMillis

// Simulación de capas de una app: "red" en IO, "UI" en Main
suspend fun llamarApi(endpoint: String): String = withContext(Dispatchers.IO) {
    delay(600)                                  // latencia de red simulada
    """{ "endpoint": "$endpoint", "ok": true }"""
}

suspend fun refrescarPantalla() = withContext(Dispatchers.Main) {
    println("[UI] giro de spinner...")           // tocaría vistas reales aquí
}

fun main() = runBlocking(Dispatchers.Main) {    // actuamos como si fuéramos el hilo UI
    val milis = measureTimeMillis {
        refrescarPantalla()

        val perfil = async { llamarApi("/perfil") }      // paralelas entre sí
        val posts  = async { llamarApi("/posts") }

        val datos = "${perfil.await()} | ${posts.await()}"

        withContext(Dispatchers.Main) { println("[UI] pintando: $datos") }
    }
    println("Pantalla cargada en ~$milis ms")    // ≈ 600 ms, no 1200
}

Mira el flujo completo: sin un solo callback anidado, el código se lee de arriba abajo como un guion secuencial —y debajo corre concurrencia real con cambio de hilos incluido—. Esa legibilidad es LA razón por la que Kotlin ganó Android.

En Android existe además la variante withContext(Dispatchers.IO) { ... } como patrón de repositorio: las funciones suspend declaran DÓNDE trabajan internamente, y el ViewModel ni se entera.

Manejo básico de excepciones

Las buenas noticias: un try/catch normal funciona igual alrededor de llamadas suspend. Las matizaciones llegan según el builder: en launch la excepción golpea al padre apenas ocurre (por eso conviene capturarla dentro del propio bloque); en async queda guardada en el Deferred y se lanza cuando llamas a await(), momento ideal para capturarla.

suspend fun servicioInestable(): String {
    delay(300)
    throw IllegalStateException("El servicio caído de nuevo")
}

fun main() = runBlocking {
    // LAUNCH: captura DENTRO del bloque, donde ocurre
    launch {
        try {
            servicioInestable()
        } catch (e: Exception) {
            println("[launch] capturado: ${e.message}")
        }
    }

    // ASYNC: la excepción viaja hasta el await(); allí se captura
    val promesa = async { servicioInestable() }
    try {
        promesa.await()
    } catch (e: IllegalStateException) {
        println("[async] capturado en await: ${e.message}")
    }

    // RED DE ÚLTIMO INSTANTE para launch sin capturar:
    val handler = CoroutineExceptionHandler { _, ex ->
        println("[handler] no atrapada: ${ex.message}")
    }
    launch(handler) { throw RuntimeException("imprevisto") }
}

Nunca absorbas una CancellationException con un catch (e: Exception) genérico: estás rompiendo el mecanismo de cancelación y tu corrutina se volverá inmortal. Si capturas Exception genérico, reenvía primero las de cancelación: if (e is CancellationException) throw e.

Cuando un hijo falla sin captura, cancela a su padre y a todos los hermanos (modelo de fallo rápido). Para jerarquías donde un fallo no debe tumbar al resto existen los SupervisorJob y supervisorScope — tema de siguiente nivel que conviene saber que existe.

Errores comunes

La curva de las corrutinas no está en la sintaxis sino en estos malentendidos recurrentes. Repásalos antes de escribir tu primer código real con concurrencia.

ErrorSíntomaSolución
runBlocking dentro de la appUI/servidor congeladoUsar scopes reales: lifecycleScope, scope del framework
Thread.sleep() en corrutinaHilo bloqueado, pool agotadodelay(), que libera el hilo
async { }.await() seguidosRendimiento secuencial disfrazadoLanzar TODOS los async primero, await después
Cancelar corrutina CPU-boundSigue corriendo eternamenteensureActive()/isActive dentro de los bucles
Tragar CancellationExceptionCancelaciones ignoradas, fugasRelanzarla siempre tras registrarla
Estado compartido mutable sin protecciónResultados distintos en cada ejecuciónConfina estado en un actor/single-thread dispatcher o usa Mutex
GlobalScope.launch por comodidadTrabajo huérfano imposible de testearInyectar/crear scopes estructurados con ciclo de vida
// ❌ catch genérico que sabotea la cancelación
try {
    trabajarLargo()
} catch (e: Exception) {
    println("error: ${e.message}")       // ¡también atrapó la cancelación!
}

// ✅ Deja pasar siempre la señal de cancelación
try {
    trabajarLargo()
} catch (e: CancellationException) {
    throw e                              // la cancelación NO se negocia
} catch (e: Exception) {
    println("error real: ${e.message}")
}

Depura tiempos con kotlinx.coroutines.debug (propiedad de JVM -Dkotlinx.coroutines.debug): los logs mostrarán qué corrutina imprimió cada línea, revelando carreras invisibles a simple vista.

Ejercicios prácticos

Resuélvelos en el playground oficial (ya incluye kotlinx.coroutines). Cada ejercicio construye sobre el anterior hasta llegar a un patrón de producción real.

  1. Latidos concurrentes: lanza dos corrutinas con launch: una imprime "tick" cada 300 ms (3 veces) y otra "tock" cada 450 ms (2 veces). Observa el orden de salida en varias ejecuciones y explica en comentario por qué varía.
  2. Paralelismo medible: con measureTimeMillis, compara descargar dos perfiles simulados (dos funciones suspend con delay(1000)) de forma secuencial versus dos async + await. Imprime ambos tiempos y verifica la diferencia (~2 s vs ~1 s).
  3. Trabajador cancelable: lanza una corrutina que imprima números del 1 en adelante cada 100 ms usando ensureActive(); desde fuera, cancélala tras medio segundo con cancel() y confirma con join() que terminó limpiamente, imprimiendo su estado final.
  4. Mini cliente resiliente: implementa suspend fun descargarConDispatcher(url: String): String que use withContext(Dispatchers.IO), simule la red con delay(500) y devuelva "datos de $url". Combínalo con un segundo endpoint mediante async/await y muestra el tiempo total con measureTimeMillis.
  5. Patrón retry profesional: escribe suspend fun <T> conReintentos(veces: Int = 3, bloque: suspend () -> T): T que ejecute el bloque y, si lanza excepción, espere delay(200 * intento) antes de reintentar; las CancellationException deben propagarse sin reintentar. Pruébalo con un servicio que falla las dos primeras veces (usa un contador) y añade un CoroutineExceptionHandler al scope para cubrir cualquier fallo final.
