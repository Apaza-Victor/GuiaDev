Tests nativos con el paquete testing

Go incluye un framework de testing en la stdlib: sin dependencias, sin configuración, integrado en las herramientas. Las reglas son mínimas: archivos terminados en _test.go, funciones TestXxx que reciben *testing.T, y fallas con t.Errorf/t.Fatal:

Primer test

// matematicas.go
package utilidades

func Sumar(a, b int) int { return a + b }

func Dividir(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("división por cero")
    }
    return a / b, nil
}
// matematicas_test.go  ← MISMO paquete, archivo _test.go
package utilidades

import "testing"

func TestSumar(t *testing.T) {
    resultado := Sumar(2, 3)
    esperado := 5
    if resultado != esperado {
        t.Errorf("Sumar(2,3) = %d; esperado %d", resultado, esperado)
    }
}

func TestDividirPorCero(t *testing.T) {
    _, err := Dividir(10, 0)
    if err == nil {
        t.Fatal("se esperaba error al dividir por cero")
    }
}
$ go test
PASS
ok      miapp/utilidades   0.012s

$ go test -v          # verboso: cada test listado
$ go test ./...       # TODO el proyecto recursivamente

Diferencia entre helpers: t.Error marca fallo y CONTINUA el test; t.Fatal lo aborta ahí mismo (imprescindible cuando lo siguiente depende del paso previo, como usar una variable nil).

Table-driven tests: EL idiom de testing en Go

En lugar de copiar-pegar un test por caso, defines una tabla de entradas/esperados y la recorres con subtests nombrados vía t.Run:

func TestDividir(t *testing.T) {
    casos := []struct {
        nombre     string
        dividendo  float64
        divisor    float64
        esperado   float64
        quiereErr  bool
    }{
        {"division exacta", 10, 2, 5, false},
        {"con decimales", 7, 4, 1.75, false},
        {"por cero", 5, 0, 0, true},
        {"negativos", -9, 3, -3, false},
    }

    for _, tc := range casos {
        t.Run(tc.nombre, func(t *testing.T) {
            res, err := Dividir(tc.dividendo, tc.divisor)
            if tc.quiereErr {
                if err == nil {
                    t.Fatalf("esperaba error, obtuve resultado %v", res)
                }
                return
            }
            if err != nil {
                t.Fatalf("error inesperado: %v", err)
            }
            if res != tc.esperado {
                t.Errorf("%v/%v = %v; esperado %v",
                    tc.dividendo, tc.divisor, res, tc.esperado)
            }
        })
    }
}
$ go test -v -run TestDividir/por_cero
=== RUN   TestDividir
=== RUN   TestDividir/por_cero
--- PASS: TestDividir/por_cero (0.00s)

Añadir un caso nuevo = añadir UNA línea a la tabla. El fallo reporta el NOMBRE del caso (-run TestDividir/por_cero lo ejecuta solo). Esta estructura escala de 4 a 400 casos sin duplicar lógica.

Benchmarks y cobertura

Benchmarks: medir, no adivinar

Las funciones BenchmarkXxx(b *testing.B) se ejecutan repetidamente hasta obtener mediciones estables. El framework decide cuántas iteraciones (b.N):

func BenchmarkConcatenar(b *testing.B) {
    for i := 0; i < b.N; i++ {
        s := ""
        for j := 0; j < 100; j++ {
            s += "x" // O(n²): concatena copiando todo cada vez
        }
        _ = s
    }
}

func BenchmarkBuilder(b *testing.B) {
    for i := 0; i < b.N; i++ {
        var sb strings.Builder // amortizado O(n)
        for j := 0; j < 100; j++ {
            sb.WriteString("x")
        }
        _ = sb.String()
    }
}
$ go test -bench=.
BenchmarkConcatenar-8    21834    54812 ns/op
BenchmarkBuilder-8      891244      1342 ns/op   ← 40x más rápido

Cobertura de código

$ go test -cover
coverage: 87.3% of statements

$ go test -coverprofile=c.out && go tool cover -html=c.out
# abre el navegador coloreando líneas cubiertas/olvidadas

La cobertura mide EJECUCIÓN, no aserciones: una línea puede recorrerse mil veces sin verificar nada. Apunta a coberturas altas en lógica de negocio crítica, pero desconfía del número como meta en sí mismo.

Mocks con interfaces: la recompensa del diseño

Como las interfaces se satisfacen implícitamente, simular dependencias es trivial: define la interfaz donde la CONSUMES y crea un fake para tests:

// Producción consume esta interfaz pequeña:
type RepositorioUsuarios interface {
    Obtener(id int) (*Usuario, error)
}

// Fake para tests: 5 líneas, sin frameworks de mocking
type RepoFalso struct {
    usuarios map[int]*Usuario
}

func (r *RepoFalso) Obtener(id int) (*Usuario, error) {
    u, ok := r.usuarios[id]
    if !ok {
        return nil, fmt.Errorf("usuario %d: %w", id, os.ErrNotExist)
    }
    return u, nil
}

func TestServicioConRepoFalso(t *testing.T) {
    svc := &ServicioEmails{Repo: &RepoFalso{
        usuarios: map[int]*Usuario{1: {Nombre: "Ana"}},
    }}
    err := svc.EnviarBienvenida(1)
    if err != nil {
        t.Fatalf("envío falló: %v", err)
    }
}

No necesitas gomock ni testify para el 90% de los casos: un struct con mapas basta. Los frameworks de mocking brillan solo en interacciones complejas con verificación de llamadas.

Módulos y herramientas

go.mod y go.sum

Cada proyecto Go es un módulo declarado en go.mod. Ahí viven su nombre (ruta de import), la versión de Go y sus dependencias directas:

$ go mod init github.com/tuusuario/miapp

module github.com/tuusuario/miapp

go 1.22

require (
    github.com/gin-gonic/gin v1.9.1
    golang.org/x/text v0.14.0
)
ComandoHace qué
go get ruta@v1.2.3Añade/actualiza dependencia a versión concreta
go get -u ./...Actualiza todas las dependencias a menores/patches
go mod tidyLimpia no usadas y sincroniza go.sum — ejecútalo tras refactorear
go mod why paqueteExplica POR QUÉ está esa dependencia
go mod vendorSnapshot local de deps para builds reproducibles offline

go.sum guarda hashes criptográficos de cada módulo descargado: si alguien publica contenido distinto bajo misma versión, tu build falla en vez de ejecutar código alterado. Comítalo siempre.

Estructura estándar de proyecto

miapp/
├── go.mod              # definición del módulo + deps
├── go.sum              # hashes de integridad
├── cmd/
│   └── servidor/
│       └── main.go     # punto de entrada DELINADO: solo wiring
├── internal/           # ¡compilador impide importarlo desde fuera!
│   ├── api/
│   │   ├── handlers.go
│   │   └── handlers_test.go
│   └── almacen/
│       ├── db.go
│       └── db_test.go
├── pkg/                # código PÚBLICO pensado para otros proyectos
│   └── validadores.go
├── Makefile
└── README.md
  • cmd/nombre/main.go: cada binario tiene su carpeta; main solo conecta piezas.
  • internal/: privacidad a nivel de MÓDULO — ni forks pueden importarlo.
  • pkg/: opcional; úsala solo si otros módulos consumirán ese código.
  • Tests junto al código: db_test.go vive al lado de db.go. Nunca carpeta /test separada salvo tests end-to-end.

Compilación cruzada trivial

Go compila binarios nativos para cualquier plataforma desde tu laptop actual, sin toolchains extra:

Sistema destinoComando
Linux 64-bit$env:GOOS="linux"; $env:GOARCH="amd64"; go build
Windows 64-bit$env:GOOS="windows"; $env:GOARCH="amd64"; go build
macOS Apple Silicon$env:GOOS="darwin"; $env:GOARCH="arm64"; go build
Raspberry Pi / ARM$env:GOOS="linux"; $env:GOARCH="arm64"; go build

El flujo completo de release de un proyecto Go típico cabe en tres comandos: go vet ./... && go test ./... && go build ./cmd/servidor. Sin Docker necesario, sin runtime a instalar en el servidor: el binario ES el deploy.

Ejercicios prácticos

  1. Primera suite: crea módulo calculadora con funciones Sumar, Restar, Multiplicar y Dividir; escríbeles table-driven tests incluyendo casos borde (negativos, división por cero) y corre go test -v.
  2. Subtests quirúrgicos: añade un caso que falle a propósito y usa -run para ejecutarlo individualmente; luego arregla la función hasta verde.
  3. Duelo de benchmarks: compara búsqueda lineal vs binaria sobre 100.000 elementos ordenados; documenta los ns/op obtenidos en un comentario.
  4. Repositorio falso: diseña servicio de pedidos contra interfaz RepositorioPedidos; implementa versión real en memoria y fake para tests; prueba el flujo "crear pedido → calcular total" sin base de datos.
  5. Multiplataforma: compila tu binario para Windows, Linux y macOS ARM desde tu máquina; verifica con file (o tamaño/extensión) que generaste tres artefactos distintos.
