Goroutines y channels

La concurrencia no es un añadido en Go: está en el corazón del lenguaje. Una goroutine es una función que se ejecuta en paralelo con solo escribir go delante. No es un thread del sistema operativo (que cuesta ~1MB de stack): es un hilo verde gestionado por el runtime de Go, con un arranque de ~2KB y capacidad de mantener cientos de miles simultáneas en tu laptop.

Lanzar goroutines

func saludar(id int) {
    fmt.Printf("Hola desde la goroutine %d\n", id)
}

func main() {
    go saludar(1)          // se ejecuta EN PARALELO
    go saludar(2)

    time.Sleep(100 * time.Millisecond) // ¡necesario para este demo!
    fmt.Println("main termina")
}

main no espera a sus goroutines: cuando retorna, TODO el programa muere, dejando goroutines a medias. El Sleep de arriba es truco didáctico; en código real la coordinación se hace con WaitGroups o channels, nunca con sleeps.

Channels: tuberías tipadas entre goroutines

Un channel transmite valores de un tipo concreto entre goroutines, sincronizando automáticamente emisor y receptor. La flecha <- indica dirección:

resultados := make(chan string) // canal SIN buffer

// Productor
go func() {
    resultados <- "dato procesado" // BLOQUEA hasta alguien reciba
    close(resultados)
}()

// Consumidor
valor := <-resultados // BLOQUEA hasta que llegue algo
fmt.Println(valor)

Buffered vs sin buffer

Cerrar canales y range

El productor cierra el canal para anunciar "no habrá más datos". El consumidor puede iterar hasta el cierre con range — la forma más limpia de consumir una secuencia concurrente:

numeros := make(chan int)

go func() {
    defer close(numeros)
    for i := 1; i <= 5; i++ {
        numeros <- i * i
    }
}()

for v := range numeros { // termina SOLO al cerrar el canal
    fmt.Println(v)
}
// 1 4 9 16 25

// Verificar cierre manualmente:
v, abierta := <-numeros // abierta == false si estaba cerrado

Enviar a un canal cerrado provoca panic. Regla de oro: solo el productor cierra, y solo si tiene sentido señalar fin. Cerrar dos veces también panica.

Anatomía de un pipeline productor → canal → workers

select y sync.WaitGroup

WaitGroup: esperar a un equipo de goroutines

sync.WaitGroup es el contador de tareas más simple y usado: incrementas por cada tarea lanzada y cada goroutine se resta al terminar. Wait() bloquea hasta llegar a cero:

urls := []string{
    "https://golang.org",
    "https://go.dev",
    "https://pkg.go.dev",
}

var wg sync.WaitGroup

for _, url := range urls {
    wg.Add(1) // +1 ANTES de lanzar
    go func(u string) {
        defer wg.Done() // -1 al terminar, SIEMPRE
        resp, err := http.Get(u)
        if err != nil {
            fmt.Println(u, "ERROR:", err)
            return
        }
        resp.Body.Close()
        fmt.Println(u, "→", resp.Status)
    }(url)
}

wg.Wait() // bloquea hasta que todas terminen
fmt.Println("Scrapeo completo")

Desde Go 1.22 las variables de bucle son por-iteración, así que el parámetro u string ya no sería estrictamente necesario. En bases de código anteriores ES obligatorio capturarlo como parámetro o variable local — usar la variable de bucle directa era LA fuente #1 de bugs de concurrencia en Go.

select: esperar sobre múltiples canales

select es como un switch, pero para operaciones de canales: bloquea hasta que ALGUNO esté listo y ejecuta esa rama. Con varios listos, elige aleatoriamente (evita inanición):

canalA := make(chan string)
canalB := make(chan string)

go func() { time.Sleep(50 * time.Millisecond); canalA <- "desde A" }()
go func() { time.Sleep(10 * time.Millisecond); canalB <- "desde B" }()

for i := 0; i < 2; i++ {
    select {
    case msg := <-canalA:
        fmt.Println(msg)
    case msg := <-canalB:
        fmt.Println(msg)
    }
}

Timeouts: select + time.After

El patrón más importante de programación de redes en Go: nunca confiar en que una operación responda:

select {
case respuesta := <-consultaServidor():
    fmt.Println("OK:", respuesta)
case <-time.After(2 * time.Second):
    fmt.Println("Timeout: el servidor no respondió")
}

Mutex: cuando SÍ toca memoria compartida

A veces un simple contador no merece un canal. sync.Mutex protege secciones críticas:

contador := struct {
    sync.Mutex
    valor int
}{}

var wg sync.WaitGroup
for i := 0; i < 1000; i++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        contador.Lock()
        contador.valor++
        contador.Unlock()
    }()
}
wg.Wait()
fmt.Println(contador.valor) // 1000 garantizado (sin mutex: valor impredecible)

Detecta carreras de datos con go run -race main.go. El race detector reporta accesos concurrentes desprotegidos con trazas exactas. Ejecútalo siempre antes de subir código concurrente a producción.

Patrón worker pool completo

El patrón estrella de concurrencia en Go: N workers consumen de una cola de trabajos compartida y publican resultados en otro canal. Controlas exactamente cuántos recursos usas independientemente de cuántos trabajos lleguen:

func main() {
    const numWorkers = 3

    trabajos := make(chan int, 100)
    resultados := make(chan string, 100)

    // Arrancar el pool: cada worker vive en su propio bucle infinito
    var wg sync.WaitGroup
    for w := 1; w <= numWorkers; w++ {
        wg.Add(1)
        go worker(w, trabajos, resultados, &wg)
    }

    // Enviar 9 trabajos
    for t := 1; t <= 9; t++ {
        trabajos <- t
    }
    close(trabajos) // señal: no hay más trabajo

    wg.Wait()          // esperar a que los workers acaben
    close(resultados)

    for r := range resultados {
        fmt.Println(r)
    }
}

func worker(id int, trabajos <-chan int, resultados chan<- string, wg *sync.WaitGroup) {
    defer wg.Done()
    for t := range trabajos { // termina al cerrar 'trabajos'
        time.Sleep(time.Duration(rand.Intn(100)) * time.Millisecond)
        resultados <- fmt.Sprintf("worker %d procesó trabajo %d", id, t)
    }
}

Fíjate en los tipos de los parámetros: <-chan int significa "solo puedo recibir" y chan<- string "solo puedo enviar". El compilador impide que un worker publique en la cola de trabajos o robe de los resultados: las direcciones documentan la arquitectura.

Este pool escala cambiando UN número: 3 workers para laptops modestas, 200 para servidores. La lógica no cambia. Es el mismo patrón detrás de scrapers masivos, procesadores de colas y pipelines de ETL escritos en Go.

context.Context: cancelación cooperativa

¿Cómo cancelas un trabajo en curso? No puedes matar una goroutine desde fuera (por diseño). La respuesta de Go es context.Context: un valor que viaja por toda la cadena de llamadas llevando plazos (deadline), cancelaciones y datos de petición:

func buscarDatos(ctx context.Context, query string) ([]byte, error) {
    ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
    defer cancel() // libera recursos aunque todo salga bien

    req, _ := http.NewRequestWithContext(ctx, http.MethodGet,
        "https://api.ejemplo.com?q="+query, nil)

    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        if errors.Is(err, context.DeadlineExceeded) {
            return nil, fmt.Errorf("búsqueda '%s' excedió 3s: %w", query, err)
        }
        return nil, err
    }
    defer resp.Body.Close()
    return io.ReadAll(resp.Body)
}
ConstructorPara qué
context.Background()Raíz en servers/main
context.WithTimeout(parent, d)Plazo máximo absoluto
context.WithCancel(parent)Cancelar bajo demanda (ej: cliente desconectó)
context.WithValue(parent, k, v)Datos de petición (request-id, usuario autenticado) — con moderación

Convención universal: ctx es siempre el primer parámetro, llamado ctx. Si una función hace I/O y no acepta context, te estás privando de timeouts y cancelación limpia.

Errores comunes

Error típicoSíntomaCorrecto
Lanzar goroutines y no esperarlasPrograma muere antes de que terminenWaitGroup / channel de resultados / errgroup
Capturar la variable de bucle en closures (Go <1.22)Todas las goroutines ven el ÚLTIMO valorPasarla como parámetro de la closure
Fuga de goroutine: enviar sin receptor posibleMemoria crece eternamenteCanal con buffer + select con default/timeout, o contexto cancelable
Enviar a canal cerrado / doble closepanic: send on closed channelSolo el productor cierra, una sola vez, con sync.Once si aplica
Olvidar wg.Done() en un camino con return tempranoWait() cuelga para siempredefer wg.Done() inmediatamente tras Add
Compartir map entre goroutines sin lock"fatal error: concurrent map writes" (crash duro)sync.Mutex/RWMutex o sync.Map según acceso

El crash de mapa concurrente NO es recuperable con recover: mata el proceso entero. Es el error más caro de producción en equipos nuevos en Go — protégelo siempre que dos goroutines puedan tocar el mismo map.

Ejercicios prácticos

  1. Saludo ordenado: lanza 5 goroutines que impriman su índice y coordínalas con WaitGroup; luego modifica para que los resultados lleguen por un canal y main los imprima en orden recibido.
  2. Generador de cuadrados: implementa el pipeline generador → cuadrados → impresor usando DOS channels y range; verifica que cierras ambos canales correctamente.
  3. Búsqueda distribuida: dado un slice de 20 números, repártelos entre 4 workers que busquen un objetivo; el primero que lo encuentre publica en un canal y main cancela el resto con contexto.
  4. API con timeout: haz 3 peticiones HTTP reales (o simuladas con sleep) concurrentes aplicando timeout global de 1 segundo con select + time.After; imprime cuáles ganaron y cuáles expiraron.
  5. Contador seguro medido: incrementa un contador compartido 10.000 veces con 50 goroutines tres veces: sin protección, con Mutex y con canal atómico; compara resultados y explica las diferencias en comentarios.
