Múltiples retornos y el patrón error

Go no tiene excepciones en el flujo normal del lenguaje. En su lugar, las funciones pueden devolver varios valores, y la convención universal es devolver el resultado junto a un valor de tipo error. Esta decisión hace que los fallos sean parte visible de cada firma: imposible ignorar lo que el compilador te muestra en la cara.

El retorno múltiple

Una función puede devolver dos, tres o más valores. El más común es el par (resultado, error):

func dividir(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("división por cero")
    }
    return a / b, nil // nil = sin error
}

resultado, err := dividir(10, 2)
if err != nil {
    fmt.Println("Fallo:", err)
    return
}
fmt.Println("Resultado:", resultado) // 5

nil representa "nada" en Go (punteros, interfaces, maps, slices, channels vacíos). Un error == nil significa éxito. No existe undefined ni null-checks encadenados: el cero válido de cada tipo cubre ese rol.

Nombrando retornos: documentación viva

Puedes nombrar los valores de retorno en la firma. Mejora la autodocumentación y permite retornos "desnudos", aunque estos deben usarse con moderación:

func minMax(numeros []int) (minimo, maximo int) {
    if len(numeros) == 0 {
        return 0, 0
    }
    minimo, maximo = numeros[0], numeros[0]
    for _, n := range numeros[1:] {
        if n < minimo { minimo = n }
        if n > maximo { maximo = n }
    }
    return // retorna mínimo y máximo ya asignados
}

Closures y funciones como valores

Las funciones son ciudadanos de primera clase: se asignan a variables, se pasan como argumentos y capturan su entorno:

func contador() func() int {
    cuenta := 0
    // La closure captura 'cuenta' entre llamadas
    return func() int {
        cuenta++
        return cuenta
    }
}

siguiente := contador()
fmt.Println(siguiente(), siguiente(), siguiente()) // 1 2 3

defer, variádicas y utilidades

defer: ejecutar al salir, pase lo que pase

defer programa una llamada para el momento en que la función termina — retorne por donde retorne, incluso con panic. Es EL mecanismo para liberar recursos (cerrar archivos, conexiones, mutex): colocas el cierre justo al lado de la apertura y nunca olvidas ninguno de los múltiples caminos de salida.

func leerConfig(ruta string) error {
    archivo, err := os.Open(ruta)
    if err != nil {
        return err
    }
    defer archivo.Close() // se ejecutará SIEMPRE al salir

    datos, err := io.ReadAll(archivo)
    if err != nil {
        return err // Close() corre igualmente
    }
    fmt.Println("Config leída:", len(datos), "bytes")
    return nil // Close() corre también aquí
}

Los defers se ejecutan en orden LIFO (el último registrado, primero en ejecutarse), como una pila:

defer fmt.Println("primero registrado, último en correr")
defer fmt.Println("segundo")
// Salida al terminar:
//   segundo
//   primero registrado, último en correr

Los argumentos de un defer se evalúan en el momento del registro, no al ejecutarse: defer log.Println("procesados:", n) imprimirá el valor que tenía n cuando se registró la línea, no el final. Si necesitas el valor final, pasa un puntero o hazlo dentro de una closure.

Funciones variádicas

Un parámetro final con ... acepta cualquier número de argumentos, recibidos como slice. Así funcionan fmt.Println, append o errors.Join:

func sumar(numeros ...int) int {
    total := 0
    for _, n := range numeros {
        total += n
    }
    return total
}

fmt.Println(sumar(1, 2))          // 3
fmt.Println(sumar(1, 2, 3, 4))    // 10

valores := []int{5, 10, 15}
fmt.Println(sumar(valores...))    // spread: expandir el slice

Errores como valores: crear, envolver, inspeccionar

error es solo una interfaz diminuta: Error() string. Cualquier tipo que implemente ese método ES un error. Esta simplicidad permite componer errores, envolverlos con contexto y compararlos programáticamente.

Crear errores simples

// Estáticos
var ErrVacio = errors.New("la lista no puede estar vacía")

// Dinámicos con formato
func validarEdad(edad int) error {
    if edad < 0 {
        return fmt.Errorf("edad inválida: %d años", edad)
    }
    return nil
}

Envolver errores con %w: contexto sin perder el original

Desde Go 1.13, fmt.Errorf con el verbo %w crea un error que CONTIENE al original. Cada capa añade contexto (qué estaba haciendo el código) conservando la causa raíz consultable:

func cargarUsuario(id int) (*Usuario, error) {
    fila, err := db.Query("SELECT * FROM usuarios WHERE id = ?", id)
    if err != nil {
        // %w ENVUELVE err: conserva la causa para quien inspeccione
        return nil, fmt.Errorf("cargando usuario %d: %w", id, err)
    }
    defer fila.Close()
    // ...
    return u, nil
}

Añade contexto al envolver respondiendo "¿qué intentabas hacer?", no "¿qué pasó?" (eso ya lo dice el error interno). Compara: "cargando usuario 42: conexión rechazada" frente al inútil "conexión rechazada" flotando en los logs.

errors.Is y errors.As: inspección robusta

FunciónPregunta que respondeEjemplo
errors.Is(err, objetivo)¿Este error ES (o envuelve a) el error X?errors.Is(err, os.ErrNotExist)
errors.As(err, &tipo)¿En la cadena hay un error del TIPO T?errors.As(err, &pathError)
 
datos, err := os.ReadFile("config.yaml")
if err != nil {
    if errors.Is(err, os.ErrNotExist) {
        fmt.Println("Sin config: usando valores por defecto")
        return defaults(), nil
    }
    return nil, fmt.Errorf("leyendo config: %w", err)
}

// Con tipos personalizados:
var errSaldo *SaldoInsuficienteError
if errors.As(err, &errSaldo) {
    fmt.Printf("Faltan %.2f\n", errSaldo.Faltante)
}

Comparar con == (if err == ErrVacio) falla si el error fue envuelto alguna vez. Usa siempre errors.Is/As: recorren toda la cadena de wrapping.

panic y recover: la válvula de emergencia

panic detiene el flujo inmediatamente y deshace la pila ejecutando los defers pendientes; recover detiene esa desestructuración SOLO dentro de un defer. Su uso legítimo es estrecho:

Situación¿panic?Alternativa correcta
Entrada de usuario inválidaNoDevolver error
Recurso no disponible / red caídaNoDevolver error + reintentar
Bug de programador (índice fuera de rango)Panic implícito OKCorregir el bug
Inicialización global imposible de completarSí (arranque)log.Fatal / panic en init
Evitar que un panic en un worker tumbe el servidor—recover en el wrapper de goroutine
 
// Patrón real: proteger un servidor HTTP de panics en handlers
func safeHandler(fn http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                log.Printf("PANIC recuperado: %v\n%s", rec, debug.Stack())
                http.Error(w, "Error interno", http.StatusInternalServerError)
            }
        }()
        fn(w, r)
    }
}

Si te encuentras usando panic para errores esperables ("archivo no encontrado", "JSON inválido"), estás rompiendo la filosofía del lenguaje. Los errores son valores: trátalos como tales.

  1. Calculadora robusta: implementa calcular(a float64, op string, b float64) (float64, error) que soporte +, -, *, / y valide división por cero y operadores desconocidos con fmt.Errorf.
  2. Errores personalizados: define type EdadInvalidaError struct{ Edad int } con método Error() string; haz que validarEdad lo devuelva y demuestra errors.As desde otro paquete/función.
  3. Wrapping en cadena: construye tres funciones anidadas (leerArchivo → parsear → procesar) donde cada una envuelva con contexto distinto usando %w; imprime la cadena completa con fmt.Println(err) y luego extrae la causa con errors.Is.
  4. LIFO demostrado: escribe una función con cinco defers que imprimen números; predice la salida en un comentario ANTES de ejecutar y verifica.
