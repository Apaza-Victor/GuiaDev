Structs: datos con forma

Go no tiene clases. Tiene structs: agrupaciones de campos con tipos definidos por ti. Esta distinción no es semántica menor — es la declaración de que Go privilegia la composición de datos simples sobre jerarquías de herencia profundas. Un struct es un valor concreto, sin magia: se copia al asignarlo, se compara campo a campo y vive donde lo pongas (stack o heap, según el compilador decida).

Definición y creación de instancias

// Definición del tipo
type Producto struct {
    ID       int
    Nombre   string
    Precio   float64
    Stock    int
}

// Creación: literal NOMBRADO (el idiomático)
teclado := Producto{
    Nombre: "Teclado mecánico",
    Precio: 89.99,
} // ID y Stock toman sus zero values: 0

// Literal posicional: compacto pero frágil
monitor := Producto{2, "Monitor 24\"", 199.50, 10}

// Con new(): puntero a zero value
temp := new(Producto) // &Producto{ID:0, Nombre:"", ...}
temp.Nombre = "Borrador"

Usa SIEMPRE literales nombrados en código real. El posicional rompe silenciosamente si alguien reordena o inserta campos en el struct: tu compilación pasará… con los valores cambiados de sitio.

Structs son VALORES: la copia importa

Al asignar o pasar un struct a una función, Go copia TODOS sus campos. Esto es una característica, no un defecto: significa inmutabilidad accidental y ausencia de efectos laterales sorpresa:

original := Producto{ID: 1, Nombre: "Mouse", Precio: 25}
copia := original
copia.Precio = 30 // NO afecta a original

fmt.Println(original.Precio) // 25
fmt.Println(copia == original) // false: comparación campo a campo

Dos structs son comparables con == si TODOS sus campos lo son (números, strings, bools, otros structs comparables). Si contienen slices o maps, la comparación directa no compila: tendrás que comparar campo por campo o usar reflect.DeepEqual.

Métodos y composición

Métodos: funciones con receptor

Cualquier función puede "pegarse" a un tipo declarando un receptor entre func y el nombre. No hay this/this implícito mágico: tú eliges el nombre (convención: primera letra del tipo).

// Value receiver: recibe UNA COPIA del struct
func (p Producto) Resumen() string {
    return fmt.Sprintf("%s — $%.2f", p.Nombre, p.Precio)
}

// Pointer receiver: opera SOBRE el original
func (p *Producto) Reponer(unidades int) {
    p.Stock += unidades // modifica el struct real
}

tv := Producto{Nombre: "TV 55\"", Precio: 450}
fmt.Println(tv.Resumen())

tv.Reponer(5)          // azúcar sintáctico: Go toma &tv automático
fmt.Println(tv.Stock)  // 5

¿Value o pointer receiver? La regla práctica

CriterioValue receiver (p Producto)Pointer receiver (p *Producto)
Muta el structNo (trabaja sobre copia)Sí
Coste por llamadaCopia completa del structSolo copia el puntero (8 bytes)
Nil-safetyNo puede ser nilPuede recibir nil (debes validarlo)
Consistencia de interfazAmbos receptores satisfacen interfacesSolo *T queda en el conjunto de métodos

La regla de oro de la comunidad: si UN método necesita pointer receiver, TODOS los métodos del tipo deben usarlo. Mezclar ambos genera conjuntos de métodos inconsistentes y bugs sutiles con interfaces.

Embedding: composición en vez de herencia

Go no tiene herencia. En su lugar, un struct puede embeber otro, y sus campos/métodos quedan accesibles como si fueran propios ("promoción"). Es delegación explícita, no jerarquía:

type Motor struct {
    Caballos int
    Encendido bool
}

func (m *Motor) Arrancar() { m.Encendido = true }

type Auto struct {
    Motor     // embebido: SIN nombre de campo
    Marca string
}

a := Auto{Motor: Motor{Caballos: 150}, Marca: "Toyota"}
a.Arrancar()            // promocionado desde Motor
fmt.Println(a.Caballos) // también promovido: 150
fmt.Println(a.Motor.Encendido) // acceso completo siempre disponible

¿Necesitas el comportamiento del Motor? Lo embebes. ¿Dejas de necesitarlo? Lo quitas. Sin clases abstractas, sin constructores encadenados, sin frágiles jerarquías de cinco niveles. Si dos structs comparten comportamiento, la respuesta idiomática suele ser: extrae una interfaz.

Constructores y serialización

El patrón NewX()

Como no existe constructor, la convención es una función NewX() que garantiza invariantes antes de devolver el struct. Puede devolver valor o puntero según el caso:

type CuentaBancaria struct {
    titular string
    saldo   float64
}

// Campos privados → solo este paquete puede crear cuentas inválidas... o no
func NewCuentaBancaria(titular string) (*CuentaBancaria, error) {
    if titular == "" {
        return nil, errors.New("titular requerido")
    }
    return &CuentaBancaria{titular: titular, saldo: 0}, nil
}

func (c *CuentaBancaria) Depositar(monto float64) error {
    if monto <= 0 {
        return fmt.Errorf("monto debe ser positivo: %v", monto)
    }
    c.saldo += monto
    return nil
}

Tags para JSON y más

Los tags son metadatos adjuntos a campos, leídos vía reflexión por librerías como encoding/json, ORMs y validadores:

type APIUsuario struct {
    ID        int      `json:"id"`
    Nombre    string   `json:"nombre"`
    Email     string   `json:"email"`
    Password  string   `json:"-"`              // NUNCA serializar
    CreadoEn  time.Time `json:"creado_en"`
}

u := APIUsuario{ID: 7, Nombre: "Ana", Email: "ana@dev.io", Password: "secreto"}
salida, _ := json.Marshal(u)
fmt.Println(string(salida))
// {"id":7,"nombre":"Ana","email":"ana@dev.io","creado_en":...}

El tag json:"-" omite el campo en la serialización. Olvidarlo en contraseñas o tokens es una fuga de seguridad clásica. Revisa SIEMPRE qué expone tu struct antes de publicar un endpoint.

Errores comunes

Error típicoQué pasa realmenteSolución
Método value receiver que "no guarda cambios"Modifica la copia; el original intactoPointer receiver cuando hay mutación: func (p *Producto) ...
Mezclar value y pointer receivers en un mismo tipoConjunto de métodos inconsistente; interfaces fallanTodos pointer o todos value dentro del tipo
Comparar structs con slices/maps usando ==No compila: "cannot be compared"Comparar campo a campo o reflect.DeepEqual (tests)
Literal posicional tras añadir un campoValores desplazados silenciosamenteLiterales nombrados siempre
Creer que embedding ES herenciaSorpresas: no hay polimorfismo automático ni overridePensar en composición + interfaces
Exponer structs mutables desde APIsCualquiera corrompe el estado internoCampos privados + métodos + NewX validador

Ejercicios prácticos

  1. Inventario básico: define Producto con métodos ValorTotal() (precio×stock, value receiver) y Vender(n int) error (pointer receiver que valida stock suficiente).
  2. Banco seguro: implementa CuentaBancaria con campos privados, NewCuentaBancaria validadora, Depositar/Retirar con errores personalizados envueltos en %w, y método String() que implemente fmt.Stringer.
  3. Composición de figuras: crea Dimensiones (alto, ancho) embebida en Ventana y Puerta; demuestra la promoción de campos y un método compartido Area() definido sobre Dimensiones.
  4. API JSON: modela un struct Pedido con tags json correctos (omitir campos internos, renombrar a snake_case), serialízalo y deserialízalo de vuelta comprobando roundtrip.
  5. Comparador manual: dado un struct con slice interno (que no admite ==), escribe IgualA(otro T) bool campo por campo y pruébalo con casos positivos y negativos.
