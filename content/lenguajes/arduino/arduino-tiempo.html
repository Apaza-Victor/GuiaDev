El problema de delay()

La función delay(ms) es la primera que casi todo el mundo aprende para "esperar": congela la ejecución el número de milisegundos indicado. En un ejemplo sencillo como Blink funciona perfecto, pero tiene una limitación importante: mientras el micro espera, no hace absolutamente nada más. No lee botones, no muestra datos, no atiende sensores.

Imagina este sketch: un LED integrado parpadea cada segundo… y quieres que un botón lo apague. Con delay(1000) la placa pasará medio «atontada»: cuando pulsas el botón justo en medio del parpadeo, no responde hasta que acaba la espera. El tiempo real que el programa "vive" se pierde en esperas ciegas.

int led = 13;
int boton = 2;
int activo = true;

void setup() {
  pinMode(led, OUTPUT);
  pinMode(boton, INPUT_PULLUP);
}

void loop() {
  // Si pulsas el botón aquí, no se verá hasta que terminen los delays
  if (digitalRead(boton) == LOW) {
    activo = !activo;   // alterna el estado
  }

  if (activo) {
    digitalWrite(led, HIGH);
    delay(1000);        // ❌ bloquea TODO durante 1 s
    digitalWrite(led, LOW);
    delay(1000);        // ❌ el botón queda ignorado casi todo el tiempo
  }
}

Ideas erróneas comunes

  • "Un retardo no es mucho." Los delays se acumulan; tres retardos de 1 s hacen que tu programa deje de responder 3 s.
  • "Solo usaré delay en este sitio." Cada delay que añades es un punto donde el micro queda ciego.
  • "El micro procesa delay en segundo plano." No: delay() bloquea la CPU por completo (salvo interrupciones).

¿Entonces delay() está mal?

No, solo está mal usado. Es perfectamente aceptable en setup(), para esperas puntuales en el arranque (por ejemplo, dar tiempo a un sensor o a un módulo), para demos y prototipos simples. El problema aparece cuando necesitas un programa reactivo, que atienda varias cosas a la vez. Para eso existe millis().

Decimos que delay() "no es robusto" porque hace el tiempo ciego: pierdes la noción de cuánto tiempo real lleva esperando y de si ocurrieron eventos durante la pausa. Es ideal para aprender, pero hay que superarlo pronto.

---

millis() y micros()

La alternativa a delay() es medir el tiempo con un contador interno de la placa y comparar: en vez de "parar", le preguntamos al hardware cuánto tiempo ha pasado desde que arrancó. La función clave es millis(), que devuelve el número de milisegundos transcurridos desde que comenzó el programa, como un unsigned long (32 bits). Su versión más precisa es micros(), que devuelve microsegundos.

FunciónDevuelveTipoDesborda a los…
millis()Milisegundos desde el arranqueunsigned long~49,7 días
micros()Microsegundos desde el arranqueunsigned long~71,6 minutos

La cuenta y su límite: el desbordamiento

Un unsigned long puede contar hasta 4.294.967.295. En milisegundos eso son unos 49,7 días; en microsegundos, apenas 71,6 minutos. Cuando se alcanza el máximo, el contador vuelve a cero (overflow). No pasa nada de malo —como verás, la técnica correcta de comparación con resta funciona igual tras el desbordamiento—, pero hay que evitar comparaciones que fallen en ese instante.

Precisión: micros() no mide a nivel de instrucción. Con un reloj de 16 MHz, micros() tiene una resolución real de unos 4 microsegundos y no es fiable para medir tiempos inferiores a varios microsegundos.

Las funciones no bloquean

La gran ventaja: millis() y micros() no detienen la ejecución. Solo contestan una pregunta ("¿cuánto ha pasado?") y el programa sigue su curso. Eso permite construir temporizadores sin bloquear.

Las funciones funcionan solo midiendo tiempo transcurrido (elapsed time): no existe una "hora del día" interna. Para fecha/hora real se necesita un módulo RTC (como DS1307 o DS3231) o sincronismo por red (NTP) con WiFi.

Temporizador con millis()

El patrón clásico para hacer algo cada cierto intervalo, sin bloquear, es este:

unsigned long anterior = 0;   // marca del último disparo
const unsigned long intervalo = 1000;  // cada 1000 ms

void setup() {
  pinMode(LED_BUILTIN, OUTPUT);
}

void loop() {
  // Si ya ha pasado el intervalo desde la última vez…
  if (millis() - anterior >= intervalo) {
    anterior = millis();          // actualiza la marca
    digitalWrite(LED_BUILTIN, !digitalRead(LED_BUILTIN)); // parpadea
  }
  // Aquí el programa sigue disponible: nada bloqueado
}

Este sketch hace lo mismo que Blink (parpadeo de 1 s) pero sin llamar a delay(): mientras no toca el parpadeo, el loop() sigue girando y puede atender botones, sensors o serial. El LED integrado alterna su estado cada segundo.

¿Por qué millis() - anterior es correcto incluso tras overflow?

Gracias a la aritmética modular de los unsigned long. Imagina que anterior vale 4.294.967.200 y millis() ya desbordó y vale 100. La resta se hace en aritmética sin signo de 32 bits y da el valor correcto (~196 ms), exactamente como si el contador nunca hubiera dado la vuelta:

// 100 - 4294967200 da el tiempo correcto incluso tras el overflow,
// porque todas las operaciones se hacen con unsigned long (módulo 2^32).
if (millis() - anterior >= intervalo) {
  anterior = millis();
  // ...
}

La clave es restar (millis() - anterior) y comparar con >= en lugar de comparar millis() directo con un objetivo fijo. Así el intervalo se comporta bien ocurra o no el desbordamiento.

Sketch completo y comentado

// Parpadeo sin delay: un LED blink mejor
const int led = 9;
unsigned long ultimaVez = 0;      // cuándo cambiamos por última vez
const unsigned long periodo = 500; // cada 500 ms

void setup() {
  pinMode(led, OUTPUT);
}

void loop() {
  if (millis() - ultimaVez >= periodo) {
    ultimaVez = millis();          // reinicia la cuenta
    digitalWrite(led, !digitalRead(led));  // alterna el LED
  }
}

Multitarea sin bloqueos

El superpoder de millis() es poder hacer varias tareas "a la vez" en un único loop(): basta con varios temporizadores independientes, cada uno con su propia variable de marca. El micro no hace nada en paralelo de verdad, pero reacciona tan rápido que el resultado parece simultáneo.

En este ejemplo un LED parpadea cada 500 ms, otro cada 1200 ms y el puerto serie refresca un valor dos veces por segundo, todo en el mismo bucle:

unsigned long tLed1 = 0, tLed2 = 0, tSerial = 0;

const unsigned long pLed1 = 500;   // cada 0,5 s
const unsigned long pLed2 = 1200;  // cada 1,2 s
const unsigned long pSerial = 500; // dos veces por segundo

void setup() {
  pinMode(9, OUTPUT);
  pinMode(10, OUTPUT);
  Serial.begin(115200);
}

void loop() {
  // Temporizador 1: LED del pin 9
  if (millis() - tLed1 >= pLed1) {
    tLed1 = millis();
    digitalWrite(9, !digitalRead(9));
  }
  // Temporizador 2: LED del pin 10 (otro ritmo)
  if (millis() - tLed2 >= pLed2) {
    tLed2 = millis();
    digitalWrite(10, !digitalRead(10));
  }
  // Temporizador 3: refresco del serial
  if (millis() - tSerial >= pSerial) {
    tSerial = millis();
    Serial.println(analogRead(A0));
  }
}

Máquina de estados: un semáforo

Cuando una tarea pasa por distintas fases, almacenas el estado actual en una variable y cambias de fase según el tiempo:

int estado = 0;                 // 0:rojo, 1:verde, ...
unsigned long tEstado = 0;

const int rojo = 11, amarillo = 12, verde = 13;
const unsigned long tRojo = 4000;
const unsigned long tVerde = 3000;
const unsigned long tAmarillo = 1000;

void setup() {
  pinMode(rojo, OUTPUT);
  pinMode(amarillo, OUTPUT);
  pinMode(verde, OUTPUT);
}

void loop() {
  switch (estado) {
    case 0:
      digitalWrite(rojo, HIGH);
      digitalWrite(verde, LOW);
      if (millis() - tEstado >= tRojo) { estado = 2; tEstado = millis(); }
      break;
    case 2:
      digitalWrite(verde, HIGH);
      digitalWrite(rojo, LOW);
      if (millis() - tEstado >= tVerde) { estado = 1; tEstado = millis(); }
      break;
    case 1:
      digitalWrite(verde, LOW);
      digitalWrite(amarillo, HIGH);
      if (millis() - tEstado >= tAmarillo) { estado = 0; tEstado = millis(); }
      break;
  }
}

No es magia: el `loop()` sigue siendo secuencial y ejecuta una instrucción tras otra. La diferencia es que cada pasada es tan corta y frecuente que ninguna tarea "roba" el tiempo de las demás. Mientras una espera su intervalo, las otras se ejecutan.

Patrones avanzados

Si necesitas muchas tareas, el patrón se puede generalizar (varias marcas en un array o estructuras), y para proyectos grandes existen librerías de scheduler o RTOS ligeros (por ejemplo TaskScheduler o enfoques con Scheduler en placas con soporte). Son herramientas avanzadas; el patrón con millis() cubre la gran mayoría de necesidades.

Otras funciones de tiempo

Además de millis() y micros(), existen otras utilidades de tiempo en Arduino:

FunciónQué haceBloquea
delay(ms)Espera ms milisegundosSí
delayMicroseconds(us)Espera us microsegundos (muy preciso para pulsos)Sí
millis()Devuelve ms desde el arranqueNo
micros()Devuelve microsegundos desde el arranqueNo
  • delayMicroseconds() es útil para generar trenes de pulsos precisos (servos, protocolos de un solo hilo); no uses delay() para eso, su resolución no da.
  • micros() es más preciso que millis() pero se desborda a los ~71,6 minutos y no sirve para marcar intervalos largos.

Guardar la marca entre llamadas

Para medir intervalos hay que recordar el momento anterior entre una vuelta del loop() y la siguiente, por eso se usa una variable global unsigned long:

unsigned long ultimaMarca = 0;   // recuerda la última vez

void loop() {
  if (millis() - ultimaMarca >= 1000) {
    ultimaMarca = millis();      // guarda el nuevo momento
    Serial.println("Ha pasado 1 segundo");
  }
}

Secciones críticas e interrupciones

En situaciones de máxima criticidad (por ejemplo, midiendo un pulso exacto) puedes desactivar temporalmente las interrupciones con noInterrupts() y volver a activarlas con interrupts(). Es una técnica avanzada a usar con pinzas, porque mientras dura el bloque la CPU no atiende eventos externos.

Ninguna de estas funciones da una fecha ni una hora del calendario. millis() solo cuenta desde que se encendió la placa. Si tu proyecto necesita hora real (reloj en pantalla, registro con marca de tiempo), necesitas un módulo RTC (DS1307/DS3231) o sincronización NTP vía WiFi.

---

Errores comunes

Trabajar con tiempo en Arduino tiene trampas típicas. Estas son las más importantes:

1. Declarar anterior como int

El mayor error de todos: usar int en vez de unsigned long para las marcas. Un int de 16 bits se desborda a los ~32,7 segundos (32167 ms), rompiendo el temporizador en menos de un minuto. Siempre: unsigned long anterior = 0;

// ❌ int se desborda a los ~32 segundos
// int anterior = 0;

// ✅ unsigned long dura 49,7 días
unsigned long anterior = 0;

2. Olvidar actualizar anterior = millis()

Si condicionas con millis() - anterior >= intervalo pero nunca actualizas anterior, entrarás en el bloque cada vuelta del loop sin parar (o, si la comparación se desincroniza, el arranque se bloquea). La línea anterior = millis(); dentro del if es imprescindible.

3. Comparar millis() > objetivo directamente

Comparar contra un objetivo fijo en vez de restar falla cuando el contador se desborda o cuando la marca es casi el máximo:

// ❌ Falla en el desbordamiento
// if (millis() > objetivo) { ... }

// ✅ Correcto: la resta es robusta al overflow
if (millis() - anterior >= intervalo) { ... }

4. Usar delay() dentro de bloques que deben ser reactivos

Mezclar delay() con temporizadores de millis() reintegra el bloqueo que intentabas evitar. Un delay(2000) en medio del loop() congela también a tus temporizadores de millis().

5. Suponer que micros() es preciso a nivel de instrucción

micros() tiene una resolución real de unos 4 microsegundos con el reloj de 16 MHz y no es fiable para tiempos inferiores. Para pulsos muy cortos usa delayMicroseconds() u otras técnicas.

6. Bloquear el loop con lectura serial larga

Un while (Serial.available()) { … } muy largo (o un parseInt() esperando datos que no llegan) detiene todos los temporizadores. Si necesitas leer y temporizar a la vez, procesa pocos bytes por vuelta del loop() en lugar de vaciar todo el búfer de golpe.

Regla de oro: usa siempre unsigned long, actualiza la marca dentro del if, y compara con resta. Con esos tres hábitos el desbordamiento de millis() deja de ser un problema y tus temporizadores serán a prueba de bombas.

Ejercicios

Afianza el tiempo sin bloqueos con estos ejercicios, de menor a mayor dificultad:

  1. LED 1 s con millis (sin delay): reescribe el sketch Blink para que el LED integrado parpadee cada segundo usando millis() y sin llamar a delay() en el loop(). Comprueba que un botón conectado a otra tarea responde mientras el LED parpadea.
  2. Dos LEDs a ritmos distintos: conecta dos LEDs a los pines 9 y 10 y haz que parpadeen a 500 ms y 1200 ms respectivamente, con dos temporizadores independientes de millis().
  3. Semáforo con estados: construye el semáforo de la lección (rojo 4 s, verde 3 s, amarillo 1 s) y adapta los tiempos para que el ciclo completo dure 10 s exactos.
  4. Botón N veces + parpadeo simultáneo: un botón cuenta cuántas veces se pulsa (y lo muestra por serial) mientras un LED parpadea cada segundo con millis(); después de cada pulso, apaga el LED brevemente como confirmación, sin bloquear el parpadeo.
  5. Cronómetro por serial con dos botones: un botón inicia/pausa un cronómetro que muestra los segundos transcurridos por serial, y otro botón lo reinicia a cero. Utiliza millis() para medir el tiempo y comprueba que el serial no se bloquea.
