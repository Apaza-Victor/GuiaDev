¿Qué es una interrupción?

Una interrupción es un evento hardware que pausa el programa en curso, salta a una función especial llamada ISR (Interrupt Service Routine) y, al terminar, vuelve exactamente al punto donde estaba. Es como si estuvieras redactando un informe y te llamaran por teléfono: dejas lo que hacías, atiendes la llamada y, al colgar, continúas donde lo dejaste. ¿Por qué importa? Porque el programa no tiene que estar mirando continuamente para reaccionar: sin interrupciones, detectar un pulso breve exige que el loop() lea ese pin constantemente, y si en ese instante está ocupado (una espera con delay(), una operación larga…), el evento se pierde para siempre.

Interrupciones externas vs. temporizadores

En el microcontrolador conviven dos grandes familias: externas (por pin), que saltan cuando un pin cambia de estado (flanco de subida o de bajada) y son las protagonistas de esta lección con attachInterrupt(); e internas (temporizadores), que saltan cada cierto tiempo programado según el reloj del chip y se esconden detrás de millis(), de la señal PWM y de librerías como Servo o Tone.

El ejemplo típico es contar los pulsos de un encoder o de un sensor de flujo: esos pulsos duran microsegundos y llegan en cualquier momento mientras el loop() hace algo lento. Un bucle que muestrea no puede garantizar no perderse ninguno; una interrupción los captura siempre.

La interrupción no hace que el programa "vaya más rápido": lo que hace es garantizar que un evento no se pierda, pase lo que pase en el loop(). El coste es un pequeño retardo al saltar y volver de la ISR.

attachInterrupt y pines compatibles

La función que conecta una interrupción externa con tu código es attachInterrupt(), con esta firma:

attachInterrupt(digitalPinToInterrupt(pin), nombreISR, modo);

El primer argumento es el pin, envuelto en digitalPinToInterrupt(pin): así el mismo código funciona en distintas placas aunque la tabla de pines cambie. El segundo es el nombre de tu ISR (sin paréntesis) y el tercero, el modo que dispara la interrupción:

ModoCuándo se dispara
RISINGCuando el pin pasa de LOW a HIGH (flanco de subida)
FALLINGCuando el pin pasa de HIGH a LOW (flanco de bajada)
CHANGEEn cualquier cambio de estado (subida o bajada)
LOWMientras el pin esté a nivel bajo (¡se repite continuamente!)

¿Qué pines soportan interrupciones externas?

No todos los pines valen: solo los que el microcontrolador conecta a sus entradas de interrupción (INT). En las placas clásicas la lista es corta:

PlacaPines con interrupción externaInterrupciones
Uno / Nano2, 3INT0, INT1
Mega 25602, 3, 18, 19, 20, 21INT0 a INT5
Leonardo / Micro0, 1, 2, 3, 7INT0 a INT4
ESP32 / ESP8266Casi cualquier GPIOMuchas y flexibles

Un contador mínimo

volatile unsigned int pulsos = 0;
void contar() {
  pulsos++;                      // la ISR: corta y simple
}
void setup() {
  Serial.begin(9600);
  attachInterrupt(digitalPinToInterrupt(2), contar, RISING);
}
void loop() {
  Serial.println(pulsos);
  delay(500);
}

Para desactivar la interrupción de un pin se usa detachInterrupt(digitalPinToInterrupt(pin)), útil cuando el evento ya no te interesa (por ejemplo, al entrar en un modo de reposo por software).

Las reglas de la ISR

La ISR es un mundo aparte dentro de tu programa. Mientras se ejecuta, el flujo principal está congelado y, por defecto, las demás interrupciones están deshabilitadas. De ahí salen unas reglas de oro que hay que respetar siempre:

  • Debe ser corta y rápida: cuanto menos tiempo bloquee el programa principal, mejor. Piénsala como un "marcar y salir".
  • Nada de delay(): no aporta nada útil y congela todo el sistema, incluidos millis() y el propio loop().
  • Poco o nada de Serial: imprimir dentro de la ISR desperdicia tiempo y puede corromper la comunicación si la llamada llega a mitad de un envío.
  • Nada de tareas pesadas: escribir en tarjetas SD, radios o pantallas queda prohibido: son operaciones lentas y no atómicas.
  • Sin bucles que esperen: un while que se queda esperando dentro de la ISR bloquea el microcontrolador indefinidamente.
void miISR() {
  contador++;                       // ✅ legal y rápido: solo suma
  // delay(100);                    // ❌ prohibido: congela el sistema
  // Serial.println(contador);      // ⚠️ evítalo dentro de la ISR
}

¿Qué pasa al terminar?

Cuando la ISR acaba, el hardware restaura el punto exacto donde se interrumpió el programa: la CPU guarda la dirección de retorno y los registros en la pila. Tu programa "no sabe" que ha sido pausado; simplemente continúa como si nada hubiera pasado.

El consejo clave: marcar o incrementar, trabajar en el loop

La técnica más saludable es que la ISR solo marque un flag o incremente un contador, y deje todo el trabajo de verdad (mostrar datos, cambiar salidas, tomar decisiones) para el loop(). Así la interrupción dura microsegundos y el sistema se mantiene estable: piensa en la ISR como un botón de pausa, porque mientras está activa el loop() no corre.

Flags y volatile

Todo lo que comparte la ISR con el loop() (contadores, flags, lecturas de sensores) es una variable compartida entre dos "hilos" de ejecución: el principal y el de interrupción. Para que el compilador no haga trampas, esas variables deben declararse con la palabra clave volatile.

Sin volatile, el compilador puede cachear el valor de la variable en un registro y leer un dato obsoleto: aunque la ISR la modifique, tu loop() seguirá viendo el valor antiguo. volatile le ordena al compilador leer siempre de la memoria real.

Contador de pulsos con volatile

volatile unsigned long pulsos = 0;   // modificada en la ISR
void contar() {
  pulsos++;
}
void setup() {
  Serial.begin(9600);
  attachInterrupt(digitalPinToInterrupt(2), contar, RISING);
}
void loop() {
  Serial.print("Pulsos: ");
  Serial.println(pulsos);
  delay(500);
}

El patrón flag

Cuando no quieres contar sino avisar de que ocurrió algo, se usa un flag: la ISR lo pone a true y el loop() lo consulta y lo limpia.

volatile bool evento = false;         // aviso de la ISR
void detectar() {
  evento = true;                      // solo avisa; el trabajo va en loop()
}
void setup() {
  Serial.begin(9600);
  attachInterrupt(digitalPinToInterrupt(3), detectar, FALLING);
}

void loop() {
  if (evento) {                       // ¿ha llegado un aviso?
    evento = false;                   // consumir el aviso
    Serial.println("Evento detectado");
  }
}

El atasco de lectura: noInterrupts() e interrupts()

En un AVR, una unsigned int ocupa 2 bytes y se lee en dos pasos. Si una interrupción ocurre entre ambos, puedes leer una mezcla: un byte de una lectura y otro de la siguiente. Para leer un contador multi-byte de forma atómica, se bloquean las interrupciones durante la lectura.

volatile unsigned int conteo = 0;     // 2 bytes: lectura no atómica
unsigned int leerConteo() {
  unsigned int copia;
  noInterrupts();                     // congelar las interrupciones
  copia = conteo;                     // lectura completa de los 2 bytes
  interrupts();                       // reanudar
  return copia;
}

Regla mental: toda variable compartida con una ISR se declara volatile; y si ocupa más de un byte y la lees o modificas desde el loop(), protégela con noInterrupts()/interrupts().

Debounce de botones

Cuando pulsas un botón físico, los contactos metálicos rebotan: hacen y deshacen el contacto durante unos milisegundos antes de asentarse. El resultado es que el microcontrolador puede ver varios flancos en una sola pulsación, como un rápido parpadeo ruidoso. A ese fenómeno se le llama rebote (bounce) y hay que filtrarlo.

Soluciones hardware vs. software

EnfoqueCómo se haceVentaja
HardwareCondensador en paralelo con el botón, disparador de Schmitt o chip dedicadoSe resuelve sin tocar el código
SoftwareIgnorar los cambios que llegan durante unos 50 ms tras el último válidoBarato, flexible y sin componentes extra

Debounce con millis()

La versión estándar usa millis() para descartar los cambios demasiado cercanos al último válido. Este sketch alterna un LED con un botón sin que los rebotes lo confundan:

const int BOTON = 2;
const int LED = 13;
int estadoBoton = HIGH;               // estado filtrado actual
unsigned long ultimoCambio = 0;
const unsigned long DEBOUNCE = 50;    // milisegundos de filtro

void setup() {
  pinMode(BOTON, INPUT_PULLUP);       // resistencia interna: LOW = pulsado
  pinMode(LED, OUTPUT);
}

void loop() {
  int lectura = digitalRead(BOTON);

  if (lectura != estadoBoton && millis() - ultimoCambio > DEBOUNCE) {
    ultimoCambio = millis();
    estadoBoton = lectura;
    if (estadoBoton == LOW) {                  // flanco válido
      digitalWrite(LED, !digitalRead(LED));    // alternar el LED
    }
  }
}

Antirrebote dentro de la ISR

Si el botón está conectado a un pin de interrupción, puedes aplicar el mismo filtro temporal dentro de la propia ISR: los rebotes del mismo pulso llegan con menos de 50 ms de diferencia y se ignoran.

volatile int pulsaciones = 0;
volatile unsigned long ultimoPulso = 0;
const unsigned long DEBOUNCE = 50;
void pulso() {
  unsigned long ahora = millis();
  if (ahora - ultimoPulso > DEBOUNCE) {        // primer flanco válido
    ultimoPulso = ahora;
    pulsaciones++;                             // se cuenta una sola vez
  }
}

El filtro de 50 ms es un valor clásico: más largo que el rebote típico de un botón y más corto que una pulsación humana real (que dura cientos de ms). Si tu botón es ruidoso o viejo, sube la constante a 80–100 ms.

Interrupción vs. polling

Polling (muestreo) es el enfoque simple: el loop() pregunta continuamente con digitalRead() a sus entradas. Interrupción invierte el modelo: no preguntas tú, te avisan a ti. ¿Cuándo conviene cada uno?

CriterioPollingInterrupción
FacilidadMuy simple y legibleRequiere dominio de ISR y volatile
LatenciaDepende de la velocidad del loopRespuesta casi inmediata
Eventos lentos (botones)SuficienteÚtil pero no imprescindible
Pulsos cortos / frecuencia altaFácil perder eventosEl estándar (encoders)
Si el loop se atascaTodo se pierdeLas ISR siguen disparándose
CosteNingunoRetardo, pila y complejidad

¿Cuándo elegir qué?

Polling: botones que pulsas con el dedo, interruptores de estado y sensores que cambian despacio, siempre que el loop() esté despejado. Simple y suficiente. Interrupción: encoders, contadores de pulsos (flujo, tacómetros, ruedas), pulsos muy cortos, o cuando el loop() hace tareas lentas y no puede vigilar entradas.

Consejo práctico

Si el evento puede ocurrir en cualquier instante y perderlo es inaceptable, usa interrupción. Si solo quieres conocer el estado de una entrada de vez en cuando y el loop está despejado, el polling es más simple y robusto. Muchos proyectos mezclan ambos: la lógica general con polling y uno o dos flancos críticos con interrupción.

Ante la duda, empieza con polling: añade una interrupción solo cuando compruebes que pierdes eventos. Una ISR mal diseñada produce bugs más difíciles de diagnosticar que un muestreo lento.

Errores comunes

1. Olvidar volatile

unsigned long pulsos = 0;   // ❌ sin volatile: el loop puede leer valores viejos
void contar() { pulsos++; }
// volatile unsigned long pulsos = 0;   // ✅ corrección

2. Operaciones lentas dentro de la ISR

void isr() {
  delay(200);               // ❌ congela TODO el sistema
  // Marca un flag y deja lo lento para el loop(); nunca al revés.
}

3. Usar Serial dentro de la ISR

Imprimir durante la ISR desperdicia microsegundos preciosos y puede desordenar la comunicación si la llamada llega a mitad de un envío. Guarda el dato y publícalo desde el loop().

4. Olvidar digitalPinToInterrupt

attachInterrupt(2, contar, RISING);                       // ❌ frágil
attachInterrupt(digitalPinToInterrupt(2), contar, RISING); // ✅ portable

5. Usar el modo LOW sin cuidado

Con LOW la interrupción se dispara mientras el pin esté bajo: si no lo subes pronto, volverá a saltar en cuanto la ISR termine y el programa nunca continuará. Prefiere RISING/FALLING para detectar flancos.

6. Leer o modificar contadores multi-byte sin protección

if (pulsos > 100) { }     // ⚠️ 2+ bytes: la ISR puede "atacar" a media lectura
// Usa una copia con noInterrupts() / interrupts() alrededor.

Lo mismo aplica si el loop() escribe una variable que también escribe la ISR: una escritura a medias de 2 o 4 bytes deja un valor corrupto para la interrupción.

El fallo más caro de esta lección es creer que las interrupciones "aceleran" el código. No lo hacen: traen exactitud. Programarlas mal (variables no volatile, ISR largas, modo LOW) produce bugs intermitentes que son de los más difíciles de depurar que existen.

Ejercicios

Cinco retos ordenados de menor a mayor dificultad. Necesitarás una placa Uno (o compatible), un botón, resistencias, LEDs y cables.

  1. Contador de pulsos: conecta un botón (o un sensor de flujo) al pin 2 y muestra por el Monitor Serie el total de pulsos acumulado con una ISR en modo RISING. Recuerda declarar el contador volatile y probar qué pasa si lo olvidas.
  2. Botón con debounce: reproduce el sketch de debounce con millis() que alterna un LED. Cambia la constante DEBOUNCE a 5 ms y pulsa rápido: observa y explica por qué ahora parece que el LED "duda".
  3. Detector de flanco: con el modo CHANGE y un volatile bool, imprime un mensaje cada vez que el botón cambie de estado y, en el loop(), cuenta cuántos cambios hubo en 10 segundos con millis().
  4. Mini encoder: usa los pines 2 y 3 en modo CHANGE con dos flags. Cuenta "adelante" cuando el pin A cambie antes que el B y "atrás" en el caso contrario. Es la semilla de un encoder rotatorio real.
  5. Semáforo con alarma: monta un semáforo de 3 LEDs con su ciclo normal. Añade un botón en el pin 3 cuya ISR (con debounce temporal) ponga un flag de alarma; al leerlo, el loop() debe interrumpir el ciclo y parpadear el ámbar hasta que se pulse de nuevo.
