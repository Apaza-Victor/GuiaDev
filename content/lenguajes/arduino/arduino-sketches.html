¿Qué es un sketch?

En el mundo de Arduino un programa se llama sketch ("boceto" en inglés), un término que refuerza la idea de experimentación rápida: escribes, subes y pruebas en segundos. Un sketch se guarda en un fichero con extensión .ino dentro de una carpeta que lleva el mismo nombre que el archivo (por ejemplo Blink/Blink.ino).

Puede parecer que escribes en un lenguaje nuevo llamado "Arduino", pero en realidad escribes C++ real. Lo que ocurre es que el entorno añade una capa: el preprocesador del IDE se encarga automáticamente de generar los #include necesarios (el de Arduino.h entre ellos), de insertar las declaraciones de tus funciones y de construir un programa C++ completo antes de pasárselo al compilador avr-g++. Por eso puedes usar un pinMode() en setup() sin haberlo declarado nunca antes.

El sketch tiene prioridad sobre el fichero C++ completo que el IDE genera al vuelo: tu código es el cuerpo y el compilador lo rodea de toda la infraestructura (el main, el init(), las cabeceras) que la placa necesita para arrancar.

Anatomía básica de un sketch

Todo sketch, del más simple al más complejo, sigue esta estructura lógica de arriba a abajo:

1. #include ...            //  librerías (opcional)
2. #define o const ...     //  constantes con nombre
3. variables globales      //  el estado compartido del programa
4. void setup()            //  configuración: se ejecuta 1 vez
5. void loop()             //  bucle principal: se repite sin fin

Las constantes de pin son el primer contacto con esta estructura en casi todos los proyectos:

#define PIN_LED 13          // constante del preprocesador

const int PIN_BOTON = 2;    // constante en tiempo de compilación

int contadorPulsaciones = 0;   // variable global: su valor perdura

Usa const int en lugar de #define siempre que puedas: es más seguro, respeta los tipos y el compilador lo optimiza igual de bien. El resultado en el microcontrolador es idéntico.

setup() y loop()

Todo sketch define obligatoriamente dos funciones: setup() y loop(). Ninguna de las dos recibe parámetros ni devuelve nada (su tipo de retorno es void). Sus nombres describen exactamente qué hacen:

  • setup() se ejecuta una sola vez al encender la placa. Aquí configuras los pines (pinMode), inicias la comunicación serie (Serial.begin) y dejas todo listo.
  • loop() se ejecuta en bucle infinito, una y otra vez, durante toda la vida del programa. Aquí vive la lógica diaria: leer sensores, decidir, escribir salidas.

El flujo de ejecución real es este:

encender placa
    │
    ▼
setup()          ← se ejecuta UNA vez
    │
    ▼
loop() ─────► loop() ─────► loop() ─────► loop() ...
    ▲                               
    └── se repite para siempre ──────┘

Puedes verificarlo tú mismo con el Monitor Serie:

void setup() {
  Serial.begin(9600);                    // inicia la comunicación serie
  Serial.println("setup(): una sola vez");
}

void loop() {
  Serial.println("loop(): otra pasada mas");
  delay(500);                            // espera 500 ms antes de repetir
}
setup(): una sola vez
loop(): otra pasada mas
loop(): otra pasada mas
loop(): otra pasada mas
...

¿Quién llama a estas funciones?

En un programa "normal" de C++ la ejecución empieza en main(). En Arduino el main() existe, pero está escondido en el fichero pregenerado que el IDE crea por ti. Su forma simplificada es esta:

int main(void) {
  init();            // configura temporizadores y hardware base
  setup();           // tu código de configuración, una vez
  while (1) {        // bucle infinito
    loop();          // tu código principal, una y otra vez
  }
}

Como loop() corre sin parar, nada de lo que escribas fuera de él (instrucciones sueltas al final del archivo) llegará nunca a ejecutarse. Si quieres que algo pase una vez, va en setup(); si quieres que se repita, va en loop().

Compilar y subir el código

El IDE ofrece dos botones que conviene no confundir, aunque viven juntos en la barra superior:

BotónQué haceCombinación de teclas
VerificarComprueba el código sin compilar nada que se quede en la placa: no se subeCtrl + R / ⌘ + R
SubirVerifica y, si todo es correcto, compila y graba el firmware en el microcontrolador por USBCtrl + U / ⌘ + U

Subir implica primero verificar, así que "subir sin verificar" no existe: el botón Subir siempre compila antes de grabar. Lo que sí conviene es practicar el hábito de pulsar Verificar mientras estás escribiendo, para detectar errores antes de molestar a la placa.

El proceso completo

Cuando pulsas Subir ocurren estas fases en cadena:

  1. Validación: el preprocesador prepara tu .ino y lo convierte en C++ completo.
  2. Compilación: avr-g++ traduce el código a lenguaje máquina del microcontrolador (un fichero .hex).
  3. Grabación vía USB: el IDE resetea la placa y el bootloader (un pequeño programa de fábrica que reside en el microcontrolador) recibe los datos y escribe el firmware en la memoria flash.

En la terminal de mensajes de la parte inferior verás todo lo que pasa. Frases útiles a reconocer: Sketch uses 924 bytes (memoria flash: el programa), Global variables use 9 bytes of dynamic memory (SRAM: las variables) y, al final, Done uploading.

El aviso "low memory available, stability problems may occur" es serio. El ATmega328P (Arduino Uno) solo tiene 2 KB de SRAM y 32 KB de flash. Si te quedas sin SRAM el programa puede comportarse de forma errática sin explicación lógica.

Si la subida falla con errores de port o avrdude, revisa la placa y el puerto seleccionados en Herramientas: son la causa más frecuente de un Failed uploading.

El primer programa: Blink

El "hola mundo" de Arduino consiste en hacer parpadear el LED integrado de la placa. En el Uno y la mayoría de placas ese LED está conectado al pin 13, y el lenguaje lo llama LED_BUILTIN. No necesitas ningún componente externo. Este es el sketch completo:

void setup() {
  pinMode(LED_BUILTIN, OUTPUT);   // el pin 13 configurado como salida
}

void loop() {
  digitalWrite(LED_BUILTIN, HIGH);   // 5 V en el pin: el LED se ENCIENDE
  delay(1000);                        // espera 1000 ms (1 segundo)
  digitalWrite(LED_BUILTIN, LOW);     // 0 V en el pin: el LED se APAGA
  delay(1000);                        // espera otro segundo
}

Línea a línea:

  1. pinMode(LED_BUILTIN, OUTPUT): declara el pin 13 como salida, es decir, capaz de entregar tensión.
  2. digitalWrite(pin, HIGH): pone 5 voltios en el pin. La corriente circula por el LED interno y brilla.
  3. delay(1000): detiene el programa 1000 milisegundos con el LED encendido.
  4. digitalWrite(pin, LOW): pone 0 voltios, la corriente deja de circular y el LED se apaga.
  5. El segundo delay(1000) mantiene el LED apagado otro segundo, y loop() vuelve a empezar: un parpadeo de 1 Hz.

delay() bloquea el microcontrolador por completo: durante esos milisegundos el chip no puede leer botones ni sensores. Para parpadear está bien, pero en proyectos con varias tareas reales aprenderás a sustituirlo por millis() (lo veremos en una lección posterior).

Prueba a cambiar delay(1000) por delay(100) y verás un parpadeo rapidísimo; con delay(2000) obtendrás pausas largas. Definir el retardo como const int TIEMPO = 1000; al inicio del sketch hace el ajuste todavía más cómodo.

Organización y comentarios

Un sketch vive semanas, a veces meses, y siempre acaba en manos de otra persona (o de tu yo del futuro). Organizarlo bien es tan importante como saber escribir C++. El primer hábito es una cabecera de fichero que documente el proyecto:

/*
 * Autor:       Ana García
 * Fecha:       29 de agosto de 2026
 * Descripción: Hace parpadear el LED integrado (pin 13).
 * Hardware:    Arduino Uno + LED_BUILTIN.
 */
 
void setup() {
  // ...

Arduino soporta dos estilos de comentario, ambos ignorados por el compilador:

  • // comentario de una línea: explica una instrucción o un bloque corto.
  • /* ... */ comentario de varias líneas: ideal para cabeceras y explicaciones largas.

Convenciones que mantienen el orden

  • Orden lógico: includes → constantes → variables globales → setup() → loop() → funciones auxiliares.
  • Nombres descriptivos: pinLed o PIN_LED antes que x; leerBoton() antes que f().
  • Documenta el cableado: un comentario que diga qué va en cada pin ahorra volver a mirar los esquemas.
  • Separa secciones: usa cabeceras de comentario para agrupar fases (lectura, lógica, salida).
// ---------- CONFIGURACIÓN ----------
const int PIN_LED = 9;

// ---------- Variables de estado ----------
int brillo = 0;

void setup() {
  // Cableado: LED + resistencia 220 ohm -> pin 9, cátodo a GND
  pinMode(PIN_LED, OUTPUT);
}

Es preferible que el código se lea solo y que los comentarios cuenten el porqué, no el qué: // anima con retardo corto para evitar parpadeo visible aporta más que // le doy un valor a brillo.

Errores comunes

1. No seleccionar la placa ni el puerto correctos

Subir un sketch para un Uno estando seleccionado un Nano o un puerto equivocado termina siempre en Failed uploading. Revisa Herramientas → Placa y Herramientas → Puerto antes de pulsar Subir.

2. Olvidar el punto y coma

pinMode(LED_BUILTIN, OUTPUT)   // ❌ falta el ';' → error de compilación
pinMode(LED_BUILTIN, OUTPUT);  // ✅

3. Usar delay() para todo

Encadenar delay() para simular tiempos hace que la placa quede "ciega" a botones y sensores mientras espera. El síntoma clásico: un LED que responde siempre tarde. La solución a futuro es millis().

4. Usar un cable USB sin datos

Muchos cables USB solo alimentan (cargan) y no llevan pistas de datos: la placa se enciende pero el IDE no la ve. Prueba con otro cable o comprueba en Herramientas → Puerto si aparece el dispositivo.

5. Conectar un LED directamente sin resistencia

Un LED externo a 5 V sin limitador se estropea (y puede dañar el pin). Siempre en serie una resistencia de 220 o 330 Ω para prototipos.

6. Escribir el pin equivocado con LED_BUILTIN

LED_BUILTIN se refiere al LED integrado en la placa, no a un LED que hayas conectado al pin 13 de manera externa en otra placa. Si usas otra placa, mira su documentación.

digitalWrite(LED_BUILTIN, HIGH);   // ✅ Si quieres el LED interno
digitalWrite(13, HIGH);            // ✅ equivalente en el Uno
digitalWrite(10, HIGH);            // ❌ no es el LED integrado

El error nº 1 de quien empieza es no subir el sketch y asumir que el programa "cambió". Si el LED no parpadea, pregunta primero: ¿se subió de verdad? ¿está la placa conectada al puerto correcto?

Ejercicios

Resuélvelos en orden creciente de dificultad. Todos se hacen solo con el LED integrado, sin componentes externos, ni siquiera el cable: el LED_BUILTIN ya está conectado.

  1. Blink a 3 segundos: modifica Blink para que el LED esté encendido 2 segundos y apagado 1 segundo. Observa la diferencia de ritmo.
  2. SOS en código Morse: tres parpadeos cortos (200 ms), tres largos (600 ms) y tres cortos de nuevo, con pausas de 200 ms entre destellos y 1 s entre letras. Define los tiempos como constantes al inicio del sketch.
  3. Cambia el pin del LED: conecta un LED externo con su resistencia 220 Ω al pin 9 y modifica Blink para usarlo. Reemplaza LED_BUILTIN por una constante PIN_LED definida al inicio.
  4. Comenta cada línea: abre Blink y escribe un comentario // que explique lo que hace cada línea, y una cabecera /* */ con autor, fecha y descripción. Después verifica que sigue compilando.
  5. Reporte de compilación: sube Blink y anota en la terminal: bytes de flash usados, bytes de SRAM usados y el porcentaje de cada memoria. ¿Cuánto espacio libre le queda al microcontrolador para crecer?
