Parámetros tipados y retorno: inferido vs anotado

Las funciones son donde el tipado rinde más: los parámetros son la frontera de entrada de tu lógica y el retorno su compromiso de salida. Anotarlos convierte cada llamada incorrecta en un error de compilación, no en un bug descubierto por un usuario.

// Parámetros anotados (obligatorio) + retorno anotado (recomendado)
function areaRectangulo(base: number, altura: number): number {
  return base * altura;
}

// El retorno también se infiere: TS deduce number sin que lo escribas
const duplicar = (n: number) => n * 2;

// ¿Por qué anotar el retorno si se infiere? Porque protege la implementación:
function esPar(n: number): boolean {
  // return n % 2;      // ❌ Type 'number' is not assignable to type 'boolean'
  return n % 2 === 0;   // ✅ el error salta DENTRO de la función, no donde la consumes
}

Anota el retorno de toda función exportada o pública: si mañana cambia la implementación y el tipo varía, el compilador avisa en el lugar correcto en vez de romper silenciosamente a veinte consumidores.

Retornos explícitos para uniones

function clasificarEdad(edad: number): "niño" | "adolescente" | "adulto" {
  if (edad < 13) return "niño";
  if (edad < 18) return "adolescente";
  return "adulto";
}
// La firma documenta los valores posibles SIN leer el cuerpo

Funciones asíncronas: siempre Promise<T>

Toda función async devuelve una promesa; TypeScript la modela con el genérico Promise<T>, donde T es el valor resuelto (profundizaremos en la lección de genéricos):

async function cargarTasaDelDia(): Promise<number> {
  const respuesta = await fetch("/api/tasa");
  const datos = (await respuesta.json()) as { valor: number };
  return datos.valor;
}

// Al consumirla con await, el resultado ES number:
const tasa = await cargarTasaDelDia();
console.log((tasa * 100).toFixed(2));

Parámetros opcionales, por defecto y rest

TypeScript modela las tres formas en que JavaScript recibe argumentos flexibles: parámetros que pueden faltar (?), parámetros con valor por defecto (= valor) y colecciones abiertas de argumentos (...rest). Regla estructural: los obligatorios van primero; opcionales, con defecto y rest, al final.

// Opcional con ?: quien llama decide si lo pasa
function saludar(nombre: string, titulo?: string): string {
  return titulo ? `${titulo} ${nombre}` : `Hola ${nombre}`;
}
saludar("Ana");            // "Hola Ana"
saludar("Ana", "Dra.");    // "Dra. Ana"

// Con valor por defecto: implícitamente opcional Y tipado por el literal
function conectar(host: string, puerto: number = 8080): string {
  return `Conectando a ${host}:${puerto}`;
}
conectar("localhost");        // usa 8080
conectar("localhost", 3000);  // usa 3000

// Rest: N argumentos agrupados en un arreglo tipado
function total(...importes: number[]): number {
  return importes.reduce((acumulado, actual) => acumulado + actual, 0);
}
total(10, 20);          // 30
total(5, 5, 5, 5, 5);   // 25

// Combinando todo (orden correcto: obligatorios → defecto → rest)
function registrarEvento(usuario: string, nivel: string = "info",
                         ...etiquetas: string[]): void {
  console.log(`[${nivel}] ${usuario}`, etiquetas);
}
registrarEvento("ana", "warn", "seguridad", "login");

Un parámetro opcional (x?: string) tiene tipo real string | undefined: dentro de la función DEBES contemplar la ausencia antes de usarlo. Si eso molesta, probablemente necesites un valor por defecto en lugar de un opcional.

Firmas de función y contextual typing

Una firma de función describe solo su interfaz invocable —tipos de parámetros y de retorno— sin el cuerpo. Declararla como alias permite tipar variables, propiedades de objeto, parámetros de orden superior y callbacks:

// Alias de firma: recibe string, devuelve void
type Manejador = (mensaje: string) => void;

let registro: Manejador;

registro = (msg) => console.log(msg);   // ✅ compatible
registro = (msg) => console.warn(msg);  // ✅ otra implementación válida
// registro = (msg) => msg.length;
// ❌ Type 'number' is not assignable to type 'void'

Contextual typing: el compilador lee el contexto

Cuando asignas una función a un destino ya tipado, NO necesitas re-anotar los parámetros: TypeScript los infiere desde el contexto. Esto hace que los callbacks de map, filter o addEventListener funcionen sin una sola anotación:

const nombres = ["ana", "luis", "marta"];

// 'nombre' ya SABE que es string: viene del contexto del arreglo
const enMayusculas = nombres.map((nombre) => nombre.toUpperCase());

// Sin contexto habría que anotar a mano:
const sola: (n: string) => string = (n) => n.toUpperCase();

Todas las formas de declarar una firma

Callbacks tipados y el matiz del retorno void

Los callbacks son funciones que pasamos como argumento para que «alguien más» las ejecute después. Tiparlas define el contrato exacto: qué recibirá tu función y qué se espera que devuelva.

type CallbackProgreso = (porcentaje: number, etapa: string) => void;

function descargar(url: string, alProgresar: CallbackProgreso): void {
  let avance = 0;
  const temporizador = setInterval(() => {
    avance += 25;
    alProgresar(avance, url);     // ejecutamos el contrato
    if (avance >= 100) clearInterval(temporizador);
  }, 400);
}

descargar("informe.pdf", (pct, fuente) => {
  console.log(`${fuente}: ${pct}%`);   // parámetros inferidos por contexto
});

El detalle fino: retorno void en callbacks ES especial

Un retorno void significa «a quien invoca no le importa lo que devuelvas». Por eso, curiosamente, una implementación que devuelve algo sí es asignable a una firma que declara void:

// map espera (valor, indice, arreglo) => desconocido... USA el retorno.
// forEach espera (valor, indice, arreglo) => void... IGNORA el retorno.

const numeros = [1, 2, 3];
const duplicados = numeros.map((n) => n * 2);    // [2, 4, 6] ✅

numeros.forEach((n) => n * 2);                   // ⚠️ compila: void descarta todo
numeros.forEach((n) => { console.log(n * 2); }); // ✅ intención clara

Ese «privilegio» de void explica bugs clásicos: usar map donde iba forEach compila igual… pero descarta los resultados. Cuando diseñes tus propias APIs con callbacks, declara void como retorno para comunicar: «devolver algo aquí no sirve de nada».

Sobrecarga: varias firmas, una implementación

A veces una misma función acepta formas de llamada distintas y devuelve tipos distintos según la entrada. Las overloads declaran todas las firmas públicas válidas y luego UNA implementación compatible con todas. Quien consume la función ve solo las sobrecargas; la implementación queda oculta:

// FIRMAS PÚBLICAS (lo que ve el consumidor)
function crearElemento(selector: string): HTMLElement;
function crearElemento(indice: number, texto: string): HTMLLIElement;

// IMPLEMENTACIÓN ÚNICA (compatible con ambas; NO es llamable directamente)
function crearElemento(a: string | number, b?: string): HTMLElement {
  if (typeof a === "string") {
    return document.querySelector(a) as HTMLElement;
  }
  const li = document.createElement("li");
  li.textContent = b ?? "";
  li.dataset.indice = String(a);
  return li;
}

// El consumo ahora es preciso según cómo llames:
const modal = crearElemento("#modal");      // HTMLElement
const item = crearElemento(3, "Tercero");   // HTMLLIElement
item.textContent = "editable";              // ✅ sabe que es un <li> concreto

// crearElemento(true);
// ❌ No overload matches this call.

Reglas de oro de la sobrecarga

  • Las firmas se evalúan de arriba hacia abajo: ordena de la más específica a la más general.
  • Solo la última firma lleva cuerpo; las anteriores terminan en ;.
  • La implementación debe ser compatible con todas las firmas declaradas.
  • La implementación NO es llamable desde fuera: solo cuentan las firmas públicas.

No abuses: cada overload es una promesa más que mantener. Antes de sobrecargar pregúntate si dos funciones con nombres distintos serían más claras, o si un parámetro de unión con narrowing resuelve el caso con menos maquinaria.

never y chequeos de exhaustividad

Cuando haces narrowing sobre una unión con un switch, TypeScript va reduciendo el tipo en cada rama. Si al final del switch el valor quedó de tipo never, significa que TODOS los casos están cubiertos. Ese hecho permite construir un guardián que rompe la compilación cuando alguien añade un caso nuevo y olvida atenderlo:

type Forma = "circulo" | "rectangulo" | "triangulo";

function descripcion(forma: Forma): string {
  switch (forma) {
    case "circulo":    return "Figura redonda";
    case "rectangulo": return "Cuatro lados rectos";
    case "triangulo":  return "Tres lados";
    default: {
      // Si llegamos aquí, a forma ya no le queda ningún tipo posible:
      const imposible: never = forma;
      throw new Error(`Forma no atendida: ${imposible}`);
    }
  }
}
// Ahora añadimos una forma nueva a la unión…
type Forma = "circulo" | "rectangulo" | "triangulo" | "hexagono";

// …y SIN tocar la función, el compilador GRITA:
// ❌ Type '"hexagono"' is not assignable to type 'never'
// La compilación falla hasta que atiendas el caso nuevo. ¡Ese es el objetivo!

Este patrón convierte el switch en un contrato autodefensovo: agregar un miembro a la unión genera errores de compilación en cada switch incompleto del proyecto. Exhaustividad verificada por máquina, no por disciplina humana.

Ejercicios prácticos

Compila cada ejercicio con tsc --noEmit hasta lograr cero errores en strict:

  1. Básico: Escribe pagoTotal(importe: number, propina?: number): number donde la propina por defecto sea el 10%. Verifica ambos caminos de llamada.
  2. Rest + firma: Crea el alias Promedio = (...valores: number[]) => number, implementa dos versiones (aritmética y ponderado) y pásalas como argumento a una función informar(calcular: Promedio, datos: number[]).
  3. Callback void: Implementa cuentaAtras(segundos: number, alTerminar: () => void) usando setInterval. Demuestra el matiz de void devolviendo accidentalmente un número desde el callback y explica por qué compila.
  4. Sobrecarga: Diseña formatearFecha(input: Date): string y formatearFecha(iso: string, formato: "corto" | "largo"): string con overloads y una única implementación.
  5. Desafío exhaustividad: Modela EstadoPedido = "carrito" | "pagado" | "enviado" | "entregado". Escribe siguienteEstado(actual) con switch + guardián never que devuelva el estado siguiente (o null en entregado). Añade el estado "devuelto" y verifica que la compilación falla hasta atenderlo.
