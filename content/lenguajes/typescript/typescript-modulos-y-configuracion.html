Módulos ES: import y export

Desde ES2015, JavaScript estandarizó sus módulos con import/export, y TypeScript los adopta tal cual añadiendo tipos a la ecuación. Cada archivo con al menos un import o export es un módulo: su contenido queda encapsulado y solo lo visible mediante exportaciones se comparte.

// 📄 matematica.ts — exportaciones nombradas y por defecto
export function duplicar(n: number): number { return n * 2; }
export const PI = 3.1416;

export default class Calculadora {
  sumar(a: number, b: number): number { return a + b; }
}
// 📄 app.ts — consumo de las exportaciones
import Calculadora, { duplicar, PI } from "./matematica";
//     ↑ default      ↑ llaves: nombradas (el nombre DEBE coincidir)

const calc = new Calculadora();
console.log(calc.sumar(duplicar(2), PI)); // 7.1416

// Renombrar al importar para evitar colisiones:
import { duplicar as doblar } from "./matematica";

Import type-only: importar tipos sin código

Cuando solo necesitas el TIPO de otro módulo (no sus valores), la sintaxis import type lo deja explícito. El compilador elimina esa importación en la salida: cero código viaja al runtime:

// 📄 tipos.ts
export interface Usuario { nombre: string; edad: number }
export function crearUsuario(): Usuario { /* ... */ }
// 📄 app.ts
import type { Usuario } from "./tipos";        // SOLO el tipo (borrado al compilar)
import { crearUsuario } from "./tipos";        // el valor real

// También en línea dentro de una importación mixta:
import { crearUsuario, type Usuario } from "./tipos";

function imprimir(u: Usuario): void {          // ✅ tipo disponible
  console.log(`${u.nombre} (${u.edad})`);
}
imprimir(crearUsuario());

Con la opción "verbatimModuleSyntax" (o el clásico "isolatedModules") activas, TypeScript te OBLIGA a marcar las importaciones puramente tipadas: evita que bundlers modernos se confundan sobre qué líneas deben sobrevivir al build.

Barrels (index.ts), re-export y resolución de módulos

A medida que el proyecto crece, las rutas de importación se vuelven largas (../../servicios/usuario/servicio-usuario). El patrón barrel centraliza las exportaciones de una carpeta en un único index.ts, que actúa como puerta de entrada del paquete:

// 📄 modelos/index.ts — barrel: re-exporta todo lo público de la carpeta
export { Usuario, type Perfil } from "./usuario";
export { Producto } from "./producto";
export * from "./factura";            // re-exporta TODO el módulo factura

// 📄 app.ts — imports limpios, sin rutas internas frágiles
import { Usuario, Producto, Factura } from "./modelos";   // resuelve a modelos/index.ts

Cómo resuelve TypeScript las rutas

Ruta escritaSignificado
"./utilidades"Ruta RELATIVA al archivo actual: obligatoria en tu código de aplicación
"lodash"Módulo de node_modules: busca su package.json y sus definiciones de tipos
"@modelos/usuario"Alias configurado en tsconfig (paths) o en el bundler

La opción moduleResolution define el ALGORITMO de búsqueda: "bundler" es el recomendado hoy si tu código pasa por Vite/webpack/esbuild; "node10"/"classic" son herencias históricas que conviene evitar en proyectos nuevos.

Los barrels mejoran la ergonomía pero pueden inflar el bundle si el empaquetador no hace tree-shaking bien. Regla práctica: barrels por carpeta de dominio sí; un barrel gigante para todo el proyecto, no.

tsconfig.json: las opciones clave explicadas

El archivo tsconfig.json (generado con npx tsc --init) es el cerebro del compilador: define A QUÉ JavaScript transpila, DÓNDE vive tu código y QUÉ tan estricto será el chequeo. Estas son las opciones que debes dominar antes que ninguna otra:

OpciónQué controlaValor típico moderno
targetVersión de JS generada (sintaxis final)ES2020 o superior
libAPIs disponibles para el chequeo (DOM, ES2023...)["ES2022", "DOM"]
moduleSistema de módulos de la SALIDAESNext (bundler) / NodeNext (Node)
moduleResolutionAlgoritmo para encontrar módulosbundler / NodeNext
rootDirCarpeta raíz de tus fuentes./src
outDirCarpeta donde cae el JS compilado./dist

tsconfig mínimo profesional, comentado

{
  "compilerOptions": {
    // ¿Qué JavaScript producimos? ES2020 trae optional chaining nativo
    "target": "ES2020",

    // Sistema de módulos de la salida: ESNext para bundlers modernos
    "module": "ESNext",
    "moduleResolution": "bundler",

    // APIs que el compilador debe conocer (navegador + estándar ES2022)
    "lib": ["ES2022", "DOM", "DOM.Iterable"],

    // Estructura del proyecto: src → dist
    "rootDir": "./src",
    "outDir": "./dist",

    // Calidad máxima desde el día uno
    "strict": true,

    // Interoperabilidad con CommonJS y velocidad de chequeo
    "esModuleInterop": true,
    "skipLibCheck": true,

    // Mapas .map para depurar el TS original en el navegador
    "sourceMap": true
  },
  // Qué archivos compila este proyecto
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}

target vs lib: dos decisiones distintas

Es un error clásico confundirlas. target decide cómo se ESCRIBE el JavaScript de salida (¿usa ?? nativo o lo reescribe?). lib decide qué APIs CONOCE el compilador al verificar (¿existe Array.at()? ¿existe window?). Puedes compilar hacia ES2020 y aun así verificar contra las APIs de ES2022.

No pongas target: "ES5" «por compatibilidad» sin necesidad: multiplica el peso del bundle (downleveling de async/await y clases) y te obliga a arrastrar polyfills. Consulta la cobertura real de tu audiencia en caniuse antes de decidir.

Modo strict y opciones de calidad

"strict": true no es UNA opción sino un paquete de verificaciones que juntas transforman al compilador en un revisor exigente. Son las banderas que más bugs han eliminado en la historia de TypeScript:

Bandera incluida en strictQué previene
noImplicitAnyValores «sin tipo» que quedan como any silencioso
strictNullChecksAcceder a algo que puede ser null/undefined sin comprobarlo
strictFunctionTypesAsignar funciones con parámetros incompatibles
strictBindCallApplyUsos incorrectos de bind/call/apply
strictPropertyInitializationPropiedades de clase declaradas pero nunca inicializadas
noImplicitThisthis ambiguo dentro de funciones
useUnknownInCatchVariablesAsumir que todo error lanzado es Error
{
  "compilerOptions": {
    // El paquete completo de rigor:
    "strict": true,
    // Equivalente a activarlas una a una:
    // "noImplicitAny": true,
    // "strictNullChecks": true,
    // "strictFunctionTypes": true,
    // ... etc.

    // Compatibilidad con paquetes antiguos escritos en CommonJS:
    "esModuleInterop": true,

    // NO re-chequear el código de node_modules (velocidad ×10):
    "skipLibCheck": true,

    // Genera .map junto a cada .js para depurar el TypeScript original:
    "sourceMap": true,

    // Extras muy recomendados fuera del paquete strict:
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noFallthroughCasesInSwitch": true
  }
}

skipLibCheck: true acelera mucho la compilación porque ignora errores DENTRO de las definiciones de terceros… pero no desactiva el chequeo de TU código contra esas librerías. Es un compromiso de velocidad estándar y seguro.

Iniciar cualquier proyecto nuevo con "strict": true es la decisión de mayor retorno de toda la configuración: activarlo DESPUÉS, sobre miles de líneas, puede generar cientos de errores de golpe.

Formas de ejecutar TypeScript: tsc, bundlers y ts-node/tsx

El navegador y Node no entienden TypeScript: SIEMPRE hace falta un paso que lo convierta a JavaScript. Hay tres arquitecturas posibles, y elegir bien desde el inicio evita reconfigurar todo el proyecto después:

1) Compilador puro: tsc

# Compila todo el proyecto según tsconfig.json (src → dist)
npx tsc

# Modo watch: recompila al guardar (ideal para Node.js en desarrollo)
npx tsc --watch

# Ejecutar la salida con Node
node dist/index.js

2) Bundler: Vite / webpack / esbuild

npm install -D vite

# Desarrollo: servidor con HMR que transpila TS al vuelo (sin tsc)
npx vite

# Producción: bundle optimizado listo para desplegar
npx vite build

El bundler transpila pero NO verifica tipos. La práctica estándar es combinar: Vite para velocidad + tsc --noEmit como control de calidad (en el script build de muchos scaffolds aparece literalmente tsc && vite build).

3) Ejecución directa: ts-node / tsx

npm install -D tsx

# Corre el .ts directamente: transpila en memoria al vuelo
npx tsx src/index.ts

# Perfecto para scripts, prototipos y herramientas de línea de comando
npx tsx src/scripts/migrar-datos.ts --seco

Project references: teaser de monorepos

Cuando un repositorio aloja varios paquetes (@app/api, @app/web, @app/comun), los project references permiten compilar cada parte por separado declarando dependencias entre proyectos ("references": [{"path": "../comun"}]), con builds incrementales que solo recompilan lo cambiado.

Regla rápida de elección: frontend → bundler (Vite); API/librería Node → tsc (+ watch); scripts y prototipos → tsx. Y siempre tsc --noEmit en CI como juez final de tipos.

    "target": "ES2020",
    "module": "ESNext",

Cuida qué exportas: cada símbolo público de un módulo es una promesa de mantenimiento. Si algo solo existe para uso interno de la carpeta, NO lo re-exportes en el barrel — el encapsulamiento también aplica a los tipos.

Ejercicios prácticos

Trabaja sobre un proyecto nuevo inicializado con npx tsc --init:

  1. Básico: Crea dos módulos (operaciones.ts y app.ts). Exporta tres funciones nombradas y una clase por defecto; impórtalas todas y ejecuta con tsx.
  2. Type-only: En un módulo modelos.ts, exporta una interfaz Tarea y una función fábrica. En otro archivo impórtala con import type y comprueba en el .js compilado que esa línea desapareció.
  3. Barrel: Organiza tres modelos en una carpeta modelos/ con su index.ts. Refactoriza los imports de app.ts para consumirlos solo vía barrel.
  4. Configuración: Partiendo del tsconfig mínimo profesional, cambia target a ES5 y compara tamaño y contenido del .js generado (async/await y clases). Devuélvelo a ES2020 y documenta la diferencia.
  5. Desafío integral: Monta el flujo completo: estructura src/ → dist/, scripts dev/check/build en package.json, un módulo de dominio con tipos importados type-only y un barrel. Haz fallar npm run check introduciendo un error de tipo a propósito y corrígelo hasta compilar limpio en strict.
