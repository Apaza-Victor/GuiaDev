¿Qué es TypeScript?

TypeScript es un lenguaje de programación creado por Microsoft y presentado en octubre de 2012, liderado por Anders Hejlsberg, el mismo ingeniero que creó Turbo Pascal y C#. Su idea central es simple pero poderosa: tomar JavaScript —el lenguaje más ejecutado del planeta— y añadirle un sistema de tipos estáticos que detecta errores antes de correr el código, no después de que el usuario los sufra.

Técnicamente hablando, TypeScript es un superconjunto tipado de JavaScript: todo código JavaScript válido es también código TypeScript válido. Esto significa que puedes renombrar un archivo .js a .ts y seguirá funcionando, e ir agregando tipos de forma gradual, sin reescribir tu proyecto desde cero.

JavaScript vs TypeScript

Ejemplo: el mismo bug, dos momentos distintos

// JavaScript: este error solo estalla cuando alguien ejecuta la página
function calcularTotal(precio, cantidad) {
  return precio * cantudad; // ❌ typo: ReferenceError en producción
}

// TypeScript: el compilador marca la línea ANTES de que exista el navegador de por medio
function calcularTotalSeguro(precio: number, cantidad: number): number {
  return precio * cantidad; // ✅ verificado en tiempo de compilación
}

El nombre lo resume: Type + Script. No es un lenguaje exótico: sigues escribiendo JavaScript, pero con un asistente incansable que revisa cada línea mientras tecleas.

Los tipos viven solo en tiempo de compilación

Este es el concepto más importante de toda la lección: TypeScript no agrega ninguna verificación de tipos cuando tu programa corre. Las anotaciones se usan durante la compilación y luego desaparecen por completo — proceso conocido como type erasure (borrado de tipos).

El resultado es JavaScript limpio y sin rastros de tipos, ejecutable en cualquier navegador o versión de Node.js:

// saludo.ts (lo que tú escribes)
const nombre: string = "GuiaDev";
const version: number = 5;

function saludar(quien: string): string {
  return `Hola desde ${quien}`;
}

console.log(saludar(nombre));
// saludo.js (lo que genera el compilador: JavaScript puro)
const nombre = "GuiaDev";
const version = 5;
function saludar(quien) {
    return `Hola desde ${quien}`;
}
console.log(saludar(nombre));

Fíjate: : string, : number y : string en el retorno simplemente no existen en la salida. Por eso TypeScript nunca ralentiza tu aplicación en runtime: toda la inversión en tipos se paga una sola vez, durante el desarrollo.

Consecuencia directa: TS no valida datos externos

interface UsuarioAPI {
  edad: number;
}

// El compilador te cree... pero la API puede responder otra cosa
const respuesta = await fetch("/api/usuario");
const datos = (await respuesta.json()) as UsuarioAPI;

// Si la API envió edad: "treinta", esto falla AQUÍ, en runtime:
console.log(datos.edad.toFixed(0)); // 💥 TypeError: toFixed is not a function

Nunca confundas tipo con garantía de runtime. Un as o una interfaz son una promesa que TÚ haces al compilador sobre datos que vienen de fuera. Valida entradas externas (formularios, APIs, JSON de terceros) con validadores como Zod antes de confiar en ellas.

Instalación y primer programa

La forma recomendada hoy es instalar TypeScript como dependencia de desarrollo dentro de tu proyecto, no globalmente. Así cada miembro del equipo y el servidor de CI usan exactamente la misma versión del compilador.

# 1. Crear el proyecto (si aún no existe package.json)
npm init -y

# 2. Instalar TypeScript como dependencia de desarrollo
npm install -D typescript

# 3. Verificar la versión instalada
npx tsc --version
# Salida: Version 5.5.4 (o superior)

# 4. Generar un tsconfig.json con configuración base
npx tsc --init

Tu primer archivo .ts, de principio a fin

// saludo.ts
function construirSaludo(nombre: string, entusiasmo: number): string {
  const signos: string = "!".repeat(entusiasmo);
  return `¡Hola, ${nombre}${signos}`;
}

const mensaje: string = construirSaludo("GuiaDev", 3);
console.log(mensaje);
# Compilar: genera saludo.js junto al .ts
npx tsc saludo.ts

# Ejecutar el resultado con Node.js
node saludo.js
¡Hola, GuiaDev!!!

¿Qué pasa si violamos el contrato?

// Pasamos un texto donde se esperaba un número:
construirSaludo("GuiaDev", "mucho");
// ❌ Argument of type 'string' is not assignable to parameter of type 'number'.
saludo.ts:9:31 - error TS2345: Argument of type 'string' is not assignable
to parameter of type 'number'.

Con npm install -D typescript el compilador vive dentro de node_modules y se invoca con npx tsc. La instalación global (npm i -g typescript) es cómoda para pruebas rápidas, pero provoca el clásico «en mi máquina sí compila» cuando las versiones difieren entre el equipo y la CI.

El CLI de tsc: compile, watch y check

El comando tsc (TypeScript Compiler) es toda la herramienta de build que necesitas para empezar. Estas son sus banderas más usadas en el día a día:

ComandoQué haceCuándo usarlo
tscCompila según el tsconfig.json del proyectoBuild local y en CI
tsc archivo.tsCompila un archivo suelto, ignorando el tsconfigExperimentos rápidos
tsc --watchVigila los archivos y recompila al guardarMientras desarrollas
tsc --noEmitSolo verifica tipos, sin generar archivosChequeo rápido o paso de calidad en CI
tsc --initCrea un tsconfig.json comentadoAl iniciar un proyecto
tsc --project ./configUsa otro archivo de configuraciónMonorepos con varios tsconfig

Scripts recomendados en package.json

{
  "scripts": {
    "build": "tsc",
    "dev": "tsc --watch",
    "check": "tsc --noEmit"
  }
}
npm run check   # ¿Hay errores de tipos? No genera nada, solo informa
npm run dev     # Recompila cada vez que guardas un archivo
npm run build   # Compila todo el proyecto a la carpeta final

tsc --watch recompila aunque haya errores (emite el JavaScript igualmente, salvo que actives noEmitOnError). Acostúmbrate a leer los mensajes rojos del watch: describen el archivo, la línea y el motivo exacto del problema.

De JavaScript a TypeScript: adopción gradual

Migrar no es un evento, es un proceso. Como los tipos son opcionales y graduales, la estrategia habitual es: renombrar archivos, dejar que el compilador infiera lo que pueda, y tipar primero las zonas más críticas (funciones compartidas, límites con APIs, modelos de datos).

// PASO 1: JavaScript tal cual, renombrado a .ts (compila sin cambios)
function aplicarDescuento(precio, porcentaje) {
  return precio - precio * (porcentaje / 100);
}

// PASO 2: tipamos la frontera pública de la función
function aplicarDescuentoV2(precio: number, porcentaje: number): number {
  return precio - precio * (porcentaje / 100);
}

// PASO 3: ahora el compilador nos protege de usos incorrectos
aplicarDescuentoV2(100, 15);   // ✅ 85
// aplicarDescuentoV2(100, "quince");
// ❌ Argument of type 'string' is not assignable to parameter of type 'number'

Cuando el código heredado todavía no está listo para ser tipado por completo, la opción allowJs del tsconfig.json permite conviva JavaScript plano durante la transición:

{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": true,
    "strict": true
  },
  "include": ["src/**/*"]
}

La migración típica dura días, no meses. Empieza activando strict solo en los archivos nuevos, corrige los errores más baratos primero (parámetros y retornos de funciones públicas) y deja los any temporales documentados con un comentario // TODO: tipar.

Por qué la industria lo adoptó

Los lenguajes no triunfan por moda, sino por resolver dolores reales. En equipos grandes de JavaScript aparecieron tres problemas crónicos: bugs de tipos que solo se descubrían en producción, miedo a refactorizar y código cuya intención había que adivinar leyendo implementaciones. TypeScript ataca los tres de raíz.

Proyecto / EmpresaRol de TypeScript
AngularSe escribe en TypeScript desde su origen; los componentes son clases tipadas
Visual Studio CodeEditores enteros construidos con TS: miles de módulos bajo control de tipos
Vue 3Reescrito internamente en TypeScript para ofrecer tipado de primera clase
Slack, Airbnb, AsanaMigraron bases de código masivas reportando caídas significativas de bugs post-deploy
Deno, Bun, Node.jsRuntimes modernos con soporte o herramientas nativas para TS
Librerías (React, Express...)Publiquian definiciones de tipos junto al paquete: la documentación vive en tu autocompletado

Beneficios que explican la adopción

  • Los tipos son documentación ejecutable: la firma (usuario: Usuario) => boolean explica más que tres párrafos de comentarios que pueden quedar desactualizados.
  • Refactorizar deja de dar miedo: renombra una propiedad y el compilador lista todas las líneas rotas, en segundos.
  • Onboarding acelerado: quien llega nuevo explora el dominio navegando los tipos, sin leer todo el código.
  • El editor se vuelve proactivo: autocompletado contextual, detección temprana y «ir a definición» fiables.

En encuestas anuales de desarrolladores (Stack Overflow, State of JS), TypeScript aparece sistemáticamente entre los lenguajes más queridos y más demandados en ofertas de empleo front-end y Node.js. Aprenderlo es prácticamente un requisito del mercado actual.

Errores comunes del principiante

ErrorSíntomaSolución
Creer que TS valida en runtimeConfías ciegamente en datos de una API tipados con asValidar entradas externas (Zod, comprobaciones manuales)
Abusar de any«Lo puse en any y dejó de quejarse»Tipar bien o usar unknown + narrowing
Iniciar sin strictProyecto que acumula null sorpresivos"strict": true desde el día uno
Instalar solo globalmenteCI con otra versión falla donde local pasabaDependencia de desarrollo por proyecto
Ignorar errores «porque igual compila»Deuda técnica invisible acumulándose--noEmit como puerta de calidad en CI
// ❌ Silenciar al compilador no arregla el problema, solo apaga la alarma
const datos: any = JSON.parse(texto);
console.log(datos.usaurio.nombre); // typo que TS jamás detectará en any

// ✅ Mantener el tipo y dejar que el compilador trabaje
const datosTipados: { usuario: { nombre: string } } = JSON.parse(texto);
// TS avisa: Property 'usaurio' does not exist on type '{ usuario: ... }'

Por defecto tsc emite JavaScript aunque haya errores de tipos. Un build verde no significa un proyecto sano: haz que tu pipeline ejecute tsc --noEmit y falle ante cualquier error.

Ejercicios prácticos

Practica lo aprendido creando un proyecto nuevo con npm install -D typescript y npx tsc --init:

  1. Básico: Crea un archivo presentacion.ts con una función presentar(nombre: string, edad: number): string que devuelva un mensaje usando template literals. Compílala con npx tsc y ejecútala con Node.
  2. Explorar el borrado de tipos: Abre el .js generado y verifica que no queda ninguna anotación de tipo. Añade un comentario en el .ts y confirma que sí viaja a la salida.
  3. Cazar un error: Provoca deliberadamente tres errores de compilación (tipo equivocado, argumento faltante, argumento de más). Anota el código TS de cada error y qué mensaje muestra el compilador.
  4. Automatizar: Configura los scripts build, dev y check en package.json. Prueba npm run dev editando el archivo en vivo y observa la recompilación automática.
  5. Desafío: Toma cualquier función JavaScript que hayas escrito antes, pásala a TypeScript con parámetros y retorno tipados, y documenta con un comentario qué error concreto te habría ahorrado el tipado. Compila con --noEmit hasta lograr cero errores.
