La interfaz como contrato de forma

Una interface describe la forma (shape) de un objeto: qué propiedades existen, de qué tipo son y cuáles son obligatorias. No genera código en runtime —es pura compilación—, pero actúa como un contrato: cualquier valor que declare cumplirla debe tener exactamente esas propiedades, ni faltarle ni sobrarle tipos incorrectos.

El beneficio es doble: el compilador verifica cada uso y tu editor convierte la interfaz en autocompletado, documentación flotante y detección temprana de errores.

interface Usuario {
  readonly id: number;      // solo lectura: no puede reasignarse tras crearlo
  nombre: string;
  email?: string;           // propiedad OPCIONAL: puede no venir
}

const u: Usuario = {
  id: 1,
  nombre: "María",
  // email no es obligatorio: el objeto sigue siendo válido sin él
};

// u.id = 99;
// ❌ Cannot assign to 'id' because it is a read-only property

u.email = "maria@dev.io";  // ✅ asignar está permitido; REASIGNAR id, no

Opcional con ? y lectura defensiva

function saludar(usuario: Usuario): string {
  // email puede ser undefined: hay que contemplarlo
  return usuario.email
    ? `Hola ${usuario.nombre}, te escribimos a ${usuario.email}`
    : `Hola ${usuario.nombre}, no tenemos tu email`;
}

Nombra las interfaces en PascalCase singular (Usuario, no IUsuario ni Usuarios): es la convención dominante en la comunidad TypeScript moderna.

Métodos, propiedades función e index signatures

Dentro de una interfaz hay dos sintaxis para declarar algo invocable: como método (saludar(): void) o como propiedad función (saludar: () => void). A efectos prácticos casi son equivalentes; la diferencia fina es que la forma de método permite declarar sobrecargas y es ligeramente más permisiva al extender. Elige una y sé consistente en todo el proyecto:

SintaxisEjemploMatices
Métodosaludar(): void;Idiomática para clases; admite declarar sobrecargas
Propiedad funciónsaludar: () => void;Deja claro que la propiedad es un VALOR reemplazable
interface Reloj {
  horaActual: Date;
  notificar: () => void;   // propiedad que guarda una función
  sincronizar(): void;     // método clásico
}

Index signatures: objetos con claves dinámicas

Cuando no sabes los nombres de las propiedades de antemano (diccionarios, configuraciones, resultados agrupados por clave), una index signature declara «cualquier clave de tipo X tendrá valores de tipo Y»:

interface DiccionarioIdiomas {
  [clave: string]: string;   // cualquier clave string → valor string
}

const saludos: DiccionarioIdiomas = {
  es: "Hola",
  en: "Hello",
  qu: "Allillanchu",
};

saludos.fr = "Bonjour";          // ✅ cualquier clave nueva es válida
// const mal: number = saludos.es;
// ❌ Type 'string' is not assignable to type 'number'

// Mezcla de claves fijas y dinámicas: las fijas deben respetar el tipo base
interface Inventario {
  [sku: string]: number;   // cada SKU apunta a una cantidad
  totalArticulos: number;  // también number: compatible con la firma índice
}

Las index signatures son generosas: aceptan cualquier clave, incluso las escritas con typo. Si conoces el conjunto cerrado de claves, prefiere un objeto con propiedades explícitas o claves literales unidas ("es" | "en") para conservar el chequeo.

Herencia con extends e intersecciones con &

Las interfaces se extienden con extends, heredando todas las propiedades del padre. A diferencia de las clases, una interfaz puede extender varias a la vez, componiendo contratos grandes desde piezas pequeñas — el principio de composición aplicado a tipos:

interface Entidad {
  id: number;
  creadoEn: Date;
}

interface Nombrable {
  nombre: string;
}

interface Etiquetable {
  etiquetas: string[];
}

// Una interfaz extendiendo VARIAS: hereda todo
interface Articulo extends Entidad, Nombrable, Etiquetable {
  precio: number;
}

const post: Articulo = {
  id: 1,
  creadoEn: new Date(),
  nombre: "TypeScript para equipos",
  etiquetas: ["typescript", "web"],
  precio: 29.99,
};

Intersecciones con type: combinar formas existentes

Los type aliases logran lo mismo con el operador & (intersección): el resultado tiene TODAS las propiedades de cada miembro. Es la herramienta natural cuando quieres añadir campos a un tipo ya definido sin tocar su declaración original:

type ConPermiso = { permisos: string[] };
type Admin = Usuario & ConPermiso;   // Usuario + permisos

const admin: Admin = {
  id: 2,
  nombre: "Root",
  permisos: ["borrar-usuarios", "ver-auditoria"],
};

Teaser: implementar interfaces en clases

// Las clases pueden firmar un contrato con implements (lección de POO):
class RepositorioUsuarios implements Entidad {
  constructor(public id: number, public creadoEn: Date) {}
}
// Si falta una propiedad o cambia el tipo, el compilador lo marca al instante

Diferencia sutil pero importante: si dos interfaces extendidas declaran la misma propiedad con tipos incompatibles, obtienes un error claro. Si dos miembros de una intersección chocan igual, el resultado se vuelve silenciosamente never para esa propiedad — los errores de intersección son más difíciles de leer.

Type aliases: uniones, tuplas y más allá de los objetos

Un type alias crea un NOMBRE para cualquier tipo existente, no solo para objetos. Es la única herramienta capaz de nombrar uniones, tuplas, primitivos personalizados y patrones avanzados — cosas donde las interfaces simplemente no llegan:

// Alias de primitivo: da semántica a un tipo genérico
type DNI = string;
type AnioNacimiento = number;

// Alias de UNIÓN: imposible de expresar con interface
type Estado = "activo" | "inactivo" | "pendiente";
type ID = number | string;

// Alias de TUPLA: tampoco existe interface para esto
type Coordenada = [lat: number, lng: number];
const oficina: Coordenada = [-12.046, -77.043];

// Alias de forma de objeto (equivalente a interface)
type Punto = { x: number; y: number };

let estado: Estado = "activo";
// estado = "borrado";
// ❌ Type '"borrado"' is not assignable to type 'Estado'

Call signatures: nombrar la firma de una función

Con un alias también puedes describir cómo se llama a una función (su firma completa: parámetros y retorno). Esto permite declarar variables, parámetros y retornos «de tipo función» reutilizables:

// Firma: recibe dos números, devuelve uno
type Operacion = (a: number, b: number) => number;

const suma: Operacion = (a, b) => a + b;      // parámetros inferidos del alias
const resta: Operacion = (a, b) => a - b;

function calcular(op: Operacion, x: number, y: number): number {
  return op(x, y);
}

calcular(suma, 4, 2);   // 6
calcular(resta, 4, 2);  // 2

// Sintaxis equivalente dentro de interface (útil para librerías):
interface Comparador {
  (a: string, b: string): number;
}

Nombrar firmas de función (Operacion, ManejadorDeEvento, Validador) hace que las APIs de tus módulos se lean como frases y evita repetir la misma flecha anónima veinte veces por archivo.

Interface vs type alias: ¿cuál usar?

Llegados aquí, ambas herramientas parecen intercambiables para objetos… y de hecho lo son en el 90% de los casos. Pero tienen diferencias estructurales reales que conviene conocer para elegir con criterio y no por costumbre:

Capacidadinterfacetype
Describir forma de objetoSíSí
Extender / heredar otras formasextends (varias a la vez)& intersecciones
Union types❌ No soporta✅ Su terreno natural
Tuplas y mapeos avanzados❌ No✅ Sí
Primitivos con semántica❌ No✅ type DNI = string
Declaration merging (fusionarse con otra del mismo nombre)✅ Sí: las declaraciones se combinan automáticamente❌ Error por nombre duplicado
Errores del compilador al fallarMás claros («is not assignable to interface X»)A veces crípticos en intersecciones largas
Rendimiento de compilaciónLigeramente mejor en proyectos enormesComparable

Declaration merging: la superpotencia (y peligro) de interface

interface VentanaConfig {
  ancho: number;
}
interface VentanaConfig {
  alto: number;
}
// ¡Ambas declaraciones SE FUSIONAN en una sola interfaz!
const config: VentanaConfig = { ancho: 800, alto: 600 };

// Con type sería error duplicado:
// type VentanaConfig = { ... } // ❌ Duplicate identifier 'VentanaConfig'

Regla práctica adoptada por la mayoría de equipos: interface para formas de objeto públicas (extensibles, fusionables, errores claros) y type para todo lo demás: uniones, tuplas, utilidades y composiciones. Lo importante es no mezclar criterios dentro del mismo proyecto.

Caso real: tipar una respuesta de API

Aquí es donde todo lo anterior se vuelve rentable. El flujo típico de una app moderna consume endpoints REST que devuelven JSON: sin tipos, cada respuesta.data.usuario.direccion.ciudad es un acto de fe. Con interfaces, la estructura del contrato externo queda documentada y verificada en todos los puntos donde se usa.

// 1) Modela el contrato del endpoint tal como responde el backend
interface Direccion {
  ciudad: string;
  pais: string;
}

interface UsuarioAPI {
  id: number;
  nombre: string;
  email: string;
  direccion?: Direccion;      // el backend no siempre la incluye
  roles: string[];
}

// 2) La respuesta envuelta: patrón habitual en APIs paginadas
interface RespuestaPaginada<T> {
  datos: T[];
  pagina: number;
  total: number;
}

// 3) Función de acceso con retorno tipado
async function obtenerUsuarios(pagina: number): Promise<RespuestaPaginada<UsuarioAPI>> {
  const respuesta = await fetch(`/api/usuarios?pagina=${pagina}`);
  if (!respuesta.ok) throw new Error(`HTTP ${respuesta.status}`);
  return (await respuesta.json()) as RespuestaPaginada<UsuarioAPI>;
}

Consumo: autocompletado y verificación gratis

const { datos, total } = await obtenerUsuarios(1);

for (const usuario of datos) {
  console.log(`#${usuario.id} ${usuario.nombre}`);        // ✅ autocompletado real
  console.log(usuario.direccion?.ciudad ?? "Sin ciudad"); // ✅ opcional contemplado

  // console.log(usuario.nombres);
  // ❌ Property 'nombres' does not exist on type 'UsuarioAPI'
  //    ¿Backend cambió el campo? Lo sabes AL COMPILAR, no en producción
}

El as final confía en que el backend cumple su parte. Para APIs críticas o de terceros, combina los tipos con validación runtime (Zod, Valibot): las interfaces describen lo esperado, el validador garantiza lo recibido.

Buenas prácticas con interfaces y types

PrácticaRazón
Extraer a interface/type cualquier forma usada más de dos vecesFuente única de verdad; un cambio actualiza todo el proyecto
Nombrar por dominio, no por técnicaFacturaPendiente comunica más que TipoObjeto2
Marcar readonly lo que no debe mutarseEl compilador protege tus invariantes sin costo
Opcional ? solo si REALMENTE puede faltarCada opcional obliga a todos los consumidores a defenderse
Componer contratos pequeños con extends/&Mejor diez piezas claras que una interfaz-monstruo de 30 campos
No duplicar formas «parecidas pero distintas»Si dos tipos difieren en un campo, extiende o interseca
// ❌ Interfaz-monolito difícil de mantener
interface UsuarioCompleto {
  id: number; nombre: string; email: string; calle: string; ciudad: string;
  pais: string; rolAdmin: boolean; rolEditor: boolean; fechaAlta: Date;
}

// ✅ Composición desde piezas reutilizables
interface Identidad { id: number; nombre: string; email: string }
interface Ubicacion { calle: string; ciudad: string; pais: string }
interface Rol { permisos: string[] }

type Usuario = Identidad & Partial<Ubicacion>;   // teaser de utility types
type Administrador = Usuario & Rol;

Evita exportar tipos «por si acaso» con campos opcionales para todo: terminas construyendo sistemas defensivos donde nada es confiable. Modela primero el caso feliz estricto y relaja SOLO donde el dominio realmente permite ausencia.
