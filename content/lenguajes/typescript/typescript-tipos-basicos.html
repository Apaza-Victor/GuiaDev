Anotaciones de tipo e inferencia automática

En TypeScript puedes declarar explícitamente el tipo de un valor con la sintaxis de dos puntos (: tipo) —una anotación— o dejar que el compilador lo deduzca solo mediante la inferencia. TypeScript es muy bueno adivinando: si inicializas una variable con un valor, su tipo queda inferido al instante y verificado para siempre.

// Anotación explícita: tú declaras el contrato
let edad: number = 25;
let nombre: string = "Ana";

// Inferencia: el compilador deduce los tipos sin que escribas nada
let ciudad = "Madrid";        // tipo inferido: string
let temperatura = 21;         // tipo inferido: number
let activo = true;            // tipo inferido: boolean

ciudad = "Lima";              // ✅ sigue siendo string
// ciudad = 42;
// ❌ Type 'number' is not assignable to type 'string'

¿Cuándo anotar y cuándo confiar en la inferencia?

SituaciónRecomendaciónMotivo
Variable local con valor inicialNo anotesLa inferencia es exacta y el código queda más limpio
Parámetros de funciónAnota siempreEl compilador no puede adivinar qué recibirá tu función
Retorno de funciones públicasAnotaDocumenta la API y detecta errores antes del return
Variables sin inicializarAnotaSin anotación quedan como any implícito (prohibido en modo strict)
Límites con librerías o JSON externoAnotaEs donde el compilador no tiene información previa
// Patrón profesional: anotar en la frontera, inferir en el interior
function calcularIva(precioBase: number): number { // frontera tipada
  const tasa = 0.21;                     // inferido: number
  const total = precioBase * (1 + tasa); // inferido: number
  return total;
}

Anotar de más no es «más seguro», solo es más ruido. Regla de oro de la comunidad: anota parámetros y retornos públicos; deja que las variables locales se infieran.

Tipos primitivos, arreglos y tuplas

TypeScript ofrece los mismos primitivos que JavaScript, ahora verificables: string, number, boolean, null y undefined. Con strictNullChecks activo, null y undefined son tipos propios y no se cuelan dentro de string o number.

const producto: string = "Teclado";
const precio: number = 49.99;      // enteros y decimales: mismo tipo
const disponible: boolean = true;

// null y undefined también son tipos (con strictNullChecks)
let descuento: null = null;        // solo acepta null
let pendiente: undefined = undefined;

Arreglos: dos sintaxis equivalentes

const numeros: number[] = [10, 20, 30];        // sintaxis preferida
const nombres: Array<string> = ["Ana", "Luis"]; // equivalente genérico

numeros.push(40);          // ✅ number
// numeros.push("50");
// ❌ Argument of type 'string' is not assignable to parameter of type 'number'

// Arreglo mixto real: declara una unión de tipos (sección siguiente)
const mixto: (string | number)[] = ["edad", 25, "altura", 180];

Tuplas: longitud y tipos fijados por posición

Un arreglo normal crece libremente; una tupla fija cuántos elementos tiene y de qué tipo es cada posición. Es ideal para datos cortos donde la posición ES el significado:

// [nombre, edad] — la posición define el tipo
let persona: [string, number] = ["Ana", 25];

persona[0].toUpperCase();  // ✅ TS sabe que la posición 0 es string
persona[1] + 5;            // ✅ la posición 1 es number

// persona = [25, "Ana"];
// ❌ Type 'number' is not assignable to type 'string'

// Casos clásicos: coordenadas, pares clave-valor, filas de CSV
const puntoGPS: [number, number] = [40.4168, -3.7038];
const filaCSV: [string, number, boolean] = ["Ana", 25, true];

// Tupla de solo lectura con etiquetas (TypeScript moderno)
const config: readonly [host: string, puerto?: number] = ["localhost", 3000];

En una tupla, tupla[0] y tupla[1] tienen tipos distintos: el orden importa. Si los elementos pueden intercambiar posición o necesitas nombres claros, un objeto { nombre: string; edad: number } comunica mejor.

Union types y literal types

Una unión (a | b) expresa «este valor puede ser A o B». Es la herramienta natural para identificadores que llegan como número o texto, configuraciones opcionales o respuestas que alternan entre formas. Al recibir una unión, TypeScript solo permite usar lo común a todos sus miembros… hasta que hagas narrowing comprobando cuál es realmente.

let idUsuario: string | number;

idUsuario = "A1024";   // ✅
idUsuario = 1024;      // ✅

// Mientras sea una unión, solo operaciones comunes a ambos:
console.log(idUsuario.toString()); // ✅ ambos tipos tienen toString()
// idUsuario.toUpperCase();
// ❌ Property 'toUpperCase' does not exist on type 'number'

Narrowing: reducir la unión con comprobaciones

function mostrarId(id: string | number): void {
  if (typeof id === "string") {
    // Dentro del if, TS sabe que id ES string
    console.log(id.trim().toUpperCase());
  } else {
    // En el else, necesariamente es number
    console.log(id.toFixed(2));
  }
}

Literal types: valores concretos como tipos

TypeScript también permite tipos cuyo único valor posible es un literal concreto. Combinados con uniones forman «enumeraciones ligeras» sin necesidad de crear un enum:

type Talla = "small" | "medium" | "large";
type Direccion = "asc" | "desc";
type EstadoPedido = "carrito" | "pagado" | "enviado" | "entregado";

function elegirTalla(talla: Talla): void {
  console.log(`Talla seleccionada: ${talla}`);
}

elegirTalla("medium");   // ✅
// elegirTalla("gigante");
// ❌ Argument of type '"gigante"' is not assignable to parameter of type 'Talla'
//    ¡Los typos se detectan al compilar!
HerramientaEjemploÚsala cuando…
Unión de tiposnumber | stringEl valor puede ser de varias familias de tipos
Literal simplelet modo: "lectura"Solo existe un valor válido (raro, pero útil)
Unión de literales"small" | "large"Hay un conjunto cerrado de opciones válidas
Narrowingif (typeof x === "string")Necesitas operar sobre UN miembro de la unión

Las uniones de literales convierten errores silenciosos («alguien escribió meduim») en errores de compilación inmediatos. Úsalas para estados, tamaños, direcciones y cualquier conjunto cerrado de valores.

Tipando objetos y funciones en línea

Para objetos pequeños de uso puntual puedes describir su forma (shape) directamente en línea. Cuando la misma forma aparece más de dos veces en tu código, extrae la a una interface o type — tema central de la próxima lección.

const usuario: { nombre: string; edad: number; premium: boolean } = {
  nombre: "Luis",
  edad: 30,
  premium: false,
};

// Propiedad opcional en línea: sufijo ?
const config: { host: string; puerto?: number } = { host: "localhost" };
console.log(config.puerto ?? 8080); // 8080: la propiedad puede no existir

Funciones: retorno inferido vs retorno anotado

// Retorno anotado explícitamente
const saludar = (nombre: string): string => `Hola ${nombre}`;

// El retorno también se INFIERE: esta flecha devuelve string sin anotarlo
const gritar = (texto: string) => texto.toUpperCase() + "!";

// Función que retorna una UNIÓN: conviene anotar para documentar la intención
function formatear(valor: number, moneda: "USD" | "EUR"): string | number {
  return moneda === "USD" ? `$${valor}` : `${valor} €`;
}

formatear(99, "EUR");   // "99 €"
formatear(99, "USD");   // "$99"

Cuando una función devuelve cosas distintas según la entrada (como formatear, que responde string | number), anota el retorno aunque TS lo infiera: la firma pública queda documentada y cualquier cambio accidental dispara un error.

any vs unknown vs void vs never

Estos cuatro tipos describen la falta o imposibilidad de valores, y confundirlos es fuente clásica de bugs y de malas decisiones de diseño. La tabla siguiente es probablemente la más importante de toda la lección:

TipoSignifica¿Se usa libremente?Uso recomendado
any«No sé qué es»: desactiva TODO el chequeoSí, salta todas las verificacionesCasi nunca; solo migraciones temporales marcadas con TODO
unknown«No sé qué es, pero demuéstralo antes de usarlo»No: exige validar o hacer narrowing primeroDatos externos: respuestas de API, JSON.parse, inputs de usuario
voidLa función no devuelve nada significativoSolo asignable a null/undefinedFunciones de efectos secundarios: loguear, renderizar, notificar
neverNunca habrá un valor: siempre lanza, bucle infinito, caso imposibleNingún tipo es asignable a neverFunciones que lanzan errores; exhaustividad en switches

any y unknown frente al mismo problema

// ❌ any: la puerta abierta. Compila... y estalla en producción
let dato: any = JSON.parse('{"nivel": 3}');
dato.cualquierCosa.sinSentido(); // TS calla; JS lanza TypeError

// ✅ unknown: la puerta con cerradura. Obliga a validar
let seguro: unknown = JSON.parse('{"nivel": 3}');

if (typeof seguro === "object" && seguro !== null && "nivel" in seguro) {
  const nivel = (seguro as { nivel: number }).nivel;
  console.log(`Nivel ${nivel}`); // ✅ validado antes de usar
}
// seguro.nivel;
// ❌ Object is of type 'unknown' — el compilador te protege

void y never en funciones

// void: hace trabajo pero no retorna nada útil
function registrarEvento(mensaje: string): void {
  console.log(`[LOG] ${mensaje}`);
  // no hay return (o return; a secas)
}

// never: la ejecución NUNCA termina normalmente
function falloCritico(msg: string): never {
  throw new Error(msg);
}

function bucleMonitoreo(): never {
  while (true) { /* sondeo perpetuo del servidor */ }
}

any se contagia. Un valor any asignado a otra variable vuelve «infectado» de any a esa variable. Cada any es un agujero en el sistema de tipos por donde entran bugs que TypeScript jamás te avisará. Si no sabes el tipo, usa unknown.

Type assertions y manejo de null/undefined

Hay momentos en que TÚ sabes algo que el compilador no puede deducir —por ejemplo, qué elemento del DOM vas a encontrar—. Las type assertions (valor as Tipo) le dicen al compilador «confía en mí, trátalo como X». No convierten nada en runtime: solo cambian cómo el compilador lo mira.

// El DOM devuelve HTMLElement | null, pero tú sabes cuál input buscas:
const emailInput = document.querySelector("#email") as HTMLInputElement;
console.log(emailInput.value); // ✅ ahora TS conoce .value y sus métodos

// Sintaxis angle-bracket (<string>valor): válida, PERO prohibida en .tsx
const largo = (<string>mensaje).length;

// Doble aserción para casos límite: pasa por unknown antes de reconvertir
const valorRaro = "42" as unknown as number; // ⚠️ legal pero sospechoso

Cada as es una promesa sin verificación: si mientes («esto es HTMLInputElement» cuando no lo es), el error aparecerá en runtime igual que en JavaScript puro. Regla práctica: assertions solo en los bordes (DOM, librerías mal tipadas) y nunca dentro de la lógica de negocio.

strictNullChecks: el null ya no se cuela

Con "strictNullChecks": true, null y undefined dejan de ser asignables a cualquier tipo. El compilador te obliga a demostrar que el valor existe ANTES de usarlo:

function buscarUsuario(id: number): string | null {
  return id === 1 ? "Ana" : null;
}

const nombre = buscarUsuario(7);

// console.log(nombre.toUpperCase());
// ❌ 'nombre' is possibly 'null' — el compilador exige comprobarlo

// Forma 1: narrowing explícito
if (nombre !== null) {
  console.log(nombre.toUpperCase()); // ✅ aquí es string garantizado
}

// Forma 2: optional chaining + nullish coalescing
const saludo = nombre?.toUpperCase() ?? "Invitado";
HerramientaSintaxisQué resuelve
Narrowing con ifif (x !== null)Demuestra al compilador que el valor existe
Optional chainingusuario?.perfil?.emailCorta la cadena devolviendo undefined si algo falta
Nullish coalescingx ?? valorPorDefectoFallback SOLO ante null/undefined (no ante 0 o "")
Aserción puntualel!. / as TipoÚltimo recurso cuando tú tienes certeza extra

strictNullChecks convierte el clásico «TypeError: Cannot read properties of null» en un error de compilación. Es la opción de tsconfig que más bugs ha prevenido en la historia de JavaScript; actívala siempre vía "strict": true.

// ❌ Fallback con ||: el 0 es un valor LEGÍTIMO aquí, pero se pierde
const volumen = Number(entrada) || 50;

// ✅ ?? respeta el 0 y solo sustituye ante null/undefined:
const volumenCorrecto = entrada === null ? 50 : Number(entrada);

// ❌ Aserción mentirosa: compila, rompe en runtime
const edadRota = (respuestaAPI as { edad: string }).edad.toFixed();
// ✅ Validar de verdad antes de afirmar el tipo
const esPerfil = typeof respuestaAPI === "object" && respuestaAPI !== null;

Cuando dudes cómo tipar un dato, pregúntate: ¿son alternativas reales? entonces unión; ¿es un objeto con campos que a veces faltan? entonces propiedad opcional ?; ¿no tengo idea de qué llega? entonces unknown. La respuesta nunca debería ser any.

Ejercicios prácticos

Resuélvelos en modo strict sobre el proyecto de la lección anterior:

  1. Básico: Declara una constante de cada primitivo SIN anotar y verifica con el editor (hover) qué tipo infirió. Luego fuerza un error asignando otro tipo y lee el mensaje del compilador.
  2. Tupla vs arreglo: Modela un punto GPS como tupla [number, number] y como objeto { lat: number; lng: number }. Provoca un error intercambiando los valores de la tupla y explica por qué el objeto lo habría evitado.
  3. Unión con narrowing: Escribe formatearId(id: string | number): string que devuelva el id en mayúsculas si es texto, o con ceros a la izquierda hasta 6 dígitos si es número. El narrowing es obligatorio.
  4. Literales: Crea el tipo Nivel = "básico" | "intermedio" | "avanzado" y una función recomendar(nivel: Nivel): string. Demuestra con una captura del error que recomendar("experto") no compila.
  5. Desafío: Recibe un unknown desde JSON.parse que representa { producto: string; precio: number }. Valida su forma con comprobaciones de tipos y propiedades, y calcula el IVA solo si todo es correcto. Prohibido usar any: debe compilar en strict sin aserciones injustificadas.
