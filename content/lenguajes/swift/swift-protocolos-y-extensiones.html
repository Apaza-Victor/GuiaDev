Protocolos: contratos de capacidades

Un protocolo define qué debe saber hacer un tipo, sin decir cómo. Es un contrato: "si firmas aquí, te comprometes a ofrecer estas propiedades y métodos". A diferencia de la herencia clásica, cualquier tipo puede firmar muchos contratos a la vez —structs, clases y enums—, lo que abre el polimorfismo sin jerarquías rígidas.

protocol Vehiculo {
    var velocidadMaxima: Int { get }        // al menos legible
    var encendido: Bool { get set }         // legible y escribible
    func arrancar() -> String               // método obligatorio
}

struct Coche: Vehiculo {
    var encendido = false
    let velocidadMaxima = 180

    func arrancar() -> String {
        encendido ? "¡Vroom!" : "Gira la llave primero"
    }
}

enum Patinete: Vehiculo {
    case electrica, clasica

    var velocidadMaxima: Int { self == .electrica ? 25 : 15 }
    var encendido: Bool { get { true } set { } }
    func arrancar() -> String { "Patada inicial" }
}

Anatomía de los requisitos

RequisitoSintaxis en el protocoloSignifica
Propiedad consultablevar x: Int { get }Debe poder leerse (almacenada o computada)
Propiedad modificablevar x: Int { get set }Lectura y escritura obligatorias
Métodofunc mover(distancia: Double)Firma exacta, cuerpo lo pone cada tipo
Inicializadorinit(nombre: String)Todos los conformantes saben construirse así

Cuando el requisito es un init, las structs deben marcar su implementación como required init(...) si son finales no hace falta, pero en clases sí: garantiza que las subclases también lo cumplan.

Extensiones: ampliar tipos existentes

Una extensión añade métodos, propiedades computadas e inicializadores a cualquier tipo —incluso los que no escribiste tú, como Int, String o Date—. Es la herramienta perfecta para dotar de superpoderes a la librería estándar:

extension Int {
    func veces(_ tarea: () -> Void) {
        for _ in 0..<self { tarea() }
    }

    var enDolares: String { "$\(self)" }
}

3.veces { print("hola") }     // hola × 3
print(250.enDolares)          // $250

extension String {
    var iniciales: String {
        split(separator: " ").compactMap { $0.first }.map(String.init).joined()
    }
}
"Lenguaje de Programación Swift".iniciales   // "LPS"

Conformancia retroactiva

La combinación letal: extensión + protocolo permite que tipos ya existentes firmen tus contratos, aunque su código fuente sea intocable:

protocol Describible {
    var descripcion: String { get }
}

// Int y Double ahora cumplen MI protocolo, sin tocar la librería estándar
extension Int: Describible {
    var descripcion: String { "El número entero \(self)" }
}

extension Double: Describible {
    var descripcion: String { "El decimal \(self)" }
}

print(7.descripcion)       // El número entero 7
print(3.14.descripcion)    // El decimal 3.14

Límite importante: las extensiones no pueden añadir propiedades almacenadas (solo computadas). Tampoco pueden sobrescribir métodos existentes, únicamente añadir nombres nuevos.

Usa extensiones para organizar: agrupa en una extension todo lo relativo a cada protocolo que conforme tu tipo. Los archivos grandes se vuelven índices navegables.

Implementaciones por defecto y polimorfismo

Una extensión sobre el propio protocolo puede ofrecer implementaciones por defecto para sus requisitos. El efecto es espectacular: el método deja de ser obligatorio para quien conforme, pero sigue estando disponible para quien llame. Cada tipo decide si acepta el regalo o aporta su propia versión:

protocol Describible {
    var descripcion: String { get }
}

extension Describible {
    func describir() -> String {   // implementación por defecto
        return descripcion
    }
}

struct Libro: Describible {
    let titulo: String
    var descripcion: String { "Libro: \(titulo)" }
    // hereda describir() tal cual
}

struct EdicionLujo: Describible {
    let titulo: String
    var descripcion: String { "Edición de lujo: \(titulo)" }

    func describir() -> String {   // sobrescribe el defecto
        "✨ \(descripcion) ✨"
    }
}

Polimorfismo real vía protocolos

Un array del tipo del protocolo mezcla instancias dispares; cada llamada ejecuta la versión correcta sin conocer las clases concretas. Esto es polimorfismo sin herencia:

let biblioteca: [any Describible] = [
    Libro(titulo: "Swift 101"),
    EdicionLujo(titulo: "Algoritmos"),
    42            // ¡recuerda: Int también es Describible!
]

for item in biblioteca {
    print(item.describir())
}
// Libro: Swift 101
// ✨ Edición de lujo: Algoritmos ✨
// El número entero 42

El patrón delegate

El patrón más famoso de Apple: un objeto (sujeto) necesita avisar de eventos o pedir decisiones, pero no quiere acoplarse a quién escucha. Le basta con exigir que su delegado cumpla un protocolo. UIKit entero funciona así: tablas, botones, campos de texto…

protocol ReproduccionDelegate: AnyObject {
    func reproductor(_ r: Reproductor, cambioA cancion: String)
    func reproductorTermino(_ r: Reproductor)
}

class Reproductor {
    weak var delegado: ReproduccionDelegate?   // weak: evita ciclos de retención

    func reproducir(_ cancion: String) {
        print("Sonando: \(cancion)")
        delegado?.reproductor(self, cambioA: cancion)
    }
}

class PantallaPrincipal: ReproduccionDelegate {
    func reproductor(_ r: Reproductor, cambioA cancion: String) {
        print("[UI] Actualizando portada de \(cancion)")
    }
    func reproductorTermino(_ r: Reproductor) {
        print("[UI] Mostrando lista siguiente")
    }
}

let pantalla = PantallaPrincipal()
let player = Reproductor()
player.delegado = pantalla
player.reproducir("Bohemian Rhapsody")
// Sonando: Bohemian Rhapsody
// [UI] Actualizando portada de Bohemian Rhapsody

¿Por qué weak es imprescindible?

El delegado casi siempre es un objeto de larga vida (una pantalla, un controlador). Si el sujeto lo reteniera fuertemente, ambos se sostienen mutuamente y ARC nunca libera ninguno: el ciclo de retención que viste en la lección anterior. Con weak, cuando la pantalla muere, el reproductor ve delegado == nil y sigue funcionando —por eso el opcional—.

Sin weak este patrón fuga memoria silenciosamente. La regla mnemotécnica de la plataforma: delegate siempre weak, y el protocolo debe declararse : AnyObject porque solo las clases pueden participar en ciclos.

POP frente a OOP

Durante décadas la reutilización se resolvió con herencia: una clase base y subclases especializadas. La experiencia enseñó sus costes: jerarquías frágiles donde cambiar la base rompe a todos los hijos, imposibilidad de heredar de dos padres y exclusión de los value types. La respuesta de Swift es la programación orientada a protocolos (POP): capacidades pequeñas componibles en lugar de árboles genealógicos.

CriterioOOP con herenciaPOP con protocolos
ReutilizaciónCódigo heredado verticalmenteImplementaciones default componibles
Cantidad de "padres"Uno soloLos protocolos que quieras
Funciona con struct/enumNoSí (y son el estándar recomendado)
Riesgo típicoClase base frágil, efectos sorpresaProtocolos inflados si no se disciplina
TestabilidadMocks por subclasificaciónTipos test dobles conformando el mismo protocolo

Asociatedtype: el adelanto genérico

Los protocolos también pueden hablar de "algún tipo, aún sin decidir", mediante associatedtype. Así define la librería estándar Collection, y por eso arrays, strings y sets comparten APIs idénticas sin compartir ancestro:

protocol Contenedor {
    associatedtype Elemento
    mutating func agregar(_ elemento: Elemento)
    var cantidad: Int { get }
}

struct Pila<T>: Contenedor {
    private var items: [T] = []
    mutating func agregar(_ elemento: T) { items.append(elemento) }
    var cantidad: Int { items.count }
}

var pila = Pila<String>()
pila.agregar("swift")     // el compilador fijó Elemento = String solo
print(pila.cantidad)      // 1

No necesitas elegir bando: usa structs + protocolos para modelar capacidades y reserva clases para identidad compartida. Esa mezcla pragmática es exactamente el estilo del código moderno de Apple.

Buenas prácticas con protocolos

1. Protocolos pequeños y enfocados

// ❌ Un contrato gigante obliga a implementarlo todo aunque no aplique
protocol Gestionable {
    func guardar(); func borrar(); func imprimir(); func exportarPDF()
}

// ✅ Capacidades atómicas que se combinan según necesidad
protocol Guardable { func guardar() }
protocol Exportable { func exportarPDF() }
struct Factura: Guardable, Exportable { /* solo lo que toca */ }

2. Nombres que revelan intención

Convenciones de la plataforma: capacidades terminan en -able/-ible (Codificable, Comparable) y los roles de comunicación son sustantivos (Delegate, DataSource). Un nombre bien elegido elimina la necesidad de documentación.

3. Añadir requisitos rompe; añadir métodos en extensión, no

// ⚠️ Añadir esto al protocolo obliga a actualizar TODOS los conformantes
protocol Guardable {
    func guardar(en nube: Bool)      // breaking change para la librería ajena
}

// ✅ Nuevo comportamiento como método de extensión: nadie se rompe
extension Guardable {
    func guardarEnNube() { guardar() }
}

Antes de crear un protocolo nuevo pregúntate: ¿tendré al menos dos tipos distintos que lo cumplan? Si la respuesta es no, quizá solo necesitas un struct bien diseñado. Los protocolos valen por la variedad que habilitan.

Ejercicios prácticos

De menor a mayor dificultad:

  1. Voladores: define el protocolo Volador con volar() -> String y haz que dos structs (Pajaro, Dron) lo cumplan con mensajes distintos; recorre un array de [any Volador] imprimiendo cada despegue.
  2. Superpoderes numéricos: extiende Double con kilometrosAMillas() y millasAKilometros(); después crea el protocolo Medible y logra conformancia retroactiva de Double.
  3. Galería describible: parte del ejemplo Describible y añade una tercera estructura propia; genera un array heterogéneo (incluye un Int) ordenado por longitud de descripción usando sorted { … }.
  4. Temporizador delegado: implementa class Temporizador con weak var delegado que notifique cada tick simulado; crea una clase Alarma conforme que cuente los ticks y avise al llegar a cinco; comprueba imprimiendo direcciones o usando === que el delegado es el esperado.
  5. Contenedores genéricos: usando associatedtype, completa un protocolo Contenedor con agregar, extraer y cantidad; implementa Pila (LIFO) y Cola (FIFO) como structs genéricos y demuestra su comportamiento con Strings e Ints.
