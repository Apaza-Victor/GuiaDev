Structs: tipos por valor

Los struct agrupan datos y comportamiento relacionados bajo un mismo nombre, igual que una clase… con una diferencia filosófica enorme: al asignarlos o pasarlos, se copian. Son tipos por valor, como los Int o los arrays que ya conoces. Cada variable posee su propia copia independiente:

struct Punto {
    var x = 0.0, y = 0.0

    mutating func mover(dx: Double, dy: Double) {
        x += dx
        y += dy
    }
}

var a = Punto(x: 1, y: 2)
var b = a                  // COPIA completa e independiente
b.x = 99

print(a.x)                 // 1  ← 'a' ni se enteró
print(b.x)                 // 99

La misma regla protege las constantes: un let con struct congela todo el valor, propiedad por propiedad. No hay matices ni sorpresas parciales:

let origen = Punto()
// origen.x = 10    ❌ error: 'origen' es constante y sus propiedades también

La guía oficial de Apple es clara: empieza siempre por struct y sube a clase solo cuando tengas una razón concreta. La copia elimina efectos secundarios, simplifica la concurrencia y hace el código predecible.

Clases: tipos por referencia

Una clase, en cambio, crea objetos por referencia: asignar no copia el objeto, solo comparte otra flecha apuntando al mismo. Dos variables pueden mutar "lo mismo" sin saberlo, para bien (compartir estado real: una sesión, una vista) y para mal (efectos a distancia):

class Contador {
    var total = 0
    func incrementar() { total += 1 }
}

let c = Contador()         // ¡'let' pero mutable POR DENTRO!
c.incrementar()

let d = c                  // MISMA instancia, no copia
d.total                    // 1
d.incrementar()
print(c.total)             // 2 ← 'c' ve los cambios de 'd'

Fíjate en el detalle revolucionario del ejemplo: c es let y aun así su contenido cambia. En clases, let congela la flecha (no podrás apuntar a otro objeto), no el objeto apuntado.

Gestión de memoria: ARC

Las instancias de clase viven en el montículo (heap) y Swift las libera automáticamente mediante ARC (Automatic Reference Counting): cuenta cuántas referencias apuntan a cada objeto y lo destruye al llegar a cero. No hay recolector de basura pausando el programa, pero sí responsabilidad: si dos objetos se retienen mutuamente para siempre, esa memoria nunca se libera (ciclos de retención).

La regla mental: struct = fotocopia, clase = documento compartido en la nube. Si editas la fotocopia, nadie más lo nota; si editas el documento compartido, cambian todos los lectores a la vez.

Inicializadores y deinit

Swift exige que toda propiedad tenga valor antes de usar una instancia. Para lograrlo con mínimo esfuerzo, los structs reciben gratis el memberwise initializer: un constructor con un parámetro por cada propiedad almacenada:

struct Libro {
    let titulo: String
    var paginas: Int = 300     // valores por defecto hacen el parámetro opcional
}

// El compilador generó init(titulo:paginas:) por ti
let l1 = Libro(titulo: "Swift en serio", paginas: 480)
let l2 = Libro(titulo: "Poemas")            // usa el defecto

Inicializadores personalizados

struct Temperatura {
    var celsius: Double

    init(celsius: Double) { self.celsius = celsius }

    init(fahrenheit: Double) {
        self.init(celsius: (fahrenheit - 32) * 5 / 9)   // delegar en otro init
    }
}

Temperatura(celsius: 100)
Temperatura(fahrenheit: 212)   // ambas: 100 °C

Ojo: si defines un init propio dentro del cuerpo del struct, el memberwise gratuito desaparece. Truco profesional: pon los inicializadores extra en una extension Temperatura { } y conservarás ambos mundos.

deinit: solo en clases

Cuando ARC destruye una instancia de clase, puede ejecutarse su deinit: el lugar para cerrar archivos, desconectar observadores o liberar recursos externos. Los structs no lo tienen (no hay referencia que contar): otro motivo por el que las clases son "más máquina" que los structs.

class Conexion {
    deinit { print("Cerrando sockets…") }   // justo antes de morir
}
var conexion: Conexion? = Conexion()
conexion = nil        // ARC llega a cero → imprime el mensaje

Propiedades computadas y observadores

No todo lo que expone un tipo necesita almacenarse. Las propiedades computadas calculan su valor al vuelo mediante get (y opcionalmente set): ocupan cero memoria extra y garantizan coherencia porque derivan de datos reales:

Tipo de propiedad¿Guarda memoria?Ejemplo típico
Almacenada (var nombre: String)SíDatos crudos del modelo
Computada (var area: Double { get set })No, se calculaDerivados: área, impuestos, iniciales
Solo lectura (var descripcion: String { })NoTexto derivado, formato
struct Rectangulo {
    var ancho: Double, alto: Double      // almacenadas

    var area: Double {                   // computada de solo lectura
        ancho * alto
    }

    var diagonal: Double {
        (ancho * ancho + alto * alto).squareRoot()
    }
}

var r = Rectangulo(ancho: 3, alto: 4)
r.area          // 12
r.diagonal      // 5.0

get y set: propiedades puente

Con set puedes escribir también, convirtiendo entre representaciones. El nuevo valor llega implícitamente como newValue:

struct Horno {
    var fahrenheit: Double = 32
    var celsius: Double {
        get { (fahrenheit - 32) * 5 / 9 }
        set { fahrenheit = newValue * 9 / 5 + 32 }
    }
}

var horno = Horno()
horno.celsius = 180       // escribe a través del setter
print(horno.fahrenheit)   // 356.0

Observadores: willSet y didSet

Las propiedades almacenadas pueden reaccionar a cambios sin convertir el tipo en clase ni escribir accesores completos: willSet corre antes de asignar (recibe newValue) y didSet después (con acceso al oldValue). Perfectos para registrar, validar o refrescar interfaz:

struct Reproductor {
    var volumen = 50 {
        willSet { print("De \(volumen) a \(newValue)…") }
        didSet {
            if volumen > 100 { volumen = 100 }   // didSet puede corregir
        }
    }
}

var player = Reproductor()
player.volumen = 150
// De 50 a 150…   ← willSet
// (didSet recorta y deja volumen = 100)

Métodos mutating

Aquí aparece la regla más peculiar de los structs: sus métodos no pueden modificar las propiedades de self a menos que declares el método mutating. ¿Por qué? Porque un struct es un valor: modificarlo significa reemplazarlo, y Swift quiere que esa intención quede escrita en el código:

struct Billetera {
    var pesos: Int = 0

    func consultarSaldo() -> Int { pesos }        // solo lectura: normal

    mutating func depositar(_ monto: Int) {
        pesos += monto                            // requiere mutating
    }

    mutating func vaciar() -> Int {
        let saldo = pesos
        self = Billetera()                        // mutating permite REEMPLAZAR self
        return saldo
    }
}

var billetera = Billetera()
billetera.depositar(500)

let congelada = Billetera(pesos: 100)
// congelada.depositar(1)   ❌ error: no puedes mutar un valor constante

En clases no existe mutating: todos sus métodos pueden mutar libremente porque operan sobre una referencia. Esa asimetría resume la diferencia entre ambos mundos: el valor debe pedir permiso explícito para cambiar.

Identidad, herencia y la gran decisión

=== compara identidad; == compara valor

Con clases dispones del operador ===: ¿son literalmente el mismo objeto en memoria? Con structs no existe tal pregunta: cada copia es un mundo. El operador ==, en cambio, compara contenido y funciona en ambos si el tipo conforma Equatable:

struct TarjetaStruct: Equatable { let numero: String }
class TarjetaClass: Equatable { let numero: String
    static func == (a: TarjetaClass, b: TarjetaClass) -> Bool { a.numero == b.numero }
}

let t1 = TarjetaStruct(numero: "123"), t2 = TarjetaStruct(numero: "123")
t1 == t2                       // true: mismo contenido

let c1 = TarjetaClass(numero: "123"), c2 = c1
c1 == c2                       // true
c1 === c2                      // true: exactamente el mismo objeto
TarjetaClass(numero: "123") === c1   // false: dos objetos distintos aunque iguales

Herencia frente a protocolos

Solo las clases heredan (una única superclase), reutilizando código y comportamiento verticalmente. Los structs no heredan, pero pueden conformar cuantos protocolos quieras, compartiendo capacidades horizontalmente. La comunidad Swift ha girado hacia protocolos + extensiones (protocol-oriented programming) precisamente porque evitan jerarquías rígidas; lo disecaremos en la próxima lección.

¿Struct o clase? Tabla de decisión

Pregunta claveSí → usa
¿Modela un dato con atributos (dinero, punto, usuario)?struct
¿Necesitas identidad única compartida (sesión, vista, caché)?class
¿Requiere heredar de otra clase u Objective-C?class
¿Se pasará entre hilos o quieres evitar efectos laterales?struct
¿Controlar ciclo de vida con deinit?class
Modelo típico de app SwiftUI (@State, modelos)struct

Errores comunes con structs y clases

1. Esperar que una función modifique tu struct

func subirNivel(_ jugador: inout Jugador) { ... }   // ✅ inout declara la mutación
subirNivel(&jugador)                                 // el & avisa en la llamada
// Sin inout, la función recibió una COPIA: tus cambios se pierden silenciosamente

2. Confundir qué congela let según el tipo

let punto = Punto(x: 1, y: 1)
// punto.x = 2        ❌ struct: let congela TODO

let sesion = Sesion()
sesion.usuario = "ana"   // ✅ clase: let solo congela la referencia

3. Perder el memberwise initializer

// ❌ Definir init dentro del struct elimina el generado automáticamente
// ✅ Mover el init personalizado a una extensión lo conserva
struct Producto { let nombre: String; let precio: Double }
extension Producto {
    init(json: [String: Any]) { ... }
}
Producto(nombre: "Té", precio: 2.0)   // sigue disponible

4. Crear ciclos de retención sin darse cuenta

class Padre {
    var hijo: Hijo?
    deinit { print("Padre liberado") }
}
class Hijo {
    var padre: Padre?   // ⚠️ referencia fuerte mutua: ninguno muere jamás
    deinit { print("Hijo liberado") }
}
// Solución: declarar uno de los lados como weak (próxima lección, patrón delegate)

El bug más traicionero del mundo clases es creer que tienes una copia cuando tienes un alias. Si dos partes de tu app "misteriosamente" cambian juntas, busca una referencia compartida antes de culpar al azar.

Ejercicios prácticos

Ordenados por dificultad creciente:

  1. Rectángulo completo: define un struct con ancho y alto, propiedades computadas area y perimetro, y demuestra que asignarlo a otra constante no sincroniza los cambios.
  2. Termostato con reglas: crea un struct cuyo celsius sea propiedad computada puente sobre fahrenheit (get/set), y añade un observador didSet que registre cada cambio con el valor anterior.
  3. Cuenta compartida vs copiada: implementa class CuentaBancaria (saldo mutable) y struct Dinero equivalente; transfiere ambas a dos variables y documenta con comentarios quién ve los cambios de quién, usando === donde aplique.
  4. Vector matemático: construye un struct Vector2D con método mutating escalar(_:), propiedad computada magnitud, conformancia a Equatable y un inicializador extra en extension que acepte ángulo y longitud conservando el memberwise.
  5. Refactor arquitectónico: parte de tres clases con herencia Vehiculo → Coche/Moto; refactorízalas a structs con un protocolo común Vehiculo, justifica en comentarios cada decisión con la tabla de esta lección y explica qué gana el diseño (menos estado compartido, más testeable).
