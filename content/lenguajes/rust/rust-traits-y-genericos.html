Traits: contratos de comportamiento compartido

Un trait define qué puede hacer un tipo, sin dictar cómo. Es el equivalente funcional a las interfaces de otros lenguajes — pero con superpoderes: métodos con implementación por defecto, implementación condicional y generics integrados. Donde la herencia encadena clases frágilmente, los traits componen comportamientos:

trait Resumen {
    fn autor(&self) -> String;              // OBLIGATORIO: cada tipo lo define

    fn preview(&self) -> String {           // OPCIONAL: implementación por defecto
        format!("Artículo por {}", self.autor())
    }
}

struct Articulo { titulo: String }
struct Podcast { episodio: u32 }

impl Resumen for Articulo {
    fn autor(&self) -> String {
        format!("Equipo GuiaDev ({})", self.titulo)
    }
    // preview() heredado tal cual del trait
}

impl Resumen for Podcast {
    fn autor(&self) -> String {
        format!("Episodio #{}", self.episodio)
    }
    fn preview(&self) -> String {          // lo SOBREESCRIBIMOS
        format!("🎧 Escucha el episodio {}", self.episodio)
    }
}

Los métodos por defecto pueden llamar a los obligatorios (como preview usa autor): así defines plantillas de comportamiento que cada tipo especializa al mínimo.

Los traits imprescindibles de la stdlib

Antes de crear los tuyos, domina los que ya vienen incluidos. Algunos se obtienen gratis con #[derive]; otros exigen implementación manual porque dependen de decisiones de diseño:

TraitPara qué sirveCómo obtenerlo
DebugImprimir con {:?}/{:#?}#[derive(Debug)]
CloneCopia profunda explícita (.clone())#[derive(Clone)]
CopyDuplicación implícita barata#[derive(Copy, Clone)] (solo campos Copy)
DefaultValor neutro (Tipo::default())#[derive(Default)]
PartialEq/EqComparar con == y !=#[derive(PartialEq)]
DisplayImpresión bonita para usuarios con {}MANUAL: es una decisión de formato
use std::fmt;

#[derive(Debug, Clone, PartialEq, Default)]
struct Punto {
    x: i32,
    y: i32,
}

// Display NO es derivable: TÚ decides cómo se ve para humanos
impl fmt::Display for Punto {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "({}, {})", self.x, self.y)
    }
}

fn main() {
    let p = Punto { x: 3, y: -2 };
    let q = p.clone();

    println!("Debug:   {:?}", p);
    println!("Display: {}", p);              // usa nuestro impl Display
    println!("¿Iguales? {}", p == q);       // PartialEq derivado
    println!("Default: {:?}", Punto::default());   // (0, 0)
}

Hábito ganador: deriva Debug siempre, más Clone/PartialEq/Default cuando tengan sentido. Implementa Display solo cuando ese struct vaya a mostrarse a usuarios finales.

Genéricos con trait bounds: funciones para muchos tipos

Sin genéricos duplicarías funciones por cada tipo; sin restricciones, el compilador no sabría qué puedes hacer con T. La solución son los trait bounds: exigir que T implemente ciertos traits:

// T debe saber compararse: PartialOrd es el bound mínimo necesario
fn mayor<T: PartialOrd>(a: T, b: T) -> T {
    if a > b { a } else { b }
}

// where: legible cuando las restricciones crecen
fn combinar<T, U>(t: T, u: U) -> String
where
    T: std::fmt::Display + Clone,
    U: std::fmt::Display,
{
    format!("{} y {}", t, u)
}

fn main() {
    println!("{}", mayor(7, 3));            // i32 implementa PartialOrd ✅
    println!("{}", mayor("peras", "manzanas")); // &str también ✅
    // mayor(5, 3.5);                        // ❌ tipos distintos: no compila
    println!("{}", combinar(42, "respuestas"));
}

Structs genéricas

Los mismos bounds aplican a tus propios tipos contenedores:

struct Contenedor<T> {
    valor: T,
}

impl<T: std::fmt::Display> Contenedor<T> {
    fn nuevo(valor: T) -> Self {
        Self { valor }                       // abreviatura campo=variable
    }

    fn mostrar(&self) {
        println!("Contengo: {}", self.valor);
    }
}

fn main() {
    Contenedor::nuevo(10).mostrar();
    Contenedor::nuevo("texto").mostrar();
}

Rust hace monomorfización: genera una copia especializada de cada combinación de tipos usada. Los genéricos tienen coste cero en ejecución — a diferencia de Java, donde hay boxing y borrado de tipos.

impl Trait: genéricos sin nombres

Cuando solo necesitas decir "algún tipo que implementa X", la sintaxis impl Trait ahorra declarar un parámetro genérico completo. Es azúcar legible para casos simples:

use std::fmt::Display;

// En PARÁMETROS: equivale a fn gritar<T: Display>(x: T)
fn gritar(x: impl Display) {
    println!("¡{}!", x.to_string().to_uppercase());
}

// En RETORNO: "devuelvo ALGÚN tipo concreto que implementa este trait"
fn numero_favorito() -> impl Iterator<Item = i32> {
    [42, 7, 2026].into_iter().filter(|n| n % 7 == 0)
}

fn main() {
    gritar("rust");
    gritar(99);

    for n in numero_favorito() {
        println!("múltiplo: {}", n);
    }
}

-> impl Trait promete UN tipo concreto fijo elegido dentro de la función: no puedes devolver en un branch un EnteroIterador y en otro un ParIterador. Si necesitas alternar tipos reales en runtime, esa es la señal para pasar a dyn Trait.

dyn Trait vs impl Trait: dos formas de polimorfismo

Rust ofrece dos estrategias de polimorfismo. El static dispatch (genéricos/impl Trait) resuelve el tipo en compilación generando código especializado. El dynamic dispatch (dyn Trait) resuelve en runtime mediante una tabla de funciones (vtable), a cambio de flexibilidad:

Aspectoimpl Trait / genéricosdyn Trait
ResoluciónTiempo de compilación (monomorfización)Tiempo de ejecución (vtable)
RendimientoCero coste; permite inlineSalto indirecto por llamada
Colecciones heterogéneasImposibles (todas del mismo T)Sí: Vec<Box<dyn Trait>>
Cuándo usarBibliotecas y hot pathsPlugins, UIs, listas mixtas
trait Dibujable {
    fn dibujar(&self) -> String;
}

struct Circulo { radio: f64 }
struct Cuadrado { lado: f64 }

impl Dibujable for Circulo {
    fn dibujar(&self) -> String { format!("● r={}", self.radio) }
}
impl Dibujable for Cuadrado {
    fn dibujar(&self) -> String { format!("■ l={}", self.lado) }
}

fn main() {
    // dyn Trait: mezcla tipos DISTINTOS bajo una misma interfaz
    let lienzo: Vec<Box<dyn Dibujable>> = vec![
        Box::new(Circulo { radio: 2.0 }),
        Box::new(Cuadrado { lado: 5.0 }),
    ];

    for forma in &lienzo {
        println!("{}", forma.dibujar());   // dispatch dinámico por vtable
    }
}

Regla de decisión: usa genéricos por defecto (gratis); recurre a dyn Trait cuando necesites mezclar tipos concretos en una colección o quieras reducir la explosión de monomorfización en binarios grandes.

Supertraits e implementación condicional

Supertraits: exigir otra habilidad previa

Un trait puede declarar que quien quiera implementarlo, primero debe implementar otro. Jugador: Display significa "todo jugador es imprimible":

use std::fmt::{self, Display};

trait Jugador: Display {                 // Display es SUPERTRAIT
    fn puntuacion(&self) -> u32;

    fn tarjeta(&self) -> String {        // default que YA puede usar {}
        format!("{} → {} pts", self, self.puntuacion())
    }
}

struct Humano { nombre: String, puntos: u32 }

impl Display for Humano {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{}", self.nombre)
    }
}

impl Jugador for Humano {
    fn puntuacion(&self) -> u32 { self.puntos }
}

Implementación condicional (blanket impls)

Puedes implementar un trait SOLO cuando los genéricos cumplen ciertas condiciones — así funciona toda la stdlib: impl<T: Clone> Clone for Vec<T> significa que un Vec es clonable exactamente cuando sus elementos lo son. La composición de capacidades fluye automáticamente.

Errores comunes con traits y genéricos

Error / síntomaCausaSolución
E0277: the trait bound is not satisfiedFalta implementar el trait pedido o ampliar el boundImpl el trait o relaja/revisa la restricción
E0117: orphan rule violationImpl de trait externo para tipo externoEnvuelve el tipo en tu propio newtype
Método no encontrado pese a existirEl trait no está importado al scopeAñade use Trait; (clásico con iteradores)
Dos branches devuelven tipos distintos con impl Traitimpl Trait exige UN solo tipo concretoUsa Box<dyn Trait> o unifica el tipo
expected T, found U en función genéricaLlamas con dos tipos distintos donde se exigía unoUnifica argumentos o añade dos parámetros genéricos
derive(Clone) fallaAlgún campo no implementa CloneClona el campo o deriva Clone también ahí

No conviertas todo en dyn Trait para "arreglar" errores de genéricos: pierdes rendimiento y seguridad de tipos. Primero intenta simplificar los bounds; dyn es la herramienta de último recurso consciente. Y recuerda la orphan rule: solo puedes implementar un trait si el trait o el tipo son tuyos; para tipos ajenos, envuélvelos en un newtype propio.

Los traits son la clave de lectura de toda documentación Rust: cuando veas fn foo(x: impl Into<String>), ya sabes qué acepta y qué garantiza sin leer el cuerpo.

Ejercicios prácticos

Réslolos en orden creciente; los últimos combinan traits, genéricos y dispatch.

  1. Tu primer trait: crea el trait Vehiculo con método obligatorio ruedas(&self) -> u8 y método default describir(&self); impleméntalo para structs Coche y Moto y llama ambos métodos desde main.
  2. Stdlib aplicada: define struct Temporizador con #[derive(Debug, Default, PartialEq)]; implementa Display manualmente para mostrar "00:30" estilo reloj y compara dos instancias con ==.
  3. Genéricos con bounds: escribe fn maximo<T: PartialOrd + Copy>(lista: &[T]) -> Option<T> que devuelva None si la lista está vacía; pruébala con i32, f64 y char.
  4. Colección heterogénea: con el trait Dibujable del ejemplo, añade una tercera figura Triángulo y construye un Vec<Box<dyn Dibujable>> con las tres; itera dibujando cada una.
  5. Proyecto integrador: diseña trait Exportable con supertrait Debug, una struct genérica Reporte<T: Exportable + Display> y una función que acepte impl Iterator de reportes; decide y JUSTIFICA en comentarios dónde usaste static vs dynamic dispatch.
