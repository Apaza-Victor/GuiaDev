¿Qué es Cargo?

Cargo es mucho más que un compilador con interfaz: es el sistema oficial de Rust que combina gestor de dependencias, sistema de build, corredor de pruebas y generador de documentación en una sola herramienta coherente. Si has sufrido configurando Makefiles en C++ o virtualenvs en Python, Cargo te parecerá un lujo: todo proyecto Rust se compila igual en cualquier máquina con un solo comando.

Cargo resuelve tres problemas históricos del desarrollo nativo: la descarga automática de librerías desde crates.io (el registro central de paquetes), la resolución de versiones compatibles entre ellas y la orquestación del compilador rustc con los flags correctos para cada perfil.

# Crear un proyecto binario (aplicación ejecutable)
cargo new mi_app
cd mi_app

# Crear una biblioteca reutilizable por otros proyectos
cargo new --lib mi_libreria

# Verificar que todo compila SIN generar binario (muy rápido)
cargo check

Estructura estándar de un proyecto

mi_app/
├── Cargo.toml          # manifiesto: metadatos y dependencias
├── Cargo.lock          # versiones exactas bloqueadas
└── src/
    ├── main.rs         # punto de entrada del BINARIO
    └── lib.rs          # raíz de la LIBRERÍA (opcional)

Un proyecto puede tener binario y librería a la vez: la lógica reutilizable vive en src/lib.rs y src/main.rs solo orquesta. En proyectos medianos conviene dividir la librería en módulos por carpeta:

// src/lib.rs — declara los módulos; Cargo busca src/red/mod.rs o src/red.rs
pub mod red;
pub mod utilidades;

// src/main.rs — consume lo exportado por la propia librería
fn main() {
    let estado = mi_app::red::conectar("localhost");
    println!("Estado: {:?}", estado);
}

Los workspaces agrupan varios crates en un repositorio compartiendo Cargo.lock y target/: basta un Cargo.toml raíz con [workspace] y members = ["app", "nucleo"]. Es el patrón de proyectos grandes como ripgrep.

Cargo.toml y las dependencias

El manifiesto usa formato TOML. Las dos secciones esenciales son [package] (identidad del crate) y [dependencies] (lo que consumes de crates.io):

[package]
name = "mi_app"        # nombre único del crate
version = "0.1.0"      # versión semántica del PROYECTO
edition = "2021"       # edición del lenguaje

[dependencies]
serde = { version = "1", features = ["derive"] }  # features opcionales
rand = "0.8"           # forma corta: solo versión
clap = "4"

[dev-dependencies]     # solo para tests y benchmarks
pretty_assertions = "1"

Semver y el caret implícito

Escribir rand = "0.8" no pide esa versión exacta: Cargo interpreta un rango caret (^0.8). La regla cambia según el número mayor, y entenderla evita sorpresas:

EspecificadorRango aceptadoLectura práctica
"0.8">=0.8.0 <0.9.0En 0.x el menor actúa como mayor: solo parches seguros
"0.8.5">=0.8.5 <0.9.0Mínimo 0.8.5 con techo 0.9.0
"1" o "1.2">=1.0.0 <2.0.0Cualquier 1.x compatible hacia atrás

Ojo con crates en 0.x: su API puede romperse entre minor versions y muchos proyectos quedan atascados en versiones viejas por esto. El archivo Cargo.lock congela las versiones exactas para builds reproducibles: súbelo siempre al repositorio.

Comandos esenciales de Cargo

El flujo diario gira en torno a una docena de verbos. Esta tabla cubre el 95% de tu vida con Cargo:

ComandoQué hace
cargo new nombreCrea un proyecto binario con Git inicializado
cargo new --lib nombreCrea una biblioteca sin main
cargo runCompila si hace falta y ejecuta
cargo buildCompila en modo dev hacia target/debug
cargo build --releaseCompila optimizado hacia target/release
cargo checkValida tipos y ownership sin generar binario
cargo testEjecuta todos los tests incluidos los doctests
cargo doc --openGenera documentación HTML y la abre
cargo clippyLinter con ~700 revisiones de idiomaticidad

Integra cargo fmt y cargo clippy desde el primer día (o en CI). La comunidad los considera obligatorios: código sin pasar Clippy rara vez pasa revisión en proyectos serios.

Perfiles dev vs release

El perfil dev prioriza velocidad de compilación para iterar rápido; release activa las optimizaciones agresivas del backend LLVM priorizando la ejecución. La diferencia puede ser de 5x a 50x en código numérico.

Ajustedev (por defecto)--release
Optimización (opt-level)0, sin optimizar3, máxima
Info de depuraciónIncluida (backtraces útiles)No incluida
Overflow checks en enterosPánico al desbordarDeshabilitados (wrap-around)
Tiempo de compilaciónSegundosMinutos en proyectos grandes
Artefacto entarget/debug/target/release/
# Personalización opcional en Cargo.toml
[profile.release]
opt-level = 3
lto = true            # Link-Time Optimization: binarios más rápidos
strip = true          # quita símbolos: binarios más pequeños

Nunca juzgues el rendimiento de Rust en modo dev: un bucle de 800ms en debug puede bajar a 20ms en release. Mide SIEMPRE con cargo run --release.

Tests integrados sin frameworks

Rust trae testing de primera clase sin dependencias externas: cualquier función anotada con #[test] se ejecuta con cargo test. La convención es agruparlas en un módulo tests al final del archivo, que solo se compila cuando pruebas:

fn suma(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]                    // este módulo SOLO se compila con cargo test
mod tests {
    use super::*;               // importa todo lo del archivo padre

    #[test]
    fn suma_dos_numeros() {
        assert_eq!(suma(2, 3), 5);
    }

    #[test]
    fn suma_con_negativos() {
        assert_eq!(suma(-2, -3), -5);
    }

    #[test]
    #[should_panic]             // el test PASA si el código panea
    fn dividir_por_cero_panea() {
        let _ = dividir(10, 0); // supón que divide! hace panic con 0
    }
}

Las macros de aserción más útiles son assert_eq!, assert_ne! y assert!(condicion). Todas aceptan un mensaje personalizado como último argumento para fallar con contexto.

Ejecuta un único test durante el desarrollo con cargo test nombre_del_test: es mucho más rápido y muestra los valores reales obtenidos cuando falla.

Documentación con /// y cargo doc

Rust distingue dos tipos de comentarios. Los normales (//) son para quien lee el código; los comentarios de documentación (///) generan páginas HTML profesionales con cargo doc, igual que las docs oficiales de la stdlib:

/// Calcula el área de un rectángulo.
///
/// # Ejemplos
///
/// ```
/// let area = mi_app::area_rectangulo(2.0, 3.0);
/// assert_eq!(area, 6.0);
/// ```
pub fn area_rectangulo(base: f64, alto: f64) -> f64 {
    base * alto
}

Doctests: ejemplos que nunca mienten

Fíjate en el bloque ``` dentro del comentario: no es decorativo. Cargo lo compila y ejecuta como un test real cada vez que corres cargo test. Si cambias la función y olvidas actualizar el ejemplo, la compilación lo detecta.

cargo doc --open     # genera target/doc/ y abre el navegador
cargo test           # también ejecuta los doctests embebidos
SintaxisAlcanceUso típico
///Documenta el ítem inmediatamente inferiorFunciones, structs, módulos públicos
//!Documenta el archivo o módulo contenedor enteroCabecera de lib.rs explicando la librería
//Comentario normal, ignorado por rustdocNotas internas para desarrolladores

Los comentarios de doc soportan Markdown: encabezados como # Panics, # Errors y # Examples son convenciones estándar reconocidas por rustdoc y por toda la comunidad.

Buenas prácticas con Cargo

Cargo te deja hacer casi todo, pero hay hábitos que separan proyectos amateurs de proyectos mantenibles:

  • Commitea Cargo.lock en binarios: garantiza builds reproducibles para todo tu equipo.
  • Ciclo interno rápido: alterna cargo check mientras escribes y reserva cargo build/run para probar.
  • fmt + clippy antes de cada commit: idealmente automatizado con hooks o CI.
  • Actualiza con criterio: cargo update respeta semver, pero revisa changelogs de crates 0.x.
  • Divide binario y librería (main.rs + lib.rs): permite tests unitarios sin arrancar la app.
  • Documenta lo público: si otra persona (o tú en 6 meses) lo va a usar, merece ///.
  • Audit dependencias: cargo audit avisa de vulnerabilidades conocidas en tus crates.
# Rutina de calidad completa antes de subir código
cargo fmt --check && cargo clippy -- -D warnings && cargo test

No añadas dependencias "porque sí": cada crate suma tiempo de compilación y superficie de riesgo. Antes de elegir, mira descargas recientes, mantenimiento y versión mínima de Rust en crates.io.

Ejercicios prácticos

Completa estos ejercicios en orden; cada uno construye sobre el anterior y consolida el flujo de trabajo con Cargo.

  1. Proyecto desde cero: crea saludador con cargo new, inspecciona el árbol generado y ejecútalo con cargo run. Luego valida cuánto tarda cargo check frente a cargo build.
  2. Dependencia externa: añade rand con cargo add rand, abre Cargo.toml e identifica qué rango semver quedó escrito. Genera e imprime un número aleatorio entre 1 y 100.
  3. Librería + binario: crea src/lib.rs con una función pública duplicar(n: i32) -> i32 documentada con /// y un doctest; llámala desde main.rs.
  4. Suite de tests: añade al menos tres tests para duplicar (positivos, negativos, cero) usando assert_eq!; corre cargo test y luego un solo test por su nombre.
  5. Pipeline de calidad: introduce deliberadamente dos problemas que Clippy detecte (por ejemplo, un return innecesario o variables prefijables), corrígelos guiándote por sus sugerencias, y termina dejando limpio el comando cargo fmt && cargo clippy && cargo test.

Dominar Cargo temprano multiplica tu velocidad en todo lo demás: es la caja de herramientas que usarás todos los días.
