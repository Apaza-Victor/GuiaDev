Dos clases de fallos: panic! y Result

Rust separa los problemas en dos categorías con mecanismos distintos. Los errores irrecuperables son bugs: violaciones de invariantes tras las cuales no tiene sentido continuar (índice fuera de rango, configuración corrupta). Para ellos existe panic!, que detiene la ejecución desenrollando el stack. Los errores recuperables son situaciones esperables: un archivo inexistente, entrada mal formateada, red caída. Para ellos existe Result, que convierte el fallo en un valor normal del lenguaje:

Criteriopanic!Result<T, E>
NaturalezaBug o invariante rotaSituación esperable y manejable
Quién decide qué hacerNadie: se detiene todoEl llamante con match o ?
Ejemplos típicosBug lógico, assert fallidoArchivo faltante, JSON malformado
Frecuencia esperadaNunca en producciónRutinaria, todos los días
Aparece en la firmaNo: invisible para el llamanteSí: el tipo documenta el riesgo
fn main() {
    let config_ok = false;
    if !config_ok {
        panic!("configuración corrupta: no puedo arrancar");   // aborta TODO
    }
}

Nunca uses panic! para validar entrada de usuario: un dato incorrecto es por definición un error recuperable. Resérvalo para condiciones que evidencian un bug tuyo.

---

Result<T, E>: errores como valores

Result<T, E> es simplemente un enum: Ok(valor) cuando todo fue bien, Err(error) cuando no. El éxito y el fracaso quedan tipados en cada firma — quien llama SABE que la operación puede fallar:

use std::num::ParseIntError;

fn parsear_edad(texto: &str) -> Result<i32, ParseIntError> {
    texto.trim().parse::<i32>()     // parse devuelve Result: lo devolvemos tal cual
}

fn main() {
    match parsear_edad("42") {
        Ok(n) => println!("Edad registrada: {}", n),
        Err(e) => eprintln!("Entrada inválida: {}", e),   // stderr, no stdout
    }
}

unwrap y expect: prototipar sí, producción no

Para avanzar rápido existen atajos que extraen el valor interior o paniquean si hay Err. Legítimos en tests, ejemplos y prototipos; peligrosos en código real:

fn main() {
    // unwrap(): panica si hay Err, sin contexto
    let n = "99".parse::<i32>().unwrap();

    // expect(): igual pero TU mensaje acompaña al panic — siempre mejor
    let home = std::env::var("HOME").expect("HOME debe existir aquí");

    println!("{} {}", n, home);
}

Cada unwrap() es una bomba de tiempo: funciona en tu máquina y revienta en producción con el primer dato raro. Regla profesional: tests pueden usarlo; código de producto maneja el Err con match, combinators como unwrap_or, o propaga con el operador ?.

---

El operador ?: propagación encadenada

Cuando tu función no sabe resolver un error, lo correcto es pasarlo hacia arriba. Sin azúcar sintáctica cada paso exige su propio match con Err(e) => return Err(e); el operador ? condensa todo eso:

use std::fs::File;
use std::io::{self, Read};

fn leer_config() -> Result<String, io::Error> {
    let mut archivo = File::open("config.txt")?;      // si Err → return automático
    let mut contenido = String::new();
    archivo.read_to_string(&mut contenido)?;          // encadena tantos ? como pasos
    Ok(contenido)
}

Cómo funciona ? bajo el capó

Aplicado a un Result: si es Ok(v), evalúa a v y continúa; si es Err(e), ejecuta return Err(From::from(e)) al instante. Esa conversión vía From permite incluso traducir tipos de error distintos hacia el que declara tu función — la base de la sección siguiente.

? solo puede usarse en funciones que devuelven Result u Option. Si intentas usarlo donde no procede, el compilador te sugiere cambiar la firma: otra señal del sistema de tipos trabajando a tu favor.

Errores personalizados con enum propio

Usar String como tipo de error pierde información y complica los match. La solución profesional modela tus fallos como un enum propio —una variante por causa— e implementa tres piezas estándar:

use std::fmt;

#[derive(Debug)]                    // Debug lo exige el ecosistema de errores
enum ErrorApp {
    EdadInvalida(i32),
    NombreVacio,
}

// Pieza 1: Display — mensaje humano para logs y usuarios
impl fmt::Display for ErrorApp {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ErrorApp::EdadInvalida(n) => write!(f, "edad {} fuera de rango", n),
            ErrorApp::NombreVacio => write!(f, "nombre vacío"),
        }
    }
}

// Pieza 2: Error — trait marcador que integra con toda la stdlib
impl std::error::Error for ErrorApp {}

fn validar(nombre: &str, edad: i32) -> Result<String, ErrorApp> {
    if edad < 0 || edad > 130 { return Err(ErrorApp::EdadInvalida(edad)); }
    if nombre.trim().is_empty() { return Err(ErrorApp::NombreVacio); }
    Ok(format!("{} ({})", nombre.trim(), edad))
}

fn main() {
    match validar("", 300) {
        Ok(resumen) => println!("Válido: {}", resumen),
        Err(e) => eprintln!("Rechazado: {}", e),   // usa nuestro Display
    }
}

Tres piezas, un patrón: enum con variantes por causa + impl Display (mensaje humano) + impl Error (integración). Con eso tus errores son inspeccionables con match y compatibles con cualquier librería Rust.

From: conversión automática para el ?

Problema clásico: tu función abre archivos Y parsea números; cada operación devuelve un tipo de error distinto. ¿Qué E pones en la firma? Implementas From de cada error externo hacia el tuyo, y el operador ? traduce solo:

#[derive(Debug)]
enum ErrorApp {
    Archivo(std::io::Error),
    Numero(std::num::ParseIntError),
}

impl From<std::io::Error> for ErrorApp {          // puente 1
    fn from(e: std::io::Error) -> Self { ErrorApp::Archivo(e) }
}

impl From<std::num::ParseIntError> for ErrorApp { // puente 2
    fn from(e: std::num::ParseIntError) -> Self { ErrorApp::Numero(e) }
}

fn procesar(ruta: &str) -> Result<i32, ErrorApp> {
    let contenido = std::fs::read_to_string(ruta)?;   // io::Error → ErrorApp::Archivo
    let numero: i32 = contenido.trim().parse()?;      // ParseIntError → ErrorApp::Numero
    Ok(numero * 2)
}
// Dos tipos de error distintos, UNA firma limpia, cero map_err manuales.

Antes de escribir un .map_err(...) manual, pregúntate si falta un impl From. Una vez escrito, todos los ? de tu codebase se benefician gratis.

main() -> Result y Box<dyn Error>

Incluso main puede devolver un Result: si llega un Err, Rust imprime el error y termina con código de salida distinto de 0 — perfecto para scripts y CLIs. Para no definir un enum propio en cada proyecto, existe el comodín Box<dyn Error>: un puntero a CUALQUIER valor que implemente el trait Error:

use std::error::Error;

fn main() -> Result<(), Box<dyn Error>> {
    let config = std::fs::read_to_string("app.toml")?;  // io::Error encaja aquí

    let puerto: i32 = config
        .lines().next().ok_or("archivo vacío")?         // &str → error dinámico
        .split('=').nth(1).ok_or("falta el puerto")?
        .trim().parse()?;                                // ParseIntError también

    println!("Servidor escuchando en el puerto {}", puerto);
    Ok(())
}
Tipo de errorCuándo elegirloCoste
Box<dyn Error>Apps, scripts, prototipos rápidosAlocación + dispatch dinámico
Enum propioLibrerías y código serioCero: todo estático
StringNunca en producciónImposible de matchear bien

Box<dyn Error> sacrifica la posibilidad de hacer match por variante (solo puedes inspeccionar el mensaje o bajar el tipo con downcast). En librerías públicas usa siempre enums propios.

El ecosistema: thiserror y anyhow

Escribir Display + From a mano es educativo pero repetitivo. El ecosistema estandarizó dos crates que automatizan cada mitad del problema (se añaden a Cargo.toml con cargo add):

  • thiserror — para LIBRERÍAS: genera Display, source() e impl Error desde atributos.
  • anyhow — para APLICACIONES: un Box<dyn Error> mejorado con contexto y backtrace (.context("mensaje")? añade información al propagar).

Buenas prácticas de manejo de errores

  • No tragues errores: un let _ = resultado; descarta silenciosamente fallos que volverán como bugs misteriosos.
  • Propaga con ? y añade contexto cuando subas niveles (.context(...) con anyhow o mensajes propios).
  • Panic solo para bugs: asserts internos e invariantes imposibles; nunca entrada externa.
  • Errores específicos en librerías, genéricos (Box/anyhow) en binarios.
  • Implementa Display legible: tus errores acabarán en logs que personas leerán a las 3 AM.

Buena noticia final: gracias a Result y ?, el "manejo de errores" deja de ser try/catch disperso y se convierte en parte del flujo normal de tipos. Tus funciones declaran sus modos de fallo y el compilador impide ignorarlos.

Ejercicios prácticos

Réslolos en orden; cada uno introduce una pieza nueva del sistema de errores.

  1. Detecta el pánico: escribe una función dividir(a: i32, b: i32) que haga panic! si b == 0, pruébala, y luego reescríbela devolviendo Result<i32, String>; consume ambas versiones con match.
  2. Parseo robusto: lee una edad desde un string fijo ("treinta"), intenta parsearla con unwrap() y observa el panic; corrígelo con match mostrando un mensaje amable.
  3. Cadena de ?: implementa leer_y_sumar(ruta) -> Result<i32, io::Error> que lea un archivo con dos números separados por salto de línea y devuelva su suma usando el operador ? en cada paso fallible.
  4. Error propio completo: crea el enum ErrorInventario con variantes StockInsuficiente(String) y ProductoInexistente(u32); implementa Display + Error y úsalo en una función vender(codigo, cantidad) -> Result<f64, ErrorInventario>.
  5. Main tolerante: convierte un programa simple en main() -> Result<(), Box<dyn Error>> que lea dos archivos y sume sus primeras líneas parseadas; haz que falle borrando uno y verifica el código de salida con $LASTEXITCODE.
