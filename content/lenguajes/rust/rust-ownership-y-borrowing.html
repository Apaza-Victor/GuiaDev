Stack vs Heap: el mapa del territorio

Todas las reglas de ownership existen por cómo se organiza la memoria en ejecución. El stack es una región ordenada y ultrarrápida donde viven los valores de tamaño conocido en compilación: enteros, booleanos, punteros. El heap es la zona flexible donde se colocan datos cuyo tamaño solo se conoce al correr: el contenido de un String, los elementos de un Vec. Acceder al heap cuesta más: hay que pedir espacio al asignador y llegar hasta él mediante un puntero.

Cuando una función termina, su marco del stack se descarta automáticamente. La pregunta que ownership responde es otra: ¿quién libera el bloque del heap? Sin garbage collector, alguien debe liberarlo exactamente una vez.

TamañoFijo y conocido en compilaciónDinámico, crece en ejecución

Ownership: las tres reglas y el move

Ownership es el conjunto de reglas con las que el compilador decide quién limpia cada dato del heap. Son solo tres, pero gobiernan todo:

  1. Cada valor en Rust tiene un único dueño (una variable) en todo momento.
  2. Solo puede haber un dueño a la vez.
  3. Cuando el dueño sale del scope, el valor se libera automáticamente (se llama a drop).
fn main() {
    {                                   // abre un scope interno
        let s = String::from("dueño temporal");
        println!("{}", s);
    }                                   // ← aquí drop(s): heap liberado SIN GC

    let s1 = String::from("guía");
    let s2 = s1;                        // MOVE: la propiedad pasa a s2
    // println!("{}", s1);              // ❌ error[E0382]: s1 ya no posee nada
    println!("{}", s2);                 // ✅ solo el dueño actual puede usarla
}

Move semantics: transferir, no copiar

La asignación let s2 = s1; no duplica el bloque del heap (sería caro); transfiere el "control remoto": ptr/len/cap pasan a s2 y s1 queda invalidada. Así se evita el clásico bug de C++ llamado double free: dos variables creyendo ser dueñas del mismo bloque. El compilador lo explica con el error E0382: borrow of moved value, sugiriendo incluso s1.clone() si la copia fuera aceptable.

Si vienes de Python o JavaScript, este es EL momento de choque: pasar una variable a una función también hace move, y no podrás usarla después. No es un bug del compilador: es el diseño funcionando.

Mover hacia funciones y devolver propiedad

fn consumir(s: String) {
    println!("consumo {}", s);
}                       // s muere aquí: la función ahora es la dueña final

fn producir() -> String {
    String::from("nuevo dueño")   // la propiedad sale hacia quien llame
}

fn main() {
    let texto = String::from("adiós");
    consumir(texto);            // mueve el valor DENTRO de la función
    // println!("{}", texto);   // ❌ moved value: ya pertenece a consumir

    let recuperado = producir();   // y devolverlo transfiere la propiedad afuera
    println!("{}", recuperado);
}

Copy vs Clone: dos formas de duplicar

¿Por qué los enteros NO sufren moves? Porque implementan el trait Copy: son tan baratos de duplicar bit a bit que la asignación copia implícitamente y ambas variables siguen válidas. Los tipos del heap (String, Vec) no pueden ser Copy —duplicarlos sería caro—, así que ofrecen Clone: una copia profunda explícita.

TipoAsignar b = a hace...¿a sigue usable?
i32, f64, bool, charCopy implícito (bits duplicados)Sí, siempre
Tuplas de tipos CopyCopy implícitoSí, siempre
String, Vec<T>, HashMapMOVE (transfiere propiedad)No
Tus structs propiosMOVE salvo que derives Copy/CloneDepende
fn main() {
    // COPY: implícito y barato
    let n1 = 42;
    let n2 = n1;
    println!("{} y {} siguen vivos", n1, n2);

    // CLONE: copia profunda EXPLÍCITA (cuesta tiempo y memoria)
    let s1 = String::from("original");
    let s2 = s1.clone();            // duplica también el heap
    println!("{} y {}", s1, s2);    // ✅ ambos válidos
}

Rust exige escribir .clone() a propósito para hacer visible dónde se paga el coste de copiar. Si te ves añadiendo clones para "callar" al compilador, detente: probablemente necesitas referencias, no copias.

Move y borrow en un diagrama

Antes de entrar a las referencias, fija la intuición visual. Un move cambia quién es dueño sin tocar el heap; un borrow deja la propiedad intacta y entrega acceso temporal:

MOVE   : s1 ──✗──► heap        s2 ──► heap      (el heap NO se copia)
BORROW : r1 = &s , r2 = &s ──► leen el heap de s, que sigue siendo el
         ÚNICO dueño y lo liberará UNA sola vez al salir del scope.

Referencias y las reglas del borrowing

Mover valores hacia funciones es incómodo si luego los necesitas. La solución son las referencias: acceder al dato sin adquirir su propiedad. Con & tomas un préstamo de lectura; con &mut, un préstamo de escritura:

fn longitud(s: &String) -> usize {   // pide prestado, NO toma propiedad
    s.len()
}

fn agregar(saludo: &mut String) {    // préstamo mutable para escribir
    saludo.push_str(", mundo");
}

fn main() {
    let texto = String::from("hola");

    let largo = longitud(&texto);     // préstamo temporal, luego devuelto
    println!("'{}' mide {} caracteres", texto, largo);  // ✅ texto sigue vivo

    let mut saludo = String::from("hola");
    agregar(&mut saludo);              // hay que pedir &mut EXPLÍCITAMENTE
    println!("{}", saludo);            // "hola, mundo"
}

Las reglas del borrowing

El préstamo tiene condiciones estrictas que el borrow checker verifica en compilación. En cualquier punto del programa vale exactamente UNO de estos dos escenarios:

  • Una o muchas referencias inmutables (&T): cualquier cantidad de lectores simultáneos.
  • Exactamente una referencia mutable (&mut T): un único escritor, sin lectores concurrentes.

Nunca ambas a la vez. Y ninguna referencia puede sobrevivir al dato que presta (nada cuelga).

fn main() {
    let mut v = vec![1, 2, 3];

    let r3 = &v;
    v.push(5);                 // ❌ error[E0502]: mutar mientras r3 está vivo
    println!("{}", r3[0]);     // ✅ solución: usar r3 antes del push (NLL)
}

Gracias a la Non-Lexical Lifetimes (NLL), un préstamo termina en su último uso, no al final del bloque. Acortar el alcance de tus referencias es la herramienta número uno para calmar al borrow checker.

Referencias colgantes: imposibles por diseño

fn colgante() -> &String {          // ❌ esto NO compila
    let s = String::from("adiós");
    &s                               // s muere al terminar la función:
}                                    // devolver &s dejaría un puntero inválido
// error[E0106]: missing lifetime specifier — Rust exige probar
// que la referencia sobrevive a la función.

Adelanto: lifetimes

Cuando el compilador no puede inferir cuánto vive una referencia entre varias implicadas, te pide anotarlo con lifetimes: fn mas_larga<'a>(x: &'a str, y: &'a str) -> &'a str declara que el resultado vive como mínimo tanto como ambas entradas. No crean valores nuevos ni cambian nada en runtime: son metadatos para el borrow checker. Las verás a fondo cuando construyas APIs más complejas; por ahora basta reconocerlas.

Slices: vistas sin copiar (&str y &[T])

Un slice es una referencia a una secuencia contigua de elementos: un puntero + longitud, sin copiar nada. El tipo &str que ya usaste en literales ES un slice de cadena:

fn main() {
    let frase = String::from("Hola mundo en Rust");

    let hola = &frase[0..4];      // "Hola" — vista sobre los bytes de frase
    let resto = &frase[5..];      // desde el índice 5 hasta el final
    let todo = &frase[..];        // toda la cadena

    println!("{} | {} | {}", hola, resto, todo);
}                                  // frase sigue siendo la dueña única
SliceApunta aEjemplo
&strBytes UTF-8 de un texto&texto[0..4], "literal"
&[T]Elementos contiguos de array/Vec&v[1..3]

Firma idiomática: prefiere parámetros genéricos como &str y &[T] antes que &String/&Vec<T>. Por coerción de deref aceptan ambos casos y tu API resulta más flexible.

Los rangos de &str cortan por BYTES, no por caracteres: &texto[0..3] hace pánico si cae dentro de un carácter multibyte (como 'ñ' o '🚀'). Para recorrer por caracteres usa .chars().

Errores comunes del borrow checker

Estos cuatro mensajes concentran el 90% de las peleas iniciales con el compilador. Apréndelos como viejos conocidos:

ErrorCausa raízSalida típica
E0382 borrow of moved valueUsar variable tras un movePasa &valor o clona conscientemente
E0502 cannot borrow as mutable...Solapaste & con &mutReduce el alcance de los préstamos
E0597 does not live long enoughLa referencia sobrevive al dueñoDevuelve valor propio (String) no referencia
E0106 missing lifetime specifierFirma ambigua entre entradas/salidaAnota lifetimes explícitos ('a)

No "resuelvas" el borrow checker sembrando .clone() por todas partes: funciona pero esconde el problema real (diseño de propiedades) y mata rendimiento. Entiende el mensaje, reorganiza alcances, y clona solo cuando el coste esté justificado.

Buenas noticias: el borrow checker es conservador pero justo. Si compila, tu código no tiene carreras de datos ni punteros colgantes — toda esa clase de bugs desaparece de tu depurador.

Ejercicios prácticos

Hazlos en orden: provocar el error y arreglarlo enseña más que evitarlo.

  1. Detecta el move: crea un String, asígnalo a otra variable, intenta imprimir la original, lee el error E0382 completo y arréglalo de dos formas: con .clone() y pasando una referencia.
  2. Función que presta: escribe fn contar_vocales(texto: &str) -> u32 y llámala tres veces seguidas con el mismo String para demostrar que los préstamos inmutables pueden repetirse libremente.
  3. Rompe las reglas a propósito: dentro de un mismo scope, mantén un &vec activo mientras haces push; observa E0502 y corrígelo acotando el préstamo en un bloque interno.
  4. Slices de texto: dada la frase "Aprendiendo Rust con GuiaDev", extrae con slices la primera palabra, la última (con split_whitespace().last()) y una función palabra_mas_larga(frase: &str) -> &str.
  5. Reto lifetime: implementa fn mas_larga<'a>(x: &'a str, y: &'a str) -> &'a str, pruébala con un literal estático y un String local, y explica por qué el compilador rechaza devolver una referencia creada DENTRO de la función.
