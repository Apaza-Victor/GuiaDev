¿Para qué sirve y cuándo usarla? Concepto

El desarrollo en C# y .NET se apoya en un conjunto de IDEs y herramientas: Visual Studio, Rider, VS Code con el SDK, la CLI de dotnet y paquetes de calidad. Esta página compara estas opciones y orienta sobre cuándo usar cada herramienta.

¿Para qué se usa?

  • Desarrollar, compilar y depurar proyectos .NET en Visual Studio o Rider.
  • Usar la CLI de dotnet para scaffolding, build, test y publicación sin IDE.
  • Integrar formato, análisis estático y tests con las herramientas del SDK.
  • Gestionar paquetes y dependencias con los repositorios ya configurados.

¿En qué casos conviene usarla?

  • Para desarrollar sobre Windows con la experiencia completa de Visual Studio.
  • Cuando el proyecto es multiplataforma y se prefiere VS Code o Rider con el SDK.
  • Para automatizar builds y CI/CD usando la CLI de dotnet en repositorios.

No dependas solo del IDE para publicar o testear: domina la CLI de dotnet porque es la base de CI/CD y de trabajo en equipo. El editor es una comodidad; el SDK es el que realmente genera el artefacto.

La CLI: dotnet CLI

dotnet new sln -o Solucion
dotnet new classlib -o Lib && dotnet new console -o App
dotnet sln add Lib App            # organiza proyectos en como .sln
dotnet add App reference Lib      # referencia entre proyectos
dotnet build                      # compila
dotnet run --project App          # ejecuta
dotnet test                       # corre tests
dotnet publish -c Release -o dist # publica una carpeta desplegable
dotnet tool install --global dotnet-ef   # EF Core CLI

# Templates propios
dotnet new install /ruta/mi-plantilla

Todo en .NET puede hacerse con la CLI: crear, compilar, testear, publicar. Es el primer comando que debes dominar antes de abrir el IDE.

Diagnóstico y perfilado Diagnóstico

// dotnet-counters: métricas de proceso en vivo
dotnet tool install --global dotnet-counters
dotnet-counters monitor --process-id 1234
// Muestra CPU, GC, memoria, excepciones en tiempo real.

// dotnet-dump: snapshot de una app en ejecución
dotnet tool install --global dotnet-dump
dotnet-dump collect -p 1234 -o mem.dump
dotnet-dump analyze mem.dump   # "clrstack", "dumpheap -stat"

// dotnet-trace: perfilado de eventos
dotnet tool install --global dotnet-trace
dotnet-trace collect -p 1234 --format speedscope

# Visual Studio: profiler de CPU, asignaciones y snapshot de memoria integrados
# jetBrains dotMemory / dotTrace: alternativas multiplataforma de pago
# PerfView: deep-dive de eventos (gratuito, de Microsoft)

Los comandos `dotnet-counters` + `dotnet-dump` + `dotnet-trace` cubren el diagnóstico sin necesidad de IDE: métricas, dump de memoria y eventos de rendimiento.

Contenedores y despliegue Cloud

# Dockerfile para ASP.NET Core (multi-stage)
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY --from=build /app .
EXPOSE 8080
ENTRYPOINT ["dotnet", "App.dll"]

# Publicación en Azure/AWS/locales
dotnet publish -c Release -o publish
# Azure: "az webapp deploy"; AWS: "dotnet-aws-lambda" tool
# AOT nativo: dotnet publish -c Release -r win-x64 -p:PublishAot=true
#   (arranque instantáneo y binario sin JIT/Runtime instalado)

AOT (NativeAOT) compila a nativo con `PublishAot`, reduciendo arranque y memoria; útil en serverless. Pesa en tamaño y no soporta toda la reflexión dinámica.

Calidad de código: analyzers y formato Calidad

// analizadores de .NET (EditorConfig + CodeAnalysis)
// .editorconfig activa reglas por severidad:
[*.cs]
dotnet_diagnostic.CA1801.severity = warning   # parámetro no usado
dotnet_diagnostic.IDE0090.severity = warning  # evitar 'new Tipo()' con var

// formato automático
dotnet format whitespace --folder .   # solo espacios
dotnet format style --folder .
dotnet format analyzers --folder .    # reglas de análisis
// o al estilo global: dotnet format --verify-no-changes (CI friendly)

Vigila que `dotnet format` y `dotnet build` en CI fallen si hay problemas: tienes calidad automática sin depender del criterio individual en cada PR.

Ejercicios prácticos Reto

  1. Con la CLI crea solución + librería + consola y compila desde terminal.

  4. Escribe el Dockerfile de un WebAPI y compila/ejecuta en contenedor.
