¿Para qué sirve y cuándo usarla? Concepto

Kotlin comparte el ecosistema JVM y además tiene frameworks propios. Esta página compara Ktor, un framework asíncrono y ligero del propio ecosistema, con Spring Boot en su variante para Kotlin, y menciona Compose para interfaces.

¿Para qué se usa?

  • Construir backends ligeros y asíncronos con corrutinas mediante Ktor.
  • Aprovechar la madurez del ecosistema Spring escribiendo en Kotlin.
  • Desarrollar interfaces multiplataforma con Compose.

¿En qué casos conviene usarla?

  • En microservicios donde priman rendimiento y bajo overhead.
  • En equipos que ya dominan Spring y pasan a Kotlin de forma gradual.
  • En apps Kotlin multiplataforma que comparten lógica de negocio.

Ktor es más flexible pero te obliga a ensamblar más piezas; Spring Boot trae todo preconfigurado. Decide si prefieres control o velocidad inicial, no ambos a la vez.

Ktor: servidor Kotlin-first Backend

import io.ktor.server.application.*
import io.ktor.server.engine.*
import io.ktor.server.netty.*
import io.ktor.server.routing.*
import io.ktor.server.response.*
import io.ktor.server.request.*

fun main() {
    embeddedServer(Netty, port = 8080) {
        routing {
            get("/saludo/{nombre}") {
                call.respondText("Hola ${call.parameters["nombre"]}")
            }
            post("/usuarios") {
                val body = call.receive<String>()
                call.respond("recibido: $body")
            }
        }
    }.start(wait = true)
}

Ktor (Netty/CIO engines) da rutas, middleware (frac), auto-doc con OpenAPI y se integra con corutinas de serie. Empieza con Generador `start.ktor.io`.

Spring Boot con Kotlin Framework

import org.springframework.boot.autoconfigure.SpringBootApplication
import org.springframework.boot.runApplication
import org.springframework.web.bind.annotation.*

@SpringBootApplication
class MiApp

fun main(args: Array<String>) {
    runApplication<MiApp>(*args)
}

@RestController
@RequestMapping("/api/usuarios")
class UsuarioController {
    @GetMapping("/{id}")
    fun obtener(@PathVariable id: Long) = Usuario(id, "Ana")
}

data class Usuario(val id: Long, val nombre: String)

Kotlin se integra nativo en Spring: data classes para DTO, null-safety para campos y corutinas (`suspend` en endpoints) con `spring-webflux`.

Exposed y persistencia Datos

// Exposed (JetBrains): DSL SQL-céntrico para Kotlin
import org.jetbrains.exposed.sql.*
import org.jetbrains.exposed.sql.transactions.transaction

object Usuarios : Table("usuarios") {
    val id = integer("id").autoIncrement()
    val nombre = varchar("nombre", 100)
    override val primaryKey = PrimaryKey(id)
}

fun main() {
    Database.connect("jdbc:sqlite:app.db", "org.sqlite.JDBC")
    transaction {
        SchemaUtils.create(Usuarios)
        Usuarios.insert { it[nombre] = "Ana" }
        Usuarios.selectAll().forEach { println(it[Usuarios.nombre]) }
    }
}
// Alternativas: Spring Data JPA (con Kotlin), Exposed DAO,
//              jdbi para SQL directo, R2DBC para reactive

Exposed es el ORM de JetBrains con DSL tipado; Spring Data JPA es el estándar sino; para SQL directo jdbi. Elige según tu framework.

Testing: kotest y JUnit Calidad

// JUnit 5: el estándar interoperable con Java
import org.junit.jupiter.api.Test
import kotlin.test.assertEquals

class CalculadoraTest {
    @Test
    fun sumaEsCorrecta() {
        assertEquals(5, Calculadora.suma(2, 3))
    }
}

// Kotest: estilo funcional con muchos matchers
import io.kotest.core.spec.style.StringSpec
import io.kotest.matchers.shouldBe

class CalcSpec : StringSpec({
    "suma dos números" {
        Calculadora.suma(2, 3) shouldBe 5
    }
})

// MockK: framework de mocks para Kotlin (alternativa a Mockito)
// Correr con Gradle: ./gradlew test

kotest es el framework favorito de Kotlin; MockK para mocks; JUnit 5 para compartir test con Java. `kotest` + `MockK` + Gradle es el stack común.
