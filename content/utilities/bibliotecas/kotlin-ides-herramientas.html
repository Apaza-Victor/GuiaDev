¿Para qué sirve y cuándo usarla? Concepto

El desarrollo con Kotlin se apoya en herramientas maduras: IntelliJ IDEA como IDE de referencia, Android Studio para móvil, Gradle con su DSL en Kotlin para los builds y linters como KtLint y Detekt para la calidad del código.

¿Para qué se usa?

  • Editar, depurar y refactorizar con IntelliJ, el entorno oficial del lenguaje.
  • Desarrollar apps Android con Android Studio y el plugin de Kotlin.
  • Configurar builds y dependencias con Gradle en Kotlin DSL.

¿En qué casos conviene usarla?

  • En proyectos Android nuevos escritos en Kotlin desde la primera línea.
  • En backends JVM que quieren builds con Gradle Kotlin DSL.
  • En equipos que aplican análisis estático con Detekt en el CI.

Kotlin multiplataforma añade complejidad de configuración en expect y actual y en el build. No lo actives si el proyecto no necesita más que un destino real.

IDEs Kotlin: IntelliJ y Android Studio IDE

# IntelliJ IDEA (Community/Ultimate): el de JetBrains para JVM/Kotlin
#   - plugin Kotlin integrado (o automático)
#   - refactorizaciones, debugging, convertidor Java->Kotlin
# Android Studio (basado en IntelliJ): para apps Android
#   incluye emulador, Gradle Android y Jetpack Compose preview
# VS Code: extensión "Kotlin (Multiplatform)" para edición ligera
# Kotlin Multiplatform: JetBrains ofrece "Fleet" (de pago) reciente

IntelliJ es la sede de Kotlin: soporte más profundo. Android Studio imprescindible si trabajas en móvil. Ambos compatibles con todo el tooling de JetBrains.

kotlinc, Gradle y herramientas CLI CLI

# Compilar directamente
kotlinc Main.kt -include-runtime -d app.jar
# Gradle: build estándar (Kotlin DSL build.gradle.kts)
./gradlew build
./gradlew test
# Maven también soporte con kotlin-maven-plugin

# ktlint: linter de código Kotlin
ktlint src/**/*.kt
# detekt: análisis estático con reglas (como spotbugs)
detekt
# kover: cobertura de código (de JetBrains)
./gradlew koverMergedReport

Gradle+Kotlin DSL es el build del ecosistema; ktlint (formato/lint) y detekt (reglas estáticas) se integran como plugins de Gradle.

Herramientas Android específicas Android

# adb: conectar/depurar dispositivos y emuladores
adb devices
adb install app-debug.apk
adb logcat                  # logs del dispositivo
adb shell dumpsys          # servicios del sistema

# Emulador: avdmanager / Android Studio Device Manager
# Herramientas de UI: Layout Inspector, Compose Preview
# Performance: Android Profiler (CPU/mem/red/batería)
# Tamaño/bugs: R8 (shrinker), ProGuard (minifier)

# CI Android: Gradle Managed Devices + GitHub Actions (ReactiveCircus/android-emulator-runner)

Android trae su propia caja de herramientas: adb, emulador, profiler. La CI con emulador GitHub Actions cubre tests de instrumentación automática.

Kotlin Multiplatform y despliegue KMP

// KMP (Kotlin Multiplatform): compartir lógica Android+iOS+web+desktop
//   - kotlin-multiplatform plugin en Gradle
//   - expect/actual para APIs de plataforma
expect fun currentPlatform(): String
actual fun currentPlatform() = "Android"

// Uso típico: compartir modelos, networking, lógica de negocio
// publicar (Android): assembleRelease, track a/b en Google Play
// iOS: Kotlin/Native + Compose Multiplatform para UI compartida

# Despliegue backend (Spring Boot/Ktor) en contenedor
./gradlew bootJar
docker build -t mi-api .
docker run -p 8080:8080 mi-api

KMP permite compartir lógica entre plataformas con `expect/actual`. Para apps nuevas: un backend JVM + app Android (y KMP cuando llegues a iOS).

Ejercicios prácticos Reto

  1. Convierte una clase Java existente a Kotlin usando el conversor de IntelliJ.
  2. Configura ktlint+détect en Gradle y hazlo fallar en CI si hay lints.
  3. Instala y usa adb para ver bugs de logcat de una app propia.
  4. Crea un módulo KMP `shared` con `expect/actual currentPlatform`.
  5. Genera `bootJar` de Spring Boot y desplega en Docker (healthcheck).
