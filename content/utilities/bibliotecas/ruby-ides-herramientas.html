¿Para qué sirve y cuándo usarla? Concepto

El entorno de desarrollo en Ruby combina el editor (RubyMine, VS Code con Solargraph), el control de calidad (RuboCop, bundler-audit, Brakeman), la depuración (byebug, pry) y el despliegue (Docker, Puma/Nginx, PaaS). Esta página reúne esas herramientas de producción.

¿Para qué se usa?

  • Autocompletado y navegación de código con Solargraph (LSP) en cualquier editor.
  • Lint y estilo con RuboCop, con reglas específicas para Rails.
  • Detectar vulnerabilidades de gemas y código con bundler-audit y Brakeman.
  • Depurar con byebug y medir rendimiento con benchmark o stackprof.

¿En qué casos conviene usarla?

  • Equipos que comparten convenciones: RuboCop y bundler-audit en CI.
  • Investigar bugs de flujo con byebug en lugar de prints aislados.
  • Rails en producción: audit de gemas y Brakeman antes de cada release.

No dejes `binding.pry` ni `byebug` en producción: bloquean la ejecución en esa línea. En producción se monitoriza con logs y métricas reales; la depuración interactiva es solo para desarrollo local.

RuboCop, Bundler Audit y brakeman Calidad

# RuboCop: linting y estilo (convención Ruby estricta)
gem install rubocop
rubocop --require rubocop-rails
rubocop --auto-gen-config    # generar excepciones iniciales
rubocop -a                   # autocorregir lo seguro

# Bundler Audit: vulnerabilidades en gemas
gem install bundler-audit
bundle audit check --update

# Brakeman: análisis de seguridad para Rails
gem install brakeman
brakeman -A                  # scan completo

# Mejora: intégralos en la CI (railsoft, semgrep...)

RuboCop (estilo) + bundler-audit (vulns) + Brakeman (seguridad Rails) son el tándem de calidad barato que cualquier proyecto Ruby debería ejecutar.

Depuración: byebug y debug Debug

# byebug (o la gema debug de Rails)
require "byebug"
byebug                 # pausa con consola interactiva
# Comandos: next, step, continue, display, backtrace, break line

# Técnicas de scripting
require "pry"
binding.pry
# inside the editor: VSCode Ruby (ruby-debug-ide) con breakpoints visuales

# Profiling: benchmark, memory profiler, stackprof
require "benchmark"
Benchmark.realtime { 1_000_000.times { 2 ** 10 } }
# stackprof: muestras por método para hotspots
gem install stackprof

No dejes `binding.pry`/`byebug` en producción: se bloquean en esa línea. M o bien usa logs y métricas en producción.

Producción y despliegue Ruby Ops

# App Rails en contenedor
FROM ruby:3.3-slim
RUN apt-get update && apt-get install -y build-essential libpq-dev
WORKDIR /app
COPY Gemfile Gemfile.lock ./
RUN bundle install
COPY . .
EXPOSE 3000
CMD ["bin/rails", "server", "-b", "0.0.0.0"]

# Alternativas de despliegue
#  - Heroku/Render/Fly: PaaS sin administrar servidores
#  - Puma + Nginx en una VPS (config típica)
#  - Kubernetes para escalar (con Dockerfile arriba)
#  - Kamal (de Rails): deploy simple con Docker solo
#  - Sidekiq necesita Redis: planifica env vars para el worker

Puma + Nginx o un PaaS + Kamal cubre los escenarios típicos de Rails. Todos hoy pasan por CI que corre `bundle exec rspec` y `brakeman`.

Ejercicios prácticos Reto

  1. Instala Solargraph en VS Code y usa "ir a definición" en una gema.
  2. Ejecuta RuboCop en tu app Rails y corrige 5 ofensas con `-a`.
  3. Haz `bundle audit check` y explica las vulnerabilidades que reporte.
  4. Coloca `binding.byebug` en un job lento y recorre variables con next/step.
  5. Escribe el Dockerfile de tu Rails + puma y despliégalo en Heroku/Render.
