¿Para qué sirve y cuándo usarla? Concepto

La experiencia de desarrollo en Perl depende del entorno: perlbrew para gestionar versiones, cpanm para instalar módulos, el lenguaje de servidor perl-languageserver para el editor y prove para ejecutar pruebas.

¿Para qué se usa?

  • Instalar y alternar versiones de Perl con perlbrew en el usuario.
  • Instalar módulos de CPAN de forma rápida con cpanm.
  • Depurar y probar módulos con prove y las herramientas de testing de la distribución.

¿En qué casos conviene usarla?

  • En entornos de usuario donde no quieres tocar el Perl del sistema.
  • En desarrollo con editores modernos mediante el lenguaje de servidor.
  • Para asegurar calidad con pruebas antes de cada despliegue.

Configura perl-languageserver con la misma versión de perlbrew que usa el proyecto: si el LSP inspecciona otra versión, los diagnósticos serán engañosos.

Editores y LSP Perl IDE

# Opciones:
#   - Padre (PADRE) IDE antiguo Perl; comunidad alterna
#   - VS Code: extensión "perl" + "Perl Language Server" (options)
#   - IntelliJ + plugin Perl
#   - Vim/NeoVim con perlbrew y entorno: recomendar brown-visual
# Mejor opción hoy: VS Code + extensions (perl, perl-env) y
#   use dzil (Dist::Zilla) como orquesta de proyecto

No hay un solo LSP maduro; VS Code con las extensiones Perl es lo más práctico, y `perl -c` (sintaxis) más `prove` lo hacen bien verificable desde terminal.

perlcritic, Perl::Tidy y buenas prácticas Calidad

# perlcritic: linter de estilo (estándares de la comunidad)
cpanm Perl::Critic
perlcritic --severity 3 script.pl
# config personalizada en .perlcriticrc

# perltidy: formateo/clasificación de código
cpanm Perl::Tidy
perltidy -b -bext='/' # .bak al remoto

# análisis
perl -c script.pl                     # solo sintaxis
prove -l t/                           # tests
perldoc -f function                   # documentación
# Dist::Zilla para packaging, MiniCPAN para repos locales

Perl::Critic aplica "Perl Best Practice"; perltidy normaliza estilo; `perl -c` es el sanity check clásico de sintaxis en cualquier script.

Depuración: settrace, Devel::NYTProf Debug

# Depuración interactiva: perl debugger (-d)
perl -d script.pl
# dentro: b breakpoint, s step, n next, p print, w watch, C continuar

# Tracing de variables - warn/Data::Dumper (rápido)
use Data::Dumper; warn Dumper(\@datos);

# Devel::NYTProf: perfilador de rendimiento
cpanm Devel::NYTProf
perl -d:NYTProf script.pl
nytprofhtml

# recursos: perlmonks, perldoc, stackoverflow (etiqueta perl)

`perl -d` y breakpoints funcionan por terminal; poderoso aunque menos visual. En IDE meJorar: Padre soporto debug también. NYTProf es el gold standard de profiling.

Despliegue y empaquetado Ops

# Distribución con Dist::Zilla (dzil) o Module::Build
dzil build          # genera tarball distribuible
dzil test           # corre tests antes de build
# Empaquetar script standalone: par / PAR (App::PAR)
#   puede crear ejecutables con perl incluyendo módulos
# cpanfile + Carton para lock de versiones

# Despliegue en contenedor

FROM perl:5.40-slim
RUN cpm install -g --no-test @cpanfile
COPY . /app
WORKDIR /app
EXPOSE 3000
CMD ["starman", "--listen", ":3000", "app.pl"]

Dist::Zilla y Carton estabilizan el ciclo de lanzamientos; starman (Plack server prefork) es el worker de producción típico; la imagen `perl:slim` lleva la base mínima.

Ejercicios prácticos Reto

  1. Corre `perlcritic --severity 3` sobre tu script y corrige 5 avisos.
  2. Aplica perltidy y revisa el diff.
  3. Usa `perl -d` para depurar un bucle con múltiples breakpoints.
  4. Perfilea con NYTProf un script que procese 100K líneas.
  5. Arma un Dockerfile perl+slim con starman para tu app web.
