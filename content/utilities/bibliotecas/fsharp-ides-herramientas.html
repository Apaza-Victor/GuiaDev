¿Para qué sirve y cuándo usarla? Concepto

El desarrollo en F# se apoya en editores con el complemento Ionide y en la toolchain de .NET: VS Code, Visual Studio y JetBrains Rider ofrecen soporte integrado. Esta página compara las opciones de IDEs y herramientas para escribir F# con fluidez.

¿Para qué se usa?

  • Completado, inferencia y documentación con Ionide en VS Code.
  • Compilar, ejecutar y probar proyectos F# con la CLI de dotnet.
  • Explorar y ejecutar fragmentos con FSI, la consola interactiva de F#.
  • Formatear y analizar código para mantener calidad.

¿En qué casos conviene usarla?

  • Para el desarrollo diario en VS Code con Ionide.
  • Cuando aprovechas la consola FSI para prototipar lógica de datos.
  • Para integrar tests y builds de F# en CI/CD.

No dependas solo del IDE: la consola FSI y la CLI de dotnet son clave para explorar y compilar F#. Si usas VS Code, instala Ionide y familiarízate con FSI para sacar máximo partido al lenguaje.

---

Editores y F# IDE IDE

# VS Code + Ionide (el LSP de F#)
code --install-extension ionide.ionide-fsharp
# ionide: FS (LSP), debugging, FSI, formateo
# Visual Studio (Windows): soporte F# incluido (excepcional)
# Rider (JetBrains): plugin F# opcional
# dotnet fsi (REPL) está siempre disponible en terminal

# Config: formatter Fantomas integrado en Ionide
# CI: dotnet build / test

Ionide (LSP) es el estándar en VS Code; VS Studio en Windows es de facto para .NET. `dotnet fsi` para probar scripts; Fantomas para formatear.

---

Fantomas, dotnet tools y calidad CLI

# Fantomas: formatter oficial de F# (configurable)
dotnet tool install -g fantomas
fantomas *.fs *.fsx
fantomas --check src/        # CI

# Herramientas de calidad en .NET
dotnet tool install -g dotnet-ef          # Entity Framework CLI
dotnet tool install -g sonarscanner       # SonarQube análisis
dotnet build --no-restore
dotnet test
# FSharpCompiler.Service para analizar; Ionide cubre IDE

# BenchmarkDotNet para microbenchmarks (es de C#, funciona igual)

`dotnet tool` instala utilidades globales (Fantomas, ef, sonarscanner). Fantomas es obligatorio en proyectos serios; `dotnet build/test` el ciclo básico.

Depuración y FSI Debug

# FSI (F# Interactive) como laboratorio
dotnet fsi
#   enviar línea, revisar tipos (;; separa envíos)
# In Ionide/VS: envía a FSI con atajo (Alt+Enter)

# Debugger completo: VS/Rider/Ionide ponen breakpoints
#   (xx: junto con .NET: watch, callstack)
# Logs con Logger/printfn; props:
#   #time "on" | #quieton

# Profiling .NET : dotnet-trace / dotnet-counters
dotnet tool install -g dotnet-trace
dotnet-trace collect -- dotnet run

FSI es tu mejor amigo: envía fragmentos y pregúntale tipos. Para perfiles reales: usa dotnet-trace (contador, sampling) y `#time` para experimentos rápidos.

Publicar y desplegar Ops

# Publicar binario autocontenido (Giraffe/console)
dotnet publish -c Release -r linux-x64 --self-contained
# genera binario native plugin runtime (puede caber ~50-100MB)
# para menor tamaño: selfcontained false + runtime de la imagen

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /app
COPY *.fsproj ./
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -r linux-x64 --self-contained false -o out

FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY --from=build /app/out .
EXPOSE 8080
ENTRYPOINT ["dotnet", "MiApp.dll"]

`dotnet publish` autocontenido = sin runtime instalado en el destino; o multi-stage con imagen aspnet. Kestrel (ASP.NET) escucha en 0.0.0.0:8080 con UseUrls/ASPNETCORE_URLS.
