¿Para qué sirve y cuándo usarla? Concepto

Un ORM mapea las tablas de la base de datos a objetos de tu lenguaje y viceversa, acelerando el CRUD típico. Esta página explica cuándo conviene usar uno (SQLAlchemy, Prisma, Hibernate, EF Core, Eloquent, GORM) y cuándo es mejor un query builder (Knex, jOOQ) o SQL directo.

¿Para qué se usa?

  • Crear, leer, actualizar y borrar registros sin escribir SQL a mano.
  • Modelar relaciones y migraciones desde el código del dominio.
  • Mantener las consultas tipadas y cercanas al lenguaje del equipo.
  • Ejecutar consultas complejas con query builders manteniendo control y seguridad.

¿En qué casos conviene usarla?

  • CRUD estándar con pocas consultas complejas: el ORM multiplica la productividad.
  • Aplicaciones cuyo modelo de dominio cambia a menudo y necesitan migraciones guiadas.
  • Equipos que prefieren expresarse en el lenguaje de alto nivel en vez de SQL crudo.

Cuando la consulta se vuelve retorcada (subqueries anidadas, funciones de ventana, modelos de datos raros), el SQL directo o un query builder es más claro y rápido que pelear con el ORM. Y aprende a leer el SQL que genera tu ORM: ahí aparecen los problemas de N+1.

Ejemplo: las mismas tablas en tres ORMs Ejemplo

# SQLAlchemy (Python)
class Usuario(Base):
    __tablename__ = "usuarios"
    id = Column(Integer, primary_key=True)
    nombre = Column(String(100))
    ordenes = relationship("Orden")

sesion.add(Usuario(nombre="Ana"))
sesion.commit()
adultos = sesion.query(Usuario).filter(Usuario.nombre.like("A%")).all()

// Prisma (TypeScript)
const usuario = await prisma.usuario.create({
  data: { nombre: "Ana", email: "ana@x.com" },
});
const mayores = await prisma.usuario.findMany({
  where: { ordenes: { some: { total: { gt: 100 } } } },
  orderBy: { id: "desc" },
});

// GORM (Go)
db.Create(&Usuario{Nombre: "Ana"})
var adultos []Usuario
db.Where("nombre LIKE ?", "A%").Find(&adultos)

La lógica es similar en todos: definir el modelo, crear, consultar con condición. Cada ORM tiene su dialecto; aprender uno facilita los demás.

Query builders para control fino Consulta

// Knex (JS): las mismas consultas pero con build programático
const usuarios = await knex("usuarios")
  .join("ordenes", "ordenes.usuario_id", "usuarios.id")
  .where("ordenes.total", ">", 100)
  .select("usuarios.nombre", knex.raw("SUM(ordenes.total) AS total"))
  .groupBy("usuarios.id")
  .orderBy("total", "desc");

// jOOQ (Java): SQL tipado en Java
List<Usuario> u = dsl
  .selectFrom(USUARIO)
  .where(USUARIO.NOMBRE.like("A%"))
  .orderBy(USUARIO.ID.desc())
  .fetch();

# PyDAL / peewee son alternativas ligeras a SQLAlchemy
from peewee import *
db = SqliteDatabase("app.db")
class Usuario(Model):  # select con sintaxis similar
    db.connect()

Los query builders dan el control del SQL sin perder la construcción tipada/programática. Perfectos para consultas dinámicas complejas.

Más allá del SQL puro: hibridos y NoSQL Datos

-- PostgreSQL con JSONB: mezclar documental y relacional
CREATE TABLE eventos (id SERIAL PRIMARY KEY, payload JSONB);
CREATE INDEX ON eventos USING GIN (payload);
SELECT * FROM eventos WHERE payload @> '{"tipo": "login"}';

# Alternativas NoSQL según caso
#  - MongoDB/Redis: documentos/caché                                                                  - caso clave
#  - Elastic/OpenSearch: búsqueda full-text y logs
#  - ClickHouse/ TimescaleDB: series temporales y OLAP
# Patrón poliglota: SQL para transacciones + una herramienta dedicada para lo demás

JSONB de PostgreSQL cubre muchos usos "documentales" sin cambiar de base. Añade Redis para caché/contadores y Elastic para búsqueda en texto.
