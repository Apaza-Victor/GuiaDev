¿Para qué sirve y cuándo usarla? Concepto

Escribir PowerShell en un editor sin asistencia es propenso a errores: elegir bien la herramienta marca la diferencia entre scriptear a ciegas y trabajar con autocompletado, ayuda integrada y depuración. Esta página repasa los editores, consolas y utilidades que acompañan al lenguaje en el día a día.

¿Para qué se usa?

  • Editar scripts con autocompletado, resaltado y análisis estático (VS Code + extensión PowerShell).
  • Depurar paso a paso, con puntos de interrupción e inspección de variables.
  • Ejecutar y probar cmdlets en consolas modernas (pwsh, Windows Terminal).
  • Mantener estilo y calidad: PSReadLine y PSScriptAnalyzer.

¿En qué casos conviene usarla?

  • Desarrollo diario: VS Code con la extensión oficial de Microsoft PowerShell.
  • Automatización ligera: el propio terminal o la consola clásica de Windows.
  • Equipos grandes: añade PSScriptAnalyzer al pipeline para mantener un estilo consistente.

PowerShell 7 (pwsh) es el shell moderno y multiplataforma: evita quedarte en Windows PowerShell 5.1 salvo que un módulo antiguo lo exija. Y no confundas editor con runtime: puedes ejecutar tus scripts contra pwsh desde cualquier IDE.

VS Code + extensión PowerShell IDE

# VS Code con la extensión PowerShell (Microsoft)
code --install-extension ms-vscode.PowerShell
#   - LSP (PowerShell Editor Services): lint, autocompletado
#   - ISE (Integrated Scripting Environment) es legacy:
#       VS Code la reemplaza; el ISE no acepta PS 7
# Windows Terminal se recomienda como terminal base (mejor que consola)

# En otros editores: Neovim con lspconfig + PowerShell Editor Services
# JetBrains IDE: plugin PowerShell

VS Code + extensión PowerShell (basada en PowerShell Editor Services/LSP) es el estándar moderno; el ISE quedó para PowerShell 5.1 en Windows.

PSScriptAnalyzer: lint oficial Calidad

# PSScriptAnalyzer: el analizador estático oficial
Install-Module -Name PSScriptAnalyzer
Invoke-ScriptAnalyzer -Path . -Recurse -Severity Warning, Error

# Reglas de estilo/seguridad: PSUseShouldProcessForStateChangingFunctions,
#   PSUseSingularNouns, AvoidUsingPlainTextForPassword, etc.
# Supresiones por línea con [Diagnostics.CodeAnalysis.SuppressMessage]
# Formato integrado en VS Code con la extensión PowerShell Preview
# Integración en CI: Invoke-ScriptAnalyzer en steps de Actions

PSScriptAnalyzer detecta errores y malas prácticas; se integra en IDE y CI. Junto con Pester forman el piso de calidad para scripts de producción.

Depuración PowerShell Debug

# En VS Code: breakpoints, watch, step (DAP con PowerShell)
# Desde terminal también: Set-PSBreakpoint -Script x.ps1 -Line 14
Set-PSBreakpoint -Script .\script.ps1 -Line 14
Get-PSCallStack                # pila actual de ejecución

# Mensajes de log clasificados (streams)
Write-Verbose "detalle" -Verbose
Write-Debug "x" -Debug
Write-Information "INFO" -InformationAction Continue

# Errores: $Error[0], try/catch/finally, -ErrorAction
try {
    Get-Item inexistente.txt -ErrorAction Stop
} catch {
    Write-Error "falló: $($_.Exception.Message)"
}

VS Code (DAP) es el debugger visual; desde terminal con `Set-PSBreakpoint` + `Get-PSCallStack`. Los streams (Verbose/Debug/Information) organizan el logging.

Empaquetar y CI/CD Ops

# Nada especial: scripts .ps1 + módulos (.psm1) son "el paquete"
# Opciones:
#   - Publicar módulo en PSGallery (NuGet): Publish-Module
#   - nuspec vía NuGet cli para distribución privada
#   - Convertir a exe con PS2EXE (opcional, no recomendado)

# CI/CD en GitHub Actions: runner de Windows vienen con pwsh
#   steps:
#     - run: |
#         Install-Module Pester -Force
#         Invoke-Pester -CI
#   En Azure DevOps: task PowerShell@2

El "deployable" es el módulo/script + tests. Corre en cualquier runner (Windows/Linux/MAC) con pwsh. La gestión de identidades va por secretos (GH) o service connections.
