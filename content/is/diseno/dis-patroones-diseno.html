¿Qué son los patrones de diseño?

Un patrón de diseño es una solución general y reutilizable para un problema recurrente en el diseño de software. No es código listo para copiar, sino una plantilla conceptual que describe cómo estructurar las clases y objetos para resolver un problema específico en un contexto concreto.

El término se popularizó con el libro "Design Patterns: Elements of Reusable Object-Oriented Software" (1994), escrito por cuatro autores conocidos como la Gang of Four (GoF): Erich Gamma, Richard Helm, Ralph Johnson y John Vlissides. El libro cataloga 23 patrones divididos en tres categorías.

Los patrones no se inventan: se descubren observando soluciones que funcionan bien una y otra vez en la industria. Cada patrón tiene un problema, un contexto y una solución documentados.

Ventajas

  • Proporcionan un vocabulario común entre desarrolladores (dices "Singleton" y todos entienden).
  • Ofrecen soluciones probadas, reduciendo errores de diseño.
  • Facilitan el mantenimiento y la evolución del código.
  • Acortan el tiempo de diseño y revisión.

Riesgos

El abuso de patrones (sobre-ingeniería) complica el código sin necesidad. Un patrón mal aplicado puede ser peor que no usar ninguno. Su uso debe responder a un problema real, no a la moda.

---

Clasificación: creacionales, estructurales y de comportamiento

Los 23 patrones GoF se clasifican según su propósito en tres grandes grupos.

CategoríaPropósitoEjemplos
CreacionalesControlan la creación de objetos para que el sistema no dependa de cómo se instancian.Singleton, Factory Method, Abstract Factory, Builder, Prototype.
EstructuralesDefinen cómo componer clases y objetos para formar estructuras más grandes y flexibles.Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight.
De comportamientoDefinen cómo interactúan y se distribuyen las responsabilidades entre objetos.Observer, Strategy, Command, State, Template Method, Iterator, Memento.
La clasificación no es rígida: algunos patrones pueden solaparse (un Decorator es estructural pero cambia comportamiento). La categoría es una guía para memorizarlos y elegirlos, no una regla dogmática.

---

Patrones creacionales

Los patrones creacionales abstraen la creación de objetos, ocultando la lógica de instanciación y permitiendo que el sistema sea independiente de los tipos concretos.

Singleton

  • Qué es: garantiza que una clase tenga una única instancia y un punto de acceso global a ella.
  • Cuándo usarlo: cuando debe existir exactamente una instancia, como una conexión de base de datos o un registro de configuración.

Factory Method

  • Qué es: define una interfaz para crear objetos, pero deja que las subclases decidan qué clase concreta instanciar.
  • Cuándo usarlo: cuando no se sabe de antemano qué tipo de objeto se necesita y se quiere delegar la decisión.

Builder

  • Qué es: separa la construcción de un objeto complejo de su representación, permitiendo construir paso a paso.
  • Cuándo usarlo: con objetos con muchos parámetros opcionales o de construcción progresiva (ej. un pedido con configuraciones diversas).

Prototype

  • Qué es: crea nuevos objetos clonando una instancia existente (el prototipo) en lugar de instanciar.
  • Cuándo usarlo: cuando crear desde cero es costoso o cuando se quieren muchas variaciones de un objeto base.
Los creacionales son especialmente útiles para desacoplar el código cliente de las clases concretas: el cliente trabaja con la abstracción, y quién decide "qué concreto crear" queda encapsulado y fácil de cambiar.

---

Patrones estructurales

Los patrones estructurales componen clases y objetos para formar estructuras más grandes, flexibles y fáciles de mantener.

Adapter

  • Qué es: convierte la interfaz de una clase en otra que el cliente espera, actuando de "traductor".
  • Cuándo usarlo: para integrar componentes o librerías con interfaces incompatibles sin modificar su código.

Decorator

  • Qué es: añade responsabilidades a un objeto de forma dinámica, envolviéndolo.
  • Cuándo usarlo: cuando se necesitan combinar comportamientos opcionales (ej. cifrado, registro/logging) sin modificar la clase base.

Facade

  • Qué es: ofrece una interfaz simplificada ante un conjunto complejo de subsistemas.
  • Cuándo usarlo: para dar una fachada única a un sistema complejo o externo y ocultar su complejidad.

Proxy

  • Qué es: proporciona un sustituto o intermediario que controla el acceso a otro objeto.
  • Cuándo usarlo: para carga diferida, control de acceso o caché de un objeto costoso (ej. un proxy de servicio remoto).
Distinción clave: Adapter cambia la interfaz de una clase para hacerla compatible; Decorator añade comportamiento manteniendo la misma interfaz. Confundirlos es uno de los errores de diseño más comunes.

---

Patrones de comportamiento

Los patrones de comportamiento se centran en la interacción entre objetos y en cómo distribuyen responsabilidades.

Observer

  • Qué es: define una dependencia uno-a-muchos: cuando un objeto cambia, notifica a todos sus dependientes automáticamente.
  • Cuándo usarlo: en notificaciones, eventos o sincronización de vistas (ej. UI que reacciona a cambios de datos).

Strategy

  • Qué es: define una familia de algoritmos intercambiables encapsulados en clases separadas.
  • Cuándo usarlo: cuando un comportamiento tiene varias variantes seleccionables en tiempo de ejecución (ej. distintos métodos de pago).

Command

  • Qué es: encapsula una petición como un objeto, permitiendo parametrizar, encolar y deshacer operaciones.
  • Cuándo usarlo: para operaciones que se deben poder deshacer, encolar o registrar (ej. editores con "deshacer").

State

  • Qué es: permite que un objeto cambie su comportamiento según su estado interno, como si cambiara de clase.
  • Cuándo usarlo: cuando un objeto pasa por estados con reglas distintas (ej. estados de un pedido, una máquina de estados).

Template Method

  • Qué es: define el esqueleto de un algoritmo en una clase base y deja que las subclases implementen pasos concretos.
  • Cuándo usarlo: cuando varias clases comparten la misma estructura de proceso pero difieren en pasos específicos.
La frontera entre Strategy y State suele confundir: Strategy elige un algoritmo de forma externa y deliberada; State cambia el comportamiento del propio objeto en función de su estado. Pensarlo así aclara cuándo usar cada uno.

---

Cuándo usar y cuándo evitar patrones

Los patrones son herramientas, no fines. Elegirlos mal genera complejidad innecesaria.

**Usa un patrón cuando:** - Enfrentas un problema recurrente con una solución conocida. - El patrón simplifica el código, no lo complica. - Necesitas flexibilidad para cambios futuros probables. - El equipo ya lo conoce y comparte el vocabulario.
**Evita patrones cuando:** - El problema es trivial y una solución directa basta. - Lo aplicas "por moda" o para impresionar. - La flexibilidad que aporta no se necesita hoy. - El patrón añade más complejidad de la que resuelve.
Empieza con una solución simple y funcional, y aplica patrones solo cuando el diseño lo exija. Refactorizar hacia un patrón cuando aparece la necesidad real es más sano que forzarlo desde el inicio.

Resumen

- **Definición:** los patrones de diseño son soluciones generales y reutilizables a problemas recurrentes, catalogados por la Gang of Four (GoF) en 1994. - **Clasificación:** creacionales (crean objetos), estructurales (componen clases) y de comportamiento (definen interacciones). - **Creacionales:** Singleton, Factory, Builder, Prototype. - **Estructurales:** Adapter, Decorator, Facade, Proxy. - **Comportamiento:** Observer, Strategy, Command, State, Template Method. - **Clave:** usa patrones cuando simplifiquen y resuelvan un problema real; evítalos cuando añadan complejidad innecesaria.
