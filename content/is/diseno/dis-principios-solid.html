¿Qué es SOLID?

SOLID es un acrónimo que agrupa cinco principios de diseño orientado a objetos que buscan crear software más comprensible, flexible y mantenible. Fueron formulados y popularizados por Robert C. Martin (Uncle Bob) a inicios de la década de 2000.

El propósito de SOLID no es la perfección estética, sino reducir el coste del cambio: un sistema que respete estos principios es más fácil de extender y de mantener a lo largo del tiempo.
SOLID se aplica mejor de forma incremental: no intentes cumplir los cinco en cada clase desde el primer día. Refactoriza hacia ellos cuando el código empiece a doler, guiándote por los síntomas reales.

S: Responsabilidad Única (SRP)

El principio de responsabilidad única (Single Responsibility Principle) establece que una clase debe tener un solo motivo para cambiar: debe encapsular una única responsabilidad del sistema.

SRP no significa "la clase hace una sola cosa", sino que "la clase tiene una sola razón para ser modificada". Si dos actores o áreas de negocio dependen de ella, cualquier cambio solicitado por uno puede romper al otro.

Ejemplo que VIOLA el SRP

class Pedido {
  +calcularTotal()
  +aplicarDescuento()
  +enviarCorreoConfirmacion()
  +generarFacturaPDF()
}

Aquí la clase concentra persistencia, validación de negocio, notificación y exportación. Cualquier cambio en el correo, en el PDF o en las reglas de descuento la altera: hay demasiados motivos para modificar la misma clase.

Cómo corregirlo

class Pedido {
  +calcularTotal()
  +aplicarDescuento()
}

class Notificador {
  +enviarCorreoConfirmacion(correo)
}

class GeneradorPDF {
  +generarFacturaPDF(pedido)
}

Cada responsabilidad (validar pagos, notificar, generar PDF) pasa a su propia clase con un motivo único de cambio.

No confundas SRP con "una clase debe tener un solo método". Se trata de coherencia de responsabilidad, no de contar líneas o métodos. Una clase de validación con varios métodos sigue cumpliendo un solo propósito.

O: Abierto/Cerrado (OCP)

El principio abierto/cerrado (Open/Closed Principle) afirma que una clase debe estar abierta a la extensión pero cerrada a la modificación: se puede añadir comportamiento nuevo sin tocar el código ya escrito y probado.

La clave del OCP es definir una abstracción estable (interfaz o clase base) y que el código dependa de esa abstracción. Las nuevas funcionalidades llegan como nuevas implementaciones, no como complicados if/else que modifican código existente.

Ejemplo que VIOLA el OCP

// Sin OCP: cada nuevo tipo obliga a modificar el switch
double calcular (Pedido p) {
  if (p.tipo == "local") return p.total * 1.0;
  if (p.tipo == "internacional") return p.total * 1.15;
  if (p.tipo == "urgente") return p.total * 1.05;
  return p.total;
}

Cada nuevo tipo de envío obliga a editar esta función, arriesgando romper los casos existentes.

Cómo corregirlo

interface CalculadoraEnvio {
  double calcular(Pedido p);
}
class EnvioLocal implements CalculadoraEnvio {
  double calcular(Pedido p) { return p.total; }
}
class EnvioInternacional implements CalculadoraEnvio {
  double calcular(Pedido p) { return p.total * 1.15; }
}

Ahora añadir un tipo de envío es crear una clase nueva que implementa la interfaz: el código existente no se toca, solo se extiende.

Para aplicar OCP bien, primero identifica el punto de variación: lo que cambia se aísla tras una interfaz, y lo que permanece estable queda abierto a nuevas implementaciones.

L: Sustitución de Liskov (LSP)

El principio de sustitución de Liskov (Liskov Substitution Principle), definido por Barbara Liskov, establece que si una clase S es subtipo de T, entonces los objetos de T pueden sustituirse por objetos de S sin alterar la correctitud del programa.

En la práctica: las subclases deben respetar el contrato de la clase base. Si una subclase rompe las precondiciones, las postcondiciones o los invariantes de la base, el código que depende de la base fallará silenciosamente.

Ejemplo que VIOLA el LSP

class Rectangulo {
  int alto, ancho;
  void setAlto(int a) { alto = a; }
  void setAncho(int a) { ancho = a; }
  int area() { return alto * ancho; }
}
class Cuadrado extends Rectangulo {
  void setAlto(int a) { alto = a; ancho = a; }  // viola el contrato
  void setAncho(int a) { ancho = a; alto = a; } // viola el contrato
}

Un Cuadrado que fuerza ancho == alto rompe la invariante del Rectangulo. Si el código cliente establece el ancho y luego lee el alto esperando que no cambie, se comportará mal con un cuadrado.

Solución

Rediseñar la jerarquía: Rectangulo y Cuadrado como objetos inmutables o como clases sin herencia entre sí (ambos implementan una interfaz Forma con area()).

Detectar una violación de LSP suele ser subjetiva y tardía. Un síntoma típico: tener que comprobar el instanceof para tratar distinto a las subclases. Si te encuentras haciendo eso, revisa la jerarquía de herencia.
Preferir composición sobre herencia reduce las violaciones de LSP: en lugar de forzar una relación "es-un" artificial, se compone un objeto con el comportamiento que necesita.

I: Segregación de Interfaces (ISP)

El principio de segregación de interfaces (Interface Segregation Principle) sostiene que es mejor tener muchas interfaces pequeñas y específicas que una interfaz grande y generalista que obligue a los clientes a implementar métodos que no usan.

Ningún cliente debe ser forzado a depender de métodos que no utiliza. Una interfaz "gorda" obliga a implementaciones vacías o que lanzan excepciones, propagando acoplamiento innecesario.

Ejemplo que VIOLA el ISP

interface Empleado {
  void trabajar();
  void gestionarEquipo();
  void firmarNominas();
}

Un simple Desarrollador que solo trabaja se ve obligado a implementar gestionarEquipo() y firmarNominas() aunque no le correspondan.

Cómo corregirlo

interface Trabajador { void trabajar(); }
interface Jefe extends Trabajador { void gestionarEquipo(); }
interface Gerente extends Jefe { void firmarNominas(); }

class Desarrollador implements Trabajador { void trabajar() {...} }
class GerenteRRHH implements Gerente { ... }

Cada cliente usa solo la interfaz que necesita. Añadir una nueva responsabilidad no obliga a implementarla a todos.

El ISP guarda relación con el SRP: si una interfaz crece con responsabilidades distintas, es señal de que debería dividirse. Una interfaz enfocada es más fácil de implementar, probar y reutilizar.

D: Inversión de Dependencias (DIP)

El principio de inversión de dependencias (Dependency Inversion Principle) establece dos reglas:

  • Los módulos de alto nivel no deben depender de módulos de bajo nivel; ambos deben depender de abstracciones.
  • Las abstracciones no deben depender de los detalles; los detalles deben depender de las abstracciones.
DIP invierte la "flecha de dependencia": en lugar de que el negocio dependa de la base de datos o del proveedor de correo (detalles), todo depende de interfaces definidas por el propio negocio. Los detalles se vuelven intercambiables.

Ejemplo que VIOLA el DIP

class Facturador {
  BaseDeDatosMySQL db;              // depende de un detalle concreto
  Facturador(BaseDeDatosMySQL db) { this.db = db; }
  void guardar(Factura f) { db.insertar(f); }
}

Si mañana se cambia a PostgreSQL, hay que modificar el Facturador y recompilar todo lo que depende de él.

Cómo corregirlo

interface RepositorioFacturas {
  void guardar(Factura f);
}
class Facturador {
  RepositorioFacturas repo;         // depende de la abstracción
  Facturador(RepositorioFacturas repo) { this.repo = repo; }
  void guardar(Factura f) { repo.guardar(f); }
}

El Facturador depende de la interfaz RepositorioFacturas. La implementación concreta se inyecta desde fuera (inyección de dependencias), sin tocar el código de negocio.

DIP se complementa con la inyección de dependencias (DI): no es la clase quien crea sus dependencias con new, sino que se le pasan desde fuera. Esto también facilita el testing con mocks.
DIP no es lo mismo que "inyección de dependencias": DI es la técnica, DIP es el principio orientado a invertir la dirección de las dependencias. Aplicar uno sin el otro no logra el desacoplamiento deseado.

Impacto práctico

SOLID no se aplica por dogmatismo: cada principio ataca un síntoma concreto de la mala calidad del código.

PrincipioProblemática que resuelveBeneficio observable
SRPClases con muchas responsabilidadesClases enfocadas, fáciles de entender y testear.
OCPModificación continua del códigoExtensión con menos riesgo de romper lo ya probado.
LSPJerarquías de herencia frágilesComposición y abstracciones que se pueden sustituir con seguridad.
ISPInterfaces "gordas" que obligan implementaciones vacíasClientes que solo dependen de lo que usan.
DIPDependencias de detalles concretosSistema desacoplado, intercambiable y testeable con mocks.
En conjunto, SOLID conduce a un código con menor acoplamiento y mayor cohesión, lo que se traduce en volver a conectar con los principios del diseño modular: cada pieza hace una cosa, se comunica por interfaces y cambia con independencia del resto.
Úsalo como guía de refactoring: cuando te cueste explicar qué hace una clase (SRP), tengas que tocar muchas clases para un cambio (OCP), o dependas de detalles de terceros (DIP), es momento de aplicar el principio correspondiente.
SOLID no garantiza por sí solo una buena arquitectura; es un cimiento. Debe combinarse con patrones de diseño, estilos arquitectónicos y buenas prácticas de testing para lograr sistemas robustos y evolutivos.

Resumen

- **SOLID:** cinco principios de diseño OO de R. C. Martin para lograr código comprensible, flexible y mantenible. - **SRP:** una clase con un único motivo para cambiar. - **OCP:** abierto a extensión, cerrado a modificación (depender de abstracciones estables). - **LSP:** las subclases deben poder sustituir a su clase base respetando su contrato. - **ISP:** preferir muchas interfaces pequeñas y específicas. - **DIP:** los módulos deben depender de abstracciones, no de concreciones (uso de inyección de dependencias). - **Impacto:** menor acoplamiento, mayor cohesión y coste de cambio reducido, aplicados de forma incremental como guía de refactoring.
