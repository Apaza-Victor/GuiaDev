¿Qué es el diseño modular?

El diseño modular es una técnica de diseño de software que divide un sistema en módulos independientes, cada uno responsable de una parte bien definida de la funcionalidad. Cada módulo encapsula su comportamiento interno y expone una interfaz clara y controlada hacia el resto del sistema.

Un módulo es una unidad de software con cohesión interna y una interfaz externa bien definida. El objetivo es que cada módulo se pueda desarrollar, probar, modificar y reutilizar de forma relativamente aislada.

Un buen módulo es como una "caja negra": quien lo usa solo conoce su interfaz (qué hace y cómo invocarlo), no su implementación (cómo lo hace internamente). Esto oculta la complejidad y reduce el impacto de los cambios.

Partición en módulos

La modularidad parte de la división y conquista: el problema global se descompone en subproblemas más pequeños y manejables.

  • Descomposición: dividir el sistema según funcionalidad, datos o procesos.
  • Composición: construir el sistema ensamblando módulos ya definidos.
  • Comprensión: cada pieza es más fácil de entender por separado.
  • Continuidad: un cambio se localiza en uno o pocos módulos.
  • Protección: los fallos y errores quedan contenidos en su módulo.

Ventajas del diseño modular

VentajaDescripción
MantenibilidadLos cambios se localizan sin afectar al resto del sistema.
ReutilizaciónLos módulos pueden usarse en otros proyectos o contextos.
PruebasCada módulo se prueba de forma aislada (unit testing).
Trabajo paraleloVarios desarrolladores trabajan en módulos distintos sin fricción.
EscalabilidadSe añaden funcionalidades agregando módulos.
La modularidad no es gratis: un exceso de módulos muy pequeños puede generar sobre-ingeniería, más interfaces que mantener y una curva de aprendizaje más larga. El equilibrio depende del tamaño y la complejidad del sistema.

Cohesión: qué tan enfocado es un módulo

La cohesión mide el grado en que los elementos de un módulo están relacionados entre sí y persiguen un mismo propósito. Una buena cohesión implica que el módulo hace una sola cosa bien hecha.

Regla de oro: alta cohesión = módulo enfocado y comprensible. Un módulo con alta cohesión es más fácil de mantener, probar y reutilizar, porque todas sus partes trabajan en el mismo objetivo.

Tipos de cohesión (de alta a baja)

CohesiónTipoDescripción
AltaFuncionalTodos los elementos contribuyen a una única función bien definida.
▼SecuencialLa salida de un elemento es la entrada del siguiente, en una secuencia.
▼ComunicacionalLos elementos operan sobre los mismos datos.
▼ProcedimentalLos elementos se ejecutan en un orden determinado por un proceso.
▼TemporalLos elementos se agrupan solo porque se ejecutan al mismo tiempo.
▼LógicaLos elementos realizan funciones similares pero no relacionadas (ej. un "manejador mixto").
BajaCoincidentalLos elementos se agrupan por casualidad, sin relación real. Evitar.
La cohesión coincidental es la peor: reunir código sin relación solo porque estaba "a mano". Conduce a módulos difíciles de entender y con cambios que se propagan sin sentido. Apunta siempre a la cohesión funcional.

---

Acoplamiento: qué tan conectados están los módulos

El acoplamiento mide el grado de dependencia entre módulos. Mientras la cohesión mira dentro del módulo, el acoplamiento mira entre módulos.

Regla de oro: bajo acoplamiento = módulos independientes y fáciles de cambiar. Cuanto menos dependa un módulo de detalles de otros, más fácil será modificar uno sin romper el resto.

Tipos de acoplamiento (de bajo a alto)

AcoplamientoTipoDescripción
BajoSin acoplamientoLos módulos no tienen ninguna dependencia entre sí. Ideal, casi imposible en la práctica.
▼De datosSe comparten únicamente datos simples (parámetros). El mejor tipo práctico.
▼De sello / estamp (Stamp)Se pasan estructuras de datos completas, aunque solo se use parte.
▼De controlSe pasa información de control (banderas, modo) que altera el flujo del módulo.
▼ExternoDependencia de un formato de datos o protocolo externo compartido.
▼ComúnVarios módulos comparten un área de datos global.
AltoDe contenidoUn módulo accede o modifica directamente el interior de otro. Evitar.
El acoplamiento de contenido es el peor: viola el encapsulamiento al manipular variables internas de otro módulo. Cualquier cambio interno rompe a los dependientes. Elimínalo siempre mediante interfaces.
El acoplamiento de control también es señal de diseño pobre: si pasas un booleano para que el otro decida qué hacer, ese conocimiento "de qué debería hacer" está mal ubicado. Mejor divide la lógica en módulos específicos.

Un sistema bien diseñado combina ambos: cada módulo es muy enfocado (alta cohesión) y se comunica con los demás mediante interfaces simples y estables (bajo acoplamiento). La suma de ambos produce código claro, testeable y evolutivo.

Buenas prácticas

Consejos para mantener un diseño modular sano

  • Define módulos por responsabilidad única, no por conveniencia.
  • Expón interfaces pequeñas y estables; oculta la implementación.
  • Comunica mediante datos simples en lugar de estructuras completas.
  • Ajusta el tamaño de los módulos a la complejidad del problema.
  • Escribe pruebas unitarias por módulo para asegurar su independencia.
  • Documenta las interfaces y responsabilidades de cada módulo.
Parte del código y rediseña antes de que el acoplamiento se escape de control: si para hacer un cambio necesitas tocar varios módulos a la vez, es síntoma de alto acoplamiento. Refactoriza separando responsabilidades.
Evita los singletons globales y las variables globales: convierten el acoplamiento "común" en una trampa silenciosa que hace casi imposible probar los módulos por separado.
No confundas "módulo" con "archivo". Un archivo grande puede contener varios módulos lógicos, y un módulo puede repartirse en varios archivos. La modularidad es un concepto lógico, no físico.
Un indicador práctico: el factor de acoplamiento (número de dependencias reales entre módulos dividido entre el total posible). Un valor bajo indica independencia; valores altos alertan de un sistema frágil.

Resumen

- **Modularidad:** divide el sistema en módulos independientes con interfaz clara e implementación oculta. - **Cohesión:** mide el enfoque interno del módulo; apunta a la cohesión funcional y evita la coincidental. - **Acoplamiento:** mide la dependencia entre módulos; busca el acoplamiento de datos y evita el de contenido. - **Objetivo:** alta cohesión + bajo acoplamiento = sistema mantenible, testeable y evolutivo. - **Buenas prácticas:** interfaces pequeñas, datos simples, pruebas unitarias y módulos por responsabilidad.
