¿Qué es TDD?

El Desarrollo Guiado por Pruebas (TDD, Test-Driven Development) es una práctica de ingeniería en la que las pruebas se escriben antes del código de producción. El desarrollo avanza en ciclos cortos: se escribe una prueba que falla, se escribe el código mínimo para que pase y luego se refactoriza para mejorar la calidad.

TDD popularizado por Kent Beck en los años 90 (dentro de la programación extrema) se resume en su lema: "Red, Green, Refactor". No es una estrategia de pruebas tradicional, sino una práctica de diseño: las pruebas actúan como especificación ejecutable que guía la estructura del código.

La diferencia esencial con el testing clásico: en la metodología tradicional primero se escribe la implementación y luego las pruebas para validarla. En TDD, la prueba se escribe primero y define el comportamiento esperado, forzando a pensar en el qué debería hacer antes del cómo hacerlo.

---

Ciclo: Red, Green, Refactor

El flujo de TDD es un ciclo corto y repetitivo que se ejecuta decenas de veces al día. Los guiones indican el estado de la prueba en cada fase.

FaseEstado de la pruebaAcciones
RedFalla (rojo)Escribir una prueba que falle para la nueva funcionalidad. No se escribe código de producción todavía.
GreenPasa (verde)Escribir el código mínimo necesario para que la prueba pase. La meta es pasar la prueba, sin sofisticar.
RefactorSigue en verdeMejorar el código (simplificar, eliminar duplicidad) manteniendo las pruebas pasando. El comportamiento no cambia.
Ciclo TDD (pseudocódigo):
1. (RED)     Escribir una prueba para un comportamiento nuevo -> test falla
2. (GREEN)   Implementar el código mínimo para que pase      -> test pasa
3. (REFACTOR) Limpiar código manteniendo los tests en verde  -> test sigue pasando
4. Repetir hasta completar la funcionalidad
La disciplina de "escribir solo el código mínimo" es la más difícil de respetar: la tentación de añadir funcionalidad extra en la fase Green rompe el ciclo. El código extra no está cubierto por la prueba y se convierte en deuda no verificada. Si se necesita más funcionalidad, se inicia un nuevo ciclo.

---

Beneficios de TDD

Adoptar TDD con disciplina trae beneficios que se acumulan con el tiempo:

  • Menos defectos: cada comportamiento está cubierto por una prueba desde el primer día.
  • Diseño más limpio: el código escrito para ser probable tiende a ser modular, desacoplado y con responsabilidades claras.
  • Refactorización segura: la red de pruebas permite cambiar el código interno con confianza.
  • Documentación viva: las pruebas describen cómo debe comportarse el sistema y cuándo se rompe algo lo comunican de inmediato.
  • Feedback rápido: al trabajar en ciclos cortos, el error se detecta minutos después de introducirlo.
  • Menor efecto miedo: facilita modificar y ampliar código ajeno porque las pruebas vigilan los comportamientos.
Los beneficios se ven sobre todo en el mediano y largo plazo: el proyecto que se mantiene, se refactoriza y evoluciona sin que cada cambio "rompa algo". El tiempo que se invierte escribiendo pruebas se gana con creces en depuración evitada.

---

Desafíos y críticas

TDD también tiene costo y dificultades, y no es una bala de plata:

  • Curva de aprendizaje: pensar primero en pruebas exige práctica; al principio el ritmo de desarrollo parece más lento.
  • Cobertura que da falsa seguridad: las pruebas pueden pasar sin probar bien los requisitos reales o los casos límite.
  • Pruebas mal diseñadas: pruebas acopladas a la implementación, frágiles o redundantes agregan mantenimiento sin valor.
  • No aplica a todo: en UI compleja, interfaces visuales o prototipos exploratorios el ciclo puede entorpecer en lugar de ayudar.
  • Doble esfuerzo si la funcionalidad es efímera o descartable: se escriben pruebas para código que después se desecha.
Crítica central: TDD no garantiza cobertura de todos los requisitos. Los equipos pueden caer en escribir "pruebas fáciles" que validan la implementación en lugar de probar el comportamiento del negocio. La práctica debe combinarse con pruebas de sistemas, revisión de requisitos y análisis de calidad.

Ejemplo práctico

Supongamos que necesitamos una función que devuelve el número de vocales de una cadena. Veamos el ciclo TDD completo con su verificación en un lenguaje sencillo.

Fase RED: la prueba falla porque la función no existe

# test_vocales.py
from vocales import contar_vocales

def test_contar_vocales_hola():
    assert contar_vocales("hola") == 2

Se ejecuta y falla (rojo) porque vocales aún no existe. El fallo confirma que la prueba está bien formada y que la funcionalidad falta realmente.

Fase GREEN: el código mínimo para pasar la prueba

# vocales.py
def contar_vocales(texto):
    return len([c for c in texto if c in "aeiou"])

La prueba pasa (verde). El código es mínimo: solo cubre el caso probado con minúsculas.

Nueva RED: ampliar a mayúsculas y tildes

# test_vocales.py - nuevos casos
def test_contar_vocales_mayusculas():
    assert contar_vocales("Hola") == 2

def test_contar_vocales_tildadas():
    assert contar_vocales("café") == 2

La primera prueba nueva falla: con "Hola" aún no se cuenta la "H" como no vocal de más... en realidad devuelve 1 por la 'a'. El ciclo se repite actualizando la implementación (por ejemplo, normalizando el texto a minúsculas y ampliando el conjunto de vocales) hasta que todo quede en verde.

Fase REFACTOR: mantener verde y mejorar

# vocales.py - refactor con normalización y vacíos
def contar_vocales(texto):
    if not texto:
        return 0
    vocales = set("aeiouáéíóú")
    return sum(1 for c in texto.lower() if c in vocales)
Observa el patrón: cada vez que se descubre un nuevo caso no cubierto, se escribe primero la prueba (red), luego se implementa (green) y finalmente se limpia (refactor). El conjunto de pruebas crece junto al código y siempre queda verificado.

---

Resumen

- **Definición:** TDD es escribir las pruebas antes que el código de producción; es una práctica de diseño, no solo de testing. - **Ciclo:** Red (prueba falla) → Green (código mínimo pasa) → Refactor (limpiar sin romper nada). - **Beneficios:** Menos defectos, diseño limpio, refactor seguro y documentación viva del sistema. - **Desafíos:** Curva de aprendizaje, pruebas mal diseñadas y contextos (UI, prototipos) donde no siempre aplica. - **Práctica:** El ciclo se repite en pasos pequeños que mantienen el software siempre verificado y evolutivo.
