¿Por qué colas?

Todo lo que tarde más de ~100ms y no sea necesario para responder al usuario pertenece a una cola: enviar emails, procesar videos, llamar APIs lentas, generar reportes PDF. El patrón:

Request HTTP ──► Job serializado ──► Driver (Redis/database)
                        │
Usuario recibe         ▼
respuesta YA      Worker (php artisan queue:work) procesa en background

Sin colas, un email de bienvenida de 3 segundos retrasa cada registro; con colas, el registro responde en 50ms y el email sale cuando salga.

  • database: cero infraestructura extra, ideal para empezar.
  • redis: el estándar en producción, rapidísimo.
  • sqs: servicio administrado AWS.

Configuración en .env: QUEUE_CONNECTION=database, luego php artisan queue:table && php artisan migrate.

Crear y despachar jobs

php artisan make:job ProcesarVideo
// app/Jobs/ProcesarVideo.php
class ProcesarVideo implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries = 3;        // reintentos maximos
    public int $timeout = 300;    // segundos antes de abortar

    public function __construct(
        public Video $video,          // SerializesModels guarda solo el ID
        public string $calidad = '720p'
    ) {}

    public function handle(VideoProcessor $processor): void
    {
        $processor->convertir($this->video, $this->calidad);
    }

    // Opcional: si falla tras todos los intentos
    public function failed(Throwable $e): void
    {
        Log::error('Fallo procesando video', ['id' => $this->video->id]);
    }
}

// Despachar desde controlador o listener
ProcesarVideo::dispatch($video);
ProcesarVideo::dispatch($video)->delay(now()->addMinutes(5));
ProcesarVideo::dispatch($video)->onQueue('videos');   // cola especifica

SerializesModels no serializa el objeto completo: almacena su ID y lo re-hidrata desde BD al ejecutar el job. Por eso los datos que muten durante la espera se leen frescos — y por eso nunca confíes en atributos "capturados" hace minutos.

Workers en producción

# Worker basico
php artisan queue:work

# Con supervisor en Linux (reinicia si muere)
[program:laravel-worker]
command=php /var/www/app/artisan queue:work redis --sleep=3 --tries=3 --max-time=3600
numprocs=4
autostart=true
autorestart=true
  • --tries=3: máximo de intentos por job.
  • --backoff=30: espera entre reintentos (los jobs lentos suelen fallar por dependencias externas caídas momentáneamente).
  • --max-time=3600: el worker se reinicia cada hora — libera memoria acumulada.
  • Regla de oro del deploy: tras desplegar código nuevo, ejecuta php artisan queue:restart; los workers viejos tienen el código anterior cargado en memoria.

Failed jobs y batching

# Tabla de fallos + inspeccion
php artisan queue:failed-table && php artisan migrate
php artisan queue:failed            # listar
php artisan queue:retry all         # reintentar
php artisan queue:flush             # limpiar
// Batch: grupo de jobs con callback final
Bus::batch([
    new ImportarCsv($chunk1),
    new ImportarCsv($chunk2),
])->then(fn (Batch $batch) => NotificarImportacion::dispatch())
  ->catch(fn (Batch $batch, Throwable $e) => Log::error($e))
  ->dispatch();
