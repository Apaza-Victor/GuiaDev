Eventos y listeners: el concepto

Un evento anuncia que algo ocurrió ("se registró un pedido"); los listeners reaccionan a ese anuncio. Esto desacopla el flujo principal de las tareas secundarias:

PedidoController::store()
      │ despacha
      ▼
Evento: PedidoRegistrado ──► Listener: EnviarEmailConfirmacion
                        └──► Listener: ActualizarEstadisticas
                        └──► Listener: NotificarAlmacen

El controlador solo crea el pedido y dispara el evento. Si mañana agregas "generar PDF fiscal", creas un listener nuevo — sin tocar el controlador jamás.

Crear y despachar eventos

php artisan make:event PedidoRegistrado
php artisan make:listener EnviarEmailConfirmacion --event=PedidoRegistrado
// app/Events/PedidoRegistrado.php
class PedidoRegistrado
{
    public function __construct(public Pedido $pedido) {}
}

// app/Listeners/EnviarEmailConfirmacion.php
class EnviarEmailConfirmacion
{
    public function handle(PedidoRegistrado $event): void
    {
        Mail::to($event->pedido->cliente_email)
            ->send(new ConfirmacionPedido($event->pedido));
    }
}

El registro puede ir en app/Providers/EventServiceProvider.php o — más simple — implementar la interfaz ShouldDiscoverEvents para autodescubrimiento por convención de nombres.

// Despachar desde cualquier lugar
use App\Events\PedidoRegistrado;

PedidoRegistrado::dispatch($pedido);
// o con el helper:
event(new PedidoRegistrado($pedido));

// Asincrono: el listener implementa ShouldQueue
class EnviarEmailConfirmacion implements ShouldQueue
{
    use InteractsWithQueue;
    // ...
}

Event subscribers

Un subscriber agrupa varios listeners relacionados en una sola clase:

class PedidoSubscriber
{
    public function handlePedidoRegistrado(PedidoRegistrado $e): void { /* ... */ }
    public function handlePedidoCancelado(PedidoCancelado $e): void { /* ... */ }

    public function subscribe(Dispatcher $events): array
    {
        return [
            PedidoRegistrado::class => 'handlePedidoRegistrado',
            PedidoCancelado::class => 'handlePedidoCancelado',
        ];
    }
}

// Registro en EventServiceProvider
protected $subscribe = [PedidoSubscriber::class];

Úsalo cuando varios listeners comparten dominio (todo lo del ciclo de pedidos) y prefieras una clase organizada sobre diez archivos sueltos.

Model Observers

Los observers escuchan el ciclo de vida de un modelo Eloquent sin necesidad de eventos custom:

php artisan make:observer UsuarioObserver --model=Usuario
class UsuarioObserver
{
    public function creating(Usuario $usuario): void
    {
        $usuario->token_activacion = Str::random(32);
    }

    public function deleted(Usuario $usuario): void
    {
        Storage::disk('public')->delete($usuario->avatar_path);
    }
}

// Registro en AppServiceProvider (boot)
Usuario::observe(UsuarioObserver::class);
MomentoCuándo se dispara
creating / createdAntes / después de INSERT
updating / updatedAntes / después de UPDATE
saving / savedCreate o update (ambos)
deleting / deletedAntes / después de DELETE
retrievedAl traerlo de base de datos

Diferencia clave: usa observers para invariantes del modelo (siempre que exista un usuario pasa X); usa eventos/listeners para flujos de negocio (al registrar un pedido ocurre Y). Mezclarlos hace el comportamiento imposible de rastrear.
