10.1 Organización de un proyecto real

Estructura recomendada

mi_proyecto/
├── manage.py
├── requirements.txt         # Dependencias
├── .env                     # Variables de entorno (no se sube a git)
├── mi_proyecto/             # Configuración del proyecto
│   ├── settings.py
│   ├── urls.py
│   └── wsgi.py
├── apps/                    # Aplicaciones agrupadas
│   ├── blog/
│   ├── usuarios/
│   └── tienda/
├── templates/               # Plantillas globales
├── static/                  # CSS, JS, imágenes
└── media/                   # Archivos subidos por usuarios

Buenas prácticas

  • Separar configuración por entornos: desarrollo, pruebas y producción
  • Usar variables de entorno para claves y datos sensibles
  • Módulos dentro de apps: cada app responsable de una sola funcionalidad
  • Versionar todo con Git desde el primer día

settings.py por entornos

# settings.py (base)
import os

SECRET_KEY = os.environ.get("SECRET_KEY", "clave-dev")
DEBUG = os.environ.get("DEBUG", "True") == "True"
ALLOWED_HOSTS = os.environ.get("ALLOWED_HOSTS", "").split(",")
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": os.environ.get("DB_NAME", "db.sqlite3"),
    }
}

10.2 Archivos estáticos y media

Qué son los archivos estáticos

Los archivos estáticos son CSS, JavaScript e imágenes que el servidor entrega tal cual. Django los gestiona con la app django.contrib.staticfiles.

Configuración en settings.py

# settings.py
STATIC_URL = "/static/"
STATICFILES_DIRS = [BASE_DIR / "static"]

# En producción: carpeta donde se copian todos los estáticos
STATIC_ROOT = BASE_DIR / "staticfiles"

# Archivos subidos por los usuarios
MEDIA_URL = "/media/"
MEDIA_ROOT = BASE_DIR / "media"

Uso en plantillas

<!-- En la plantilla base: cargar y usar la etiqueta static -->
{% load static %}
<link rel="stylesheet" href="{% static 'css/styles.css' %}">
<script src="{% static 'js/app.js' %}"></script>
<img src="{% static 'img/logo.png' %}" alt="Logo">

Qué hace collectstatic

Reúne todos los archivos estáticos de las apps y de STATICFILES_DIRS en la carpeta STATIC_ROOT, lista para servirse en producción.

# Copiar todos los estáticos a STATIC_ROOT
python manage.py collectstatic
# 67 static files copied to 'C:\...\staticfiles'.

Modelo con subida de archivos (media)

# blog/models.py
from django.db import models

def ruta_del_avatar(instance, filename):
    return f"avatares/usuarios/{instance.usuario.username}/{filename}"

class Perfil(models.Model):
    usuario = models.OneToOneField(
        "auth.User", on_delete=models.CASCADE, related_name="perfil"
    )
    avatar = models.ImageField(upload_to=ruta_del_avatar, blank=True)
Los campos ImageField requieren la librería Pillow: `pip install Pillow`. En producción, guardar media en disco local puede ser insuficiente; considera un bucket de S3.

10.3 Dependencias (requirements.txt) y variables de entorno

Generar el archivo de dependencias

# Guarda todas las dependencias instaladas
pip freeze > requirements.txt
django==5.0.6
gunicorn==22.0.0
whitenoise==6.6.0
psycopg2-binary==2.9.9
python-dotenv==1.0.1
Pillow==10.3.0

Instalar en otro entorno

# Instalar todas las dependencias del proyecto
pip install -r requirements.txt

Variables de entorno con python-dotenv

# .env
SECRET_KEY=cambia-esta-clave
DEBUG=False
ALLOWED_HOSTS=misitio.com,www.misitio.com
DB_NAME=mi_bd
DB_USER=usuario
DB_PASSWORD=clave_segura
# settings.py
from dotenv import load_dotenv
load_dotenv()

import os
SECRET_KEY = os.environ["SECRET_KEY"]
DEBUG = os.environ.get("DEBUG", "False") == "True"
ALLOWED_HOSTS = os.environ.get("ALLOWED_HOSTS", "").split(",")
El archivo `.env` no debe subirse al repositorio. Agrégalo a `.gitignore` y documenta las variables en un `.env.example`.

10.4 Configuración de producción

Cambios clave respecto a desarrollo

AjusteDesarrolloProducción
DEBUGTrueFalse
ALLOWED_HOSTSVacío o localhostTu dominio real
SECRET_KEYValor cualquieraClave generada y oculta
DATABASESSQLitePostgreSQL u otro servidor
STATIC_ROOTInnecesarioCarpeta de estáticos agrupados

settings.py de producción (ejemplo)

# settings.py
import os

SECRET_KEY = os.environ["SECRET_KEY"]
DEBUG = False
ALLOWED_HOSTS = os.environ["ALLOWED_HOSTS"].split(",")

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ["DB_NAME"],
        "USER": os.environ["DB_USER"],
        "PASSWORD": os.environ["DB_PASSWORD"],
        "HOST": os.environ["DB_HOST"],
        "PORT": "5432",
    }
}

# Seguridad extra con HTTPS
SECURE_SSL_REDIRECT = True
CSRF_COOKIE_SECURE = True
SESSION_COOKIE_SECURE = True
Nunca ejecutes producción con DEBUG=True: expone configuraciones, variables y mensajes de error sensibles.

10.5 Despliegue con Gunicorn y Nginx

Flujo típico

ComponenteRol
GunicornServidor WSGI que ejecuta la app Django
NginxProxy inverso: sirve estáticos y redirige a Gunicorn
PostgreSQLBase de datos de producción

Comandos del servidor

# Migraciones y estáticos antes de desplegar
python manage.py migrate
python manage.py collectstatic --noinput

# Ejecutar Gunicorn (desarrollador)
gunicorn mi_proyecto.wsgi:application --bind 127.0.0.1:8000

Configuración de Nginx (ejemplo)

# /etc/nginx/sites-available/misitio
server {
    listen 80;
    server_name misitio.com;

    location /static/ {
        alias /ruta/staticfiles/;
    }
    location /media/ {
        alias /ruta/media/;
    }
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

Alternativas PaaS

  • Railway / Render: Deploy con un Procfile y base de datos en unos clics
  • Heroku: Usa gunicorn en el Procfile y add-ons de PostgreSQL
  • VPS: Ubuntu + Gunicorn + Nginx para máximo control

Procfile (Railway/Heroku)

web: gunicorn mi_proyecto.wsgi:application
Gunicorn es para Linux. En Windows usa la librería `waitress` o despliega en un PaaS que lo gestione por ti.

10.6 Buenas prácticas de despliegue

Lista de verificación

  • DEBUG=False siempre en producción
  • ALLOWED_HOSTS con tu dominio, nunca con un comodín innecesario
  • SECRET_KEY única y guardada en variables de entorno
  • HTTPS activado (redirige los accesos por HTTP)
  • Backups automáticos de la base de datos
  • Monitorización de logs y errores del servidor
  • Revisión de seguridad con python manage.py check --deploy

Análisis de seguridad integrado

# Django revisa la configuración buscando problemas serios
python manage.py check --deploy
# System check identified 6 issues (1 serious).

Entornos de despliegue

EntornoUso
LocalDesarrollo diario con runserver
StagingMismo código de producción, sin tráfico real
ProducciónServicios estables y supervisados
Automatiza el despliegue con GitHub Actions o la plataforma que uses: esto evita errores manuales y garantiza repetibilidad.

Resumen

**Lo que aprendiste en esta sección:** - Organizar un proyecto real con apps separadas y configuración por entorno - Gestionar estáticos con `STATIC_URL` y `collectstatic` - Separar los archivos de media propios del usuario - Documentar dependencias con `requirements.txt` y usar variables de entorno - Configurar producción: DEBUG=False, ALLOWED_HOSTS y HTTPS - Desplegar con Gunicorn + Nginx o plataformas PaaS como Railway y Heroku - Seguir una checklist con el comando `python manage.py check --deploy`
