10.1 Por qué probar

Beneficios de los tests

Los tests automatizados verifican que el código funciona y detectan errores antes de que lleguen a producción. Rails incluye una suite de pruebas (MiniTest) lista para usar.

Ventajas de la automatización

BeneficioDescripción
ConfianzaSabes que los cambios no rompen lo existente
RegresiónDetectas errores introducidos en refactorizaciones
DocumentaciónLos tests describen cómo debe comportarse el código
RapidezEl feedback llega en segundos sin probar a mano

Tipos de pruebas en Rails

TipoQué verificaUbicación
ModelosValidaciones, asociaciones y lógicatest/models
ControladoresRespuestas y comportamiento HTTPtest/controllers
IntegraciónFlujos completos de la apptest/integration
SistemaPáginas completas con navegadortest/system

10.2 Pruebas de modelo

Estructura de un test de modelo

# test/models/producto_test.rb
require "test_helper"

class ProductoTest < ActiveSupport::TestCase
  test "es válido con atributos correctos" do
    producto = Producto.new(nombre: "Laptop", precio: 999.99)
    assert producto.valid?
  end

  test "no es válido sin nombre" do
    producto = Producto.new(nombre: "", precio: 10)
    assert_not producto.valid?
    assert_includes producto.errors[:nombre], "no puede estar vacío"
  end

  test "precio no puede ser negativo" do
    producto = Producto.new(nombre: "Mouse", precio: -5)
    assert_not producto.valid?
  end
end

Aserciones más comunes

AserciónQué comprueba
assertLa condición es verdadera
assert_notLa condición es falsa
assert_equalSon iguales
assert_nilEl valor es nil
assert_includesContiene el elemento

Pruebas de asociaciones y callbacks

test "pertenece a una categoría" do
  assert_respond_to Producto.new, :categoria
  assert_equal 1, Producto.reflect_on_association(:categoria).macro
end

test "asigna referencia automáticamente" do
  pedido = Pedido.new
  pedido.save
  assert_match /\APED-/, pedido.referencia
end

10.3 test dir y FactoryBot

El entorno de pruebas

Rails usa un entorno de pruebas separado (RAILS_ENV=test) con su propia base de datos para no contaminar los datos de desarrollo:

# Preparar la base de datos de pruebas
rails db:migrate
RAILS_ENV=test rails db:migrate

# O crear, migrar y cargar seeds del entorno test
rails db:test:prepare

Fixtures por defecto

Rails genera fixtures (archivos YAML de muestra) en test/fixtures/. Se cargan automáticamente antes de cada test:

# test/fixtures/productos.yml
laptop:
  nombre: Laptop
  precio: 999.99

mouse:
  nombre: Mouse
  precio: 29.99

FactoryBot para datos más flexibles

# Gemfile
gem "factory_bot_rails"
bundle install
# test/factories/productos.rb
FactoryBot.define do
  factory :producto do
    nombre { "Producto de prueba" }
    precio { 49.99 }
    association :categoria
  end

  factory :producto_barato, parent: :producto do
    precio { 9.99 }
  end
end
# Uso en los tests
producto = create(:producto)
barato = create(:producto_barato, nombre: "Promoción")
FactoryBot evita crear datos a mano y permite sobreescribir atributos fácilmente, algo más flexible que los fixtures estáticos.

10.4 Pruebas de sistema

Qué son

Las pruebas de sistema simulan el comportamiento de un usuario en el navegador usando Capybara y Selenium. Verifican la interfaz completa de extremo a extremo.

Ejemplo de test de sistema

# test/system/productos_test.rb
require "application_system_test_case"

class ProductosTest < ApplicationSystemTestCase
  test "crea un producto desde el navegador" do
    visit new_producto_path

    fill_in "Nombre", with: "Laptop"
    fill_in "Precio", with: "1299.99"
    click_on "Guardar"

    assert_text "Laptop"
    assert_current_path producto_path(Producto.last)
  end

  test "muestra errores de validación" do
    visit new_producto_path
    click_on "Guardar"

    assert_text "no puede estar vacío"
  end
end

Comandos de Capybara

ComandoQué hace
visit rutaNavega a una página
fill_in "Campo", with: vRellena un campo
click_on "Texto"Hace clic en un elemento
assert_text "Texto"Comprueba que aparece el texto
assert_current_pathComprueba la URL actual
# Ejecutar solo los tests de sistema
rails test:system

10.5 Despliegue y producción

Preparar la app para producción

Antes de desplegar conviene precompilar los assets, preparar la base de datos y comprobar que los tests pasan:

# Ejecutar todos los tests
rails test

# Precompilar los assets
RAILS_ENV=production rails assets:precompile

# Migrar la base de datos de producción
RAILS_ENV=production rails db:migrate

Opciones de despliegue

OpciónDescripción
HerokuPlataforma en la nube con soporte Rails fácil
CapistranoDespliegue de capas sobre servidores propios
Docker + RailsContenedores reproducibles en cualquier servidor
VPS manualNginx + Puma + systemd sobre un servidor Linux

Dockerfile básico para Rails

# Dockerfile
# FROM ruby:3.2-slim
# WORKDIR /app
# COPY Gemfile Gemfile.lock ./
# RUN bundle install
# COPY . .
# CMD ["rails", "server", "-b", "0.0.0.0"]

Variables de entorno

No guardes secretos en el código. Usa variables de entorno para claves, credenciales y configuraciones sensibles:

export SECRET_KEY_BASE="valor_secreto_largo"
export DATABASE_URL="postgres://usuario:pass@host/bbdd"

10.6 Seguridad y buenas prácticas

Medidas de seguridad esenciales

RiesgoProtección en Rails
XSSEscape automático con <%= %>
CSRFprotect_from_forgery activo por defecto
SQL InjectionConsultas parametrizadas con where("col = ?", v)
Asignación masivaStrong Parameters
Datos expuestosNo loguear ni serializar credenciales

Buenas prácticas

  • Usa el entorno production solo en servidores reales
  • Mantén un SECRET_KEY_BASE seguro y rotado
  • Ejecuta los tests antes de cada despliegue
  • Revisa los logs y la supervisión en producción
  • Actualiza las gemas periódicamente con bundle audit

Herramientas de reviews y calidad

# Rubocop analiza el estilo de código
bundle exec rubocop

# Brakeman busca vulnerabilidades de seguridad
bundle exec brakeman

# Ver dependencias vulnerables
bundle audit check --update
El despliegue exitoso requiere tres pilares: tests que pasen, assets precompilados y una base de datos migrada; además de secretos bien gestionados.

Resumen

**Lo que aprendiste en esta sección:** - Los tests automatizados evitan errores y refactorizaciones peligrosas - Las pruebas de modelo verifican validaciones y lógica - Los fixtures y FactoryBot generan datos de prueba - Las pruebas de sistema simulan el comportamiento del usuario - El despliegue precompila assets y migra la base de datos - Rubocop, Brakeman y bundle audit mejoran calidad y seguridad
