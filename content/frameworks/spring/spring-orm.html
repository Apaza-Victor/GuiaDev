JPA e Hibernate: conceptos base

JPA es la especificación Java para mapeo objeto-relacional; Hibernate es su implementación más usada. Spring Data JPA añade repositorios que eliminan el 90% del código repetitivo:

@Entity
@Table(name = "productos")
public class Producto {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String nombre;

    private BigDecimal precio;

    @ManyToOne(fetch = FetchType.LAZY)     // LAZY por defecto en relaciones
    @JoinColumn(name = "categoria_id")
    private Categoria categoria;

    // getters/setters
}
// Repositorio: sin implementar NADA
public interface ProductoRepository extends JpaRepository<Producto, Long> {

    List<Producto> findByNombreContainingIgnoreCase(String texto);

    List<Producto> findByPrecioBetween(BigDecimal min, BigDecimal max);

    @Query("SELECT p FROM Producto p WHERE p.categoria.nombre = :cat")
    List<Producto> porCategoria(@Param("cat") String categoria);
}

@Entity
public class Categoria {
    @OneToMany(mappedBy = "categoria", cascade = CascadeType.ALL)
    private List<Producto> productos = new ArrayList<>();

    public void agregarProducto(Producto p) {
        productos.add(p);
        p.setCategoria(this);   // sincroniza ambos lados SIEMPRE
    }
}
  • cascade: propagar operaciones (guardar pedido guarda sus líneas).
  • orphanRemoval = true: eliminar de la lista elimina de BD.
  • En bidireccionales, un solo lado es dueño (el ManyToOne); sincroniza ambos lados con métodos helper.

Lazy loading y el problema N+1

Con FetchType.LAZY, acceder a una relación dispara una consulta extra. En bucles esto explota al clásico problema N+1: 1 consulta para traer 50 pedidos + 50 consultas más (una por cliente):

SELECT * FROM pedidos;              -- 1 consulta
SELECT * FROM clientes WHERE id=1;  -- x50 mas... desastre

Soluciones, de preferencia:

// 1. JOIN FETCH en JPQL (la mas clara)
@Query("SELECT p FROM Pedido p JOIN FETCH p.cliente WHERE p.fecha > :desde")
List<Pedido> recientes(@Param("desde") LocalDate desde);

// 2. @EntityGraph cuando no quieres JPQL
@EntityGraph(attributePaths = {"cliente", "items"})
List<Pedido> findByEstado(EstadoPedido estado);

Síntoma infalible de N+1: logs SQL llenos de consultas idénticas con IDs distintos. Activa spring.jpa.properties.hibernate.generate_statistics=true en desarrollo para contarlas.

Transacciones y buenas prácticas

@Service
public class TransferenciaService {

    @Transactional   // todo o nada: rollback automatico ante excepcion
    public void transferir(Long origenId, Long destinoId, BigDecimal monto) {
        Cuenta origen = repo.findById(origenId).orElseThrow();
        Cuenta destino = repo.findById(destinoId).orElseThrow();

        origen.debitar(monto);
        destino.acreditar(monto);
        // sin save() explicito: dirty checking persiste cambios al cerrar
    }

    @Transactional(readOnly = true)   // optimizacion para lecturas
    public List<Cuenta> listar() { return repo.findAll(); }
}
  • @Transactional va en la capa de SERVICIO, no en controladores ni repositorios.
  • Dentro de una transacción NO hagas llamadas lentas (APIs externas, emails) — mantén la transacción corta.
  • DTOs para exponer datos: nunca devuelvas entidades directamente (serialización perezosa + acoplamiento).
  • Valida con Bean Validation (@NotNull, @Size) sobre DTOs antes de tocar la entidad.
