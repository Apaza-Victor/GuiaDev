El archivo astro.config.mjs

Toda la configuración de un proyecto Astro vive en astro.config.mjs. Es el corazón del proyecto: ahí se registran integraciones, se elige el modo de renderizado y se ajustan opciones de build:

import { defineConfig } from 'astro/config';
import react from '@astrojs/react';
import sitemap from '@astrojs/sitemap';

export default defineConfig({
  site: 'https://midominio.com',
  output: 'static',            // 'static' (por defecto) o 'server'
  integrations: [react(), sitemap()],
  markdown: {
    syntaxHighlight: 'shiki',
    shikiConfig: { theme: 'github-dark' }
  },
  vite: {
    resolve: { alias: { '@': '/src' } }
  }
});

Opciones que conviene conocer desde el inicio:

  • site: URL final del sitio; obligatoria para sitemap, canonical URLs y RSS.
  • base: si despliegas en subcarpeta (/blog/), aquí se define.
  • trailingSlash: controla si las URLs llevan barra final; alinéalo con tu hosting para evitar redirecciones.
  • vite: acceso directo a toda la configuración de Vite (alias, plugins, proxies).

Integraciones oficiales

Las integraciones añaden capacidades con una sola línea. Las oficiales más usadas:

IntegraciónAporta
@astrojs/react / vue / svelteComponentes de esos frameworks dentro de Astro
@astrojs/tailwindTailwind CSS preconfigurado
@astrojs/sitemapsitemap.xml automático en cada build
@astrojs/mdxSoporte MDX (JSX dentro de Markdown)
@astrojs/partytownEjecuta scripts de terceros en un web worker sin bloquear el hilo principal
 
# Instalar una integración (el CLI actualiza astro.config.mjs por ti)
npx astro add react
npx astro add tailwind sitemap

Regla minimalista de Astro: cada integración debe resolver una necesidad real. Añadir "por si acaso" es la forma más rápida de perder la velocidad que hace famoso a Astro.

Adaptadores y modo server (SSR)

Por defecto Astro genera HTML estático puro. Si necesitas endpoints dinámicos, cookies o contenido por usuario, activas SSR con un adaptador:

import netlify from '@astrojs/netlify';
import vercel from '@astrojs/vercel';

export default defineConfig({
  output: 'server',
  adapter: netlify()   // o vercel(), cloudflare(), node()
});

El enfoque recomendado en proyectos reales es híbrido: todo estático por defecto y solo las rutas específicas marcadas con export const prerender = false se renderizan bajo demanda. Lo mejor de ambos mundos: velocidad estática donde puedes, dinamismo donde debes.

Variables de entorno

Astro gestiona entornos de forma tipada y segura a través de archivos .env:

# .env
PUBLIC_API_URL=https://api.midominio.com   # visible en cliente
STRIPE_SECRET_KEY=sk_xxx                   # solo servidor/build
// Uso con import.meta.env (tipado opcional via src/env.d.ts)
const api = import.meta.env.PUBLIC_API_URL;
const secret = import.meta.env.STRIPE_SECRET_KEY; // solo en frontmatter SSR
  • Solo variables con prefijo PUBLIC_ llegan al navegador — imposible exponer secretos sin querer.
  • Define los tipos en src/env.d.ts con ImportMetaEnv para autocompletado.
  • Crea .env.production para valores distintos por entorno; nunca versiones secretos reales.

Ejercicio propuesto: toma un proyecto Astro existente y extrae todas las URLs hardcodeadas hacia variables de entorno con prefijo PUBLIC_. Verifica que el build sigue funcionando tras moverlas.
