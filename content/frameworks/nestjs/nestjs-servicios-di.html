5.1 Qué es un servicio

Definición

Un servicio en NestJS es una clase anotada con @Injectable que concentra la lógica de negocio: validaciones, acceso a datos, cálculos y comunicación con sistemas externos. Los controladores delegan en los servicios y se mantienen delgados.

Por qué separar la lógica

MotivoVentaja
Separación de responsabilidadesEl controlador solo maneja HTTP
ReutilizaciónUn servicio se usa desde varios controladores
PruebasEl servicio se prueba de forma aislada
MantenimientoLa lógica vive en un solo lugar

Ejemplo: servicio simple

import { Injectable } from '@nestjs/common';

export interface Gato {
  id: number;
  nombre: string;
  edad: number;
}

@Injectable()
export class GatosService {
  private gatos: Gato[] = [{ id: 1, nombre: 'Michi', edad: 3 }];

  obtenerTodos(): Gato[] {
    return this.gatos;
  }

  obtenerUno(id: number): Gato | undefined {
    return this.gatos.find((gato) => gato.id === id);
  }
}

5.2 La anotación @Injectable

Qué hace @Injectable

El decorador @Injectable() marca la clase como un provider que NestJS puede gestionar dentro de su contenedor de inyección de dependencias. Sin este decorador la clase no puede inyectarse en otro lugar.

Tipos de providers

TipoDescripción
ServiciosClases con lógica de negocio
RepositoriosAcceso a la base de datos
HelpersUtilidades compartidas (formateo, hash, etc.)
FactoriesCreación de objetos de configuración

Ejemplo: provider inyectable

import { Injectable } from '@nestjs/common';

@Injectable()
export class LoggerService {
  mensajes: string[] = [];

  registrar(mensaje: string) {
    const linea = `[${new Date().toISOString()}] ${mensaje}`;
    this.mensajes.push(linea);
    console.log(linea);
  }
}
El CLI genera un servicio ya anotado con `@Injectable` usando `nest g service nombre`.

5.3 Inyección de dependencias

Concepto

La inyección de dependencias (DI) es un patrón en el que las dependencias de una clase se entregan desde fuera, en lugar de crearlas dentro. NestJS la implementa con un contenedor IoC que resuelve automáticamente las dependencias declaradas en el constructor.

Inyección por constructor

import { Controller, Get } from '@nestjs/common';
import { GatosService } from './gatos.service';

@Controller('gatos')
export class GatosController {
  constructor(private readonly gatosService: GatosService) {}

  @Get()
  obtenerTodos() {
    return this.gatosService.obtenerTodos();
  }
}

NestJS detecta el tipo GatosService en el constructor, busca una instancia en el contenedor y la inyecta.

Cadena de inyecciones

Las dependencias pueden encadenarse: un controlador depende de un servicio, y ese servicio puede depender de otro provider, como un cliente HTTP o un repositorio.

import { Injectable } from '@nestjs/common';
import { LoggerService } from './logger.service';

@Injectable()
export class GatosService {
  constructor(private readonly logger: LoggerService) {}

  obtenerTodos() {
    this.logger.registrar('Se consultaron los gatos');
    return [{ id: 1, nombre: 'Michi' }];
  }
}

5.4 Registro de providers

Registro en un módulo

Para que NestJS pueda inyectar un provider, debe declararse en la propiedad providers de un módulo.

import { Module } from '@nestjs/common';
import { GatosController } from './gatos.controller';
import { GatosService } from './gatos.service';
import { LoggerService } from './logger.service';

@Module({
  controllers: [GatosController],
  providers: [GatosService, LoggerService],
})
export class GatosModule {}

Formas equivalentes de registro

// Forma corta (clase directa)
providers: [GatosService]

// Forma extendida
providers: [
  {
    provide: GatosService,
    useClass: GatosService,
  },
]

Si el provider está en otro módulo

Cuando el provider pertenece a otro módulo, ese módulo debe exportarlo y el módulo actual debe importarlo:

// core.module.ts
@Module({
  providers: [LoggerService],
  exports: [LoggerService],
})
export class CoreModule {}

// gatos.module.ts
import { CoreModule } from '../core/core.module';

@Module({
  imports: [CoreModule],
  controllers: [GatosController],
  providers: [GatosService],
})
export class GatosModule {}

5.5 Ámbito de los providers

Qué es el ámbito

El ámbito (scope) de un provider determina durante cuánto tiempo vive su instancia. NestJS usa por defecto el ámbito singleton.

ÁmbitoVida de la instanciaCuándo usarlo
DEFAULT (Singleton)Una única instancia para toda la aplicaciónCaso habitual
REQUESTUna instancia por cada peticiónDatos propios de la petición
TRANSIENTUna instancia nueva por cada inyecciónEstado por uso

Definir el ámbito por clase

import { Injectable, Scope } from '@nestjs/common';

@Injectable({ scope: Scope.REQUEST })
export class ContextoService {
  usuario: string | undefined;
}

Definir el ámbito por módulo

import { Module } from '@nestjs/common';
import { ContextoService } from './contexto.service';

@Module({
  providers: [
    {
      provide: ContextoService,
      useClass: ContextoService,
      scope: Scope.REQUEST,
    },
  ],
})
export class AppModule {}
Los providers con ámbito `REQUEST` degradan ligeramente el rendimiento y complican la composición con providers singleton. Úsalos solo cuando realmente necesites estado por petición.

5.6 Providers personalizados

Fábricas y valores

Además de clases, NestJS permite registrar providers mediante valores y fábricas, útiles para configuraciones o dependencias de terceros.

OpciónQué hace
useValueInyecta un valor fijo
useFactoryCrea la instancia con una función que puede tener dependencias
useExistingAlias de otro provider
useClassInstancia a partir de una clase

Ejemplo con useValue

import { Module } from '@nestjs/common';

export interface Configuracion {
  nombreApp: string;
  entorno: string;
}

export const CONFIGURACION = Symbol('CONFIGURACION');

const config: Configuracion = {
  nombreApp: 'MiAPI',
  entorno: 'desarrollo',
};

@Module({
  providers: [
    {
      provide: CONFIGURACION,
      useValue: config,
    },
  ],
})
export class ConfiguracionModule {}

Ejemplo con useFactory

import { Module } from '@nestjs/common';
import { LoggerService } from './logger.service';

export const URL_BASE_DATOS = Symbol('URL_BASE_DATOS');

@Module({
  providers: [
    LoggerService,
    {
      provide: URL_BASE_DATOS,
      useFactory: (logger: LoggerService) => {
        const url = process.env.DATABASE_URL ?? 'postgres://localhost/db';
        logger.registrar(`Conectando a ${url}`);
        return url;
      },
      inject: [LoggerService],
    },
  ],
})
export class DatabaseModule {}

---

Resumen

**Lo que aprendiste en esta sección:** - Un servicio concentra la lógica de negocio y se anota con `@Injectable` - La inyección de dependencias entrega dependencias a través del constructor - Los providers se registran en el array `providers` del módulo - Los ámbitos pueden ser singleton, por petición o transitorios - `useValue`, `useFactory` y `useExisting` permiten providers personalizados - Los módulos exportan providers para compartirlos con otros módulos
