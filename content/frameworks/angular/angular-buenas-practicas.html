10.1 Organización del proyecto

Estructura recomendada por funcionalidades

Una buena organización del código facilita el mantenimiento, la incorporación de nuevos desarrolladores y la escalabilidad. La comunidad Angular recomienda agrupar el código por funcionalidades (feature modules) en lugar de por tipo de archivo.

src/
├── app/
│   ├── core/                    # Servicios singleton, guards, interceptores
│   │   ├── services/
│   │   ├── guards/
│   │   └── interceptors/
│   ├── shared/                  # Componentes, directivas y pipes reutilizables
│   │   ├── components/
│   │   ├── directives/
│   │   └── pipes/
│   ├── features/                # Módulos de funcionalidad
│   │   ├── auth/
│   │   │   ├── login/
│   │   │   ├── registro/
│   │   │   └── auth.module.ts
│   │   ├── productos/
│   │   │   ├── lista/
│   │   │   ├── detalle/
│   │   │   └── productos.module.ts
│   │   └── admin/
│   ├── app.component.ts
│   ├── app.routes.ts
│   └── app.config.ts
├── assets/
├── environments/
└── styles.scss

Capas de la arquitectura

CarpetaPropósitoEjemplo
coreServicios globales, guards, interceptoresAuthService, AuthGuard
sharedPiezas reutilizables en toda la appBotón, CardComponent, pipes
featuresFuncionalidades completas de negocioLogin, Productos, Dashboard

Reglas clave

  • Un componente por archivo: cada componente vive en su propia carpeta con su template y estilos
  • Nombres descriptivos: usa el sufijo del tipo ( LoginComponent, AuthService, auth.guard.ts )
  • Barrel exports: usa archivos index.ts para simplificar importaciones
  • Separación de responsabilidades: los componentes solo manejan la vista, la lógica va en servicios
No importes directamente desde `node_modules` o desde carpetas lejanas. Usa importaciones relativas dentro de features y absolutas para core y shared.

10.2 Standalone components en Angular moderno

¿Qué cambia con standalone?

Desde Angular 14+ y consolidado en Angular 17+, los standalone components eliminan la necesidad de crear NgModules para cada funcionalidad. Cada componente se declara independiente e importa sus propias dependencias directamente.

Componente standalone vs. con módulo

// Antes (con NgModule)
@Component({
  selector: 'app-lista',
  templateUrl: './lista.component.html'
})
export class ListaComponent {}

// Después (standalone)
@Component({
  selector: 'app-lista',
  standalone: true,
  imports: [CommonModule, RouterLink],
  templateUrl: './lista.component.html'
})
export class ListaComponent {}

Configuración de la aplicación standalone

// app.config.ts
import { ApplicationConfig } from '@angular/core';
import { provideRouter } from '@angular/router';
import { provideHttpClient, withInterceptors } from '@angular/common/http';
import { routes } from './app.routes';
import { authInterceptor } from './core/interceptors/auth.interceptor';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideHttpClient(withInterceptors([authInterceptor]))
  ]
};
// main.ts
import { bootstrapApplication } from '@angular/platform-browser';
import { AppComponent } from './app/app.component';
import { appConfig } from './app/app.config';

bootstrapApplication(AppComponent, appConfig);

Ventajas de standalone

  • Menos boilerplate: no es necesario crear un NgModule para cada feature
  • Lazy loading por componente: loadComponent carga un componente individual
  • Importaciones explícitas: cada componente lista sus dependencias directamente
  • Más simple: menos archivos y menos indirección conceptual
Para todos los proyectos nuevos, Angular recomienda empezar con standalone. Los NgModules siguen siendo válidos para mantener proyectos existentes y muchas librerías de terceros aún los usan.

10.3 Estilos y arquitectura de componentes

Encapsulación de estilos

Angular encapsula los estilos de cada componente por defecto usando ViewEncapsulation.Emulated. Los estilos de un componente no afectan a otros componentes.

Opciones de encapsulación

OpciónComportamientoUso típico
EmulatedSimula Shadow DOM con atributosPor defecto, recomendado
NoneNo encapsula; los estilos son globalesEstilos que deben afectar a toda la app
ShadowDomUsa Shadow DOM nativo del navegadorCasos específicos con Web Components

Consejos de arquitectura

  • Componentes pequeños: cada componente debería hacer una sola cosa (Single Responsibility)
  • Contenedor vs. presentacional: separa componentes que gestionan estado (container) de componentes que solo muestran datos (presentational)
  • OnPush change detection: usa changeDetection: ChangeDetectionStrategy.OnPush para mejorar el rendimiento
  • Pipes para transformaciones: no formatees datos en el template; crea pipes reutilizables

Ejemplo: componente con OnPush

import { Component, Input, ChangeDetectionStrategy } from '@angular/core';

@Component({
  selector: 'app-tarjeta-producto',
  standalone: true,
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    <div class="tarjeta">
      <h3>{{ titulo }}</h3>
      <p>${{ precio }}</p>
    </div>
  `
})
export class TarjetaProductoComponent {
  @Input() titulo!: string;
  @Input() precio!: number;
}
OnPush solo vuelve a renderizar el componente cuando cambia una referencia de Input, un evento del usuario o una suscripción manual. Es significativamente más rápido que la estrategia por defecto.

10.4 Compilación para producción (ng build)

¿Qué hace ng build?

El comando ng build compila la aplicación Angular para producción: optimiza el código, reduce el tamaño de los bundles, elimina código muerto y genera archivos estáticos listos para desplegar.

Configuraciones de compilación

ConfiguraciónComandoDescripción
developmentng build --configuration developmentSin optimización, más rápido
productionng buildOptimizado por defecto

Opciones útiles

# Build estándar para producción
ng build

# Build con configuración específica
ng build --configuration=production

# Build con basename personalizado (si se sirve desde /app/)
ng build --base-href=/app/

# Build sin generar sourcemaps (menor tamaño)
ng build --source-map=false

# Build y abrir en el navegador (para probar el resultado)
ng build --open

Resultado del build

dist/mi-app/
├── browser/
│   ├── index.html
│   ├── main.abc123.js          # Bundle principal
│   ├── polyfills.def456.js     # Compatibilidad con navegadores
│   ├── styles.ghi789.css       # Estilos globales
│   └── lazy.chunk.jkl012.js    # Módulos lazy-loaded (si los hay)

Tips de rendimiento

  • Lazy loading: reduce el bundle inicial cargando módulos bajo demanda
  • Tree shaking: Angular elimina automáticamente el código no utilizado
  • Source maps: desactivarlos en producción reduce el tamaño del build
  • Análisis de tamaño: usa ng build --stats-json con webpack-bundle-analyzer
Ejecuta `ng build` antes de desplegar. El resultado en `dist/` es lo que se sube al servidor o CDN. Nunca desplegues el código fuente ni la carpeta `node_modules`.

Opciones de despliegue

Despliegue en GitHub Pages

# Instalar el paquete de despliegue
npm install -g angular-cli-ghpages

# Build con base href correcto
ng build --configuration=production --base-href=/nombre-repo/

# Desplegar la carpeta dist/browser
npx angular-cli-ghpages --dir=dist/mi-app/browser

Despliegue con Docker + Nginx

FROM node:18-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN ng build --configuration=production

FROM nginx:alpine
COPY --from=build /app/dist/mi-app/browser /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

Configuración del servidor para SPA

Independientemente de la plataforma, el servidor debe redirigir todas las rutas hacia index.html para que Angular gestione la navegación client-side:

# Configuración Nginx para SPA
location / {
  try_files $uri $uri/ /index.html;
}
Configurar la redirección del servidor para SPA es obligatorio. Sin ella, refrescar la página o acceder directamente a una ruta producirá un error 404.

10.6 Testing y buenas prácticas

Testing en Angular

Angular incluye herramientas de testing integradas: Karma para pruebas unitarias y Jasmine como framework de aserciones. La CLI genera archivos .spec.ts junto a cada componente y servicio.

Tipos de testing

TipoHerramientaQué valida
UnitariasKarma + JasmineClases, servicios, pipes de forma aislada
ComponentesAngular TestBedComponentes renderizados con su template
IntegraciónKarma + HttpClientTestingModuleFlujos completos con servicios mockeados
E2EProtractor (legado) / Cypress / PlaywrightFlujos completos en el navegador

Ejemplo: test de un componente

import { ComponentFixture, TestBed } from '@angular/core/testing';
import { SaludoComponent } from './saludo.component';

describe('SaludoComponent', () => {
  let component: SaludoComponent;
  let fixture: ComponentFixture<SaludoComponent>;

  beforeEach(async () => {
    await TestBed.configureTestingModule({
      imports: [SaludoComponent]
    }).compileComponents();

    fixture = TestBed.createComponent(SaludoComponent);
    component = fixture.componentInstance;
    fixture.detectChanges();
  });

  it('debería crear el componente', () => {
    expect(component).toBeTruthy();
  });

  it('debería mostrar el nombre del usuario', () => {
    component.nombre = 'Carlos';
    fixture.detectChanges();
    const compiled = fixture.nativeElement as HTMLElement;
    expect(compiled.querySelector('p')?.textContent).toContain('Carlos');
  });
});

Buenas prácticas resumidas

  • Testea servicios primero: son la lógica más importante y la más fácil de testear
  • Usa dependencias inyectadas: evita crear instancias directamente; usa DI para poder sustituir en tests
  • Tipa todo: evita el uso de any; define interfaces para los modelos de datos
  • No mutas estado directamente: usa spread operator o immer para actualizaciones inmutables
  • Un componente, un archivo: no combines varios componentes en un solo archivo
  • Usa la CLI: genera componentes, servicios y módulos con ng generate para mantener convenciones
  • Linting: ejecuta ng lint regularmente para detectar errores y malas prácticas
Invierte tiempo en tests desde el principio. Un proyecto con buena cobertura de tests es más fácil de mantener, refactorizar y desplegar con confianza.

Resumen

**Lo que aprendiste en esta sección:** - Organiza el proyecto por **funcionalidades** (core, shared, features) para mantener la escalabilidad - Los **standalone components** eliminan la necesidad de NgModules en proyectos nuevos - Usa **OnPush change detection** y componentes pequeños para mejorar el rendimiento - **ng build** compila y optimiza la aplicación; el resultado en `dist/` se despliega al servidor - Configura siempre la **redirección del servidor** para que todas las rutas lleguen a index.html - Los **tests** (unitarias, componentes y E2E) garantizan la calidad y facilitan el mantenimiento
