Clustered vs Nonclustered

La distinción que organiza TODO el diseño físico de SQL Server: la tabla clustered ES el orden físico; los nonclustered son punteros ordenados hacia ella:

AspectoCLUSTERED (la tabla)NONCLUSTERED (índice aparte)
Cantidad por tabla1 solaHasta 999
Hojas contienen…Filas completas de datosClaves + locator a fila (o INCLUDEs)
Ejemplo naturalPK IDENTITY (append-only ✅)Email, SKU, fecha+estado compuestos
Peligro clásicoGUID aleatorio → fragmentación brutalSobrecarga en cada DML si hay 20 índices
Sin definirloToma heap (sin orden) — casi nunca deseadoN/A
 
CREATE TABLE Eventos (
    evento_id BIGINT IDENTITY PRIMARY KEY CLUSTERED,   -- la tabla misma
    usuario_id INT NOT NULL,
    tipo       VARCHAR(30) NOT NULL,
    creado_el  DATETIME2 NOT NULL
);
CREATE INDEX IX_Eventos_usuario_fecha      -- nonclustered:
    ON Eventos (usuario_id, creado_el DESC); -- clave ordenada útil

-- Índice único y compuesto multi-columna:
CREATE UNIQUE NONCLUSTERED INDEX UX_Productos_sku
ON Productos (sku);

Orden de columnas en índice compuesto = orden de búsqueda: IX(a, b, c) sirve WHERE a=..., WHERE a AND b, WHERE a AND b AND c — pero NO b o c solos. Regla: igualdades primero, rango último.

INCLUDE y filtros: índices inteligentes

-- COVERING index: la query se responde SOLO leyendo el índice:
CREATE INDEX IX_Pedidos_cliente_covering
ON Pedidos (cliente_id, fecha DESC)
INCLUDE (total, estado);        -- columnas cubiertas SIN entrar al índice base
GO

SELECT total, estado FROM Pedidos
WHERE cliente_id = 42 AND fecha > '2026-01-01';
-- Plan muestra Index Seek + sin Key Lookup = covering logrado ⚡

-- Índice FILTRADO: solo una porción de filas (exclusivo T-SQL):
CREATE INDEX IX_Pedidos_pendientes
ON Pedidos (fecha, cliente_id)
WHERE estado = 'pendiente';     -- mini-índice ultradenso para la cola activa

CREATE UNIQUE INDEX UX_Email_activos
ON Clientes (email) WHERE activo = 1;   -- unicidad SOLO entre activos

Cuándo cada arma brilla

ArmaEscenario idealSeñal en el plan
INCLUDESELECT pocas columnas extra frecuentesKey Lookup eliminado tras crearlo
Filtrado WHERE=constanteEstados calientes (pendientes), soft-deleteSeek directo con Predicate en índice
Compuesto bien ordenadoMixtos igualdad+rangoSeek con Seek Predicates múltiples

El índice filtrado falla silenciosamente (no se usa) si tu query parametriza el filtro (@estado vs literal 'pendiente'): el plan debe servir cualquier valor. Funciona perfecto desde queries literales o vistas indexadas específicas.

Medir antes de optimizar: planes y estadísticas

SET STATISTICS IO ON;      -- lecturas lógicas/físicas por tabla
SET STATISTICS TIME ON;    -- CPU y elapsed reales
-- ejecuta la query... lee Messages:

-- Table 'Pedidos'. Scan count 1, logical reads 45812   ← el número que importa
-- SQL Server Execution Times: CPU time = 1234 ms

-- El plan real (no estimado):
SET STATISTICS PROFILE ON;             -- texto completo post-ejecución
-- o en SSMS: Ctrl+M (Include Actual Execution Plan)

-- Operadores buenos vs malos del plan:
-- ✅ Index SEEK: acceso quirúrgico por índice
-- ⚠️ Index SCAN: recorre TODO el índice (ok si tabla chica)
-- ❌ Table SCAN: heap entero leído — sospechoso siempre
-- 🚨 Key Lookup ×N: miles de saltos al clustered = falta INCLUDE
-- 🚨 Hash Match / Sort spill a tempdb: memoria insuficiente o stats malas

-- Estadísticas obsoletas = planes malos:
UPDATE STATISTICS Pedidos WITH FULLSCAN;      -- manual puntual
SELECT * FROM sys.dm_db_stats_properties(OBJECT_ID('Pedidos'), 1);  -- frescura

Lecturas lógicas (logical reads) es LA métrica comparable: páginas tocadas en buffer. Bajarlas 10x baja CPU y latencia proporcionalmente. El tiempo absoluto varía por caché/carga; las lecturas no mienten.

Mantenimiento: fragmentación y estadísticas

-- Diagnóstico de fragmentación:
SELECT ips.index_id, i.name,
       ips.avg_fragmentation_in_percent,
       ips.page_count
FROM sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('Eventos'),
                                    NULL, NULL, 'LIMITED') ips
JOIN sys.indexes i ON i.object_id = ips.object_id AND i.index_id = ips.index_id;

-- Remedio según severidad:
ALTER INDEX IX_Eventos_usuario_fecha ON Eventos REORGANIZE;  -- <30%: online ligero
ALTER INDEX ALL ON Eventos REBUILD WITH (ONLINE = ON);        -- >30%: reconstrucción

-- Actualizar estadísticas tras cargas masivas:
UPDATE STATISTICS Eventos;

-- Ojo con la sobrecarga: cada índice cobra en INSERT/UPDATE/DELETE:
SELECT i.name, us.user_seeks, us.user_scans, us.user_lookups, us.user_updates
FROM sys.dm_db_index_usage_stats us
JOIN sys.indexes i ON i.index_id = us.index_id AND i.object_id = us.object_id
WHERE us.database_id = DB_ID()
ORDER BY us.user_updates DESC;    -- muchos updates, cero seeks ⇒ candidato drop

"Añade un índice" no es gratis: cada uno duplica escritura potencialmente y ocupa cache valioso. La meta no es máxima velocidad de SELECT sino balance read/write sostenible. Un índice que nadie seek-ea pero todos actualizan es deuda técnica pura.

Ejercicios prácticos

  1. Laboratorio SARGable: tabla 500k filas; compara YEAR(col)=2026 vs rango con STATISTICS IO; documenta lecturas ambas.
  2. Cazador de Key Lookup: query frecuente con lookup ×10k; crea INCLUDE correcto; verifica desaparición del operador en plan.
  3. Índice filtrado vivo: cola de pendientes con índice filtrado; mide su tamaño vs índice equivalente completo; prueba uso con parámetro vs literal.
  4. Auditoría de índices muertos: usa dm_db_index_usage_stats para listar candidatos a drop en tu BD práctica; justifica cada uno.
  5. Ciclo completo: fragmenta deliberadamente (insert/delete masivo GUID), mide %, REORGANIZE vs REBUILD comparando tiempos y resultado final.
