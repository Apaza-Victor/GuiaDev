CREATE/ALTER/DROP DATABASE

-- Mínimo viable:
CREATE DATABASE Tienda;

-- Con ubicación explícita de archivos (producción):
CREATE DATABASE Tienda ON PRIMARY (
    NAME = Tienda_data,
    FILENAME = 'D:\SQLData\Tienda.mdf',
    SIZE = 100MB, MAXSIZE = 10GB, FILEGROWTH = 50MB
) LOG ON (
    NAME = Tienda_log,
    FILENAME = 'E:\SQLLogs\Tienda.ldf',
    SIZE = 50MB, MAXSIZE = UNLIMITED, FILEGROWTH = 25MB
);

-- Modificar en caliente:
ALTER DATABASE Tienda MODIFY NAME = Tienda2026;   -- o sp_renamedb
ALTER DATABASE Tienda SET RECOVERY SIMPLE;         -- modelo recuperación
ALTER DATABASE Tienda SET AUTO_SHRINK OFF;         -- casi siempre off

-- Eliminar (¡irreversible!):
DROP DATABASE IF EXISTS Tienda2026;
ArchivoExtensiónContenido
Data primario.mdfDatos + catálogo de la base
Data secundarios (opcional).ndfDatos repartidos por discos/filegroups
Log transaccional.ldfTODA operación registrada: base del rollback/recovery

DROP DATABASE no pide confirmación ni va a la papelera: borra los .mdf/.ldf del disco al instante. En scripts productivos, IF EXISTS es tu único seguro — y backups previos el real.

Esquemas (schemas): namespaces internos

Dentro de una base, los esquemas agrupan objetos: base.esquema.objeto. Sirven para organizar dominios grandes y afinar permisos por rol:

CREATE SCHEMA ventas AUTHORIZATION dbo;
CREATE SCHEMA contabilidad;
GO

CREATE TABLE ventas.Pedidos (...);
CREATE TABLE contabilidad.Asientos (...);

SELECT * FROM ventas.Pedidos WHERE ...;   -- referencia completa

-- Mover objeto entre esquemas:
ALTER SCHEMA contabilidad TRANSFER ventas.FacturasAntiguas;

-- Permisos por esquema (oro para seguridad):
GRANT SELECT ON SCHEMA::ventas TO RolConsultas;
Sin esquemasCon esquemas
300 tablas todas dbo.* mezcladasPrefijos lógicos: ventas., rrhh., finanzas.
Permisos tabla a tabla tediososUn GRANT por esquema cubre todo su grupo
Refactorizar = renombrar tablasMover con ALTER SCHEMA TRANSFER

El esquema default es dbo (database owner). Si no calificas, SQL Server resuelve primero el esquema del usuario conectado, luego dbo — fuente clásica de "Invalid object name" cuando un usuario sin schema default toca tablas que "existen".

CREATE TABLE y ALTER TABLE

CREATE TABLE dbo.Productos (
    id            INT IDENTITY(1,1) NOT NULL,
    sku           VARCHAR(20)       NOT NULL,
    nombre        NVARCHAR(100)     NOT NULL,
    precio        DECIMAL(10,2)     NOT NULL CONSTRAINT DF_prod_precio DEFAULT 0,
    activo        BIT               NOT NULL CONSTRAINT DF_prod_activo DEFAULT 1,
    CONSTRAINT PK_Productos PRIMARY KEY CLUSTERED (id),
    CONSTRAINT UQ_Productos_sku UNIQUE (sku)
);

-- Evolución segura (el 90% del trabajo real):
ALTER TABLE Productos ADD descripcion NVARCHAR(500) NULL;          -- nueva columna
ALTER TABLE Productos ADD stock INT NOT NULL CONSTRAINT DF_stock DEFAULT 0;  -- no-null necesita default
ALTER TABLE Productos ALTER COLUMN precio DECIMAL(12,2) NOT NULL;  -- cambiar tipo
EXEC sp_rename 'Productos.descripcion', 'detalle', 'COLUMN';       -- renombrar columna
EXEC sp_rename 'Productos', 'Articulos';                           -- renombrar tabla
ALTER TABLE Productos DROP COLUMN descripcion;                     -- eliminar

-- Borrar columna CON su constraint (orden correcto):
ALTER TABLE Productos DROP CONSTRAINT DF_prod_activo;
ALTER TABLE Productos DROP COLUMN activo;

En producción NUNCA cambies tipos ni borres columnas directamente: añade columna nueva, migra datos, despliega código consumiéndola, y recién después elimina la vieja. ALTER COLUMN sobre columnas indexadas/FKs falla o bloquea tablas enormes.

Tablas temporales de sistema (2016+)

CREATE TABLE dbo.Salarios (
    empleado_id INT NOT NULL PRIMARY KEY,
    monto       DECIMAL(10,2) NOT NULL,
    valido_desde DATETIME2 GENERATED ALWAYS AS ROW START NOT NULL,
    valido_hasta DATETIME2 GENERATED ALWAYS AS ROW END   NOT NULL,
    PERIOD FOR SYSTEM_TIME (valido_desde, valido_hasta)
) WITH (SYSTEM_VERSIONING = ON);      -- historial automático consultable:
SELECT * FROM Salarios FOR SYSTEM_TIME AS OF '2026-01-01';

TRUNCATE vs DELETE vs DROP

AspectoDELETETRUNCATE TABLEDROP TABLE
Qué haceBorra filas seleccionadasVacía TODAS las filasElimina tabla completa
Filtra con WHERE?✅ Sí❌ Nunca❌ Nunca
Dispara triggers?✅ DELETE triggers❌ No❌ No
Reinicia IDENTITY?❌ No✅ Sí (RESEED a seed)N/A
Rinde log mínimo?❌ Fila por fila✅ Por páginas (mucho más rápido)—
Permite ROLLBACK?✅ Sí✅ Sí (¡mito que dice que no!)✅ Dentro transacción
Falla si hay FK apuntando?Solo filas referenciadas❌ Siempre falla❌ Siempre falla
 
BEGIN TRAN;
TRUNCATE TABLE staging_logs;    -- sí se puede revertir:
ROLLBACK;                        -- filas de vuelta ✅

"TRUNCATE no se puede hacer ROLLBACK" es el mito #1 de entrevistas SQL Server. Es falso dentro de una transacción explícita. Lo que NO tiene vuelta atrás es ejecutarlo sin transacción: log mínimo significa menos capacidad de PITR (point-in-time recovery).

Ejercicios prácticos

  1. Base con arquitectura: crea AcademiaDB con esquemas docencia y admin; distribuye tablas (Alumnos en docencia, Facturas en admin) con referencias cruzadas.
  2. Evolución viva: parte de Productos simple y aplica 5 ALTERs progresivos documentados (columna, tipo, rename, drop con constraint, default).
  3. Laboratorio TRUNCATE vs DELETE: tabla 100k filas; cronometra DELETE completo vs TRUNCATE vs TRUNCATE+ROLLBACK; verifica mitos.
  4. Temporal playground: crea tabla temporal de sistema, actualiza precios varias veces y consulta el histórico con FOR SYSTEM_TIME AS OF.
  5. Cazador de dependencias: usa sp_help y sys.foreign_keys para listar qué bloquearía un DROP TABLE antes de intentarlo.
