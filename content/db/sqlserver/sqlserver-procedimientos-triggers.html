Procedimientos: CREATE PROCEDURE

CREATE OR ALTER PROCEDURE dbo.sp_RegistrarPedido   -- OR ALTER = idempotente
    @cliente_id INT,
    @producto_id INT,
    @cantidad   INT
AS
BEGIN
    SET NOCOUNT ON;                 -- evita "n rows affected" extra al cliente
    SET XACT_ABORT ON;              -- error ⇒ rollback automático total

    DECLARE @precio DECIMAL(10,2), @stock INT;

    BEGIN TRY
        BEGIN TRAN;

        SELECT @precio = precio, @stock = stock
        FROM dbo.Productos WITH (UPDLOCK)      -- lock de actualización
        WHERE producto_id = @producto_id;

        IF @stock < @cantidad
            THROW 50001, 'Stock insuficiente', 1;

        INSERT INTO Pedidos (cliente_id, producto_id, cantidad, total)
        VALUES (@cliente_id, @producto_id, @cantidad, @precio * @cantidad);

        UPDATE Productos SET stock -= @cantidad
        WHERE producto_id = @producto_id;

        COMMIT;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK;
        THROW;                       -- re-lanza el error original
    END CATCH
END;
GO

EXEC sp_RegistrarPedido @cliente_id=5, @producto_id=12, @cantidad=3;
Setting del procedurePor qué es sagrado
SET NOCOUNT ONSilencia DONE_IN_PROC: menos red, drivers felices
SET XACT_ABORT ONCualquier error runtime aborta y revierte TODO sin excepciones parciales
TRY/CATCH + THROW re-lanzadoRollback controlado SIN tragarse el error: la app sigue enterándose
CREATE OR ALTERMismo script re-ejecutable en todos los entornos ✅

Nunca nombres tus procedures sp_Algo: ese prefijo pertenece AL SISTEMA. SQL Server busca primero en master los sp_*, generando lookups extra y comportamientos raros. Convenciones vivas: usp_, proc_ o nada.

Parámetros OUTPUT y lógica interna

CREATE OR ALTER PROCEDURE sp_ProcesarPago
    @pedido_id     INT,
    @monto         DECIMAL(12,2),
    @aprobado      BIT          OUTPUT,      -- salida
    @codigo_error  INT          OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @saldo DECIMAL(12,2);

    SELECT @saldo = saldo FROM Clientes c
    JOIN Pedidos p ON p.cliente_id = c.cliente_id
    WHERE p.pedido_id = @pedido_id;

    IF @saldo IS NULL
    BEGIN
        SET @aprobado = 0; SET @codigo_error = 404;
        RETURN;
    END

    IF @saldo < @monto
    BEGIN
        SET @aprobado = 0; SET @codigo_error = 501;
        RETURN;
    END

    UPDATE ... ;   -- aplicar cargo
    SET @aprobado = 1; SET @codigo_error = 0;
END;
GO

-- Consumirlo:
DECLARE @ok BIT, @err INT;
EXEC sp_ProcesarPago @pedido_id=42, @monto=99.90,
                     @aprobado=@ok OUTPUT, @codigo_error=@err OUTPUT;
SELECT @ok AS aprobado, @err AS codigo;

@pais NVARCHAR(2) = NULL       -- si no llega: filtra solo si viene:
WHERE (@pais IS NULL OR pais = @pais)   -- patrón "catch-all query" clásico

Cuando sientas necesidad de un cursor o WHILE fila a fila, pregúntate primero "¿esto no es un UPDATE/JOIN set-based?". El 95% de loops T-SQL son joins mal escritos. Los cursores legítimos: mantenimiento administrativo, llamadas a procedures por elemento.

Triggers DML: inserted y deleted

-- Auditoría automática de cambios salariales:
CREATE OR ALTER TRIGGER trg_Empleados_Auditoria
ON Empleados
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;
    -- PSEUDO-TABLAS: inserted=nuevos valores, deleted=anteriores:
    INSERT INTO Auditoria_Salarios (empleado_id, salario_anterior, salario_nuevo, cuando)
    SELECT d.empleado_id, d.salario, i.salario, SYSDATETIME()
    FROM inserted i
    JOIN deleted d ON d.empleado_id = i.empleado_id
    WHERE i.salario <> d.salario;
END;
GO

-- INSTEAD OF: REEMPLAZA la operación (típico en vistas no actualizables):
CREATE TRIGGER trg_vwClientes_IOI
ON vw_ClientesConDetalle
INSTEAD OF INSERT
AS
BEGIN
    INSERT INTO Clientes (nombre, email) SELECT nombre, email FROM inserted;
    -- lógica custom para las columnas derivadas...
END;

-- Deshabilitar/eliminar:
DISABLE TRIGGER trg_Empleados_Auditoria ON Empleados;
DROP TRIGGER IF EXISTS trg_Empleados_Auditoria;
Pseudo-tablaINSERTUPDATEDELETE
insertedFilas nuevasValores post-update— vacía
deleted— vacíaValores pre-updateFilas eliminadas

Los triggers DML disparan POR SENTENCIA, no por fila: una UPDATE masiva de 50k filas entrega inserted/deleted con 50k filas. Un trigger escrito pensando "por fila" (variables escalares) se corrompe silenciosamente ante batch updates. SIEMPRE piensa set-based dentro del trigger.

Ejercicios prácticos

  1. Procedure transaccional: implementa sp_RegistrarPedido completo; prueba stock insuficiente (THROW), fallo forzado intermedio y atomicidad verificada.
  2. API con OUTPUT: sp_TransferirSaldo(cuenta_origen, destino, monto) devolviendo @exito/@saldo_restante; cubre saldo insuficiente y cuenta inexistente.
  3. Auditoría set-based: trigger AFTER UPDATE que registre TODOS los cambios de una update masiva multi-fila correctamente; demuéstralo con batch de 10k.
  4. Anti-cursor: escribe la misma tarea con cursor y con UPDATE...FROM join; cronometra ambas sobre 100k filas.
  5. INSTEAD OF real: vista compleja + trigger INSTEAD OF INSERT que reparta datos a dos tablas base; inserta vía vista y valida integridad cruzada.
