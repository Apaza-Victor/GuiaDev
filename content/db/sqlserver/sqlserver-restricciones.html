PRIMARY KEY e IDENTITY

La PK garantiza unicidad y crea automáticamente un índice. En SQL Server la combinación clásica es INT IDENTITY (autonumérico, el "auto_increment" local):

CREATE TABLE Clientes (
    id   INT IDENTITY(1000, 5) PRIMARY KEY,   -- seed 1000, salto 5
    email NVARCHAR(120) NOT NULL
);
-- inserts generan: 1000, 1005, 1010...

-- Ver el último generado en TU sesión:
SELECT SCOPE_IDENTITY() AS ultimo_id;      -- ✅ recomendado (por sesión)
SELECT @@IDENTITY;                          -- ⚠️ afectada por triggers
SELECT IDENT_CURRENT('Clientes');           -- última de CUALQUIER sesión

-- Insertar valor manual (cargas/migraciones):
SET IDENTITY_INSERT Clientes ON;
INSERT INTO Clientes (id, email) VALUES (1, 'legacy@mail.com');
SET IDENTITY_INSERT Clientes OFF;

-- Reajustar el contador:
DBCC CHECKIDENT ('Clientes', RESEED, 500);  -- próximo insert: 505

PK natural vs surrogate

EstrategiaProsContras
Surrogate INT IDENTITYCorta, estable, joins rápidosNo significa nada por sí sola
Natural (DNI, email)Autorreferencial legibleDatos reales CAMBIAN → cascade de updates
UNIQUEIDENTIFIER GUIDGenerable offline, merge fácilAncho (16B), NEWID aleatorio fragmenta índice

Patrón dominante corporativo: PK surrogate IDENTITY + constraint UNIQUE sobre la clave natural (email, DNI...). Lo mejor de ambos mundos.

FOREIGN KEY y acciones referenciales

La FK garantiza que todo hijo apunte a un padre existente — la columna vertebral del modelo relacional:

Ver código PlantUML

entity Clientes {
  * id : INT <>
  --
  email : NVARCHAR(120) <>
}

  * pedido_id : INT <>
  --
  # cliente_id : INT < Clientes.id>>
  fecha : DATETIME2
}
entity Productos {
  * producto_id : INT <>
  --
  sku : VARCHAR(20) <>
}
entity Detalle {
  * pedido_id : INT < Pedidos>>
  * producto_id : INT < Productos>>
  --
  cantidad : SMALLINT < 0>>
}
Clientes ||--o{ Pedidos : cliente_id
Pedidos ||--|{ Detalle : contiene
Productos ||--o{ Detalle : referenciado
@enduml
CREATE TABLE Pedidos (
    pedido_id  INT IDENTITY(1,1) NOT NULL,
    cliente_id INT NOT NULL,
    total      DECIMAL(12,2) NOT NULL,
    CONSTRAINT PK_Pedidos PRIMARY KEY (pedido_id),
    CONSTRAINT FK_pedidos_clientes FOREIGN KEY (cliente_id)
        REFERENCES Clientes (id)
        ON DELETE NO ACTION          -- default: bloquea borrar padre con hijos
        ON UPDATE NO ACTION,
);

-- Cascadas (usar conscientemente):
CONSTRAINT FK_detalles_pedidos FOREIGN KEY (pedido_id)
    REFERENCES Pedidos (pedido_id)
    ON DELETE CASCADE                 -- borrar pedido borra sus detalles
    ON UPDATE CASCADE;

-- SET NULL / SET DEFAULT al eliminar padre:
ON DELETE SET NULL     -- huérfanos quedan NULL (columna nullable requerida)
ON DELETE SET DEFAULT
Acción ON DELETEEfectoRiesgo
NO ACTION (default)Error si hay hijosNinguno — el seguro por defecto ✅
CASCADEBorra hijos en cadenaEliminaciones masivas accidentales ⚠️
SET NULLHuérfanos NULLSolo si negocio lo permite

CASCADE encadenado en modelos profundos puede convertir un DELETE de una fila padre en borrado en cascada de millones de filas hijas — con locks y log incluidos. Documenta cada cascada y evita cadenas de más de dos niveles.

UNIQUE, CHECK y NOT NULL

-- UNIQUE: permite UN solo NULL (a diferencia de otras BD):
CREATE TABLE Empleados (
    dni   CHAR(14) NOT NULL UNIQUE,               -- inline
    email NVARCHAR(120),
    CONSTRAINT UQ_emp_email UNIQUE (email)         -- nombrada explícita
);

-- CHECK: reglas de negocio a nivel motor:
CREATE TABLE Pedidos (
    cantidad SMALLINT NOT NULL CONSTRAINT CHK_cantidad_positiva CHECK (cantidad > 0),
    estado   VARCHAR(20) NOT NULL CONSTRAINT CHK_estado_valido
             CHECK (estado IN ('pendiente','pagado','enviado','cancelado')),
    f_nac    DATE NOT NULL,
    f_alta   DATE NOT NULL,
    CONSTRAINT CHK_fechas_coherentes CHECK (f_alta >= f_nac)
);

-- CHECK con funciones (¡cuidado rendimiento!):
ALTER TABLE Clientes ADD CONSTRAINT CHK_email_formato
CHECK (email LIKE '%_@_%._%');                    -- simple, no RFC completo

-- NOT NULL con valores default:
activo BIT NOT NULL CONSTRAINT DF_activo DEFAULT(1);

CHECK con UDFs o subconsultas NO existe (solo expresiones de fila). Y los CHECK existentes no revalidan datos antiguos salvo WITH CHECK: datos pre-existentes inválidos pueden convivir silenciosamente con tu constraint nueva.

Administrar restricciones

-- Descubrir qué constraints tiene una tabla:
EXEC sp_helpconstraint 'Pedidos';
SELECT * FROM sys.key_constraints  WHERE parent_object_id = OBJECT_ID('Pedidos');
SELECT * FROM sys.check_constraints WHERE parent_object_id = OBJECT_ID('Pedidos');

-- Deshabilitar temporalmente (cargas masivas):
ALTER TABLE Pedidos NOCHECK CONSTRAINT FK_pedidos_clientes;
-- ... carga ...
ALTER TABLE Pedidos WITH CHECK CHECK CONSTRAINT FK_pedidos_clientes;

-- Eliminar:
ALTER TABLE Pedidos DROP CONSTRAINT FK_pedidos_clientes;

NOCHECK sin re-habilitar con WITH CHECK deja la FK "no confiable": el optimizador la ignora para simplificar planes (joins eliminables) y tus datos pueden contener huérfanos invisibles. El patrón correcto siempre termina en WITH CHECK CHECK CONSTRAINT.

Checklist de diseño con constraints

  • Toda tabla tiene PK explícita con nombre (nunca anónima).
  • Claves naturales duplicadas protegidas con UNIQUE.
  • Reglas invariables del negocio en CHECK, no solo en app.
  • Constraints NOMBRADAS (migraciones limpias: DROP CONSTRAINT nombre exacto).
  • Cascadas mínimas y documentadas.

Ejercicios prácticos

  1. Modela el ER del diagrama: implementa las 4 tablas completas con TODAS las constraints nombradas del diagrama PlantUML.
  2. Laboratorio cascadas: con pedidos+detalle poblados, prueba DELETE padre con NO ACTION vs CASCADE; documenta ambos comportamientos.
  3. Cazador de huérfanos: NOCHECK una FK, inserta hijo ilegal, re-habilita con y sin WITH CHECK; usa DBCC CHECKCONSTRAINTS para detectar.
  4. IDENTITY bajo control: practica IDENTITY_INSERT, RESEED y SCOPE_IDENTITY vs @@IDENTITY con trigger intermedio que inserte en otra tabla.
  5. Guardián de negocio: añade CHECKs realistas a tu modelo (precios ≥ 0, fechas coherentes, estados válidos) e intenta violarlos todos documentando mensajes.
