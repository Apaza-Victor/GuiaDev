INSERT: variantes y recuperación de IDs

-- Multi-row estándar:
INSERT INTO Clientes (nombre, email, pais) VALUES
    ('Ana', 'ana@mail.com', 'ES'),
    ('Luis', 'luis@mail.com', 'MX'),
    ('Marta', 'marta@mail.com', 'AR');

-- INSERT ... SELECT:
INSERT INTO Archivo_2025
SELECT * FROM Pedidos WHERE YEAR(fecha) = 2025;

-- ✨ OUTPUT: recuperar lo insertado (el superpoder T-SQL):
INSERT INTO Clientes (nombre, email)
OUTPUT inserted.cliente_id, inserted.email   -- a resultados
VALUES ('Carlos', 'carlos@mail.com');

OUTPUT inserted.* INTO @tabla_temporal;      -- o capturarlo a variable tabla

DECLARE @nuevos TABLE (id INT, email NVARCHAR(120));
INSERT INTO Clientes (nombre, email)
OUTPUT inserted.cliente_id, inserted.email INTO @nuevos
VALUES ('Diana','d@mail.com'), ('Eva','e@mail.com');
SELECT * FROM @nuevos;   -- IDs exactos sin importar triggers

Obtener el ID generado: las tres vías

MétodoÁmbitoSeguro con triggers?
SCOPE_IDENTITY()Tu scope actual✅ Sí
@@IDENTITYSesión completa❌ Puede devolver ID de trigger
OUTPUT inserted.idLa sentencia✅ El más robusto (multi-fila incluido)

IDENTITY_INSERT permite insertar IDs manuales en migraciones: SET IDENTITY_INSERT Tabla ON → inserts con id explícito → OFF. Recuerda reajustar el contador con DBCC CHECKIDENT ('Tabla', RESEED, ultimo_id_insertado).

UPDATE ... FROM con JOIN

-- La sintaxis T-SQL estrella: UPDATE con FROM+JOIN:
UPDATE p
SET p.total = p.total * 0.95,
    p.modificado_el = SYSDATETIME()
FROM Pedidos p
JOIN Clientes c ON c.cliente_id = p.cliente_id
WHERE c.vip = 1;

-- Sincronizar desde tabla de staging:
UPDATE dest
SET dest.stock = src.stock,
    dest.precio = src.precio
FROM Productos dest
JOIN Staging_Inventario src ON src.sku = dest.sku
WHERE dest.stock <> src.stock OR dest.precio <> src.precio;

-- Con OUTPUT para auditar qué cambió:
UPDATE TOP (100) t
SET t.procesado = 1
OUTPUT deleted.log_id, inserted.procesado
FROM Logs t WHERE t.procesado = 0;

Si el JOIN multiplica filas (varios match por destino), SQL Server actualiza "una arbitraria" sin avisar — resultado impredecible. Garantiza unicidad del lado origen (agrupa antes) o usa MERGE con validación.

El ritual seguro antes de cualquier UPDATE serio

  1. SELECT con el MISMO FROM/WHERE: verifica filas objetivo.
  2. BEGIN TRAN + UPDATE + revisa @@ROWCOUNT contra esperado.
  3. Coincide → COMMIT. No → ROLLBACK e investiga.

DELETE con OUTPUT y archivado

-- DELETE con join estilo T-SQL:
DELETE p
FROM Pedidos p
JOIN Clientes c ON c.cliente_id = p.cliente_id
WHERE c.bloqueado = 1;

-- Archivar ANTES de borrar (patrón profesional):
DELETE d
OUTPUT deleted.* INTO Archivo_Detalle_2025   -- captura exacta de lo borrado
FROM Detalle d
JOIN Pedidos p ON p.pedido_id = d.pedido_id
WHERE p.fecha < '2025-01-01';

-- Borrado masivo por lotes (evita locks eternos):
WHILE 1 = 1
BEGIN
    DELETE TOP (10000) FROM Log_Antiguo
    WHERE creado_el < '2024-01-01';
    IF @@ROWCOUNT = 0 BREAK;
END;
Estrategia borrado masivoRiesgo evitadoCoste
DELETE único giganteNinguno… aparentementeLocks largos, log enorme, replicación colapsada ❌
Lotes DELETE TOP(n) + WHILETodo lo anterior ✅Más código; tiempo total similar
Partición switch (Enterprise)Instantáneo a nivel metadatosDiseño particionado previo

OUTPUT deleted.* INTO archivo es la pareja perfecta del borrado: auditoría EXACTA fila a fila sin triggers ni lecturas previas razonables. En entornos regulados es oro puro.

MERGE: upsert en una sentencia

MERGE compara destino vs origen y ejecuta INSERT/UPDATE/DELETE según exista o no la pareja — sincronización declarativa:

MERGE Productos AS dest
USING Staging_Productos AS src
ON dest.sku = src.sku
WHEN MATCHED AND (
        ISNULL(dest.precio,-1) <> ISNULL(src.precio,-1)
     OR ISNULL(dest.stock,-1)  <> ISNULL(src.stock,-1))
    THEN UPDATE
        SET dest.precio = src.precio,
            dest.stock  = src.stock,
            dest.actualizado_el = SYSDATETIME()
WHEN NOT MATCHED BY TARGET THEN
    INSERT (sku, nombre, precio, stock)
    VALUES (src.sku, src.nombre, src.precio, src.stock)
WHEN NOT MATCHED BY SOURCE AND dest.activo = 1 THEN
    UPDATE SET dest.activo = 0          -- descontinuar, NO borrar
OUTPUT $action, inserted.sku, inserted.precio;
-- $action = 'INSERT' | 'UPDATE' | 'DELETE' por fila afectada

Las cinco cláusulas WHEN posibles

CláusulaDispara cuando…
WHEN MATCHED [AND cond]Pareja existe → UPDATE/DELETE
NOT MATCHED BY TARGETOrigen sin pareja en destino → INSERT
NOT MATCHED BY SOURCEDestino huérfano del origen → UPDATE/DELETE
Varias WHEN MATCHED con condicionesRamas alternativas mutuamente excluyentes

MERGE exige que cada fila destino sea tocada COMO MÁXIMO una vez: origen duplicado sobre misma clave = error "The MERGE statement attempted to UPDATE or DELETE the same row more than once". Deduplica/agrega el USING antes. Y con Hint HOLDLOCK en destino para upserts concurrentes seguros.

Ejercicios prácticos

  1. Ingesta con IDs: carga multi-row capturando todos los IDs generados via OUTPUT INTO variable tabla; verifica correspondencia exacta.
  2. Update VIP ritualizado: descuento VIP con SELECT previo + transacción + @@ROWCOUNT check documentado paso a paso.
  3. Archivador anual: mueve pedidos viejos a histórico usando DELETE OUTPUT INTO dentro de UNA transacción; valida conteos cuadrando.
  4. Purga por lotes: genera 300k logs; purga con WHILE/TOP(10000) midiendo duración por lote vs intento único fallido/lento.
  5. Merge completo: staging→productos con las tres ramas WHEN + condiciones de cambio real + $action reportado; prueba concurrencia con dos sesiones simultáneas.
