Funciones de agregación

SELECT
    COUNT(*)                    AS total_pedidos,     -- todas las filas
    COUNT(fecha_envio)          AS enviados,          -- ignora NULL
    SUM(total)                  AS facturado,
    AVG(total)                  AS ticket_medio,
    MIN(total)                  AS minimo,
    MAX(total)                  AS maximo,
    STDEV(total)                AS desviacion,        -- extra T-SQL
    VAR(total)                  AS varianza
FROM dbo.Pedidos;

-- DISTINCT dentro del agregado:
SELECT COUNT(DISTINCT cliente_id) AS clientes_unicos FROM Pedidos;
SELECT AVG(DISTINCT ciudad_id) -- raro pero existe

-- STRING_AGG: el GROUP_CONCAT de T-SQL (2017+):
SELECT cliente_id,
       STRING_AGG(producto, ', ') WITHIN GROUP (ORDER BY producto) AS lista
FROM Vista_Compras
GROUP BY cliente_id;

T-SQL añade estadística real: STDEV/VAR sobre columnas numéricas. Para dashboards de control de calidad o dispersiones de precios evitas exportar datos: calculas en origen.

GROUP BY y HAVING

SELECT c.ciudad,
       COUNT(*)              AS clientes,
       AVG(edad)             AS edad_media
FROM dbo.Clientes c
WHERE c.activo = 1                    -- filtra FILAS (antes)
GROUP BY c.ciudad                     -- agrupa
HAVING COUNT(*) >= 10                 -- filtra GRUPOS (después)
   AND AVG(edad) BETWEEN 25 AND 65
ORDER BY clientes DESC;

-- Agrupar por múltiples columnas/expresiones:
SELECT YEAR(p.fecha) AS anio,
       MONTH(p.fecha) AS mes,
       p.estado,
       SUM(p.total) AS monto
FROM dbo.Pedidos p
GROUP BY YEAR(p.fecha), MONTH(p.fecha), p.estado
ORDER BY anio DESC, mes DESC;

SQL Server aplica ONLY_FULL_GROUP_BY SIEMPRE e inapelablemente: toda columna del SELECT fuera de agregados debe estar en el GROUP BY. No hay modo para "apagarlo" como en MySQL antiguo — y eso es bueno: los resultados arbitrarios de grupos mal definidos son bugs enlatados.

Window functions: agregar SIN colapsar

SELECT nombre, departamento, salario,
       AVG(salario) OVER (PARTITION BY departamento) AS media_depto,
       salario - AVG(salario) OVER (PARTITION BY departamento) AS vs_media,
       RANK()       OVER (PARTITION BY departamento ORDER BY salario DESC) AS puesto_depto,
       SUM(salario) OVER (ORDER BY contrato ROWS UNBOUNDED PRECEDING) AS acumulado
FROM dbo.Empleados;
-- Cada fila sobrevive con su grupo de contexto a la vista ✨

ROLLUP y GROUPING SETS: subtotales profesionales

Aquí SQL Server brilla frente a MySQL: subtotales multi-nivel declarativos sin UNION manual:

-- ROLLUP: jerarquía año → mes con subtotales + gran total:
SELECT YEAR(fecha)  AS anio,
       MONTH(fecha) AS mes,
       SUM(total)   AS ventas
FROM dbo.Pedidos
GROUP BY ROLLUP(YEAR(fecha), MONTH(fecha));
-- filas (año,mes) + subtotal por año + TOTAL GENERAL

-- CUBE: TODAS las combinaciones (año×estado, año, estado, total):
GROUP BY CUBE(YEAR(fecha), estado);

-- GROUPING SETS: TÚ eliges qué conjuntos:
SELECT pais, ciudad, COUNT(*) AS n
FROM dbo.Clientes
GROUP BY GROUPING SETS (
    (pais, ciudad),      -- detalle completo
    (pais),              -- subtotal país
    ()                   -- gran total
);

-- Distinguir filas de detalle vs subtotal:
SELECT GROUPING(ciudad) AS es_subtotal_ciudad,   -- 1 = fila agregada
       ciudad, COUNT(*)
FROM dbo.Clientes
GROUP BY ROLLUP(ciudad);
OperadorGenera…Uso típico
ROLLUP(a,b)(a,b) + (a) + ()Jerarquías naturales fecha/geo
CUBE(a,b)Todas las combinaciones 2ⁿAnálisis dimensional exploratorio
GROUPING SETS(...)Solo sets listadosReportes exactos sin extras
GROUPING(col)Flag 1/0 por columnaEtiquetar "TOTAL" en app/reportes

Un reporte de ventas con subtotales por mes y gran total suele escribirse como 3 queries unidas por UNION ALL. GROUPING SETS lo hace en UN solo escaneo de datos — hasta 3x más rápido en tablas grandes.

Agregaciones condicionales y PIVOT

-- KPIs múltiples en un solo escaneo:
SELECT
    COUNT(*)                                        AS total,
    SUM(CASE WHEN estado='pagado'    THEN 1 ELSE 0 END) AS pagados,
    SUM(CASE WHEN estado='pendiente' THEN 1 ELSE 0 END) AS pendientes,
    SUM(CASE WHEN estado='pagado' THEN total END)       -- sin ELSE = NULL = no suma ✅
        AS cobrado,
    AVG(CASE WHEN vip=1 THEN total END)                 AS ticket_vip
FROM dbo.Pedidos;

-- PIVOT nativo: filas → columnas:
SELECT anio, [ES], [MX], [AR]
FROM (
    SELECT YEAR(fecha) AS anio, pais, total FROM Ventas
) fuente
PIVOT (
    SUM(total) FOR pais IN ([ES], [MX], [AR])
) p;

-- La versión CASE suele ser más flexible/mantenible:
SELECT YEAR(fecha) AS anio,
       SUM(CASE WHEN pais='ES' THEN total END) AS [ES],
       SUM(CASE WHEN pais='MX' THEN total END) AS [MX],
       SUM(CASE WHEN pais='AR' THEN total END) AS [AR]
FROM dbo.Ventas
GROUP BY YEAR(fecha);

PIVOT requiere listar columnas estáticas ([ES],[MX]...): dinámico real necesita SQL dinámico. Por eso en reporting moderno gana el patrón CASE — legible, versionable y parametrizable desde la app.

Ejercicios prácticos

  1. Dashboard KPI: una sola query con total/pagados/cancelados/cobrado/ticket-vip vía SUM(CASE) sobre tus pedidos.
  2. Reporte jerárquico: ROLLUP año→mes con GROUPING() etiquetando subtotales "SUBTOTAL" y "GRAN TOTAL" en la salida.
  3. Ranking con contexto: window functions para salario vs media de departamento + rank global y departamental simultáneos.
  4. Matriz país×año: misma matriz con PIVOT nativo y con SUM(CASE); compara legibilidad y flexibilidad.
  5. Comparador de eficiencia: reporte con subtotales via 3 UNIONs vs GROUPING SETS; SET STATISTICS IO ON y documenta lecturas.
