Login vs Usuario: dos puertas distintas

El error conceptual más común: confundir el login (identidad a nivel SERVIDOR) con el usuario (su representación DENTRO de una base). Son dos cuentas mapeadas:

-- 1. LOGIN a nivel servidor (puede conectar):
CREATE LOGIN app_web WITH PASSWORD = 'ClaveFuerte123!',
    CHECK_POLICY = ON;                    -- respeta política de Windows

-- Autenticación Windows (recomendada en dominios):
CREATE LOGIN [DOMINIO\jlopez] FROM WINDOWS;

-- 2. USUARIO en cada base donde necesita trabajar:
USE Tienda;
CREATE USER app_web FOR LOGIN app_web;

-- Mapeo directo al crear:
USE Tienda;
CREATE USER jlopez FOR LOGIN [DOMINIO\jlopez];

-- Ver quién es quién:
SELECT SUSER_SNAME() AS login_actual, USER_NAME() AS usuario_en_esta_base;
NivelObjetoConcede
ServidorLogin + roles de servidorConectar, admin (sysadmin, dbcreator...)
Base de datosUsuario + roles de BDLeer/escribir/definir objetos concretos

Usuarios contenidos (contained users): CREATE USER app_web WITH PASSWORD='...' — viven SOLO dentro de la base sin login de servidor. Perfectas para Azure SQL y para mover bases entre servidores sin re-mapear SIDs.

Roles: fijos y personalizados

-- Roles FIJOS de base de datos (no se pueden crear más así):
ALTER ROLE db_datareader ADD MEMBER app_web;      -- leer TODO
ALTER ROLE db_datawriter ADD MEMBER app_web;      -- escribir TODO
-- db_ddladmin: crear/modificar objetos
-- db_accessadmin: gestionar usuarios
-- db_owner: dios de la base ⚠️ mínimo personal posible

-- Roles FIJOS DE SERVIDOR (para logins):
ALTER SERVER ROLE sysadmin ADD MEMBER [DOMINIO\dba_jefe];   -- máximo poder
-- dbcreator, securityadmin, processadmin... por necesidad real

-- ✅ ROL PERSONALIZADO: permisos exactos, sin sobrantes:
CREATE ROLE rol_ventas;
GRANT SELECT ON SCHEMA::ventas TO rol_ventas;
GRANT EXECUTE ON OBJECT::dbo.sp_RegistrarPedido TO rol_ventas;
ALTER ROLE rol_ventas ADD MEMBER usuario_app1, usuario_app2;

Jerarquía recomendada de roles por perfil

PerfilRolPuede…

Mínimo privilegio como religión: la app web NUNCA con db_owner ni datareader global. Un rol por caso de uso con grants quirúrgicos. Cuando un ataque inyecta SQL, hereda EXACTAMENTE los permisos del login de conexión — diseña asumiendo que ese día llegará.

GRANT / DENY / REVOKE

-- GRANT: conceder:
GRANT SELECT ON dbo.Clientes TO rol_analistas;
GRANT SELECT, INSERT, UPDATE ON SCHEMA::ventas TO rol_operaciones;   -- sin DELETE
GRANT EXECUTE ON dbo.sp_CalcularNomina TO rol_rrhh;
GRANT SELECT ON dbo.Clientes (nombre, ciudad) TO rol_marketing;      -- por columnas!

-- DENY: prohibición que GANA siempre (override de cualquier GRANT):
DENY DELETE ON dbo.Facturas TO PUBLIC;         -- nadie borra facturas jamás
DENY UPDATE ON Facturas (numero_fiscal) TO rol_contabilidad;

-- REVOKE: quitar lo otorgado (vuelve a default):
REVOKE SELECT ON dbo.Clientes FROM rol_temporal;
SentenciaEfecto acumulativoCaso de uso estrella
GRANTSuma permiso (+)Dar acceso funcional
DENYBloquea aunque haya GRANTs heredados (−∞)Excepciones duras por columna/tabla sensible
REVOKENeutral (0): elimina grant/deny propioRetirar accesos limpiamente

Los permisos se ACUMULAN entre roles: usuario en rol A (SELECT) + rol B (INSERT) tiene ambos. DENY es el único veto absoluto — pero úsalo con pinzas: un DENY heredado olvidado produce errores "permission denied" imposibles de rastrear años después.

Buenas prácticas de seguridad

  1. Sa deshabilitado o renombrado: contraseña kilométrica si existe; nunca usada por apps.
  2. Windows Auth primero: dominio gestiona claves y expiración; SQL Auth solo cuando no hay alternativa.
  3. Un login por aplicación/servicio: trazabilidad total de qué sistema hizo qué.
  4. Roles custom con grants mínimos: nada de db_owner por comodidad.
  5. Auditoría activa: SQL Server Audit o triggers DDL para cambios de seguridad.
  6. Encriptación en capas: TDE para reposo (archivo), Always Encrypted para columnas ultra-sensibles (tarjetas, salud).
  7. Dynamic Data Masking: teléfonos/tarjetas enmascarados automáticamente para no-privilegiados.
-- Revisión periódica de quién puede qué:
EXEC sp_helpsrvrolemember 'sysadmin';           -- ¿quién es dios?
EXEC sp_helprolemember 'db_owner';              -- ¿y dueños de bases?
SELECT * FROM sys.database_principals WHERE type = 'S';  -- usuarios SQL puros
SELECT * FROM sys.sql_logins WHERE is_policy_checked = 0; -- logins SIN política de clave ⚠️

La auditoría responde "¿quién tocó qué y cuándo?" DESPUÉS del incidente; los roles correctos lo PREVIENEN. Ambos son obligatorios: prevención sin auditoría es fe ciega; auditoría sin prevención es cámara filmando el robo.

Ejercicios prácticos

  1. Setup completo: crea login app_web → usuario en Tienda → rol custom con DML+EXEC solo sobre ventas; verifica desde otra sesión SSMS conectada como app_web.
  2. Laboratorio GRANT columnas: concede SELECT de Clientes solo (nombre,email); intenta leer salario como ese usuario y documenta el error.
  3. Prueba del DENY absoluto: usuario con GRANT DELETE vía rol + DENY DELETE directo; intenta borrar; explica por qué gana el DENY.
  4. Auditor de tu instancia: ejecuta los 4 checks de buenas prácticas; lista hallazgos y corrige los corregibles.
  5. Simulacro de intrusión: asumiendo SQL injection exitosa bajo tu login de app, enumera QUÉ podría hacer el atacante con tus grants actuales — luego reduce permisos y repite el análisis.
