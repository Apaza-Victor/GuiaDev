INNER JOIN

Devuelve únicamente filas con pareja en ambas tablas. Sintaxis idéntica a otros motores, con el matiz T-SQL de calificar esquema cuando importa:

SELECT c.nombre, p.fecha, p.total
FROM dbo.Clientes AS c
INNER JOIN dbo.Pedidos AS p ON p.cliente_id = c.id;

-- Con filtro y orden:
SELECT c.nombre, COUNT(p.pedido_id) AS pedidos, SUM(p.total) AS gastado
FROM dbo.Clientes AS c
JOIN dbo.Pedidos AS p ON p.cliente_id = c.id
WHERE p.fecha >= '2026-01-01'
GROUP BY c.id, c.nombre
HAVING SUM(p.total) > 1000
ORDER BY gastado DESC;

INNER es la keyword opcional: JOIN a secas = INNER JOIN. Pero escribirla explícita documenta intención frente al LEFT que sí exige su palabra. En equipos, convención: siempre INNER JOIN escrito completo.

LEFT / RIGHT / FULL OUTER: los tres sabores

SQL Server tiene algo que MySQL no ofrece nativamente: FULL OUTER JOIN — la unión completa de ambos lados con NULLs donde falte pareja:

-- LEFT: todos los clientes aunque no compren:
SELECT c.nombre, p.total
FROM Clientes c
LEFT JOIN Pedidos p ON p.cliente_id = c.id;

-- Anti-join: quiénes NO tienen pedido:
SELECT c.nombre
FROM Clientes c
LEFT JOIN Pedidos p ON p.cliente_id = c.id
WHERE p.pedido_id IS NULL;

-- RIGHT: espejo del LEFT (evítalo por legibilidad):
SELECT c.nombre, p.total
FROM Pedidos p
RIGHT JOIN Clientes c ON c.id = p.cliente_id;
-- == FROM Clientes c LEFT JOIN Pedidos p ...

-- ✨ FULL OUTER JOIN (exclusivo aquí): TODO de ambos lados:
SELECT ISNULL(c.email, r.email) AS email,
       CASE WHEN c.email IS NULL THEN 'solo_repositorio' 
            WHEN r.email IS NULL THEN 'solo_clientes'
            ELSE 'en_ambos' END AS origen
FROM Clientes c
FULL OUTER JOIN Repositorio_Leads r ON r.email = c.email;

Matriz de resultados según parejas faltantes

TipoSolo izquierda sin matchSolo derecha sin matchCoincidentes
INNER❌ fuera❌ fuera✅
LEFT OUTER✅ con NULLs derecha❌ fuera✅
RIGHT OUTER❌ fuera✅ con NULLs izquierda✅
FULL OUTER✅ con NULLs derecha✅ con NULLs izquierda✅

El WHERE sobre columnas del lado derecho anula tu LEFT (los NULL fallan cualquier comparación normal). Para filtrar emparejamientos conservando solitarios: mueve la condición al ON. FULL OUTER + filtros WHERE es aún más traicionero: piensa en ISNULL/COALESCE para las claves antes de filtrar.

CROSS JOIN y self join

-- CROSS JOIN explícito: combinaciones totales:
SELECT t.talla, c.color
FROM Tallas t CROSS JOIN Colores c;      -- 5×8 = 40 variantes

-- Self join jerárquico:
SELECT e.nombre AS empleado,
       j.nombre AS jefe,
       COALESCE(j.nombre, N'— CEO —') AS etiqueta_jefe
FROM Empleados e
LEFT JOIN Empleados j ON j.id = e.jefe_id;

-- Comparación dentro de misma tabla (parejas):
SELECT a.nombre, b.nombre
FROM Empleados a
JOIN Empleados b ON b.departamento_id = a.departamento_id
                 AND b.id > a.id        -- evita espejos A-B y B-A
WHERE a.departamento_id = 3;

El truco b.id > a.id en self joins genera cada par UNA sola vez (orden canónico). Esencial en consultas de parejas: comparaciones salariales, co-autores, rutas simétricas.

Encadenar más de dos tablas

-- Ticket íntegro cruzando 5 tablas:
SELECT
    c.nombre                    AS cliente,
    FORMAT(p.fecha, 'dd/MM/yyyy') AS fecha,
    pr.nombre                   AS producto,
    d.cantidad,
    d.precio_unitario           AS precio,
    d.cantidad * d.precio_unitario AS subtotal
FROM dbo.Pedidos   AS p
JOIN dbo.Detalle   AS d  ON d.pedido_id   = p.pedido_id
JOIN dbo.Productos AS pr ON pr.producto_id = d.producto_id
JOIN dbo.Clientes  AS c  ON c.cliente_id  = p.cliente_id
LEFT JOIN dbo.Categorias AS cat ON cat.categoria_id = pr.categoria_id
WHERE p.pedido_id = @id
ORDER BY subtotal DESC;

-- El mismo patrón agregado por cliente:
SELECT c.nombre, SUM(d.cantidad * d.precio_unitario) AS total_gastado
FROM dbo.Clientes c
JOIN dbo.Pedidos  p ON p.cliente_id = c.cliente_id
JOIN dbo.Detalle  d ON d.pedido_id  = p.pedido_id
GROUP BY c.cliente_id, c.nombre
ORDER BY total_gastado DESC;

Fan-out silencioso: unir pedidos→detalle→facturas donde ambas hijas multiplican filas infla SUMs al doble/triple. Solución profesional: pre-agregar una relación en subconsulta/CTE ANTES del join final.
