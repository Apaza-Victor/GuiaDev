    ROLLBACK;

NOLOCK (=READ UNCOMMITTED) es el "optimizador" favorito de los desesperados: gana velocidad leyendo datos que quizá nunca existieron o están a medias. En reportes financieros, inventarios o pagos es una bomba silenciosa. Si el lock real duele, habilita READ_COMMITTED_SNAPSHOT en la base — consistencia SIN bloqueo lector.

TRY/CATCH con ERROR_* functions

BEGIN TRY
    BEGIN TRAN;

    INSERT INTO Facturas (...) VALUES (...);
    UPDATE Stock SET cantidad -= @n WHERE producto_id = @id;

    COMMIT;
    PRINT 'Operación completada';
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK;

    SELECT
        ERROR_NUMBER()    AS numero,      -- 2627 = dup key, 547 = FK...
        ERROR_SEVERITY()  AS severidad,
        ERROR_STATE()     AS estado,
        ERROR_PROCEDURE() AS procedimiento,
        ERROR_LINE()      AS linea,
        ERROR_MESSAGE()   AS mensaje;

    THROW;                                -- re-lanzar al llamador (2012+)
END CATCH;
Herramienta de errorÉpocaCuándo usarla
THROW n, 'msg', estado2012+Default moderno ✅ respeta severidad, re-lanza limpio
RAISERRORLegacySolo por formato %s/%d dinámico heredado
ERROR_*() functions2005+Dentro de CATCH para log/auditoría del error

Rango 50000+ reservado para errores de usuario con THROW. Numéralos semánticamente (50001=stock insuficiente, 50002=saldo...) y centralízalos en documentación compartida entre DBA y app.

XACT_ABORT, @@TRANCOUNT y deadlocks

-- El patrón transaccional BULLETPROOF completo:
SET XACT_ABORT ON;              -- cualquier error ⇒ rollback TOTAL automático
BEGIN TRY
    BEGIN TRAN;

    /* operaciones... */

    COMMIT TRAN;
END TRY
BEGIN CATCH
    IF XACT_STATE() = -1        -- transacción "doomed": SOLO rollback posible
        ROLLBACK TRAN;
    ELSE IF XACT_STATE() = 1    -- aún commiteable (errores no abortivos)
        ROLLBACK TRAN;          -- decidimos revertir igualmente

    -- Log persistente del error (fuera de la tran ya muerta):
    INSERT INTO ErrorLog (numero, mensaje, procedimiento, cuando)
    VALUES (ERROR_NUMBER(), ERROR_MESSAGE(), ERROR_PROCEDURE(), SYSDATETIME());

    THROW;
END CATCH

-- Deadlock retry pattern (los deadlocks SON normales):
DECLARE @intentos INT = 3;
WHILE @intentos > 0
BEGIN
    BEGIN TRY
        EXEC sp_Transferencia ...;   -- tu lógica completa
        BREAK;                        -- éxito → salir
    END TRY
    BEGIN CATCH
        IF ERROR_NUMBER() IN (1205, 1222)   -- deadlock / lock timeout
        BEGIN
            SET @intentos -= 1;
            WAITFOR DELAY '00:00:00.200';    -- backoff corto
            CONTINUE;
        END
        THROW;                                -- otro error: propagar
    END CATCH
END

Los tres estados de XACT_STATE()

ValorSignificadoAcción válida
1Activa y commiteableCOMMIT o ROLLBACK a elección
-1Doomed (con XACT_ABORT tras error)SOLO ROLLBACK — COMMIT lanza error
0No hay transacción activaNada que gestionar

Deadlock víctima vs proceso: SQL Server ELIGE una sesión y la mata con error 1205. No es bug tuyo: es el motor resolviendo un ciclo de locks. La respuesta correcta NO es NOLOCK everywhere sino: transacciones cortas, mismo orden de acceso a tablas en todo el código, índices adecuados (menos locks tomados) y retry automático.

Ejercicios prácticos

  1. Transferencia atómica: implementar sp_TransferirSaldo bulletproof (XACT_ABORT+TRY/CATCH+THROW); forzar fallo intermedio y verificar atomicidad total.
  2. Laboratorio @@ROWCOUNT: update esperando N filas exactas; rompe expectativa deliberadamente y valida el THROW defensivo.
  3. Generador de deadlocks: dos sesiones actualizando mismas cuentas en orden inverso; provoca 1205, luego reordena acceso y verifica desaparición.
  4. ErrorLog profesional: CATCH que persista ERROR_* completo a tabla log antes de re-lanzar; consulta historial posterior.
  5. Retry engine: envuelve transferencia con patrón de 3 reintentos + backoff; simula deadlocks recurrentes y mide tasa de éxito final.
