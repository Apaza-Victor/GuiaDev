Vistas: simples, indexadas y particionadas

CREATE VIEW dbo.vw_PedidosCompletos
WITH SCHEMABINDING            -- ancla a estructura real (requerido p/ indexar)
AS
SELECT p.pedido_id, c.nombre AS cliente, p.fecha, p.total
FROM dbo.Pedidos p
JOIN dbo.Clientes c ON c.cliente_id = p.cliente_id;
GO

SELECT * FROM vw_PedidosCompletos WHERE total > 500;

ALTER VIEW vw_PedidosCompletos AS SELECT ...;   -- redefinir
DROP VIEW IF EXISTS vw_PedidosCompletos;
EXEC sp_helptext 'vw_PedidosCompletos';          -- ver su T-SQL

-- Vista INDEXADA = "materialized view" de SQL Server:
CREATE VIEW dbo.vw_VentasPorMes
WITH SCHEMABINDING AS
SELECT YEAR(fecha) AS anio, MONTH(fecha) AS mes,
       COUNT_BIG(*) AS pedidos, SUM(total) AS facturado
FROM dbo.Pedidos GROUP BY YEAR(fecha), MONTH(fecha);
GO
CREATE UNIQUE CLUSTERED INDEX IX_vVentas ON vw_VentasPorMes(anio, mes);
-- ahora SUMs mensuales se LEEN, no se calculan:

Una vista indexada acelera lecturas pero grava cada INSERT/UPDATE/DELETE de la base con mantenimiento extra. Resérvala para agregados consultados miles de veces al día, no como decoración.

Funciones escalares (UDF)

CREATE FUNCTION dbo.fn_CalcularIVA(@precio DECIMAL(10,2), @tasa DECIMAL(5,4))
RETURNS DECIMAL(10,2)
WITH SCHEMABINDING                 -- permite optimizaciones + inline
AS
BEGIN
    RETURN ROUND(@precio * @tasa, 2);
END;
GO

SELECT nombre, precio,
       dbo.fn_CalcularIVA(precio, 0.21) AS iva,
       precio + dbo.fn_CalcularIVA(precio, 0.21) AS pvp
FROM Productos;

-- ✨ SCALAR UDF INLINING (2019+): el optimizador la expande inline
-- automáticamente si cumple requisitos → coste casi nulo:
CREATE OR ALTER FUNCTION ... -- patrón moderno idempotente

El problema histórico y su solución

SituaciónPre-20192019+ con inlining
UDF escalar sobre 100k filas100k ejecuciones RBAR 🐌 desastreSe expande inline → velocidad de expresión normal ⚡
UDF en WHERE/JOINMata paralelismo y estimacionesInlinable: plan decente posible
UDF no-inlinable (multi-statement)Igual de lentoIgual — refactorizar o evitar

Regla clásica que sigue vigente en versiones viejas o UDFs complejas: una función escalar usada por fila convierte queries de milisegundos en minutos. Antes de meter un fn_() en producción caliente, mide. Si el plan muestra "Compute Scalar" dominante, inlinea manualmente la expresión.

Funciones de tabla: iTVF vs multi-statement

-- ✅ INLINE TVF (iTVF): UN solo RETURN con SELECT parametrizado.
-- Es "una vista con parámetros": el optimizador LA EXPANDE:
CREATE FUNCTION dbo.fn_PedidosCliente(@cliente_id INT)
RETURNS TABLE
WITH SCHEMABINDING
AS RETURN
(
    SELECT pedido_id, fecha, total
    FROM dbo.Pedidos
    WHERE cliente_id = @cliente_id
      AND estado <> 'cancelado'
);
GO

-- Se usa como tabla real, incluso en JOINs:
SELECT c.nombre, p.pedido_id, p.total
FROM Clientes c
CROSS APPLY dbo.fn_PedidosCliente(c.cliente_id) AS p   -- APPLY = JOIN con función
WHERE p.total > 100;

-- ❌ MULTI-STATEMENT TVF: declara tabla, llena fila a fila:
CREATE FUNCTION dbo.fn_ReporteLento(@mes INT)
RETURNS @resultado TABLE (dia INT, total DECIMAL(10,2))
AS
BEGIN
    INSERT INTO @resultado SELECT DAY(fecha), SUM(total) FROM Pedidos GROUP BY DAY(fecha);
    RETURN;
END;
-- Cardinalidad inventada=1, sin estadísticas: planes pésimos en joins ⚠️
CriterioiTVF ✅MSTVF ⚠️
Estructura internaUn SELECTBloques + variable tabla
OptimizaciónExpandida inline, plan realCaja negra, cardinalidad fija
Rendimiento en joins grandesComparable a vista/consultaColapsa
Lógica procedural (loops)No soportaSí (única ventaja)

CROSS APPLY es el compañero natural de las iTVFs: aplica la función POR CADA FILA del exterior manteniendo plan óptimo — la forma correcta de "join contra cálculo parametrizado". OUTER APPLY conserva filas sin match (como LEFT).
