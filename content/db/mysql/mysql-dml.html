INSERT: formas y trampas

El DML (Data Manipulation Language) mueve datos. INSERT tiene cuatro variantes que cubren del prototipo rápido a la carga masiva profesional:

-- 1. Columnas explícitas (LA forma correcta):
INSERT INTO clientes (nombre, email, ciudad)
VALUES ('Ana García', 'ana@mail.com', 'Madrid');

-- 2. Múltiples filas de golpe (mucho más rápido que N inserts):
INSERT INTO clientes (nombre, email, ciudad) VALUES
    ('Luis Pérez', 'luis@mail.com', 'Barcelona'),
    ('Marta Ruiz', 'marta@mail.com', 'Sevilla'),
    ('Carlos López', 'carlos@mail.com', 'Valencia');

-- 3. Omitir columnas → toman DEFAULT/NULL:
INSERT INTO clientes (nombre) VALUES ('Sin datos aún');

-- 4. Columnas posicionales frágiles (evita en producción):
INSERT INTO clientes VALUES (NULL, 'Test', 't@x.com', null);

Conflictos de UNIQUE: ON DUPLICATE KEY UPDATE

-- Upsert: insertar o actualizar si el email ya existe:
INSERT INTO clientes (email, nombre, ciudad)
VALUES ('ana@mail.com', 'Ana García M.', 'Toledo')
ON DUPLICATE KEY UPDATE
    nombre = VALUES(nombre),
    ciudad = VALUES(ciudad);

-- Ignorar duplicados silenciosamente (usar con criterio):
INSERT IGNORE INTO visitas (ip, fecha) VALUES ('1.2.3.4', NOW());

-- Reemplazo destructivo total (¡borra y reinserta! nuevo id):
REPLACE INTO sesiones (id, usuario_id) VALUES (7, 42);
EstrategiaAl chocar UNIQUEUso
INSERT puroError 1062 detiene todoCuando duplicado = bug real
INSERT IGNORESalta la fila conflictivaDeduplicación tolerante
ON DUPLICATE KEY UPDATEFusiona: actualiza camposSyncs, contadores, upsert
REPLACEBORRA vieja + inserta nuevaRaro: rompe FKs hacia la fila vieja ⚠️

REPLACE ejecuta un DELETE interno: cualquier FK con ON DELETE RESTRICT hacia esa fila fallará, y los CASCADE borrarán hijos. Si buscas "actualizar si existe", ON DUPLICATE KEY UPDATE es casi siempre la respuesta correcta.

UPDATE: cambiar con seguridad

-- Básico con WHERE (SIEMPRE WHERE salvo intención total):
UPDATE clientes SET ciudad = 'Bilbao' WHERE id = 5;

-- Varias columnas + expresiones:
UPDATE productos
SET precio = precio * 1.05,
    actualizado_en = NOW()
WHERE categoria_id = 3;

-- UPDATE con JOIN (cálculos cruzados):
UPDATE pedidos p
JOIN clientes c ON c.id = p.cliente_id
SET p.total = p.total * 0.95          -- 5% descuento VIP
WHERE c.vip = 1;

-- LIMIT como freno de emergencia:
UPDATE logs SET procesado = 1 WHERE procesado = 0 LIMIT 1000;

El ritual anti-desastre antes de CUALQUIER UPDATE serio: 1) ejecuta primero el SELECT con el MISMO WHERE; 2) revisa cuántas filas tocaría; 3) recién entonces cambia SELECT por UPDATE. En producción añade transacción explícita para poder ROLLBACK si el affected-rows no coincide con lo esperado.

START TRANSACTION;
UPDATE cuentas SET saldo = saldo - 100 WHERE id = 1;
-- ¿Rows matched: 1? Bien. COMMIT. ¿0 o 5000? ROLLBACK inmediato.
COMMIT;

DELETE y borrado seguro

DELETE FROM sesiones WHERE expirada = 1;

-- DELETE con JOIN (borrar por relación):
DELETE p FROM pedidos p
JOIN clientes c ON c.id = p.cliente_id
WHERE c.bloqueado = 1;

-- LIMIT en borrados masivos por lotes (no bloquea eternamente):
DELETE FROM logs_antiguos WHERE creado < '2024-01-01' LIMIT 10000;
-- repetir hasta affected rows = 0

Entidades de negocio (usuarios, facturas) casi siempre merecen soft delete: deleted_at DATETIME NULL. Los logs y datos derivados se borran físicos por lotes nocturnos.

INSERT ... SELECT y carga masiva

-- Copiar entre tablas:
INSERT INTO archivo_pedidos_2023
SELECT * FROM pedidos WHERE YEAR(fecha) = 2023;

-- Transformar durante la copia:
INSERT INTO reportes_mensuales (mes, total_ventas)
SELECT DATE_FORMAT(fecha, '%Y-%m'), SUM(total)
FROM ventas
GROUP BY DATE_FORMAT(fecha, '%Y-%m');

-- Carga desde CSV (servidor local):
LOAD DATA INFILE '/var/lib/mysql-files/clientes.csv'
INTO TABLE clientes_staging
FIELDS TERMINATED BY ',' ENCLOSED BY '"'
LINES TERMINATED BY '\n'
IGNORE 1 LINES                       -- saltar cabecera
(nombre, email, ciudad);

LOAD DATA requiere secure_file_priv configurado y archivo accesible por el SERVIDOR MySQL, no tu cliente. Para cargas desde app moderna, batch inserts de 500-5000 filas por statement son el sweet spot universal.

Ejercicios prácticos

  1. Pobla la tienda: inserta 10 clientes, 15 productos, 20 pedidos con detalles usando multi-row inserts; verifica conteos.
  2. Upsert real: simula sync diario: mismo INSERT...ON DUPLICATE dos veces cambiando ciudad; verifica fusión sin duplicados.
  3. UPDATE seguro ritualizado: subida de precios 8% a una categoría — SELECT previo, transacción, verificación affected rows, commit/rollback documentado.
  4. Purga por lotes: genera 200k filas de log; borra en batches de 10k midiendo tiempo por lote; compara con intento de DELETE único.
  5. Archivado anual: INSERT INTO historico SELECT de pedidos antiguos + DELETE posterior dentro de UNA transacción; valida conteos cuadrando.
