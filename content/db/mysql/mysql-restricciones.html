PRIMARY KEY y AUTO_INCREMENT

La clave primaria identifica cada fila de forma ÚNICA y NO nula. MySQL crea automáticamente un índice agrupado sobre ella (en InnoDB, la tabla física se ordena por la PK), lo que la convierte en el camino más rápido posible hacia una fila.

CREATE TABLE clientes (
    id       INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    dni      CHAR(9) NOT NULL UNIQUE      -- identidad natural separada
);

-- PK compuesta (varias columnas juntas):
CREATE TABLE inscripciones (
    alumno_id   INT UNSIGNED NOT NULL,
    curso_id    INT UNSIGNED NOT NULL,
    nota        DECIMAL(4,2),
    PRIMARY KEY (alumno_id, curso_id)     -- el PAR debe ser único
);

AUTO_INCREMENT: IDs generados

INSERT INTO clientes (dni) VALUES ('12345678A');
SELECT LAST_INSERT_ID();          -- id generado para TU conexión

-- Ver el siguiente valor:
SHOW TABLE STATUS LIKE 'clientes'\G
-- o en 8.0:
SELECT AUTO_INCREMENT FROM information_schema.TABLES
WHERE TABLE_NAME = 'clientes';

-- Reiniciar (peligroso si hay filas):
ALTER TABLE clientes AUTO_INCREMENT = 1000;
CriterioPK auto-incrementPK natural (DNI, email)
EstabilidadNunca cambia ✅Puede cambiar en la vida real
Tamaño índiceCompacto (4-8 bytes)VARCHAR pesa en cada FK hija
Joins/FKsBaratosCostosos
Sensibilidad negocioNinguna ✅DNI/email expuestos en URLs

Regla del diseño profesional: PK sintética auto_increment SIEMPRE + UNIQUE constraint sobre la clave natural (dni). Obtienes velocidad e integridad a la vez.

CREATE TABLE pedidos (
    pedido_id   INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    cliente_id  INT UNSIGNED NOT NULL,
    fecha       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    total       DECIMAL(10,2) NOT NULL DEFAULT 0,

    CONSTRAINT fk_pedido_cliente
        FOREIGN KEY (cliente_id) REFERENCES clientes(id)
        ON DELETE RESTRICT          -- no borrar cliente con pedidos
        ON UPDATE CASCADE           -- si cambia id, arrastrar hijos
);

-- Probar la protección:
INSERT INTO pedidos (cliente_id, total) VALUES (99999, 100);
-- ERROR 1452: Cannot add or update a child row (FK constraint fails)

-- Detalle SÍ cascadea (muere con su pedido), cliente NO:
CREATE TABLE detalle_pedido (
    pedido_id    INT UNSIGNED NOT NULL,
    producto_id  INT UNSIGNED NOT NULL,
    cantidad     SMALLINT UNSIGNED NOT NULL CHECK (cantidad > 0),
    precio_unit  DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (pedido_id, producto_id),
    CONSTRAINT fk_det_pedido FOREIGN KEY (pedido_id)
        REFERENCES pedidos(pedido_id) ON DELETE CASCADE,
    CONSTRAINT fk_det_producto FOREIGN KEY (producto_id)
        REFERENCES productos(id) ON DELETE RESTRICT
);

-- Inspeccionar FKs existentes:
SELECT CONSTRAINT_NAME, TABLE_NAME, REFERENCED_TABLE_NAME
FROM information_schema.KEY_COLUMN_USAGE
WHERE REFERENCED_TABLE_SCHEMA = 'tienda';

CASCADE encadenado mal diseñado borra árboles enteros por accidente (borras un país → borra ciudades → borra usuarios...). Diseña el grafo de cascadas conscientemente: solo relaciones composición fuerte.

UNIQUE, NOT NULL, DEFAULT y CHECK

CREATE TABLE usuarios (
    id         INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    email      VARCHAR(254) NOT NULL UNIQUE,        -- sin duplicados
    telefono   VARCHAR(20) NULL UNIQUE,             -- varios NULL permitidos ✅
    apodo      VARCHAR(30) NOT NULL DEFAULT 'anon',
    edad       TINYINT UNSIGNED NULL,
    pais       CHAR(2) NOT NULL DEFAULT 'ES',

    -- CHECK (MySQL 8.0.16+ ¡realmente aplica!):
    CONSTRAINT chk_edad CHECK (edad IS NULL OR (edad BETWEEN 0 AND 130)),
    CONSTRAINT chk_email_formato CHECK (email LIKE '%_@_%._%')
);

-- UNIQUE compuesto: combinación única, valores individuales repetibles:
CREATE TABLE favoritos (
    usuario_id   INT UNSIGNED NOT NULL,
    producto_id  INT UNSIGNED NOT NULL,
    UNIQUE KEY uq_fav (usuario_id, producto_id)
);
-- El mismo usuario puede favoritar productos distintos;
-- ningún producto dos veces para el mismo usuario.

Administrar restricciones con nombre

Todo constraint puede (y debe) llevar nombre explícito. Sin él, MySQL genera nombres automáticos crípticos que dificultan mantenimiento:

-- Ver TODOS los constraints de la base:
SELECT TABLE_NAME, CONSTRAINT_NAME, CONSTRAINT_TYPE
FROM information_schema.TABLE_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'tienda';

-- Añadir constraint después:
ALTER TABLE empleados
    ADD CONSTRAINT chk_salario_min CHECK (salario >= 1080.00);

-- Eliminar por NOMBRE (por eso nombrar importa):
ALTER TABLE empleados DROP CHECK chk_salario_min;
ALTER TABLE pedidos DROP FOREIGN KEY fk_pedido_cliente;
ALTER TABLE usuarios DROP INDEX email;

-- Desactivar chequeo FK temporalmente (cargas masivas):
SET FOREIGN_KEY_CHECKS = 0;
-- ... bulk load ...
SET FOREIGN_KEY_CHECKS = 1;

SET FOREIGN_KEY_CHECKS=0 deja la puerta abierta a huérfanos reales. Tras cargas masivas con esta bandera, VERIFICA integridad con LEFT JOIN buscando hijos sin padre antes de reactivar producción.

Ejercicios prácticos

  1. Modelo completo tienda: implementa las 4 tablas del diagrama ER con todos sus constraints nombrados; prueba cada error (1452, 1451, duplicate) deliberadamente.
  2. Laboratorio de acciones: tres tablas hijas con RESTRICT/CASCADE/SET NULL respectivamente; borra el mismo padre en cada una y documenta los tres comportamientos.
  3. PK compuesta real: modela matrículas (alumno+curso+periodo) con PK triple; intenta duplicar exacta y observa el rechazo.
  4. Bulk import seguro: carga CSV grande con FOREIGN_KEY_CHECKS=0; luego detecta huérfanos con LEFT JOIN ... WHERE padre IS NULL.
  5. Auditoría de constraints: consulta information_schema para listar todos los constraints de tu base; genera reporte legible con nombres faltantes (los automáticos).
