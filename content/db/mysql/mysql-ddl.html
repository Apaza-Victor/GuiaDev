Bases de datos: CREATE, ALTER, DROP

El DDL (Data Definition Language) estructura el esqueleto: bases, tablas, columnas. A diferencia del DML, sus sentencias suelen ser implícitamente commit: no hay rollback fácil tras un DROP — la precaución es tu única red.

-- Crear con charset explícito (buena práctica):
CREATE DATABASE tienda
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;

-- Evitar error si ya existe (scripts idempotentes):
CREATE DATABASE IF NOT EXISTS tienda;

-- Ver definición completa:
SHOW CREATE DATABASE tienda;

-- Modificar charset global de la base:
ALTER DATABASE tienda CHARACTER SET utf8mb4;

-- Eliminar (¡destructivo, sin confirmación!):
DROP DATABASE IF EXISTS tienda;

Los scripts de migración profesionales usan siempre IF NOT EXISTS / IF EXISTS para poder re-ejecutarse sin romper. Un script que falla a mitad porque "ya existe" detiene deployments enteros.

CREATE TABLE completo

CREATE TABLE categorias (
    id       INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    nombre   VARCHAR(60) NOT NULL UNIQUE,
    activa   TINYINT(1) NOT NULL DEFAULT 1
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE productos (
    id           INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    categoria_id INT UNSIGNED NULL,                 -- FK opcional
    sku          CHAR(12) NOT NULL,
    nombre       VARCHAR(120) NOT NULL,
    descripcion  TEXT NULL,
    precio       DECIMAL(10,2) NOT NULL,
    stock        INT UNSIGNED NOT NULL DEFAULT 0,
    creado_en    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    -- Constraints nombrados (fáciles de referenciar después):
    CONSTRAINT fk_prod_categoria
        FOREIGN KEY (categoria_id) REFERENCES categorias(id)
        ON DELETE SET NULL ON UPDATE CASCADE,
    CONSTRAINT chk_precio_positivo CHECK (precio >= 0),
    UNIQUE KEY uq_sku (sku),
    INDEX idx_categoria (categoria_id),
    INDEX idx_nombre (nombre)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

Copiar estructuras y datos

-- Clonar estructura EXACTA (sin índices ni FKs):
CREATE TABLE productos_backup LIKE productos;

-- Crear desde consulta (con datos, SIN constraints):
CREATE TABLE productos_caros AS
SELECT id, nombre, precio FROM productos WHERE precio > 1000;

-- Tabla temporal de sesión (desaparece al desconectar):
CREATE TEMPORARY TABLE tmp_calculos (
    valor DECIMAL(10,2)
);

CREATE TABLE ... AS SELECT NO copia índices, PKs ni FKs: produce tabla "plana". Para backups de estructura fiel usa LIKE; para snapshots completos usa mysqldump.

ALTER TABLE: evolucionar sin romper

-- Añadir columna:
ALTER TABLE productos
    ADD COLUMN peso_kg DECIMAL(6,3) NULL AFTER stock;

-- Añadir varias + default inteligente:
ALTER TABLE productos
    ADD COLUMN descuento_pct TINYINT UNSIGNED NOT NULL DEFAULT 0,
    ADD COLUMN actualizado_en DATETIME NULL ON UPDATE CURRENT_TIMESTAMP;

-- Modificar tipo (¡cuidado con pérdida si reduce!):
ALTER TABLE productos MODIFY nombre VARCHAR(200) NOT NULL;
ALTER TABLE productos CHANGE peso_kg peso DECIMAL(7,3);  -- rename + tipo

-- Eliminar columna (destructivo):
ALTER TABLE productos DROP COLUMN descripcion;

-- Índices y constraints post-creación:
ALTER TABLE productos ADD INDEX idx_precio (precio);
ALTER TABLE productos ADD UNIQUE KEY uq_sku (sku);
ALTER TABLE productos ADD FOREIGN KEY (categoria_id)
    REFERENCES categorias(id);
ALTER TABLE productos DROP INDEX idx_precio;

-- Renombrar tabla:
RENAME TABLE productos TO articulos;      -- o ALTER TABLE productos RENAME TO...

ALTER en producción: el elefante en la sala

Tipo de cambioBloquea tabla?Estrategia segura
Añadir columna NULL al finalInstantáneo (8.0 INSTANT)Directo
Modificar tipo VARCHAR→TEXTRebuild COMPLETO (lock largo)pt-online-schema-change / gh-ost
Añadir índice tabla grandeOnline DDL pero I/O intensoVentana baja o ALGORITHM=INPLACE monitoreado
DROP COLUMNRápido meta (8.0), espacio se recupera luegoPlanificar OPTIMIZE posterior

Un ALTER sobre tabla de 50 millones de filas puede bloquear writes durante HORAS según el motor/versión. En producción seria los cambios grandes corren con herramientas online (gh-ost, pt-osc) que clonan la tabla sincronizadamente. Nunca "pruebo en prod y ya veremos".

TRUNCATE vs DELETE vs DROP

SentenciaQué haceWHERE posible?Resetea AUTO_INCREMENTVelocidad
DELETE FROM tBorra filas (loggeadas una a una)SíNoLenta en tablas grandes
TRUNCATE TABLE tVacía TODO (drop+recreate interno)NoSí → reinicia en 1Instantánea
DROP TABLE tElimina tabla COMPLETA (estructura incluida)——Instantánea
 
TRUNCATE TABLE logs_acceso;     -- reset total rápido (dev/testing)
DROP TABLE IF EXISTS temporal_;  -- limpieza condicional de migraciones

TRUNCATE no dispara triggers ni respeta FKs que apunten a la tabla (fallará si hay hijas). Y no existe "UNDO": en autocommit ya es historia. Ante dudas en producción: DELETE transaccional o backup previo.

Ejercicios prácticos

  1. Base biblioteca: crea base con tablas autores/libros/editoriales bien relacionadas (FKs nombradas, checks, índices); documenta cada decisión.
  2. Evolución realista: añade columna ISBN único a libros, renombra una columna, agrega índice compuesto — todo vía ALTER encadenados.
  3. Snapshot seguro: LIKE para clonar estructura, INSERT INTO...SELECT para copiar datos, compara SHOW CREATE TABLE original vs clone.
  4. Truncate vs delete medido: inserta 100k filas rápidas (procedure o loop); mide tiempo de DELETE full vs TRUNCATE con profiling.
  5. Cazador del 1215: intenta crear FK hacia columna sin índice; lee el error; corrige indexando; documenta el proceso completo.
