Vistas (CREATE VIEW)

Una vista es una consulta guardada con nombre que se comporta como tabla virtual. Encapsula JOINs complejos, estandariza reportes y simplifica permisos — sin duplicar datos:

CREATE VIEW vista_pedidos_completos AS
SELECT
    p.pedido_id,
    c.nombre          AS cliente,
    c.email,
    p.fecha,
    COUNT(d.producto_id)  AS items,
    SUM(d.cantidad * d.precio_unit) AS total
FROM pedidos p
JOIN clientes c ON c.id = p.cliente_id
JOIN detalle d  ON d.pedido_id = p.pedido_id
GROUP BY p.pedido_id, c.nombre, c.email, p.fecha;

-- Se consulta como una tabla normal:
SELECT * FROM vista_pedidos_completos WHERE total > 500 ORDER BY total DESC;

-- Modificar y eliminar:
ALTER VIEW vista_pedidos_completos AS SELECT ...;
DROP VIEW IF EXISTS vista_antigua;

-- Ver su definición:
SHOW CREATE VIEW vista_pedidos_completos\G

Tipos de vistas por comportamiento

TipoINSERT/UPDATE posibles?Notas
Vista simple (1 tabla, sin agregados)Sí, con restriccionesSe actualiza la tabla base subyacente
Vista compleja (JOINs, GROUP BY)No (read-only)El caso del 95% real
WITH CHECK OPTIONInserts vía vista deben cumplir su WHEREEvita "insertar fuera de la vista"

Una vista NO guarda resultados: cada consulta la RE-EJECUTA desde cero. Una vista sobre 5 tablas gigantes usada en cada request es un problema de rendimiento heredable e invisible. Para resultados pesados pre-calculados existen las materialized views — que MySQL NO tiene nativamente; se simulan con tablas + eventos.

Procedimientos almacenados

Un procedimiento es un programa completo viviendo dentro del servidor: lógica multi-paso ejecutable con CALL. Reduce round-trips de red y encapsula operaciones transaccionales críticas:

DELIMITER $$

CREATE PROCEDURE registrar_pedido(
    IN  p_cliente_id INT UNSIGNED,
    IN  p_producto_id INT UNSIGNED,
    IN  p_cantidad SMALLINT UNSIGNED,
    OUT p_nuevo_pedido INT UNSIGNED
)
BEGIN
    DECLARE v_precio DECIMAL(10,2);
    DECLARE v_stock INT DEFAULT 0;

    START TRANSACTION;

    -- Bloquear fila producto y validar stock:
    SELECT precio, stock INTO v_precio, v_stock
    FROM productos WHERE id = p_producto_id FOR UPDATE;

    IF v_stock < p_cantidad THEN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Stock insuficiente';
    END IF;

    INSERT INTO pedidos (cliente_id, total)
    VALUES (p_cliente_id, v_precio * p_cantidad);
    SET p_nuevo_pedido = LAST_INSERT_ID();

    INSERT INTO detalle (pedido_id, producto_id, cantidad, precio_unit)
    VALUES (p_nuevo_pedido, p_producto_id, p_cantidad, v_precio);

    UPDATE productos SET stock = stock - p_cantidad WHERE id = p_producto_id;

    COMMIT;
END$$

DELIMITER ;

-- Ejecutar:
CALL registrar_pedido(5, 12, 3, @pedido);
SELECT @pedido AS nuevo_id;
PiezaRol
IN / OUT / INOUTParámetros entrada / salida / ambos

Los procedures brillan en operaciones transaccionales atómicas multi-tabla (como este pedido con stock). La contrapartida: versionado difícil, testing pobre y vendor lock-in. Regla moderna: lógica de negocio en app; procedures solo para hot paths transaccionales.

Funciones almacenadas

A diferencia del procedure, una función DEVUELVE UN VALOR y puede usarse dentro de queries como cualquier función nativa:

DELIMITER $$
CREATE FUNCTION calcular_iva(precio DECIMAL(10,2), tasa DECIMAL(4,2))
RETURNS DECIMAL(10,2)
READS SQL DATA                          -- determinismo declarado
BEGIN
    RETURN ROUND(precio * tasa, 2);
END$$

CREATE FUNCTION iniciales(nombre VARCHAR(80))
RETURNS VARCHAR(10)
DETERMINISTIC
BEGIN
    RETURN CONCAT(LEFT(nombre, 1), '.');
END$$
DELIMITER ;

-- Uso inline:
SELECT nombre, calcular_iva(precio, 0.21) AS iva,
       precio + calcular_iva(precio, 0.21) AS pvp
FROM productos;
CharacteristicSignifica
DETERMINISTICMismo input → mismo output siempre (permite cacheo/binlog STATEMENT)
NO SQLNo toca datos
READS SQL DATALee pero no escribe
MODIFIES SQL DATAEscribe datos

Una función llamada por cada FILA de una query grande (función escalar en SELECT sobre 100k filas) ejecuta 100k invocaciones interpretadas: rendimiento desastroso comparado con expresiones inline o joins calculados. Usa funciones escalares en filtros puntuales y reportes pequeños.

Triggers: reacciones automáticas

Un trigger se dispara SOLO ante INSERT/UPDATE/DELETE de una tabla concreta — antes o después de la operación. Útil para auditoría e invariantes cruzadas:

DELIMITER $$

-- Auditoría de cambios de precio:
CREATE TRIGGER trg_productos_audit
AFTER UPDATE ON productos
FOR EACH ROW
BEGIN
    IF OLD.precio <> NEW.precio THEN
        INSERT INTO historial_precios
            (producto_id, precio_anterior, precio_nuevo, cambiado_el)
        VALUES
            (NEW.id, OLD.precio, NEW.precio, NOW());
    END IF;
END$$

-- Mantener contador denormalizado consistente:
CREATE TRIGGER trg_detalle_ai
AFTER INSERT ON detalle
FOR EACH ROW
BEGIN
    UPDATE pedidos
    SET total = total + (NEW.cantidad * NEW.precio_unit)
    WHERE pedido_id = NEW.pedido_id;
END$$

DELIMITER ;

-- Ver triggers existentes:
SHOW TRIGGERS LIKE 'productos'\G
DROP TRIGGER IF EXISTS trg_productos_audit;
Momento/tipoCuándo disparaAcceso a filas
BEFORE INSERT/UPDATEAntes de escribir (puede MODIFICAR NEW)Validar/transformar valores entrantes
AFTER INSERT/UPDATE/DELETETras confirmar escrituraOLD.* y NEW.* solo lectura efectiva
OLD / NEW—OLD=valor previo, NEW=valor entrante (DELETE solo OLD, INSERT solo NEW)

Triggers invisibles = bugs invisibles: el dev que hace UPDATE directo no sabe que otro código corre detrás, multiplicando latencia silenciosamente. Documenta TODO trigger, evita cadenas trigger→tabla→trigger, y nunca lógica de negocio seria ahí dentro — auditoría sí, reglas complejas no.

Ejercicios prácticos

  1. Vista de reporting: crea vista resumen mensual de ventas (mes, pedidos, facturado, ticket medio); consúmela con filtros y ordenaciones.
  2. Procedure transaccional: implementa registrar_pedido COMPLETO del ejemplo; prueba caso feliz, stock insuficiente (SIGNAL), y verificación de atomicidad forzando fallo intermedio.
  3. Función de negocio: calcula_descuento(vip, total) con reglas por tramos; úsala en SELECT y compara performance contra CASE inline en tabla grande.
  4. Auditoría con triggers: tabla log_cambios genérica + BEFORE/AFTER UPDATE en empleados registrando quién/cuándo/qué cambió (JSON de diffs).
  5. Cazador de triggers ocultos: instrumenta tu tabla con trigger contador a otra tabla métrica; haz updates masivos y mide el coste extra del trigger con profiling.
