INNER JOIN: la intersección

Un JOIN combina filas de dos tablas según una condición. El INNER JOIN devuelve solo las filas que tienen pareja en AMBAS tablas — la intersección:

-- Sintaxis moderna (explícita):
SELECT c.nombre, p.fecha, p.total
FROM clientes c
INNER JOIN pedidos p ON p.cliente_id = c.id;

-- Equivalente antiguo implícito (evitar: mezcla filtros y joins):
SELECT c.nombre, p.fecha, p.total
FROM clientes c, pedidos p
WHERE p.cliente_id = c.id;

Siempre alias cortos de tabla (c, p). En consultas con 4-5 tablas los nombres completos convierten cada línea en un párrafo ilegible. Y califica TODAS las columnas ambiguas: id sin prefijo en join de 3 tablas es error garantizado.

LEFT/RIGHT JOIN: incluir sin pareja

LEFT JOIN conserva TODAS las filas de la tabla izquierda; donde no hay pareja en la derecha, rellena con NULL. Es EL join para preguntas del tipo "¿quiénes NO tienen...?":

-- Todos los clientes, con pedidos si existen:
SELECT c.nombre, COUNT(p.pedido_id) AS num_pedidos
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
GROUP BY c.id, c.nombre;

-- ANTI-JOIN: clientes SIN ningún pedido (el patrón estrella):
SELECT c.nombre
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id
WHERE p.pedido_id IS NULL;

-- RIGHT JOIN: espejo exacto — raramente necesario (reordena y usa LEFT):
SELECT c.nombre, p.total
FROM pedidos p
RIGHT JOIN clientes c ON c.id = p.cliente_id;
-- == mismo resultado que FROM clientes c LEFT JOIN pedidos p ...
Pregunta de negocioJoin correcto
"Pedidos con su cliente"INNER
"Clientes y sus pedidos, incluso quienes no han comprado"LEFT desde clientes
"¿Quiénes nunca han comprado?"LEFT + WHERE derecho IS NULL
"Todos los productos aunque nadie los haya vendido"LEFT desde productos

Un WHERE sobre columnas de la tabla DERECHA (ej: WHERE p.estado='pagado') CONVIERTE tu LEFT JOIN en INNER de facto: los NULL fallan el filtro y desaparecen. Si necesitas filtrar lo emparejado pero conservar los solitarios, mueve el filtro al ON.

-- ❌ pierde clientes sin pedidos pagados:
SELECT ... FROM clientes c LEFT JOIN pedidos p ON ...
WHERE p.estado = 'pagado';

-- ✅ conserva todos; solo filtra las parejas:
SELECT ... FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id AND p.estado = 'pagado';

CROSS JOIN y self join

-- CROSS JOIN: producto cartesiano (todas × todas):
SELECT t.talla, c.color
FROM tallas t CROSS JOIN colores c;      -- 6×4 = 24 combinaciones

-- Útil para matrices: precios por talla×color:
INSERT INTO matriz_precios (talla, color)
SELECT t.codigo, c.codigo FROM tallas t CROSS JOIN colores c;

-- SELF JOIN: tabla contra sí misma (jerarquías):
CREATE TABLE empleados (
    id INT UNSIGNED PRIMARY KEY,
    nombre VARCHAR(80),
    jefe_id INT UNSIGNED NULL,
    FOREIGN KEY (jefe_id) REFERENCES empleados(id)
);

SELECT e.nombre AS empleado, j.nombre AS jefe
FROM empleados e
LEFT JOIN empleados j ON j.id = e.jefe_id;   -- LEFT incluye al CEO (sin jefe)

El self join es la herramienta estándar para jerarquías almacenadas como lista de adyacencia: empleados-jefe, categorías-categoría padre, páginas-página madre. Para árboles profundos considera CTE recursiva (lección agregación avanzada / SQL moderno).

Joins encadenados: más de dos tablas

-- Ticket completo: pedido → cliente → detalle → producto → categoría:
SELECT
    c.nombre          AS cliente,
    p.fecha           AS fecha,
    pr.nombre         AS producto,
    cat.nombre        AS categoria,
    d.cantidad,
    d.precio_unit     AS precio,
    d.cantidad * d.precio_unit AS subtotal
FROM pedidos      p
JOIN clientes     c   ON c.id = p.cliente_id
JOIN detalle      d   ON d.pedido_id = p.pedido_id
JOIN productos    pr  ON pr.id = d.producto_id
LEFT JOIN categorias cat ON cat.id = pr.categoria_id
WHERE p.pedido_id = 1042
ORDER BY subtotal DESC;

-- Agregación sobre el encadenado:
SELECT c.nombre, SUM(d.cantidad * d.precio_unit) AS gastado_total
FROM clientes c
JOIN pedidos   p ON p.cliente_id = c.id
JOIN detalle   d ON d.pedido_id = p.pedido_id
GROUP BY c.id, c.nombre
HAVING gastado_total > 1000
ORDER BY gastado_total DESC;

Errores comunes

Error típicoSíntomaCorrecto
ON incompleto o condición olvidadaCROSS JOIN accidental: millones de filasSiempre ON explícito; EXPLAIN verifica
Fan-out duplicando filas (1:N tras 1:N)SUMs inflados absurdamenteAgregar por niveles o subconsultas derivadas
WHERE sobre tabla derecha en LEFT JOINSe convierte en INNER sin darte cuentaMover filtro al ON
Columna ambigua id"Column 'id' is ambiguous"Calificar siempre c.id, p.id...
Comparar con columna NULL del lado derechoParejas "desaparecen"Entender three-valued logic; IS NULL para anti-join
RIGHT JOIN innecesarios ilegiblesLógica invertida difícil de mantenerReescribir como LEFT reordenando FROM

Ejercicios prácticos

  1. Ticket completo: reconstruye el query de pedido→cliente→detalle→producto sobre tu base tienda; imprime ticket real formateado.
  2. Cazadores de huérfanos: tres anti-joins: productos sin ventas, clientes sin pedidos, categorías vacías.
  3. Laboratorio del WHERE-vs-ON: ejecuta ambas versiones del LEFT JOIN con filtro de estado; compara conteo de filas y explica diferencia.
  4. Jerarquía organizacional: con tabla empleados self-joined, lista empleado→jefe incluyendo CEO, y luego cuántos reportes directos tiene cada jefe.
  5. Cazador de fan-out: suma totales con join directo pedidos→detalle vs subconsulta pre-agregada; documenta la inflación observada y la corrección.
