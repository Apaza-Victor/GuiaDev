Conceptos clave: pipeline, stages y jobs

La arquitectura de GitLab CI se apoya en tres conceptos:

  • Job: una tarea concreta (instalar, testear, construir). Es la unidad mínima.
  • Stage: fase que agrupa jobs (build → test → deploy). Los jobs del mismo stage corren en paralelo.
  • Pipeline: la secuencia completa de stages que se ejecuta ante un push o MR.
Pipeline
├── stage: build   → [job: install]  [job: compile]
├── stage: test    → [job: unit]     [job: lint]
└── stage: deploy  → [job: staging]

Si cualquier job falla, los stages siguientes no se ejecutan: eso garantiza que nada roto avance hacia despliegue.

El archivo .gitlab-ci.yml

Toda la configuración vive en un archivo .gitlab-ci.yml en la raíz del repositorio. GitLab lo detecta automáticamente en cada push.

# .gitlab-ci.yml mínimo
stages:
  - build
  - test

instalar:
  stage: build
  image: node:20
  script:
    - npm ci

probar:
  stage: test
  image: node:20
  script:
    - npm ci
    - npm test

Cada job define al menos un stage y una lista de script. La clave image elige la imagen Docker donde corre el job.

Runners: compartidos y propios

Un runner es la máquina que ejecuta los jobs. Existen dos tipos:

  • Compartidos (shared): proporcionados por GitLab.com con minutos limitados según tu plan.
  • Específicos (self-hosted): los instalas tú; minutos ilimitados y datos dentro de tu red.
# Registrar un runner self-hosted en un contenedor
docker run --rm -it -v gitlab-runner-config:/etc/gitlab-runner \
  gitlab/gitlab-runner register

# Te pedirá:
#  - URL de GitLab        → https://gitlab.com/
#  - Token de registro    → Settings → CI/CD → Runners
#  - Executor             → docker
#  - Imagen por defecto   → docker:24

Pipeline de ejemplo completo

Pipeline Node.js típico con caché, artefactos y despliegue solo en main:

image: node:20

cache:
  paths:
    - .npm/

stages: [build, test, deploy]

build:
  stage: build
  script:
    - npm ci --cache .npm --prefer-offline
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 hour

test:
  stage: test
  script:
    - npm ci --cache .npm --prefer-offline
    - npm test

deploy-staging:
  stage: deploy
  script:
    - echo "Desplegando a staging..."
  environment: staging
  only:
    - main

Variables, caché y artefactos

  • Variables: define secretos en Settings → CI/CD → Variables (enmascaradas y protegidas) y úsalas como variables de entorno: $DB_PASSWORD.
  • Caché: persiste directorios entre pipelines para acelerar instalaciones (node_modules, .npm).
  • Artefactos: archivos que un job produce y los stages siguientes consumen, como la carpeta dist/.
variables:
  NODE_ENV: "production"

test:
  script:
    - echo "Usando $NODE_ENV"
  artifacts:
    reports:
      junit: resultados.xml   # reporte visible en la UI

Buenas prácticas

  • Mantén los pipelines rápidos: usa caché e imágenes pequeñas (alpine).
  • Falla rápido: ordena stages de lo barato a lo costoso (lint antes que tests E2E).
  • Nunca imprimas secretos en logs; usa variables protegidas.
  • Usa rules/only para ejecutar jobs solo cuando aplique (ramas, tags, cambios de rutas).
  • Versiona las imágenes base (node:20 mejor que node:latest) para builds reproducibles.
