Conceptos clave: pipeline, stages y jobs

La arquitectura de GitLab CI se apoya en tres conceptos:

  • Job: una tarea concreta (instalar, testear, construir). Es la unidad mínima.
  • Stage: fase que agrupa jobs (build → test → deploy). Los jobs del mismo stage corren en paralelo.
  • Pipeline: la secuencia completa de stages que se ejecuta ante un push o MR.
Pipeline
├── stage: build   → [job: install]  [job: compile]
├── stage: test    → [job: unit]     [job: lint]
└── stage: deploy  → [job: staging]

Si cualquier job falla, los stages siguientes no se ejecutan: eso garantiza que nada roto avance hacia despliegue.

Diferencia clave vs GitHub Actions: aquí el ORDEN viene de los stages (declarativo y global); en Actions viene de needs: entre jobs. El modelo de stages de GitLab hace pipelines "estándar" más simples — y los atípicos requieren needs: igual que Actions.

---

El archivo .gitlab-ci.yml

Toda la configuración vive en un archivo .gitlab-ci.yml en la raíz del repositorio. GitLab lo detecta automáticamente en cada push.

# .gitlab-ci.yml mínimo
stages:
  - build
  - test

instalar:
  stage: build
  image: node:20
  script:
    - npm ci

probar:
  stage: test
  image: node:20
  script:
    - npm ci
    - npm test

Cada job define al menos un stage y una lista de script. La clave image elige la imagen Docker donde corre el job.

Antes de pushear, valida tu YAML con gitlab-ci-local (local) o el linter integrado: Pipeline editor en la UI o curl --data "content=$(cat .gitlab-ci.yml)" "https://gitlab.com/api/v4/ci/lint". Un typo YAML descubierto en el runner cuesta minutos de cuota; descubierto local, cero.

Runners: compartidos y propios

Un runner es la máquina que ejecuta los jobs. Existen dos tipos:

  • Compartidos (shared): proporcionados por GitLab.com con minutos limitados según tu plan.
  • Específicos (self-hosted): los instalas tú; minutos ilimitados y datos dentro de tu red.
# Registrar un runner self-hosted en un contenedor
docker run --rm -it -v gitlab-runner-config:/etc/gitlab-runner \
  gitlab/gitlab-runner register

# Te pedirá:
#  - URL de GitLab        → https://gitlab.com/
#  - Token de registro    → Settings → CI/CD → Runners
#  - Executor             → docker
#  - Imagen por defecto   → docker:24

Un runner self-hosted registrado a nivel de INSTANCIA ejecuta jobs de cualquier proyecto que lo pida — incluidos PRs de terceros si la visibilidad lo permite. Para repos públicos, registra runners PROTEGIDOS (solo jobs de ramas protegidas) o asume riesgo de ejecución remota con tus secretos.

Pipeline de ejemplo completo

Pipeline Node.js típico con caché, artefactos y despliegue solo en main:

image: node:20

cache:
  paths:
    - .npm/

stages: [build, test, deploy]

build:
  stage: build
  script:
    - npm ci --cache .npm --prefer-offline
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 hour

test:
  stage: test
  script:
    - npm ci --cache .npm --prefer-offline
    - npm test

deploy-staging:
  stage: deploy
  script:
    - echo "Desplegando a staging..."
  environment: staging
  only:
    - main

only/except funciona pero está en modo mantenimiento: la sintaxis moderna es rules: — más expresiva (if/exists/changes combinables). En YAML nuevos usa rules; aprenderás only solo para leer pipelines ajenos antiguos.

Variables, caché y artefactos

  • Variables: define secretos en Settings → CI/CD → Variables (enmascaradas y protegidas) y úsalas como variables de entorno: $DB_PASSWORD.
  • Caché: persiste directorios entre pipelines para acelerar instalaciones (node_modules, .npm).
  • Artefactos: archivos que un job produce y los stages siguientes consumen, como la carpeta dist/.
variables:
  NODE_ENV: "production"

test:
  script:
    - echo "Usando $NODE_ENV"
  artifacts:
    reports:
      junit: resultados.xml   # reporte visible en la UI

Caché vs artefactos NO son lo mismo: caché = optimización (puede regenerarse, no garantiza presencia), artefactos = datos de negocio que los stages siguientes NECESITAN. Nunca dependas del caché para pasar dist/ al deploy — un runner distinto puede tener caché vacío.

Buenas prácticas

  • Mantén los pipelines rápidos: usa caché e imágenes pequeñas (alpine).
  • Falla rápido: ordena stages de lo barato a lo costoso (lint antes que tests E2E).
  • Nunca imprimas secretos en logs; usa variables protegidas.
  • Usa rules/only para ejecutar jobs solo cuando aplique (ramas, tags, cambios de rutas).
  • Versiona las imágenes base (node:20 mejor que node:latest) para builds reproducibles.

El arma secreta de GitLab CI: los includes y templates. Un pipeline base compartido a nivel de grupo (include: project: ci/base) evita copiar el mismo YAML en 30 repos — cambias la plantilla una vez y todos los proyectos heredan.

Ejercicios prácticos

  1. Hola Pipeline: repo con .gitlab-ci.yml mínimo (build+test Node); verifica ejecución, logs y consumo de minutos en la UI.
  2. Pipeline completo del ejemplo: implementa build→test→deploy-staging con caché npm, artefactos dist/ y environment staging.
  3. Runner propio: registra un runner docker local contra GitLab.com; etiqueta jobs para usarlo y confirma minutos ilimitados.
  4. Laboratorio rules: convierte only: main a rules modernas añadiendo: job de lint solo cuando cambien *.js (changes), deploy manual (when: manual).
  5. Template grupal: crea repo "ci-base" con pipeline reutilizable e inclúyelo desde dos proyectos distintos; modifica la base y verifica propagación.
