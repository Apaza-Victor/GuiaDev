Creación y clonado de proyectos

Un proyecto en GitLab equivale a un repositorio con todo su ecosistema (issues, pipelines, wiki). Puedes crearlo desde la web, desde la CLI o importándolo desde GitHub/Bitbucket con el asistente de importación.

# Clonar por HTTPS (pedirá token como contraseña)
git clone https://gitlab.com/grupo/api-ventas.git

# Clonar por SSH (recomendado para trabajo diario)
git clone git@gitlab.com:grupo/api-ventas.git

# Crear proyecto local y conectarlo a un repo vacío existente
git init
git remote add origin git@gitlab.com:grupo/api-ventas.git
git push -u origin main

Visibilidad y membresías

Cada proyecto tiene tres niveles de visibilidad:

  • Private: solo miembros del proyecto.
  • Internal: cualquier usuario autenticado de la instancia.
  • Public: cualquiera puede verlo.

Los miembros se agregan desde Manage → Members con roles jerárquicos: Guest, Reporter, Developer, Maintainer, Owner. El rol Developer puede hacer push a ramas no protegidas y abrir merge requests; Maintainer administra configuración y despliegues.

Ramas protegidas

En Settings → Repository → Protected branches defines quién puede hacer push y quién puede merge sobre ramas críticas como main. Es habitual protegerlas para que nadie suba directamente y todo pase por merge request revisado.

Rama: main
  Allowed to merge:   Maintainers
  Allowed to push:    Nobody   ← obliga a usar Merge Requests
  Allowed to force push: off  ← protege el historial

También puedes definir patrones con comodines, por ejemplo release/*, para proteger todas las ramas de release a la vez.

Merge Requests: flujo de trabajo

El equivalente al pull request de GitHub es el Merge Request (MR). El flujo típico:

# 1. Crea una rama de trabajo
git checkout -b feat/descuentos

# 2. Desarrolla y sube los cambios
git add . && git commit -m "feat: aplicar descuento por volumen"
git push -u origin feat/descuentos

# 3. Abre el MR (o usa el enlace que imprime git push)
git push -o merge_request.create -o merge_request.target=main

Al abrir el MR verás los cambios lado a lado, el pipeline asociado corriendo automáticamente y opciones como asignar revisores, etiquetas, milestone y cerrar issues vinculando texto como Closes #12.

Revisión y aprobaciones

En cada MR puedes exigir aprobaciones mínimas antes de permitir el merge (Settings → Merge requests → Approvals). Los revisores comentan línea por línea, sugieren cambios aplicables con un clic y aprueban cuando el código cumple los criterios.

Opciones útiles al fusionar:

MétodoEfecto en main
Merge commitConserva todos los commits + commit de fusión
SquashComprime la rama en un único commit limpio
Fast-forwardSin commit de merge; historial lineal
