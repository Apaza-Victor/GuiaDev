Usuarios, organizaciones y equipos

La estructura social de Gitea imita a GitHub:

Organización: acme-corp
├── Equipo: owners      → control total
├── Equipo: devs        → lectura/escritura en repos del proyecto X
└── Equipo: qa          → solo lectura + issues

Desde el panel de administración (/admin) puedes crear usuarios manualmente, forzar 2FA, desactivar cuentas y auditar acciones. Para empresas conviene conectar LDAP/OAuth2 en Site Administration → Authentication Sources para que las cuentas provengan del directorio corporativo.

Claves SSH y tokens

Dos mecanismos de autenticación para tu trabajo diario:

  1. Clave SSH: sube tu clave pública en Settings → SSH / GPG Keys.
# Generar clave si no tienes
ssh-keygen -t ed25519 -C "tu@correo.com"

# Copiar el contenido de ~/.ssh/id_ed25519.pub al campo SSH Key de Gitea

# Probar (ajusta puerto si usaste 2222 en Docker)
ssh -T -p 2222 git@tu-servidor.com

# Clonar vía SSH
git clone git@tu-servidor.com:22:/acme-corp/api.git
# o formato estándar si SSH corre en el puerto 22
git clone git@tu-servidor.com:acme-corp/api.git
  1. Tokens de acceso: para HTTPS, API y CI. Genera en Settings → Applications → Access Token con scopes limitados.
git clone https://tu-usuario:TOKEN@tu-servidor.com/acme-corp/api.git

Repositorios, issues y PRs

El flujo colaborativo es idéntico al que ya conoces de GitHub:

# Rama feature y push
git checkout -b feat/reportes-pdf
git push -u origin feat/reportes-pdf

# Desde la web: "New Pull Request" hacia main,
# asigna reviewers y discute línea a línea.

# O crea el PR directo desde git:
git push -o repo.private=false -o title="feat: reportes PDF" \
  origin feat/reportes-pdf
  • Protege main en Repo Settings → Branch: push bloqueado, PR obligatorio, aprobación requerida.
  • Vincula issues escribiendo #12 en commits o descripciones; usa Fixes #12 para cerrarlas al fusionar.

Gitea Actions

Desde la versión 1.19 Gitea incluye Actions, un sistema CI/CD compatible con workflows de GitHub Actions: mismos archivos YAML bajo .gitea/workflows/ (o .github/workflows/) y marketplace de actions compatible.

# .gitea/workflows/test.yml
name: Tests
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

Se habilita en app.ini:

[actions]
ENABLED = true

Necesitarás al menos un runner registrado (act_runner) ejecutándose en alguna máquina para procesar los jobs.

docker run -d --name act-runner --restart always \
  -v act-runner-data:/data \
  -e GITEA_INSTANCE_URL=https://git.tudominio.com \
  -e GITEA_RUNNER_REGISTRATION_TOKEN=TU_TOKEN \
  gitea/act_runner:latest

Mantenimiento y actualización

  • Actualizar con Docker: cambia el tag de imagen a la versión nueva y recrea el contenedor (los datos persisten en volúmenes): 
    docker compose pull && docker compose up -d
  • Backups periódicos: programa gitea dump con cron y guarda fuera del servidor.
  • Limpieza: en Site Administration existe "Health Check" y tareas de repositorios huérfanos.
  • Logs: revisa /data/gitea/log ante comportamientos raros.

Lee siempre las notas de versión antes de actualizar saltos grandes: algunas versiones exigen pasar intermedias o ejecutar migraciones.
