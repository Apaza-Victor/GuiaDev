¿Qué son los Git hooks?

Los Git hooks son scripts que Git ejecuta automáticamente en momentos clave del flujo: antes de un commit, después de un push, al reescribir historia... Viven en la carpeta oculta .git/hooks/.

.git/hooks/
├── pre-commit.sample    ← se ejecuta ANTES de crear el commit
├── commit-msg.sample    ← valida el MENSAJE del commit
├── pre-push.sample      ← se ejecuta ANTES de pushear
└── ...

El problema: .git/ no se versiona ni comparte. Si configuras hooks ahí, tus compañeros no los reciben con el clone. Ahí entra Husky: gestiona hooks dentro de una carpeta versionada (.husky/) y los instala automáticamente para todo el equipo.

El hook más olvidado y valioso: pre-push para tests. Pre-commit protege TU historial; pre-push protege el REMOTO. Validaciones caras (suite completa, builds Docker) van mejor en pre-push: no penalizan cada commit local pero sí la puerta al equipo.

---

Instalación y configuración de Husky

Husky v9+ (proyecto Node.js):

# 1. Instalar como dependencia de desarrollo
npm install --save-dev husky

# 2. Inicializar (crea .husky/ y configura core.hooksPath)
npx husky init

# 3. Verificar que package.json quedó así:
# "scripts": { "prepare": "husky" }

El script prepare hace que cada quien que ejecute npm install reciba los hooks activos automáticamente.

# Crear un hook nuevo
echo "npm test" > .husky/pre-push
git add .husky
# ¡Listo! Ahora npm test corre antes de cada push

Versión de Husky importa: los tutoriales antiguos usan husky install y archivos con shebang — sintaxis v8. En v9+ el init genera scripts planos ("npm test" sin shebang). Mezclar ambas generaciones produce hooks silenciosamente muertos.

---

Hooks pre-commit y pre-push

.husky/pre-commit — última línea de defensa antes de ensuciar el historial:

#!/usr/bin/env sh
. "$(dirname -- "$0")/_/husky.sh"

npm run lint        # estilo de código
npm run typecheck   # errores de tipos

.husky/pre-push — validaciones más costosas, solo al compartir código:

npm test            # suite completa de tests

Si cualquier comando falla (exit code ≠ 0), Git cancela la operación. Para saltarlo en emergencias: git commit --no-verify — úsalo con criterio.

HookCuándo disparaCandidatos a incluir
pre-commitAntes de cada commit locallint-staged, formateo, typecheck rápido
commit-msgTras escribir el mensajecommitlint (valida Conventional Commits)
pre-pushAntes de enviar al remotoSuite de tests completa, build
pre-rebaseAntes de reescribir historiaBloquear rebase de ramas compartidas

--no-verify es una válvula de escape, no un estilo de vida. Si tu equipo lo usa semanalmente, los hooks son demasiado lentos o ruidosos: arréglalos (más lint-staged, menos suites completas en pre-commit) en lugar de normalizar el salto de controles.

Combinar con lint-staged

Ejecutar ESLint sobre TODO el proyecto en cada commit es lento. lint-staged aplica herramientas solo a los archivos staged:

npm install --save-dev lint-staged
// package.json
{
  "lint-staged": {
    "*.{js,jsx,ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{json,css,md}": ["prettier --write"]
  }
}
# .husky/pre-commit ahora solo necesita:
npx lint-staged

Resultado: commits rápidos y archivos formateados/corregidos automáticamente justo antes de entrar al historial.

Ejemplo completo de setup

# Setup desde cero en 6 comandos:
npm install --save-dev husky lint-staged eslint prettier
npx husky init
echo "npx lint-staged" > .husky/pre-commit
echo "npm test" > .husky/pre-push

# Agregar configuración de lint-staged a package.json (ver arriba)
git add . && git commit -m "chore: husky + lint-staged"
Flujo resultante del equipo:
git commit → lint-staged corrige/stagea → si hay error grave, aborta
git push   → tests completos → si fallan, no sale nada roto

Alternativas multi-lenguaje fuera de Node: pre-commit framework (Python) y Lefthook (Go, muy rápido).

Errores comunes

Error típicoSíntomaCorrecto
Configurar hooks solo en .git/hooks/Tus compañeros no reciben nada al clonarHusky / Lefthook con carpeta versionada
Hooks lentos en pre-commitEquipo normaliza --no-verifylint-staged (solo staged), suites completas a pre-push/CI
Olvidar script "prepare"npx husky init hecho pero hooks muertos tras clone"prepare": "husky" en package.json versionado
Mixing sintaxis v8/v9Hooks silenciosamente no ejecutanAlinear versión + regenerar .husky con init actual
Formateo sin re-stagingPrettier corrige pero el commit sale SIN los arregloslint-staged gestiona git add automáticamente
Depender de hooks como única defensa--no-verify o CI saltado = nada protegeHooks = primera línea; CI = autoridad final

Ejercicios prácticos

  1. Setup desde cero: repo Node nuevo con Husky v9; crea pre-commit (lint-staged con prettier) y pre-push (npm test); verifica ambos bloqueando deliberadamente.
  2. Cronómetro de hooks: mide duración del pre-commit con eslint global vs lint-staged sobre 200 archivos; documenta la diferencia.
  3. Simulador de equipo: clona tu repo en otra carpeta, npm install y confirma que los hooks quedaron activos sin pasos manuales.
  4. Válvula de escape controlada: usa --no-verify una vez para un hotfix real de emergencia y documenta el follow-up que limpió lo que se coló.
  5. Migración cross-language: investiga Lefthook o pre-commit framework y traduce tu setup de husky a uno de ellos; compara configuración resultante.
