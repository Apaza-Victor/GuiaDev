¿Por qué estandarizar los commits?

Mensajes como "arreglos", "cambios varios" o "asdf" hacen imposible entender el historial. Conventional Commits es una especificación ligera que da estructura a los mensajes, y esa estructura se vuelve procesable por máquinas:

  • Generación automática de CHANGELOG.
  • Determinación automática de versiones semánticas (¿sube patch, minor o major?).
  • Comunicación clara de la naturaleza del cambio a todo el equipo.
  • Disparo de pipelines según el tipo de cambio.

El valor real no es estética: un historial convencional permite que HERRAMIENTAS decidan versiones y changelogs sin intervención humana. "fix" sube 2.3.0→2.3.1, "feat" →2.4.0, "feat!"/BREAKING CHANGE →3.0.0. El semver deja de ser opinión.

Ejecuta git log --oneline -20 en tu repo actual. Si la mitad son "cambios", "fixes" o typos, acabas de encontrar tu motivación para adoptar la spec.

---

La especificación: tipo, scope y descripción

<tipo>[scope opcional]: <descripción>

[cuerpo opcional]

[footer(s) opcional]

Ejemplos reales:

feat: agregar botón de pago con PayPal
fix(auth): corregir expiración de tokens
docs: actualizar guía de instalación
feat(api)!: rompe compatibilidad en endpoint /users

BREAKING CHANGE: el campo email ahora es obligatorio
PiezaReglaEjemplo
TipoObligatorio, minúscula, de la lista canónicafeat, fix
ScopeOpcional: módulo afectado(auth), (carrito)
DescripciónImperativo, minúscula, sin punto final, ≤72 charscorregir expiración de tokens
CuerpoOpcional: el POR QUÉ de la decisiónpárrafo tras línea en blanco
FooterTokens especialesBREAKING CHANGE:, Closes #42

Reglas de oro: descripción en minúsculas e imperativo ("agregar", no "agregué"), sin punto final, máximo ~72 caracteres para el título.

El cuerpo debe explicar el POR QUÉ, no listar archivos tocados — eso lo muestra git show. "Se modificó auth.js y login.ts" es ruido; "elegimos tokens cortos por requisito de auditoría X" es historia valiosa.

Tipos principales

TipoSignificadoImpacto versión (semver)
featNueva funcionalidadMINOR (1.4.0 → 1.5.0)
fixCorrección de bugPATCH (1.4.0 → 1.4.1)
docsSolo documentación—
styleFormato (espacios, comas); no afecta lógica—
refactorCambio de código que ni agrega feature ni arregla bug—
perfMejora de rendimiento—
testAgregar/corregir tests—
buildSistema de build o dependencias—
ciCambios en configuración CI/CD—
choreTareas de mantenimiento—

Dudas clásicas resueltas: ¿bug que solo existía en una rama nunca publicada? → feat o refactor, NO fix (nada "se rompió" en producción). ¿Refactor que acelera de paso? → perf si el objetivo era velocidad. ¿Actualizar dependencia? → build si afecta compilación, chore si rutinaria, fix si cerraba una vulnerabilidad.

Breaking changes y footers

Un cambio que rompe compatibilidad se marca de dos formas (ambas válidas):

# Forma 1: signo ! después del tipo/scope
refactor!: eliminar soporte para Node 16

# Forma 2: footer BREAKING CHANGE con descripción
feat: nuevo formato de respuesta API

BREAKING CHANGE: /api/users ahora devuelve array paginado.
Migración: usar response.data.items.

Otros footers útiles: Closes #42, Refs #17, Reviewed-by: Ana <ana@x.com>. Las herramientas de release leen BREAKING CHANGE para subir el MAJOR automáticamente.

Herramientas que lo aprovechan

  • commitlint: valida que cada mensaje cumpla la spec (lección siguiente).
  • semantic-release / release-please: versionan y publican automáticamente leyendo los commits.
  • git-chglog / conventional-changelog: generan el CHANGELOG.md desde el historial.
  • Commitizen: asistente interactivo para escribir commits conformes.
# El flujo completo típico:
git commit -m "feat(carrito): cupones de descuento"
# → semantic-release detecta feat → publica v2.3.0
# → changelog actualizado con la entrada nueva

Adopción gradual realista: 1) convence al equipo con la chuleta de tipos; 2) automatiza la escritura con Commitizen; 3) bloquea incumplimientos con commitlint+husky; 4) recién entonces automatiza releases. Imponer las cuatro cosas un lunes es la receta del sabotaje.

Ejercicios prácticos

  1. Auditoría retrospectiva: lista tus últimos 30 commits (git log --oneline -30) y reclasifícalos mentalmente a tipos convencionales; calcula cuántos eran "inclasificables".
  2. Rewrite guiado: toma 5 mensajes malos y reescríbelos completos: tipo, scope, descripción ≤72 chars, cuerpo explicando el porqué cuando aplique.
  3. Laboratorio breaking: documenta un cambio incompatible ficticio de tu API en ambas formas (! y footer BREAKING CHANGE con migración).
  4. Changelog manual: agrupa 10 commits convencionales tuyos en un mini CHANGELOG por categorías Features/Fixes/Otros — simula lo que haría git-cliff.
  5. Semver detective: dada una serie de commits mezclados (feats, fixes, un breaking), determina la versión siguiente correcta partiendo de v1.2.3.
