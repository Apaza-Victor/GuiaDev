Instalar y configurar commitlint

commitlint valida que los mensajes de commit cumplan Conventional Commits. Instalación en proyecto Node:

npm install --save-dev @commitlint/cli @commitlint/config-conventional

# Crear configuración
echo "export default { extends: ['@commitlint/config-conventional'] };" > commitlint.config.js

# Probar manualmente
echo "feat: nueva funcionalidad" | npx commitlint
# (sin salida = válido ✓)

echo "cambios varios" | npx commitlint
# ✗ subject may not be empty [subject-empty]
# ✗ type may not be empty [type-empty]

La config preset rechaza tipos no estándar, subjects vacíos, mayúsculas iniciales y punto final, entre otras reglas.

Las reglas tienen formato [nivel, aplicabilidad, valor]: nivel 0=off, 1=warning, 2=error; 'always' o 'never'. Así, 'type-enum': [2, 'always', ['feat','fix']] bloquea cualquier otro tipo con severidad de error.

---

Validar desde husky (commit-msg)

Con Husky ya instalado, agrega el hook commit-msg:

echo "npx --no -- commitlint --edit \$1" > .husky/commit-msg

A partir de ahora, cada git commit con mensaje inválido es rechazado al instante:

$ git commit -m "arregle cosas"
✗ type may not be empty
✗ subject may not be empty

$ git commit -m "fix: arreglé el cálculo del IVA"
[main a1b2c3] fix: arreglé el cálculo del IVA ✓

Reglas custom opcionales en commitlint.config.js:

export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'scope-enum': [2, 'always', ['auth', 'api', 'ui', 'db']],
    'header-max-length': [2, 'always', 72]
  }
};

El scope-enum es la regla más subestimada: al obligar a elegir entre scopes acordados, el historial se vuelve FILTRABLE ("muéstrame solo commits de auth"). Sin ella, cada dev inventa scopes y el valor analítico desaparece.

Commitizen: commits guiados

Commitizen invierte el enfoque: en vez de validar después, te guía durante la escritura con preguntas interactivas.

# Instalar el adaptador cz-conventional-changelog
npm install --save-dev commitizen cz-conventional-changelog

# package.json
{
  "config": {
    "commitizen": { "path": "cz-conventional-changelog" }
  },
  "scripts": { "commit": "cz" }
}
$ npm run commit
? Select the type of change:   ← flechas para elegir
❯ feat:     A new feature
  fix:      A bug fix
  docs:     Documentation changes
? What is the scope of this change? carrito
? Write a SHORT description: cupones de descuento
? Body / breaking changes? (opcional)
→ Genera: feat(carrito): cupones de descuento ✓

Uso global sin instalar nada en el repo: npx cz.

Commitizen NO reemplaza a commitlint: uno guía la escritura, el otro VALIDA. Un dev puede saltarse cz y escribir a mano — sin commitlint en commit-msg, nada lo detiene. El combo completo es: cz para comodidad + commitlint como guardia.

Changelog automático

Con commits estandarizados, el CHANGELOG se genera solo:

# Opción A: git-cliff (Rust, rápido, muy configurable)
cargo install git-cliff
git cliff -o CHANGELOG.md

# Opción B: conventional-changelog (ecosistema Node)
npx conventional-changelog-cli -p angular -i CHANGELOG.md -s
<!-- CHANGELOG.md generado -->
## v2.3.0 (2026-08-21)
### Features
* **carrito:** cupones de descuento
### Bug Fixes
* **auth:** expiración de tokens incorrecta

Nivel avanzado: semantic-release o release-please combinan todo — leen commits, deciden versión semver, generan changelog, crean tag/release de GitHub y publican a npm, todo desde CI. Ese es el destino final de un flujo de commits de calidad.

Herramienta de releaseLee…Produce…
git-cliffHistorial convencionalCHANGELOG.md configurable por plantillas
conventional-changelogHistorial (preset angular)CHANGELOG.md incremental
semantic-releaseCommits + tagsVersión semver + changelog + release + publicación npm
release-pleaseCommitsRelease PR que al mergear crea versión+changelog

Errores comunes

Error típicoSíntomaCorrecto
commitlint.config.js no versionadoCada dev valida con reglas distintasCommit del config al repo, siempre
Husky sin commitlint instalado en CIPRs con commits malos pasan el pipelinenpx commitlint --from=origin/main~1 en CI
Merge commits rechazados por la validación"Merge branch..." falla el hookIgnorar merges: 'type-enum' con regla default ya lo contempla; configurar si custom
Squash con mensaje auto-generado sucio"feat: fix: chore: ..." concatenadoRedactar título convencional al hacer squash merge
cz instalado pero nadie lo usaValidación bloqueante sin guía = frustraciónnpm run commit como camino fácil y documentado
Reglas nivel warning (1) esperando bloqueoCommits malos "pasan" igualmenteNivel 2 para reglas obligatorias

Ejercicios prácticos

  1. Batería de pruebas: instala commitlint y prueba 8 mensajes: válidos perfectos, casi-válidos (mayúscula inicial, punto final, 80 chars) e inválidos totales; documenta cada veredicto.
  2. Guardia completa: husky commit-msg + commitlint con scope-enum propio (3-5 scopes de TU proyecto); intenta violar cada regla y verifica bloqueos.
  3. Ronda guiada: realiza 3 commits reales vía npm run commit; compara tiempo/errores vs escritura manual libre.
  4. Changelog real: genera CHANGELOG.md de un repo tuyo con git-cliff; ajusta plantilla para agrupar por scope.
  5. Validación en CI: añade job que valide TODOS los commits de un PR contra origin/main usando commitlint --from; simula PR con commit inválido y confirma rechazo.
