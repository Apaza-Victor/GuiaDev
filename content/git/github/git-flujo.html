El ciclo de trabajo diario

El 90% de tu vida con Git se resume en un ciclo de cuatro pasos que repetirás miles de veces:

┌──────────┐   add    ┌─────────┐   commit   ┌──────────┐   push   ┌────────┐
│ Working  │ ───────► │ Staging │ ─────────► │ Repositorio│ ──────► │ Remoto │
│ Directory│          │  Area   │            │   Local   │          │        │
└──────────┘          └─────────┘            └──────────┘          └────────┘
      ▲                                                                  │
      └──────────────────── pull ◄──────────────────────────────────────┘
  1. Modificas archivos en tu directorio de trabajo.
  2. Preparas cambios con git add (los seleccionas conscientemente).
  3. Confirmas con git commit (foto del proyecto).
  4. Sincronizas con git pull antes y git push después.
ZonaQué contieneCómo inspeccionarla
Working DirectoryTus archivos editados, aún sin preparargit diff
Staging AreaCambios seleccionados para el próximo commitgit diff --staged
Repositorio localHistorial de commits confirmadosgit log
Remoto (GitHub)La copia compartida del proyectogit fetch && git log HEAD..origin/main

Entender las CUATRO zonas —no dos— explica casi todos los misterios de Git: ¿por qué tu commit no aparece en GitHub? (faltó push), ¿por qué el archivo "desapareció"? (estaba solo en staging). Cada comando mueve cambios ENTRE zonas específicas.

---

Add → Commit → Push paso a paso

# Ver qué cambió antes de hacer nada
git status

# Revisar el detalle línea por línea
git diff

# Preparar archivos específicos (preferible a git add .)
git add index.html css/style.css

# Confirmar con mensaje claro
git commit -m "feat: agrega validacion al formulario de contacto"

# Publicar tus commits al remoto
git push origin main

Buenos hábitos en este ciclo:

  • Commits pequeños y frecuentes: cada commit debería representar un cambio lógico completo ("agrega validación"), no media jornada ("avances").
  • Mensajes descriptivos: en imperativo y explicando el qué; tu yo del futuro (y tus compañeros) leerán ese historial.
  • Revisa siempre git status antes de añadir: evita subir archivos temporales o secretos.

git diff --staged justo antes del commit es la revisión de código más barata que existe: te sorprenderá cuántas veces descubres un console.log olvidado o un cambio no relacionado a punto de colarse.

git add . añade TODO lo modificado, incluida basura: .env con credenciales, logs, node_modules si falta .gitignore. El hábito profesional: git status → decidir archivo por archivo → git add explícito.

---

Actualizar tu copia local

Antes de empezar a trabajar y antes de publicar, sincroniza con el remoto:

# Descarga cambios y los integra a tu rama actual
git pull origin main

# Alternativa más segura: descargar sin integrar primero
git fetch origin
git log HEAD..origin/main --oneline   # ver qué hay nuevo
git merge origin/main                  # integrar cuando decidas
ComandoHace fetch?Integra?Riesgo
pullSíSí (merge automático)Conflictos sorpresa a mitad de tu trabajo
fetch + mergeSíCuando tú decidesNinguno — control total ✅
  • pull = fetch + merge automático; cómodo pero puede sorprenderte con conflictos.
  • fetch solo descarga; te deja decidir cuándo y cómo integrar.
  • Si aparece conflictos: no entres en pánico — edita los archivos marcados con <<<<<<<, elige el contenido final y confirma el merge.

Configura git config --global pull.rebase true para que pull rebase tus commits locales encima de los remotos: historial lineal sin "Merge branch 'main' of github.com..." cada dos por tres.

---

Flujo con ramas resumido

Incluso trabajando solo, la variante profesional del ciclo usa una rama por tarea:

# 1. Rama nueva desde main actualizado
git checkout main
git pull origin main
git checkout -b feature/login

# 2. Trabajas y confirmas (varios ciclos add/commit)
git add .
git commit -m "feat: pantalla de login basica"

# 3. Subes tu rama
git push -u origin feature/login

# 4. Abres Pull Request, revisan, aprueban y fusionan
# 5. Actualizas main local y borras la rama terminada
git checkout main && git pull origin main
git branch -d feature/login

Nunca hagas push directamente a main en proyectos compartidos: la rama protegida + pull request es el mínimo de seguridad colaborativa.

El flag -u (upstream) conecta tu rama local con la remota UNA sola vez: después basta git push y git pull a secas desde esa rama.

Ejercicios prácticos

  1. Ciclo completo ×5: repo propio; repite el ciclo status→diff→add selectivo→commit→push cinco veces con mensajes convencionales.
  2. Cazador de zonas: modifica 3 archivos; deja uno en working, otro en staging y commitea el tercero; identifica cada estado con los comandos de inspección.
  3. Fetch vs pull real: genera cambios remotos (desde web GitHub); practica primero fetch+log+merge, luego pull puro; compara experiencia.
  4. Rama por tarea: implementa una mini-feature completa con el flujo de ramas resumido, incluyendo PR y limpieza final.
  5. Diario de Git: durante una semana registra cada comando Git que uses; al final clasifícalos y detecta hábitos a mejorar.
