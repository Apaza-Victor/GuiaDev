¿Qué es CI? ¿Qué es CD?

CI (Continuous Integration): cada push se compila y prueba automáticamente, detectando errores minutos después de cometerlos y no semanas después. El equipo integra cambios pequeños con frecuencia sobre una rama compartida.

CD tiene dos niveles:

  • Continuous Delivery: el software queda siempre listo para desplegarse a producción (despliegue manual con un clic).
  • Continuous Deployment: cada cambio validado llega a producción automáticamente, sin intervención humana.
git push → [Build] → [Tests] → [Package] → [Deploy]
           └────── CI ─────────┘  └──── CD ────┘

La diferencia Delivery vs Deployment es ORGANIZATIVA, no técnica: ¿quién aprieta el botón final? Delivery = un humano decide cuándo (regulatorio, marketing, coordinación); Deployment = nadie decide, todo commit verde va a producción. Muchos equipos empiezan en Delivery por miedo y evolucionan a Deployment por confianza.

El requisito previo que nadie menciona: CI solo funciona con integraciones PEQUEÑAS y frecuentes. Si tu equipo vive en ramas de dos semanas, ningún pipeline salvará la integración: la automatización multiplica la cultura, no la sustituye.

Beneficios y métricas DORA

Beneficios directos: bugs detectados temprano (baratos), main siempre desplegable, releases sin drama de fin de sprint y feedback rápido al desarrollador.

Las métricas DORA (DevOps Research and Assessment) miden la madurez del proceso:

MétricaQué mide
Deployment frequencyCada cuánto despliegas a producción
Lead time for changesTiempo entre commit y estar en producción
Change failure rate% de despliegues que causan incidentes
Time to restoreCuánto tardas en recuperarte de un fallo

Equipos élite: deployments diarios/múltiples al día, lead time menor a un día, failure rate bajo 5%.

Las métricas DORA miden el PROCESO, no a las personas. El día que deployment frequency se convierte en objetivo individual de rendimiento, aparecen deployments vacíos para "cumplir cuota" — la ley de Goodhart en acción. Publícalas por equipo, celébralas como salud del sistema.

Anatomía de un pipeline

Todo pipeline CI/CD sigue el mismo esqueleto conceptual sin importar la herramienta:

1. TRIGGER     push, PR, tag, cron o manual
2. CHECKOUT    descargar el código
3. BUILD       instalar dependencias + compilar
4. TEST        unitarios → integración → E2E (falla rápida)
5. PACKAGE     imagen Docker / artefacto versionado
6. DEPLOY      staging → validación → producción
7. NOTIFY      Slack/email/issue si algo falla
  • Falla rápida: lo barato primero (lint), lo caro después (E2E).
  • Puertas (gates): aprobaciones humanas antes de producción.
  • Idempotencia: correr el pipeline dos veces debe dar el mismo resultado.

Regla de tiempos: si el pipeline tarda más de 10 minutos, la gente empieza a hacer batch de cambios y el feedback loop muere. Paraleliza jobs, cachea dependencias y separa suite rápida (<5 min en cada push) de suite completa (nocturna o pre-release).

Estrategias de ramas y triggers

La estrategia de ramas define qué corre y cuándo:

Rama/eventoPipeline típico
PR hacia mainLint + tests (validación previa)
Push a mainCI completo + deploy a staging
Tag v*Release: versión final + deploy a producción
Cron nocturnoTests pesados, escaneo de seguridad

Estrategias comunes: GitHub Flow (main + feature branches — simple, ideal para CI/CD continuo), Gitflow (develop/release/hotfix — controlado, para releases planificados) y Trunk-Based Development (integraciones pequeñas varias veces al día, feature flags).

Gitflow + CI/CD continuo es un antipatrón: la rama develop acumula días de integración diferida, justo lo que CI existe para eliminar. Gitflow tiene sentido con releases versionados lentos (software instalable); para SaaS desplegado continuamente, GitHub Flow o trunk-based ganan siempre.

Panorama de herramientas

  • GitHub Actions: nativo de GitHub; YAML simple; enorme marketplace.
  • GitLab CI: integrado en GitLab; pipelines muy potentes self-hosted.
  • Azure Pipelines: corporativo Microsoft; agentes Windows/macOS/Linux.
  • Bitbucket Pipelines: simple, dentro de Bitbucket.
  • Jenkins: el veterano self-hosted; máxima flexibilidad vía plugins.
  • Otros: CircleCI, Travis CI, ArgoCD (CD GitOps para Kubernetes).

Las siguientes lecciones profundizan en GitHub Actions y Jenkins, y cierran con una comparativa completa de plataformas y buenas prácticas universales.

Ejercicios prácticos

  1. Clasificador CD: describe 3 escenarios de equipos ficticios (banco regulado, SaaS startup, app móvil) y decide para cada uno Delivery vs Deployment justificando.
  2. Línea base DORA: mide las 4 métricas de tu proyecto actual con datos reales (tags, fechas de incidentes); documenta tu nivel (élite/alto/medio/bajo).
  3. Diseñador de anatomía: dibuja el pipeline ideal para una librería npm pública: triggers por rama/tag, orden de stages y gates.
  4. Debate Gitflow: toma un caso real tuyo de Gitflow y analiza qué ganaría/perdería migrando a GitHub Flow; escribe la recomendación final.
  5. Cronómetro mental: estima tiempos de cada stage de un pipeline típico Node (install/build/test/e2e); luego compáralo con un pipeline real cuando llegues a implementarlo.
