Conceptos: workflow, job y step

La jerarquía de GitHub Actions:

  • Workflow: proceso automatizado completo definido en un YAML bajo .github/workflows/.
  • Job: unidad que corre en una máquina virtual (runner). Los jobs corren en paralelo por defecto.
  • Step: comando shell o acción reutilizable dentro de un job. Los steps comparten máquina y filesystem.
Workflow: ci.yml
├── job: lint     (ubuntu runner)
│   ├── step: checkout
│   └── step: npm run lint
└── job: test     (paralelo a lint)
    ├── step: checkout
    └── step: npm test

Dos detalles que confunden a todos: los jobs NO comparten archivos (cada uno arranca en una VM limpia — por eso checkout se repite), y el paralelismo por defecto significa que "test" puede terminar antes que "lint". Para ordenar: needs: lint en el job dependiente.

---

El directorio .github/workflows

Primer workflow completo — CI de un proyecto Node:

# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4        # clona tu repo en el runner

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'                   # cachea ~/.npm

      - run: npm ci
      - run: npm test

uses: invoca acciones reutilizables del marketplace; run: ejecuta comandos shell. Guarda el archivo, haz push, y verás el workflow en la pestaña Actions del repo.

El nombre del archivo YAML es libre (ci.yml, build.yml), pero la UBICACIÓN es sagrada: exactamente .github/workflows/. Un espacio de más en el nombre de carpeta y GitHub lo ignora silenciosamente — el workflow simplemente nunca aparece.

Triggers y matriz de versiones

La matriz ejecuta el mismo job contra combinaciones de versiones/sistemas — perfecto para librerías multiplataforma:

jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        node: [18, 20, 22]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci && npm test
# = 6 ejecuciones en paralelo (2 SO × 3 versiones)

Otros triggers útiles: workflow_dispatch (botón manual), schedule (cron), release, issues.

fail-fast: false en la estrategia es clave durante desarrollo: sin él, el primer fallo cancela las otras 5 ejecuciones de la matriz y pierdes la información de qué combinaciones rompen. Actívalo true solo para ahorrar minutos cuando ya sabes que está verde.

Secrets y variables de entorno

Los secretos se guardan cifrados en Settings → Secrets and variables → Actions y nunca aparecen en logs:

steps:
  - name: Deploy
    env:
      API_KEY: ${{ secrets.API_KEY }}       # secreto
      NODE_ENV: production                   # variable normal
    run: ./deploy.sh
  • ${{ secrets.X }}: enmascarado en logs, solo lectura en workflows.
  • ${{ vars.X }}: variables no sensibles configurables por repo/entorno.
  • Los secrets de Environments (production) pueden exigir revisores humanos.
  • Regla de seguridad: jamás imprimas secretos ni los metas en el código.

El enmascaramiento de secrets en logs NO protege todo: si un secreto se usa para construir OTRO valor (base64, concatenación), el resultado derivado sí puede imprimirse. Y en PRs de forks, los secrets no están disponibles por diseño — nunca los habilites para repos públicos externos.

Marketplace y actions reutilizables

El Marketplace ofrece miles de acciones listas: despliegues (Vercel, AWS, Firebase), seguridad (CodeQL), notificaciones (Slack)... Las más usadas son oficiales de GitHub: checkout, setup-node, upload-artifact.

También puedes crear tus propias actions (Docker o JavaScript) o reutilizar workflows completos entre repos:

jobs:
  deploy:
    uses: mi-org/workflows-compartidos/.github/workflows/deploy.yml@v2
    with:
      entorno: produccion
    secrets: inherit

Buenas prácticas finales: fija versiones por tag (@v4 o mejor @v4.1.2/SHA), mantén workflows pequeños, usa cachés y falla rápido ordenando steps de lo barato a lo caro.

Ejercicios prácticos

  1. Primer workflow: crea ci.yml con jobs lint y test paralelos sobre un repo Node tuyo; observa la pestaña Actions y el paralelismo real.
  2. Orden forzado: añade needs: para que deploy corra tras lint+test exitosos; rompe tests deliberadamente y verifica que deploy nunca arranca.
  3. Matriz viva: matriz OS×Node (2×3); con fail-fast true y false, compara qué información obtienes cuando una combinación falla.
  4. Secret seguro: guarda un API_KEY fake, úsalo en un step que lo imprima indirectamente (echo "key=$API_KEY") y verifica el enmascaramiento en logs.
  5. Action versionada: cambia una dependencia de @v4 a SHA completo del release; documenta cómo auditarías ese cambio ante el equipo.
