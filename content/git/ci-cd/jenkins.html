¿Qué es Jenkins y cuándo usarlo?

Jenkins es el servidor de automatización open source más veterano y extendido del mundo empresarial (Java, 2011). No es un hosting: lo instalas y administras tú. Su superpoder es el ecosistema de +1800 plugins que conecta con absolutamente todo.

Úsalo cuando:

  • Necesitas control total on-premises (bancos, gobierno, salud).
  • Tienes pipelines complejos o heterogéneos que las plataformas SaaS no cubren.
  • Herencias infraestructura existente basada en Jenkins.

Evítalo si buscas cero mantenimiento: un SaaS como GitHub Actions te ahorra actualizar servidor, plugins y backups.

El costo oculto de Jenkins no es la licencia (es gratis) sino el OPERADOR: alguien debe aplicar parches de seguridad, gestionar plugins incompatibles entre sí y vigilar disco/memoria. Presupuesta 10-20% de un ingeniero para una instancia corporativa mediana.

Instalación con Docker

# Jenkins LTS con persistencia
docker run -d --name jenkins \
  -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts

# Obtener la contraseña inicial del log
docker logs jenkins | grep -A 5 "initialAdminPassword"
# o desde dentro:
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
  1. Abre http://localhost:8080.
  2. Pega la contraseña inicial.
  3. Elige "Install suggested plugins".
  4. Crea tu usuario admin — listo para usar.

El volumen jenkins_home es TODO tu Jenkins: jobs, configuración, credenciales. Sin backup de ese volumen, una actualización fallida borra años de configuración. Backup programado + Configuration as Code (plugin JCasC) para reconstruir.

Plugins esenciales

Se instalan desde Manage Jenkins → Plugins:

PluginFunción
Git + GitHub IntegrationConectar repos y webhooks
PipelineJenkinsfile y pipelines as code
Docker PipelineBuilds y push de imágenes Docker
Blue OceanUI visual moderna de pipelines
Credentials BindingGestión segura de secretos

Regla de oro: menos plugins = menos problemas de actualización. Audita y elimina los que no uses.

Los plugins son la mayor superficie de ataque de Jenkins: vulnerabilidades CVE aparecen constantemente. Activa las actualizaciones automáticas del update center, revisa avisos de seguridad mensualmente y desconfía de plugins sin mantenimiento activo (última release > 1 año).

Jenkinsfile: pipeline declarativo

El pipeline se define en un archivo Jenkinsfile versionado junto al código:

// Jenkinsfile
pipeline {
    agent any

    environment {
        NODE_VERSION = '20'
    }

    stages {
        stage('Checkout') {
            steps { checkout scm }
        }
        stage('Install') {
            steps { sh 'npm ci' }
        }
        stage('Test') {
            steps { sh 'npm test' }
            post {
                always {
                    junit 'test-results/**/*.xml'
                }
            }
        }
        stage('Deploy') {
            when { branch 'main' }
            steps { sh './deploy.sh' }
        }
    }

    post {
        failure { echo 'Notificar al equipo...' }
        success { echo 'Pipeline OK ✓' }
    }
}

Cada push dispara el pipeline; los resultados se ven como etapas coloreadas en la UI.

Declarativo vs Scripted: el declarativo (pipeline { }) es estructurado, validable y el estándar recomendado. El scripted (node { }) es Groovy puro — máximo poder, mínimo control, historial de abusos. En Jenkinsfile nuevos: declarativo siempre; scripted solo dentro de steps puntuales si no queda alternativa.

Agentes distribuidos

El controlador (master) orquesta pero conviene no ejecutar builds en él. Los agentes hacen el trabajo pesado:

  • Permanent agents: VMs/físicas dedicadas registradas vía SSH.
  • Docker agents: cada build corre en un contenedor efímero.
  • Kubernetes plugin: agentes autoescalables en clúster K8s.
pipeline {
    agent { docker { image 'node:20' } }   // build en contenedor Node
    ...
}

Etiqueta agentes (linux, gpu, windows) y asígnalas por job: agent { label 'linux && docker' }. Con esto escala horizontalmente sin límite práctico.

Ejecutar builds en el controlador es la mala práctica #1 de Jenkins: un job con sh 'rm -rf' mal escrito o un script Groovy agresivo compromete TODA la instancia (credenciales incluidas). El master orquesta; los agentes ejecutan — siempre.

Ejercicios prácticos

  1. Instalación viva: levanta Jenkins LTS con Docker, completa el wizard y protege el volumen con un backup exportado de jenkins_home.
  2. Primer Jenkinsfile: pipeline declarativo con stages Checkout/Install/Test/Deploy(when main) sobre tu repo Node; dispara con push y observa las etapas coloreadas.
  3. Agente Docker: convierte un stage a agent { docker { image 'node:20' } } y compara reproducibilidad instalando dependencias nativas (sharp/canvas) que fallan en host desnudo.
  4. Credenciales seguras: crea un secret en Credentials Binding, úsalo desde el Jenkinsfile e imprime logs verificando que NO aparece el valor.
  5. Simulacro de desastre: borra el contenedor Jenkins y reconstruye todo desde volumen backup + lista de plugins documentada; cronometra el recovery.
