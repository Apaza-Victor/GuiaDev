Criterios de comparación

Para elegir plataforma CI/CD evalúa:

  • Integración con tu hosting Git: nativa o requiere webhooks/config extra.
  • Modelo de costos: minutos incluidos, concurrencia, runners self-hosted.
  • Facilidad de configuración: YAML declarativo vs UI vs scripting.
  • Ecosistema: marketplace/plugins, comunidad, ejemplos.
  • Sistemas operativos de runners: Linux, Windows, macOS, ARM.
  • Self-hosting: ¿puedes correr todo en tu infraestructura?

El criterio que pesa más en la práctica NO está en la lista: dónde vive tu código. Actions para repo en GitHub y GitLab CI para GitLab eliminan webhooks, permisos cruzados y sincronía de usuarios — el costo de integrar una CI externa supera cualquier ventaja teórica.

Nota práctica: los YAML son tan parecidos que migrar entre plataformas suele ser cuestión de horas, no semanas.

Los minutos gratis se multiplican rápido: una matriz de 6 jobs × 10 min = 60 minutos por push. Con 20 pushes diarios, GitHub Actions consume 1200 min/día — el mes gratis vuela en dos semanas. Calcula SIEMPRE con tu matriz real, no con "un job por pipeline".

Buenas prácticas universales

  • Pipelines como código: versionados junto al proyecto, revisados por PR.
  • Falla rápida: lint → unit → build → E2E. Aborta temprano.
  • Pipelines rápidos (<10 min): caché de dependencias, paralelismo, tests selectivos.
  • Un pipeline verde es sagrado: main roto = prioridad #1 del equipo.
  • Misma vía para todos: lo que despliegas a producción pasa por el mismo pipeline que un hotfix.
  • Artefactos inmutables: construye UNA vez y promociona ese mismo binario/imagen por entornos.
  • Idempotencia y rollback: desplegar dos veces no rompe nada; volver atrás toma segundos.

"Artefactos inmutables" significa que NO se re-construye por entorno: la misma imagen Docker que pasó staging llega a producción. Rebuilds "idénticos" con dependencias flotantes han desplegado a producción código distinto al probado — bug clásico, imposible de detectar sin inmutabilidad.

---

Seguridad en pipelines

  • Secretos fuera del código: usa el almacén cifrado de la plataforma; rota credenciales periódicamente.
  • Principio de mínimo privilegio: tokens con scope solo para lo necesario.
  • Fija versiones de actions/plugins (tag o SHA) — una action comprometida es una puerta trasera.
  • Protege workflows contra PRs maliciosos: no ejecutes código de forks con secretos disponibles.
  • Escanea dependencias e imágenes (Dependabot, Trivy, Snyk) dentro del propio pipeline.
# Ejemplo: escaneo de vulnerabilidades en cada PR
- name: Escanear dependencias
  run: npm audit --audit-level=high

El vector de ataque favorito de 2024-2026: supply chain vía actions/plugins comprometidos. Un maintainer phished publica versión maliciosa; tus pipelines la ejecutan con secretos disponibles. Defensas: fijar SHA, auditar cambios de terceros, y runners efímeros que no conservan credenciales entre jobs.

---

Costos y runners propios

Los minutos SaaS se cobran con multiplicadores (Windows ×2, macOS ×10). Cuando la factura crece, hay dos palancas:

  1. Runners self-hosted: registras tus propias máquinas/VPS — minutos ilimitados sin costo de cómputo (solo tu infraestructura): 
    # GitHub Actions runner self-hosted
./config.sh --url https://github.com/mi-org/mi-repo --token TOKEN
./run.sh   # queda escuchando jobs
  2. Optimización: cachés agresivos, matrices reducidas, skip de jobs irrelevantes (paths/changes only).

Regla final: empieza simple (SaaS del hosting donde ya vives), mide tiempos y costos reales, y migra a self-hosted solo cuando los números lo justifiquen.

Ejercicios prácticos

  1. Evaluador estructurado: puntúa tus 3 plataformas candidatas (1-5) en los 6 criterios; documenta la decisión final con números, no sensaciones.
  2. Calculadora de matriz: modela tu pipeline real (jobs×minutos×pushes/día) en GitHub Actions vs GitLab CI; compara consumo mensual contra cuota gratis.
  3. Auditoría de supply chain: lista cada action/plugin externo que usas hoy; verifica versión fijada y última release del maintainer.
  4. Simulacro de inmutabilidad: intenta demostrar que staging y producción ejecutan el MISMO artefacto; si no puedes, diseña el flujo de promoción correcto.
  5. Runner self-hosted pilot: registra un runner propio en un repo privado, corre el pipeline y mide costo/tiempo vs SaaS; decide con datos si vale la pena escalar.
