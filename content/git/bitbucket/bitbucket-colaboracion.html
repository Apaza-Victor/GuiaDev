Pull Requests y revisión de código

En Bitbucket todo pasa por pull requests: abres uno desde tu rama feature hacia main, asignas reviewers, discutes línea a línea y fusionas cuando hay aprobación.

git checkout -b feat/login-oauth
git add . && git commit -m "feat: login con Google OAuth"
git push -u origin feat/login-oauth
# En la web: Create pull request → reviewers → merge checks

Opciones de fusión: Merge commit, Squash (un solo commit limpio) o Fast-forward. Puedes bloquear el merge hasta que pasen los pipelines y haya N aprobaciones mínimas.

Estrategia de ramas

Bitbucket trae soporte pensado para flujos tipo Gitflow: define en Repository settings → Branch model cuál es tu rama principal, la de desarrollo y los prefijos de ramas feature/release/hotfix.

main      → producción
develop   → integración continua del equipo
feature/* → trabajo nuevo, nace de develop
release/* → preparación de versión
hotfix/*  → correcciones urgentes sobre main

Definir el modelo hace que la UI sugiera la rama destino correcta al abrir cada PR y evita errores humanos.

Branch permissions

Con branch permissions restringes qué personas o grupos pueden hacer push, reescribir historia o eliminar ramas específicas. Lo mínimo recomendable:

  • main: solo escritura vía PR aprobado; nadie fuerza push ni borra.
  • develop: escritura del equipo, pero con checks de pipeline.
  • Patrones como release/* protegidos para el responsable de releases.

Esto previene accidentes clásicos como un git push --force que borra commits del resto del equipo.

Integración con Jira

La magia ocurre por convención de nombres. Si tu issue es WEB-42:

# Rama que referencia el ticket
git checkout -b WEB-42-carrito-compras

# Commit que menciona el ticket
git commit -m "WEB-42 #comment validación de stock agregada"
  • El ticket Jira muestra automáticamente rama, commits y PRs relacionados.
  • Palabras clave en la descripción del PR mueven el ticket: fixes WEB-42, resolves WEB-42.
  • Puedes exigir en el PR que todo commit referencie un ticket válido.

Snippets y descargas

  • Snippets: fragmentos de código compartibles públicos o privados por workspace, útiles para scripts de setup y plantillas internas.
  • Downloads: zona de archivos adjuntos del repositorio donde Pipelines puede publicar binarios compilados para QA o clientes.
  • Wiki: cada repo puede tener documentación versionada en un repo aparte.
